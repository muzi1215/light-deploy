# 任务模块文档

> 模块包：`com.lx.deploy.task` ｜ 对应数据表：`lds_task`、`lds_task_log`（任务域，lds_ 前缀） ｜ 状态：模型 + 状态机 + 执行器 + SERVER_TEST 处理器已完成，真机验证通过

## 1. 模块定位

任务模块是全平台异步任务的**模型与状态机层**：连通性测试、构建、发布等所有长耗时操作都以一条 `lds_task` 记录承载生命周期，执行过程通过 `lds_task_log` 留痕。

- 本模块提供：任务模型、任务编号规则、状态单向流转、**任务执行器（调度 + 并发约束 + 中断收敛）**、任务处理器 SPI、任务日志写入与增量拉取、人工取消；
- 本模块不提供：具体业务动作的实现（连通性测试的处理器在 `task/executor` 下，但 SSH 能力来自 `com.lx.deploy.ssh`；构建、发布处理器由后续模块以同样的 SPI 方式接入）；
- 执行器已落地：创建任务后会被自动领取执行，处理器通过 `TaskHandler` 注册，不需要修改调度代码。

## 2. 数据表结构

### 2.1 `lds_task`（异步任务）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| task_no | VARCHAR(64) | 任务编号，唯一键，后端按 `TASK-yyyyMMddHHmmss-8位随机段` 生成 |
| task_type | VARCHAR(30) | SERVER_TEST / BUILD / DEPLOY |
| biz_id | VARCHAR(32) | 关联业务主键（如服务器 ID、构建 ID、发布 ID） |
| status | VARCHAR(30) | QUEUED / RUNNING / SUCCESS / FAILED / CANCELED，默认 QUEUED |
| current_stage | VARCHAR(30) | 当前执行阶段 |
| progress | INT | 进度 0-100 |
| started_at / finished_at | DATETIME | 起止时间，由状态流转维护 |
| error_message | TEXT | 失败原因（markFailed 必填） |

### 2.2 `lds_task_log`（任务执行日志）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| task_id | VARCHAR(32) | 所属任务，写入前校验任务存在 |
| sequence_no | BIGINT | 任务内顺序号，服务端自动 max+1 分配，唯一键保证连续唯一 |
| stage | VARCHAR(30) | 日志所属阶段 |
| log_level | VARCHAR(10) | DEBUG / INFO / WARN / ERROR，默认 INFO |
| content | TEXT | 日志内容，必填 |

注意：任务日志与服务器本地 `logs/info.log` 互相独立——本地日志面向运维排障（含 requestId），任务日志面向页面展示执行过程。

## 5. 接口清单

`/task`：page / list / {id} / POST / PUT / DELETE / **PUT /{id}/cancel**（人工取消，唯一的人工干预入口）。
`/taskLog`：page / list / {id} / POST / PUT / DELETE / **GET /pull**（按顺序号增量拉取，页面实时日志专用）。

```text
GET /taskLog/pull?taskId={taskId}&lastSeq={已获取的最大顺序号}&limit=200
→ { taskId, status, statusText, finished, currentStage, progress, errorMessage, logs[], lastSeq }
```

增量锚点用 `sequence_no` 而不是主键 `id`：主键是 32 位 UUID，不具备单调递增性。前端停止轮询的条件是「`finished === true` 且本批条数 `< limit`」（满页说明还有剩余，必须再拉一次把尾部取完），约定见 AGENTS.md §20.9。

## 6. 核心业务规则与代码逻辑

### 6.1 任务编号与创建

- taskNo 未传入时自动生成 `TASK-yyyyMMddHHmmss-UUID前8位`；传入时唯一性预检（DATA_CONFLICT），数据库唯一键兜底；
- 新建任务**强制 QUEUED**，不允许调用方指定初始状态，保证所有任务都经过执行器调度；
- taskType 必须是枚举值，progress 限 0-100。

### 6.2 状态单向流转（TaskService 状态机）

```text
QUEUED ──markRunning()──▶ RUNNING ──markSuccess()──▶ SUCCESS（终态）
   │                        │
   │                        └─markFailed(errorMessage)──▶ FAILED（终态，原因必填）
   └──────cancel()──────┐
RUNNING ──cancel()──────┴──────────────────────────────▶ CANCELED（终态）
```

每个流转方法的守卫规则：

| 方法 | 允许的当前状态 | 副作用 |
| --- | --- | --- |
| markRunning | QUEUED | 记录 started_at |
| markSuccess | RUNNING | 记录 finished_at、清空 error_message |
| markFailed | RUNNING | 记录 finished_at、error_message 必填 |
| cancel | QUEUED / RUNNING | 记录 finished_at |
| updateProgress | RUNNING | 更新 current_stage + progress（0-100） |

非法流转一律抛 `DATA_CONFLICT(4005)` 并携带当前状态，便于页面提示。

### 6.3 状态字段保护

普通 `update` 接口**剔除** status / startedAt / finishedAt 后才复制属性——状态只能走流转方法，防止绕过状态机；终态任务不允许 update；只有终态任务允许 delete（QUEUED/RUNNING 任务被执行器持有，删除会造成悬空）。

### 6.4 日志顺序号（TaskLogService）

```java
// 查询该任务最新一条日志，取其顺序号加一；无日志时从 1 开始
TaskLog last = getOne(new LambdaQueryWrapper<TaskLog>()
        .eq(TaskLog::getTaskId, taskId)
        .orderByDesc(TaskLog::getSequenceNo)
        .last("LIMIT 1"));
return last == null ? 1L : last.getSequenceNo() + 1;
```

- 调用方传入的 sequenceNo 一律忽略，由服务端分配；
- 日志内容必填；logLevel 默认 INFO；写入前校验所属任务存在（注入 TaskMapper）；
- update 接口剔除 taskId / sequenceNo / logLevel——留痕字段不可改，只允许修正内容；
- 查询按 sequenceNo 升序，与实际执行顺序一致。

### 6.5 任务执行器调度与中断收敛（`task/executor`）

执行器由三个类组成，职责严格分离：

| 类 | 职责 |
| --- | --- |
| `TaskHandler` | 处理器 SPI：声明任务类型、互斥键、执行逻辑；**不修改任务状态** |
| `TaskExecutor` | 调度：轮询领取、并发上限、互斥串行、中断收敛；**不实现业务动作** |
| `ServerTestTaskHandler` | SERVER_TEST 的具体探活动作；只依赖 `TaskService` / `TaskLogService` / `SshSessionFactory` |

调度流程（`TaskExecutor` 实现 `SmartLifecycle`，容器刷新后自动启动）：

```text
定时轮询（light-deploy.task.poll-interval-ms，默认 1000ms）
        │
        ▼ listQueued(pollBatchSize)  按 create_time 升序取「排队中」任务
  取并发令牌（Semaphore = pool-size）—— 池内不留排队任务，多个任务同时到达时领不到的
        │                             本轮直接跳过，下一个轮询周期再试
        ▼
  按 lockKey 抢占互斥键（busyLockKeys）—— 键已被占用则本轮跳过该任务
        │
        ▼ 提交到工作线程池
  markRunning(taskId)  ← 带 status = 0 条件的原子更新，抢不到就跳过
        │
        ▼
  handler.execute(task)  → 正常返回 = 成功；抛异常 = 失败
        │
        ▼ finally：markSuccess / markFailed + 释放互斥键与并发令牌
```

关键设计点：

1. **领取是原子抢占**：`markRunning` 用 `update ... eq(status, QUEUED).set(status, RUNNING)` 完成流转，不写「先查状态再更新」。影响行数为 0 时再区分「任务不存在」与「状态冲突」，后者抛 `DATA_CONFLICT(4005)` 并携带当前状态；
2. **三重去重**：内存 `submittedTaskIds` 防止同一任务被本实例重复提交、`busyLockKeys` 落实服务器级互斥、数据库条件更新兜底跨实例重复（为将来多实例部署预留）；互斥键取自处理器，服务器类任务为 `server:{serverId}`，未知类型为 `unknown:{taskId}`（互不相同，避免互相阻塞）；
3. **并发上限**：线程池大小 = `light-deploy.task.pool-size`（默认 6，对应 §1 的服务器规模基线）；先取并发令牌再提交，线程池里不会堆积等待任务，队列大小语义退化为「瞬时超额」而不是「积压」；
4. **未知类型也要收尾**：找不到处理器的任务照样领取，然后直接标失败（`暂不支持的任务类型：xxx`），不允许它永远停在排队中；
5. **重启收敛（僵尸任务）**：任务进度只存在于内存和数据库，进程重启后停留在「执行中」的任务不可能续跑。启动时 `recoverInterruptedTasks()` 把残留的执行中任务（最多 200 条）统一标记为失败，原因写「平台重启导致任务执行中断，请重新提交」，避免页面永远显示执行中；
6. **日志写入失败只记 WARN**：日志是过程留痕，不能成为任务失败的原因；
7. **轮询失败节流**：数据库暂时不可用时只打一次 WARN 并按间隔重试，恢复后再次失败才重新打印，禁止每秒刷错误日志。

### 6.6 SERVER_TEST 探活项

处理器执行固定探活项（全部为只读命令，不产生副作用），每项落一条带 stage/level 的日志：

| 阶段 | 命令 | 进度 | 必需 |
| --- | --- | --- | --- |
| 建立连接 | 读取 server 行 → 解密凭据 → SSH 认证 | 10 | 是（失败即任务失败） |
| 系统信息 | `uname -a` | 30 | 是（能执行即证明通道与登录 shell 可用） |
| 系统信息 | `cat /etc/os-release \| head -2` | 35 | 否 |
| 运行时检查 | `java -version 2>&1 \| head -3` | 50 | 否 |
| 运行时检查 | `docker --version 2>&1 \| head -1` | 60 | 否 |
| 磁盘容量 | `df -h /` | 75 | 否 |
| 部署目录 | 检查 `light-deploy.agent.base-dir`（默认 `/opt/light-deploy`）是否存在且可写 | 90 | 否 |

判别规则：

- **必需项失败** → 任务整体标记失败，失败原因取自该命令的输出或退出码；
- **可选项失败** → 只记 WARN 日志，不改变任务结果（例如目标机没装 Docker，不应判定服务器不可用）；
- 部署目录检查用哨兵字符串判断结论（`LIGHT_DEPLOY_DIR_READY` / `LIGHT_DEPLOY_DIR_MISSING`），命令用 `||` 兜底保证退出码恒为 0，避免「非零退出码」与「目录不存在」两种语义纠缠；
- 每个阶段开始前调用 `reportProgress()`，返回 false 表示任务已被取消或已终态，**立即停止后续远程操作**（取消不中断已发出的命令，但不再往下发新命令）；
- 结束时汇报进度 100，日志按 `SshSession.exec` 输出逐行写入，单条命令最多 20 行。

## 7. 与其他模块的关系

| 方向 | 关系 |
| --- | --- |
| → `com.lx.deploy.ssh` | `ServerTestTaskHandler` 通过 `SshSessionFactory.open(server)` 取已认证会话；凭据解密只发生在 SSH 层（见 [SSH执行层.md](SSH执行层.md)） |
| ← server 模块 | SERVER_TEST 任务以 `biz_id = server.id` 消费服务器配置；ServerService 通过 `TaskService.hasUnfinishedTask()` 防止同一服务器重复提交测试任务 |
| ← server 模块接口 | `POST /server/{id}/test` 只创建任务并立即返回，执行与结果由任务模块异步完成（接口不阻塞等待连接结果） |
| ← 前端 | 任务列表页（任务管理 → 任务列表）查询任务、查看日志、人工取消终态前任务；服务器列表页的「连通性测试」按钮创建任务后打开日志抽屉，用 `GET /taskLog/pull` 增量拉取执行日志 |
| ← 后续构建/发布模块 | BUILD / DEPLOY 任务以 biz_id 关联 build / deployment 记录，按同样的 `TaskHandler` SPI 接入，不需要改动调度代码 |

任务状态流转由执行器独占驱动，调用链：

```text
ServerController POST /server/{id}/test
        │ 创建 QUEUED 任务
        ▼
TaskExecutor 轮询领取 → markRunning → ServerTestTaskHandler.execute → markSuccess / markFailed
        │ 每一步写一条 lds_task_log
        ▼
前端 GET /taskLog/pull?taskId=&lastSeq= 增量拉取
```

## 8. 已知边界与后续演进

- 任务执行器已落地并通过真机验证（建立连接 → 系统信息 → 运行时检查 → 磁盘容量 → 部署目录，共 21 条日志；部署目录不存在时记 WARN 而不判失败）；
- **单实例轮询**：执行器靠「轮询 + 数据库条件更新」抢占任务，当前按单实例部署设计。多实例部署时同一任务不会被重复领取，但会出现额外的空轮询开销，届时再考虑改为 Redis 队列或分布式锁；
- 顺序号分配为"查最大值+1"，任务内高并发写日志存在竞态，唯一键会兜底报错；执行器对同一任务的日志写入是串行的（单线程处理一个任务），实际风险可控；
- 取消 RUNNING 任务只是标记 CANCELED，**不会中断正在执行的远程操作**（处理器在每个阶段开始前检查状态，已发出的命令会跑完）；
- SSH 连接**未做主机密钥校验**：`SshClient` 未设置 `ServerKeyVerifier`，Apache SSHD 客户端的默认行为是接受任意主机密钥（等价于关闭校验），存在中间人风险，生产环境启用前必须补齐，见 [SSH执行层.md](SSH执行层.md)；
- 私钥只支持**未加密**的 OpenSSH / PKCS#8 文本，带口令的私钥会给出明确提示而不是静默失败；如需支持需引入口令输入通道；
- 日志接口未做分页内的关键字过滤（content LIKE），也**未对日志内容做敏感词二次过滤**（脱敏依赖 `SshSession.exec` 的输出脱敏），任务量大后可按需补充。
