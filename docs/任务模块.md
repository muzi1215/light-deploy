# 任务模块文档

> 模块包：`com.lx.deploy.task` ｜ 对应数据表：`lds_task`、`lds_task_log`（任务域，lds_ 前缀） ｜ 状态：模型 + 状态机 + 执行器 + SERVER_TEST 处理器已完成，真机验证通过

## 1. 模块定位

任务模块是全平台异步任务的**模型与状态机层**：连通性测试、构建、发布等所有长耗时操作都以一条 `lds_task` 记录承载生命周期，执行过程通过 `lds_task_log` 留痕。

- 本模块提供：任务模型、任务编号规则、状态单向流转、**任务执行器（调度 + 并发约束 + 中断收敛）**、任务处理器 SPI、任务日志写入与增量拉取、人工取消；
- 本模块不提供：具体业务动作的实现（连通性测试的处理器在 `task/executor` 下，但 SSH 能力来自 `com.lx.deploy.ssh`；构建、发布处理器由后续模块以同样的 SPI 方式接入）；
- 执行器已落地：创建任务后会被自动领取执行，处理器通过 `TaskHandler` 注册，不需要修改调度代码。

## 2. 数据表结构

### 2.1 `lds_task`（异步任务）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| task_no | VARCHAR(64) | 任务编号，唯一键，后端按 `TASK-yyyyMMddHHmmss-8位随机段` 生成 |
| task_type | VARCHAR(30) | SERVER_TEST / BUILD / DEPLOY |
| biz_id | VARCHAR(32) | 关联业务主键（如服务器 ID、构建 ID、发布 ID） |
| status | TINYINT | 任务状态：0 排队中 / 1 执行中 / 2 成功 / 3 失败 / 4 已取消，默认 0；数字编码见 `com.lx.deploy.common.constants.TaskStatus`（提供 `isValid` / `describe` / `isFinal`） |
| current_stage | VARCHAR(30) | 当前执行阶段 |
| progress | INT | 进度 0-100 |
| started_at / finished_at | DATETIME | 起止时间，由状态流转维护 |
| error_message | TEXT | 失败原因（markFailed 必填） |

### 2.2 `lds_task_log`（任务执行日志）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| task_id | VARCHAR(32) | 所属任务，写入前校验任务存在 |
| sequence_no | BIGINT | 任务内顺序号，服务端自动 max+1 分配，唯一键保证连续唯一 |
| stage | VARCHAR(30) | 日志所属阶段 |
| log_level | VARCHAR(10) | INFO / ERROR，默认 INFO |
| content | TEXT | 日志内容，必填 |

注意：任务日志写入数据库的同时会同步打印到服务器本地日志（见 §6.4），两者内容一致；区别在于本地日志带 requestId 与线程名，任务日志带 sequenceNo 与阶段，分别面向服务端 grep 与页面实时展示。

## 5. 接口清单

`/task`：page / list / detail/{id} / create / update/{id} / delete/{id} / **PUT /task/cancel/{id}**（人工取消，唯一的人工干预入口）。
`/taskLog`：page / list / {id} / POST / PUT / DELETE / **GET /pull**（按顺序号增量拉取，页面实时日志专用）/ **GET /export/{taskId}**（导出文本附件）。

```text
GET /taskLog/pull?taskId={taskId}&lastSeq={已获取的最大顺序号}&limit=200
→ { taskId, status, statusText, finished, currentStage, progress, errorMessage, logs[], lastSeq }
```

增量锚点用 `sequence_no` 而不是主键 `id`：主键是 32 位 UUID，不具备单调递增性。前端停止轮询的条件是「`finished === true` 且本批条数 `< limit`」（满页说明还有剩余，必须再拉一次把尾部取完），约定见 AGENTS.md §20.9。

### 5.1 日志导出：本模块唯一的非 JSON 响应

```text
GET /taskLog/export/{taskId}
→ 200 text/plain;charset=UTF-8
  Content-Disposition: attachment; filename="TASK-…-执行日志.txt"; filename*=UTF-8''…（中文文件名走 RFC 5987）
```

导出正文由 `TaskLogService.exportText` 拼装，结构是「任务头部摘要 + 全部日志行 + 结尾统计」：

```text
任务编号：TASK-20260925155150-985a7990
任务类型：发布任务                 ← 中文描述，读者是运维，不该要求他查 DEPLOY 是什么
任务状态：失败
关联业务主键：a788ac22…            ← 对应 build.id / deployment.id，便于跳到业务记录
当前阶段：收尾
执行进度：90%
开始时间：2026-09-25 15:51:51
结束时间：2026-09-25 15:52:23
失败原因：共 1 个目标，其中 1 个失败：阿里云轻量服务器 → …
--------------------------------------------------------------------------------
#1    2026-09-25 15:51:51  INFO   [系统] 任务开始执行：DEPLOY，关联业务主键 …
#14   2026-09-25 15:52:23  ERROR  [收尾] 目标 阿里云轻量服务器 发布失败：…
--------------------------------------------------------------------------------
共 14 条日志，导出时间：2026-09-25 17:05:00
```

几个刻意的取舍：

- **导出件自带任务头部**：任务列表的失败原因只有一行、页面日志区会被滚动淹没。导出件是要被贴进工单或转发协查的，必须自带完整上下文，否则拿到文件的人还得回平台截图；
- **不做条数上限**：导出的意义就是拿全量。单条日志长度在写入侧已由处理器限制，不会出现一条日志撑爆文件；
- **换行固定 LF、正文以换行结尾**：方便直接 diff 两次构建的日志差异；
- **不包 `ApiResponse`**：包一层 JSON 会让下载端必须多解一层。代价是响应体里没有 `traceId`，追踪改走响应头 `X-Request-Id` 与后端日志的 MDC；
- 异常路径（任务不存在等）仍由全局异常处理器返回标准 JSON 错误体，因此**前端必须先判断响应类型再决定是下载还是提示**——blob 请求在 `request.ts` 里不做业务码校验，当成附件存下来会得到一个内容是报错信息的「日志文件」；

## 6. 核心业务规则与代码逻辑

### 6.1 任务编号与创建

- taskNo 未传入时自动生成 `TASK-yyyyMMddHHmmss-UUID前8位`；传入时唯一性预检（DATA_CONFLICT），数据库唯一键兜底；
- 新建任务**强制 QUEUED**，不允许调用方指定初始状态，保证所有任务都经过执行器调度；
- taskType 必须是枚举值，progress 限 0-100。

### 6.2 状态单向流转（TaskService 状态机）

```text
QUEUED ──markRunning()──▶ RUNNING ──markSuccess()──▶ SUCCESS（终态）
   │                        │
   │                        └─markFailed(errorMessage)──▶ FAILED（终态，原因必填）
   └──────cancel()──────┐
RUNNING ──cancel()──────┴──────────────────────────────▶ CANCELED（终态）
```

每个流转方法的守卫规则：

| 方法 | 允许的当前状态 | 副作用 |
| --- | --- | --- |
| markRunning | QUEUED | 记录 started_at |
| markSuccess | RUNNING | 记录 finished_at、清空 error_message |
| markFailed | RUNNING | 记录 finished_at、error_message 必填 |
| cancel | QUEUED / RUNNING | 记录 finished_at |
| updateProgress | RUNNING | 更新 current_stage + progress（0-100） |

非法流转一律抛 `DATA_CONFLICT(4005)` 并携带当前状态，便于页面提示。

### 6.3 状态字段保护

普通 `update` 接口**剔除** status / startedAt / finishedAt 后才复制属性——状态只能走流转方法，防止绕过状态机；终态任务不允许 update；只有终态任务允许 delete（QUEUED/RUNNING 任务被执行器持有，删除会造成悬空）。

### 6.4 日志顺序号（TaskLogService）

```java
// 查询该任务最新一条日志，取其顺序号加一；无日志时从 1 开始
TaskLog last = getOne(new LambdaQueryWrapper<TaskLog>()
        .eq(TaskLog::getTaskId, taskId)
        .orderByDesc(TaskLog::getSequenceNo)
        .last("LIMIT 1"));
return last == null ? 1L : last.getSequenceNo() + 1;
```

- 调用方传入的 sequenceNo 一律忽略，由服务端分配；
- 日志内容必填；logLevel 默认 INFO；写入前校验所属任务存在（注入 TaskMapper）；
- update 接口剔除 taskId / sequenceNo / logLevel——留痕字段不可改，只允许修正内容；
- 查询按 sequenceNo 升序，与实际执行顺序一致。

**控制台同步输出**：落库成功后 `TaskLogService.echoToConsole` 会把同一条日志按级别打印到应用日志
（控制台与 `logs/info.log`），格式固定带任务 ID 与阶段前缀，服务端直接 `grep` 任务 ID 即可还原整条执行过程：

```
2026-09-25 00:12:31.507 [task-pool-1] INFO  [no-request] c.l.d.task.service.TaskLogService - [task=2026092500010001][构建] 镜像构建完成
```

- 级别只有 INFO 与 ERROR 两级：ERROR 同时进入 `logs/error.log`，便于告警采集，
  服务端日志里检索 ERROR 即可定位失败任务；
- 开关 `light-deploy.task.log-echo-enabled`（默认 `true`），关闭后日志只在平台页面可见；
- 同步输出只发生在 `TaskLogService.create`，构建 / 发布 / 连通性测试三类执行器的 `appendLog`
  最终都收敛到该方法，因此一处接入即全量覆盖。

### 6.5 任务执行器调度与中断收敛（`task/executor`）

执行器由三个类组成，职责严格分离：

| 类 | 职责 |
| --- | --- |
| `TaskHandler` | 处理器 SPI：声明任务类型、互斥键、执行逻辑；**不修改任务状态** |
| `TaskExecutor` | 调度：轮询领取、并发上限、互斥串行、中断收敛；**不实现业务动作** |
| `ServerTestTaskHandler` | SERVER_TEST 的具体探活动作；只依赖 `TaskService` / `TaskLogService` / `SshSessionFactory` |

调度流程（`TaskExecutor` 实现 `SmartLifecycle`，容器刷新后自动启动）：

```text
定时轮询（light-deploy.task.poll-interval-ms，默认 1000ms）
        │
        ▼ listQueued(pollBatchSize)  按 create_time 升序取「排队中」任务
  取并发令牌（Semaphore = pool-size）—— 池内不留排队任务，多个任务同时到达时领不到的
        │                             本轮直接跳过，下一个轮询周期再试
        ▼
  按 lockKey 抢占互斥键（busyLockKeys）—— 键已被占用则本轮跳过该任务
        │
        ▼ 提交到工作线程池
  markRunning(taskId)  ← 带 status = 0 条件的原子更新，抢不到就跳过
        │
        ▼
  handler.execute(task)  → 正常返回 = 成功；抛异常 = 失败
        │
        ▼ finally：markSuccess / markFailed + 释放互斥键与并发令牌
```

关键设计点：

1. **领取是原子抢占**：`markRunning` 用 `update ... eq(status, QUEUED).set(status, RUNNING)` 完成流转，不写「先查状态再更新」。影响行数为 0 时再区分「任务不存在」与「状态冲突」，后者抛 `DATA_CONFLICT(4005)` 并携带当前状态；
2. **三重去重**：内存 `submittedTaskIds` 防止同一任务被本实例重复提交、`busyLockKeys` 落实服务器级互斥、数据库条件更新兜底跨实例重复（为将来多实例部署预留）；互斥键取自处理器，服务器类任务为 `server:{serverId}`，未知类型为 `unknown:{taskId}`（互不相同，避免互相阻塞）；
3. **并发上限**：线程池大小 = `light-deploy.task.pool-size`（默认 6，对应 §1 的服务器规模基线）；先取并发令牌再提交，线程池里不会堆积等待任务，队列大小语义退化为「瞬时超额」而不是「积压」；
4. **未知类型也要收尾**：找不到处理器的任务照样领取，然后直接标失败（`暂不支持的任务类型：xxx`），不允许它永远停在排队中；
5. **重启收敛（僵尸任务）**：任务进度只存在于内存和数据库，进程重启后停留在「执行中」的任务不可能续跑。启动时 `recoverInterruptedTasks()` 把残留的执行中任务（最多 200 条）统一标记为失败，原因写「平台重启导致任务执行中断，请重新提交」，避免页面永远显示执行中；
6. **日志写入失败只记 WARN**：日志是过程留痕，不能成为任务失败的原因；
7. **轮询失败节流**：数据库暂时不可用时只打一次 WARN 并按间隔重试，恢复后再次失败才重新打印，禁止每秒刷错误日志；
8. **日志级别必须与任务结论对得上**：处理器表达失败的唯一方式是抛异常（执行器据此写「任务执行失败：…」并置 `status = 3`）。**禁止**「写了 ERROR 日志却正常返回」——那会让任务管理显示「成功」、日志末尾却是「任务执行成功」，中间夹着 ERROR，运维无法判断这次到底成没成。反过来，确实不属于失败的负面情况（可选探活项未安装、目录缺失等）只写 INFO/WARN，不要用 ERROR 表达。
9. **失败必须同时留痕控制台**：处理器抛异常后，`executeTask` 除调用 `failTask` 把原因写进 `lds_task_log` 与 `task.error_message` 外，还必须写一条控制台日志——业务性失败（`DeployException`）记 WARN 不打堆栈，未预期异常记 ERROR 带堆栈。**只落库不写日志**会让任务失败在服务端日志里完全不可见：既拿不到堆栈，也不知道是哪一步、哪台机器出的问题（AGENTS.md §14.3）。

> 真实事故：`DeployTaskHandler` 在收集完失败目标后只把 deployment 置为失败、自身正常返回，于是任务状态是「成功」，任务日志最后一行也是「任务执行成功」，与目标级的 ERROR 自相矛盾。修复方式是主流程汇总后主动抛异常，让部署记录与任务给出同一个结论。

### 6.6 SERVER_TEST 探活项

处理器执行固定探活项（全部为只读命令，不产生副作用），每项落一条带 stage/level 的日志：

| 阶段 | 命令 | 进度 | 必需 |
| --- | --- | --- | --- |
| 建立连接 | 读取 server 行 → 解密凭据 → SSH 认证 | 10 | 是（失败即任务失败） |
| 系统信息 | `uname -a` | 30 | 是（能执行即证明通道与登录 shell 可用） |
| 系统信息 | `cat /etc/os-release \| head -2` | 35 | 否 |
| 运行时检查 | `java -version 2>&1 \| head -3` | 45 | 否 |
| 构建依赖 | `git --version 2>&1 \| head -1` | 55 | 否 |
| 构建依赖 | `mvn -v 2>&1 \| head -1` | 60 | 否 |
| 运行时检查 | `docker --version 2>&1 \| head -1` | 68 | 否 |
| 磁盘容量 | `df -h /` | 75 | 否 |
| 部署目录 | 检查该服务器配置的部署根目录 `agent_base_dir`（服务器页面按机器维护）是否存在且可写 | 90 | 否 |

探活项**不区分构建机与目标机**：服务器档案的三个目录都有数据库默认值，无法据此判断用途，且同一台机器可能既构建又部署，因此统一按「可选依赖清单」检查（`PROBES` 里的固定列表）。

判别规则：

- **必需项失败** → 任务整体标记失败，失败原因取自该命令的输出或退出码；
- **可选项失败** → 只记一条普通（INFO）日志，不改变任务结果（例如目标机没装 Docker，不应判定服务器不可用）；
- 可选项可带 `hint`：失败时追加「怎么补」的可操作建议。`git` / `mvn` 缺失会直接导致构建阶段失败（典型报错 `bash: mvn: command not found`），因此这两项的 hint 分别给出安装命令与「在服务器档案配 `build_env_script` 补 PATH」的做法（见 [服务器模块.md §6.6](服务器模块.md)）；
- 部署目录检查用哨兵字符串判断结论（`LIGHT_DEPLOY_DIR_READY` / `LIGHT_DEPLOY_DIR_MISSING`），命令用 `||` 兜底保证退出码恒为 0，避免「非零退出码」与「目录不存在」两种语义纠缠；
- 每个阶段开始前调用 `reportProgress()`，返回 false 表示任务已被取消或已终态，**立即停止后续远程操作**（取消不中断已发出的命令，但不再往下发新命令）；
- 结束时汇报进度 100，日志按 `SshSession.exec` 输出逐行写入，单条命令最多 20 行。

### 6.7 回滚类任务的日志口径

任务日志是运维判断「这次到底做了什么」的第一入口，因此**回滚这种高代价、不可逆的动作，日志必须能独立回答六个问题**，不能只靠目标行零散的 INFO 加上执行器结尾那句「任务执行成功」——那句话不区分发布与回滚，看完不知道版本退到哪了。

| 必须出现 | 落点（`DeployTaskHandler`） |
| --- | --- |
| 开始回滚 + **开始时间** | 开场日志：`开始回滚部署 <id>，开始时间 yyyy-MM-dd HH:mm:ss` |
| 参与范围 | 紧接一条 `回滚策略 X，本次回滚 N/M 个目标`，M>N 时点明其余目标保持原版本不变 |
| **当前版本 / 回滚到什么版本** | 目标级 `回滚目标 <机器名>(<host>)：当前版本 X → 回滚到 Y，开始时间 …`，X 取 `new_version`、Y 取 `old_version` |
| **时间** | 目标级起始时间与收尾完成时间，格式 `yyyy-MM-dd HH:mm:ss`，**写进日志正文**，不只依赖日志行的落库时间 |
| **回滚成功 / 失败** | 收尾单独一条结论：`回滚成功：已成功回滚 N 个目标到历史版本…完成时间 …` / `回滚失败：…完成时间 …，请人工确认目标机当前版本`（失败走 ERROR） |
| **是否启动成功** | `restartService` 通过后写 `服务 X 启动成功（systemctl is-active = active）`；目标级成功文案写明「回滚成功，服务启动正常（当前版本 Y）」 |

配套约定：

- **成功也要留痕**：重启成功原本是静默通过的（只在失败时抛异常），回滚场景必须能核对「服务有没有起来」，所以成功路径补一条 `is-active = active` 的记录；
- **结论必须与业务记录一致**：回滚失败时除写 ERROR 日志外，还要让部署记录与任务同时失败（见 §6.5 第 8 条），不要出现「日志说失败、任务说成功」；
- **不可回滚必须提前拒绝**，而不是发一个必然无效果的任务。回滚的前置判定与原因文案见 [发布模块.md §6.5](发布模块.md)；任务侧能看到的是「一个都没进队列」，因此入口拦截才是正解。

### 6.8 PROJECT_TEST 探活项（2026-09-26 落地）

`ProjectConnectTestTaskHandler` 回答一个构建前必须知道、但只有等到构建失败才会暴露的问题：
**这台构建机现在能不能拉到代码、能不能推上镜像**。入口是 `POST /project/test/{id}`。

| 阶段 | 校验项 | 进度 | 必需 |
| --- | --- | --- | --- |
| 连接构建机 | 读 `project.build_server_id` → 服务器必须存在且启用 → SSH 登录 | 5 / 15 | 是 |
| 工具链检查 | `git --version`（必需）、`docker --version`（仅 DOCKER 运行时必需）、`mvn -v`（仅提示） | 25 | 必需项失败即失败 |
| 代码仓库校验 | `GIT_TERMINAL_PROMPT=0 git ls-remote --heads <带凭据地址> [分支]` | 45 | 是 |
| 镜像仓库校验 | 有凭据：`docker login --password-stdin`；再探测 `/v2/` 端点（https 优先，失败试 http） | 70 | 登录失败是，端点探测否 |
| **目标机前置检查** | **仅 JAR 运行时**：逐台连目标机，配了 `java_bin` 就 `test -x`、没配就 `command -v java` | 85 | 是 |
| 完成 | 三条结论行 + 进度 100 | 100 | — |

**目标机前置检查为什么不在构建机上做**：java 是应用**运行时**依赖，跑在目标机上；构建机装了什么 java 与目标机毫无关系，在构建机上探 java 探不出问题。典型故障是项目运行配置把 `java_bin` 填成 A 机的 JDK 路径，分发到 B 机时 systemd 单元里 ExecStart 指向不存在的可执行文件，服务以 `status=203/EXEC` 起不来；而单元只在首次部署生成、之后不重写，这类错误一旦发生就得上机手工改。

判定口径：`java_bin` **目标级运行配置覆盖项目级**（与发布链路 `mergeTargetConfig` 同口径，这里只取 `java_bin` 一个键）；路径须匹配 `[A-Za-z0-9._-]`，含 shell 元字符直接判失败。不可用即任务失败，失败原因写明机器名与路径，并指向「清空项目级 `java_bin` 由平台按机器自动探测，或在对应部署目标上单独覆盖」。同一台机器被多个环境绑定时会话按机器缓存，避免重复建连。

约束（完整背景见 [项目模块.md §6.7](项目模块.md)）：

- **执行位置是构建机，不是平台本机**；项目未绑定构建机时 `ProjectService.submitConnectivityTest` 直接拒绝，
  绝不悄悄改测本机——那样测出来的结论说明不了构建能否成功；
- **凭据拼装与构建链路共用一份实现**：`GitAuthSupport` / `RegistryAuthSupport` / `SecretMasker`；
- **互斥键取构建机**（`build-server:{serverId}`，与 BUILD 同键）：测试期 `docker login` 会写同机
  `~/.docker/config.json`，与正在推送的构建并发会互相登出，必须串行。读不到项目档案时回落到
  `project-test:{projectId}`，保证同一项目不会同时跑两次；
- **临时凭据文件（私钥 / 仓库密码）用完即删**，放在 `finally` 里且**不抛异常**——抛出会覆盖真正的失败原因；
- 分支不存在时 `ls-remote` 会**成功返回且输出为空**，因此必须同时判退出码与空输出；
- 提交侧防重：`ProjectService` 用 `TaskService.hasUnfinishedTask(PROJECT_TEST, projectId)` 拦重复提交。

`task_type` 在库里是字符串，因此新增该类型**不需要 DDL**。

## 7. 与其他模块的关系

| 方向 | 关系 |
| --- | --- |
| → `com.lx.deploy.ssh` | `ServerTestTaskHandler` 通过 `SshSessionFactory.open(server)` 取已认证会话；凭据解密只发生在 SSH 层（见 [SSH执行层.md](SSH执行层.md)） |
| ← server 模块 | SERVER_TEST 任务以 `biz_id = server.id` 消费服务器配置；ServerService 通过 `TaskService.hasUnfinishedTask()` 防止同一服务器重复提交测试任务 |
| ← server 模块接口 | `POST /server/test/{id}` 只创建任务并立即返回，执行与结果由任务模块异步完成（接口不阻塞等待连接结果） |
| ← project 模块接口 | `POST /project/test/{id}` 同上，创建 `PROJECT_TEST` 任务；项目列表页的「连通性测试」按钮复用同一套日志抽屉 |
| ← 前端 | 任务列表页（任务管理 → 任务列表）查询任务、查看日志、人工取消终态前任务；服务器列表页的「连通性测试」按钮创建任务后打开日志抽屉，用 `GET /taskLog/pull` 增量拉取执行日志 |
| ← 后续构建/发布模块 | BUILD / DEPLOY 任务以 biz_id 关联 build / deployment 记录，按同样的 `TaskHandler` SPI 接入，不需要改动调度代码 |

**业务记录如何找到自己的任务**：任务与业务记录只靠「`task_type` + `biz_id`」关联，业务表里不冗余存 `task_id`（避免两处状态互相打架）。因此 `build` / `deployment` 的 VO 必须在自己转换时按这两个字段反查最新一条任务并回填 `taskId` / `taskNo`，前端列表才能直接打开执行日志；漏填的表现是列表行 `taskId` 为空、点「查看日志」只得到一句「未关联异步任务」。

**任务列表页必须刷新**：列表被 keep-alive 缓存，切走再切回不会重跑 setup。任务几乎都是平台自己产生的（构建一次、发布一次各建一条），因此任务列表页在 `onActivated` 里重新拉取，否则刚触发的任务与执行中的进度一直不可见。

任务状态流转由执行器独占驱动，调用链：

```text
ServerController POST /server/test/{id}
        │ 创建 QUEUED 任务
        ▼
TaskExecutor 轮询领取 → markRunning → ServerTestTaskHandler.execute → markSuccess / markFailed
        │ 每一步写一条 lds_task_log
        ▼
前端 GET /taskLog/pull?taskId=&lastSeq= 增量拉取
```

## 8. 已知边界与后续演进

- 任务执行器已落地并通过真机验证（建立连接 → 系统信息 → 运行时检查 → 构建依赖 → 磁盘容量 → 部署目录；部署目录不存在时记普通日志而不判失败）；
- **单实例轮询**：执行器靠「轮询 + 数据库条件更新」抢占任务，当前按单实例部署设计。多实例部署时同一任务不会被重复领取，但会出现额外的空轮询开销，届时再考虑改为 Redis 队列或分布式锁；
- 顺序号分配为"查最大值+1"，任务内高并发写日志存在竞态，唯一键会兜底报错；执行器对同一任务的日志写入是串行的（单线程处理一个任务），实际风险可控；
- 取消 RUNNING 任务只是标记 CANCELED，**不会中断正在执行的远程操作**（处理器在每个阶段开始前检查状态，已发出的命令会跑完）；
- SSH 连接**未做主机密钥校验**：`SshClient` 未设置 `ServerKeyVerifier`，Apache SSHD 客户端的默认行为是接受任意主机密钥（等价于关闭校验），存在中间人风险，生产环境启用前必须补齐，见 [SSH执行层.md](SSH执行层.md)；
- 私钥只支持**未加密**的 OpenSSH / PKCS#8 文本，带口令的私钥会给出明确提示而不是静默失败；如需支持需引入口令输入通道；
- 日志接口未做分页内的关键字过滤（content LIKE），也**未对日志内容做敏感词二次过滤**（脱敏依赖 `SshSession.exec` 的输出脱敏），任务量大后可按需补充。
