# 构建模块文档

> 模块包：`com.lx.deploy.build`（含 `com.lx.deploy.release.ReleaseRecord` 的构建期自动创建）｜ 对应数据表：`build`、`build_artifact`、`release_record` ｜ 状态：后端已完成并编译通过，前端页面已联调；真机验证待进行

## 1. 模块定位

构建模块是「代码 → 可发布产物」的转化层：把 Git 仓库里的源码，在专用构建机上通过 SSH 拉取、构建、推送，产出**镜像**（DOCKER 运行时）或**文件产物**（JAR / STATIC 运行时），并登记到 `build_artifact`；构建成功后自动生成一条「可发布」的 `release_record`，交给后续发布模块消费。

- 本模块提供：构建触发（创建即执行）、构建机解析与防重、异步构建执行器（SSH 拉取 / 构建 / 推送）、产物与发布版本登记、构建记录的标准查询 / 删除；
- 本模块不提供：具体发布动作（发布模块负责）、构建机本身的连通性测试（复用任务模块 + SSH 执行层）、Git / 镜像仓库凭据的增删（凭据 / 镜像仓库模块负责）；
- 构建全程异步：**POST /build 只创建 build 记录并同步生成一条 BUILD 异步任务后立即返回**，真正的克隆 / 构建 / 推送由任务执行器的 `BuildTaskHandler` 完成，页面用 `GET /taskLog/pull` 增量拉取实时日志。

## 1.1 调用链路（前端 → 后端 → 执行器）

本模块是纵向主链第一段。**构建全程异步**：`POST /build` 只创建 build 记录并生成一条 BUILD 异步任务后立即返回，真正的克隆/构建/推送由 `TaskExecutor` 调 `BuildTaskHandler` 完成——请求与执行解耦（详见 [讲解文档.md](讲解文档.md)）。

```text
build.ts: createBuild(data)                   // 前端 api 函数（lighit-deploy-ui/src/api/build.ts:49）
        │  POST /build/create
        ▼
BuildController.create()                      // build/controller/BuildController.java:106
        ▼
BuildService.createAndTrigger(dto)            // build/service/BuildService.java:176  @Transactional
        │  校验项目/运行时/构建模式/构建机
        │  → 落 build 记录（status=0 排队中）
        │  → 生成 BUILD 异步任务（bizId=build.id），立即返回 BuildVo（含 taskId）
        ▼  （HTTP 请求结束，返回 taskId 给前端）
┄┄┄┄┄┄┄┄┄┄┄┄ 后台 TaskExecutor 每 1 秒轮询 lds_task ┄┄┄┄┄┄┄┄┄┄┄┄
TaskExecutor.executeTask()                     // task/executor/TaskExecutor.java:316
        │  markRunning 原子抢占 → handler.execute(task) @336
        ▼
BuildTaskHandler.execute(task)                // build/executor/BuildTaskHandler.java:142
        │  buildSupport.openSession 连构建机 @205 → startBuild @209 → cloneRepository @215
        │  → resolveReleaseVersion 定稿版本号 @222
        │  → 按运行时 switch 分发构建（DockerBuilder / JarPrebuildBuilder / ScriptBuildService）
        │  → assembleRelease 组装发布版本 @258
        │  → BuildService.completeSuccess @260 写 release_record（status=1 可发布）
        ▼
release_record（可发布版本）  ← 交给发布模块消费
```

产物上传（不走构建任务）：`build.ts:uploadArtifact()`（`build.ts:81`）→ `POST /build/upload` → `BuildController.upload()@127` → `ArtifactUploadService`（同步登记 `release_record`）。

## 2. 数据表结构

### 2.1 `build`（构建任务）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | VARCHAR(32) | 构建主键，MyBatis-Plus 生成的 32 位 UUID |
| project_id | VARCHAR(32) | 目标项目，关联 project.id；决定运行时、构建模式、构建配置来源 |
| deployment_id | VARCHAR(32) | 关联的部署任务，**预留字段**：v1 的「构建 → 发布版本 → 部署」是松耦合链路，构建不直接绑定某次部署，恒为空 |
| build_mode | VARCHAR(30) | 构建模式，取值见 `BuildMode` 枚举（从 project.build_mode 复制，执行器消费） |
| build_server_id | VARCHAR(32) | 专用构建机，关联 server.id；构建全程 SSH 连它执行 |
| git_commit | VARCHAR(100) | 实际构建所用的 Git 提交号，克隆后由 `git rev-parse HEAD` 回填 |
| version_seq | INT | **预留人工指定**的版本序号：发起构建时填写则用该序号生成版本号，留空表示构建成功时自动取号（项目内最大序号 +1），见 §6.6 |
| dependency_hash | VARCHAR(128) | 依赖文件摘要，**预留**：v1 不计算，恒为空（用于依赖缓存命中） |
| status | TINYINT | 构建状态：0 排队中 / 1 构建中 / 2 成功 / 3 失败，默认 0；数字编码见 `BuildStatus` |
| started_at / finished_at | DATETIME | 起止时间，由构建执行链路维护 |
| error_message | TEXT | 失败原因（截断到 2000 字符，禁止含凭据 / Token 等敏感信息） |

索引：`idx_build_project (project_id, create_time)`、`idx_build_deployment (deployment_id)`。

### 2.2 `build_artifact`（构建产物）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| build_id | VARCHAR(32) | 所属构建，关联 build.id |
| artifact_type | VARCHAR(20) | 产物类型：BASE_IMAGE / APP_IMAGE / JAR / STATIC，见 `ArtifactType` 枚举 |
| artifact_name | VARCHAR(255) | 产物名称（镜像仓库地址 + 标签 / 产物文件名） |
| artifact_tag | VARCHAR(255) | 镜像或产物标签 |
| artifact_digest | VARCHAR(255) | 镜像摘要（Docker content digest）或文件 SHA256 |
| dependency_hash | VARCHAR(128) | 依赖指纹（分层构建的基础镜像缓存 key），预留 |
| dockerfile_path | VARCHAR(255) | 实际使用的 Dockerfile 路径 |
| metadata_json | JSON | 产物附加元数据（如镜像大小、仓库地址等） |

### 2.3 `release_record`（发布版本，由构建成功自动生成）

构建成功后由 `BuildService.completeSuccess` 写入一条「可发布」记录，发布模块据此部署；本表归属发布域，但在构建链路里创建，这里列出供溯源。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| project_id | VARCHAR(32) | 项目 ID |
| version | VARCHAR(100) | 发布版本号，形如 `{项目编码}-v{版本序号}-{提交短码}`（如 `auth-7888-v3-887b603c`；无提交时提交部分退化为 `yyyyMMddHHmmss` 时间戳），项目内唯一 |
| version_seq | INT | 版本序号，项目内递增；是本表版本号字符串的权威来源，也是版本列表的排序依据，见 §6.6 |
| commit_id | VARCHAR(100) | Git 提交号（可为空） |
| artifact_path | VARCHAR(500) | JAR / 静态产物路径（文件类产物） |
| image_tag | VARCHAR(255) | Docker 镜像标签（镜像类产物） |
| image_digest | VARCHAR(255) | Docker 镜像摘要 |
| sha256 | VARCHAR(128) | 产物 SHA256（文件类产物） |
| runtime_type | VARCHAR(20) | 运行时类型：DOCKER / JAR / STATIC |
| status | TINYINT | 版本状态：0 构建中 / 1 可发布 / 2 已废弃，默认 1 |

## 3. 枚举与状态编码

| 名称 | 类型 | 取值 | 说明 |
| --- | --- | --- | --- |
| `RuntimeType` | 枚举 | DOCKER / JAR / STATIC | 运行时类型（字符串枚举，`common.enums.project`） |
| `BuildMode` | 枚举 | PROJECT_DOCKERFILE / LAYERED_DOCKER / SCRIPT_DEPLOY / ARTIFACT_ONLY / JAR_PREBUILD | 构建模式（`common.enums.project`） |
| `ArtifactType` | 枚举 | BASE_IMAGE / APP_IMAGE / JAR / STATIC | 产物类型（`common.enums.build`） |

> **运行时 × 构建模式矩阵**（规则唯一来源是 `RuntimeType.supports(BuildMode)`，与项目模块、前端下拉共用）：
> - DOCKER：`PROJECT_DOCKERFILE` / `LAYERED_DOCKER` / `JAR_PREBUILD`（产镜像，Dockerfile 来自项目仓库；`JAR_PREBUILD` 由平台先用 Maven 容器打 jar 再用项目提供的极简 Dockerfile 包镜像）；
> - JAR / STATIC：`SCRIPT_DEPLOY`（产文件）/`ARTIFACT_ONLY`（仅发布已有产物，已开放，配合 `UPLOAD` 来源走上传链路 §6.8）；
> - `ARTIFACT_ONLY` + `UPLOAD` 来源**已开放**：构建入口对 GIT 与 UPLOAD 两种来源都开放，`createAndTrigger` 通过 `RuntimeType.supports` 校验非法组合，`ARTIFACT_ONLY` 项目走 `/build/upload` 而非构建任务。

**状态 / 结果字段一律用 TINYINT 数字编码 + 常量类**（AGENTS.md §4.5）：

| 常量类 | 取值 | 说明 |
| --- | --- | --- |
| `BuildStatus`（`common.constants`） | 0 排队中 / 1 构建中 / 2 成功 / 3 失败 | 提供 `isValid` / `describe` / `isFinal` |
| `ReleaseStatus`（`common.constants`） | 0 构建中 / 1 可发布 / 2 已废弃 | 构建成功落库时固定为 1 可发布 |

## 4. 代码结构

```text

│   └── BuildController.java        # /build 标准六接口 + GET /build/artifacts/{id} + POST /build/upload

├── mapper/ （BuildMapper / BuildArtifactMapper）
├── model/  （Build + dto / vo）

    ├── BuildService.java           # 触发（createAndTrigger）+ 状态维护（startBuild/captureCommit/completeSuccess/completeFailure）
    └── ArtifactUploadService.java  # 产物上传：本地构建好的包 → 构建机产物目录 → 登记可发布版本（不走构建任务）

├── model/  ReleaseRecord.java
```

`BuildTaskHandler` 通过 `TaskHandler` SPI 自动注册（构造器注入 `List<TaskHandler>` 的 `TaskExecutor` 按 `taskType() == BUILD` 分发），`lockKey = "build-server:" + buildServerId`，保证同一台构建机同时只跑一个构建。

## 5. 接口清单

`/build`：page / list / detail/{id} / create（创建即触发）/ update/{id}（仅排队中改构建机）/ delete/{id}（仅终态可删）/ artifacts/{id}（产物清单）。

```text
POST /build/create               创建并触发构建，返回 BuildVo（含 taskId / taskNo）
POST /build/upload               上传本地已构建好的产物并登记版本（multipart，同步返回 BuildVo）
GET  /build/page                 分页查询构建记录（含 taskId / taskNo，支持 projectId / buildServerId 条件）
GET  /build/list                 列表查询构建记录（含 taskId / taskNo）
GET  /build/detail/{id}          构建详情（含 taskId / taskNo，便于直接拉日志）
GET  /build/artifacts/{id}       本次构建的全部产物
PUT  /build/update/{id}          仅排队中允许重指定构建机
DELETE /build/delete/{id}        仅终态（成功/失败）允许删除
```

`BuildVo` 额外携带 `projectName` / `buildServerName` / `statusText` / `taskId` / `taskNo`，`BuildArtifactVo` 额外携带 `artifactTypeText`。前端据此直接展示与拉取实时日志。

`taskId` / `taskNo` 由 `toVo` 统一补齐（列表与详情共用同一入口），不只在详情接口返回：前端「构建列表 → 查看日志」直接读列表行的 `taskId`，一旦列表 VO 不带该字段，页面只能弹「该构建记录未关联异步任务」，日志入口形同虚设。

## 6. 核心业务规则与代码逻辑

### 6.1 触发流程（`BuildService.createAndTrigger`）

```text
校验项目存在且启用
   → 校验 runtime_type × build_mode 组合（RuntimeType.supports）
   → DOCKER 必须绑定 registry_id（否则无处推镜像）
   → 解析构建机（请求 buildServerId → 项目档案 build_server_id → 系统默认；皆空则拒绝，见 §6.4）
   → 校验构建机存在且启用
   → 防重：同项目已有 排队中/构建中 记录则 DATA_CONFLICT
   → 落 build（status = 0 排队中，build_mode 从项目复制）
   → 生成 BUILD 异步任务（bizId = build.id，强制从排队开始）
   → 返回 BuildVo（含 taskId / taskNo）
```

方法带 `@Transactional(rollbackFor = Exception.class)`：`build` 记录与 BUILD 任务必须同生共死——任务建不起来时构建记录也不能留下，否则会出现一条既没有执行日志、也不会被调度器认可的孤儿构建（与部署创建同一条规则）。

### 6.2 异步构建执行（`BuildTaskHandler`）

任务执行器领取 BUILD 任务后，`BuildTaskHandler` 在构建机上依次：

1. **准备工作区**：在构建机档案的 `build_workspace_dir`（服务器页面按机器配置，默认 `/opt/light-deploy/build-workspace`）下为本次构建建立隔离目录；
2. **克隆代码**：按 `project.source_type` 与凭据类型选择鉴权方式——
   - HTTPS + `GIT_TOKEN`：把令牌注入仓库 URL **的密码位**（`https://oauth2:令牌@主机/路径`）。凭据明文含 `:` 时用用户自填的用户名，只填令牌时补 `oauth2` 占位——用户名位不参与认证但不能为空，Gitee / GitLab / GitHub 三家因此同一套写法（GitLab 官方「任意非空字符串」、GitHub 官方「用户名不用于认证」）；克隆成功后立即 `git remote set-url` 复位成不带凭据的地址，因为 git 会把含令牌的完整地址写进工作区 `.git/config`；
   - SSH + `SSH_KEY`：写临时私钥文件并以 `GIT_SSH_COMMAND` 指向它（凭据不进 URL，无需复位）；
   - **凭据类型与仓库协议双向校验**：`GIT_TOKEN` 只允许 `https://` 地址、`SSH_KEY` 只允许 `git@主机:组/仓库.git`，配错在拼装命令时即报「不适用于该协议」，不会拖到克隆时报「仓库不存在」；
   - 命令前统一加 `GIT_TERMINAL_PROMPT=0`：构建机是非交互会话，git 一旦转去索要凭据，报错会是 `could not read Password ... No such device or address`，把「URL 缺密码段」掩盖成「认证失败」（疑问与解答 Q-14）；
   - 凭据明文只在建连前短暂解密，命令输出经 `SecretMasker.maskSecret` 脱敏（`https://[^@/]+@` → `https://***@`，含冒号的形式同样被整体遮蔽）；
   - **地址拼装与脱敏只有一份实现**：`GitAuthSupport` / `SecretMasker`（`common/util`），与「项目连通性测试」
     处理器共用。两处各写一套会在「谁补 `oauth2`」这类细节上分叉，表现为「测试通过、构建失败」（疑问与解答 Q-15）；
3. **按运行时构建**：
   - DOCKER：Dockerfile **一律由项目仓库提供**，平台不生成模板。`PROJECT_DOCKERFILE` 用单个 Dockerfile；`LAYERED_DOCKER` 用 `Dockerfile.base` + `Dockerfile.app`，先构建并推送基础镜像；`JAR_PREBUILD` 平台先用 Maven 构建镜像在构建机打出 jar，再用项目提供的极简 Dockerfile（`build_config_json.dockerfile_path`，`FROM jre + COPY jar + COPY yml`）包成镜像，全程不生成模板；
   - JAR / STATIC：`SCRIPT_DEPLOY` 执行 `build_config_json.build_command`，再从 `artifact_path` 定位产物；
4. **产出与登记**：DOCKER 推送镜像并取 `image digest`（content digest），文件类算 `sha256sum`；统一调用 `BuildService.completeSuccess` 落 `build_artifact` + 自动生成 `release_record`；任一阶段异常调用 `completeFailure`，失败原因截断且脱敏。

构建配置解析自 `project.build_config_json`（`module_name` / `module_dir` / `build_command` / `dockerfile_path` / `artifact_path` / `image_repository`），用于多模块仓库的局部构建（AGENTS.md §23.3）。

#### 6.2.1 构建命令的执行目录

`build_command` 的执行目录由构建配置决定（`BuildTaskHandler.buildFileArtifact`）：

| `module_dir` | `module_name` | 执行目录 | 命令里该怎么写 |
| --- | --- | --- | --- |
| 有值 | — | `{工作区}/{module_dir}` | **不要**再用 `-pl` / `--projects` 指定同一模块 |
| 空 | 有值 | `{工作区}/{module_name}` | 同上 |
| 空 | 空 | `{工作区}`（仓库根） | 多模块仓库用 `-pl {子模块} -am` |

平台先把命令拼成 `cd {执行目录} && {环境前缀}{build_command}`，因此「`module_dir` 有值 + 命令里带 `-pl auth-tool`」这种组合必然失败：Maven 从 `auth-tool/pom.xml` 起构建，reactor 里没有名为 `auth-tool` 的模块，报 `Could not find the selected project in the reactor`。编辑页已对该组合直接拦截（`constants/projectConfig.ts` 的 `ConfigField.checks`），配置 JSON 模式下绕过校验时，构建日志里也会出现同样的报错。

> 产物定位不受影响：`artifact_path` / `config_paths` 一律**先按仓库根解析、找不到再按执行目录回落**，两种填写口径都支持。

#### 6.2.2 构建命令的执行环境与预检

非交互式 SSH 会话不加载 `/etc/profile`，`PATH` 里常缺「已安装但靠 profile 导出路径」的工具（典型是 Maven），直接执行只会得到一行 `bash: mvn: command not found`。为此执行构建命令前有两层保障：

1. **环境前缀**（拼在 `cd` 之后、构建命令之前，作用于同一个 shell）：
   - 平台固定执行 `. /etc/profile >/dev/null 2>&1`（输出丢弃，不污染构建日志）；
   - 紧接着执行构建机档案的 `build_env_script`（单行，可选，见 [服务器模块.md §6.6](服务器模块.md)），用于补 profile 里也没有的路径；
2. **命令可执行性预检**（`checkBuildCommandExecutable`）：用**与正式执行相同的前缀**探测命令首词——
   - `PATH` 形式（如 `mvn`）用 `command -v` 查，含 `/` 的路径形式（如 `/opt/.../bin/mvn`）用 `test -x` 判断；
   - 首词识别会跳过 `KEY=VALUE` 前缀，因此 `JAVA_HOME=/usr/lib/jdk1.8.0_121 mvn ...` 检测的是 `mvn` 而不是 `JAVA_HOME`；
   - 预检不通过直接判任务失败，并在任务日志与异常信息里给出三种处理方式（安装工具 / 在服务器档案补 PATH / 在 `build_command` 里写绝对路径），避免用户只看到 `command not found` 无从下手。

> 预检与正式执行共用前缀这一点很关键：若预检不带前缀，会出现「profile 里已配好 Maven、预检却说找不到」的误判。

#### 6.2.3 构建日志的记录规则

构建过程的所有远程命令输出都由 `BuildTaskHandler` 写入任务日志（`lds_task_log`），规则如下：

| 场景 | 记录方式 |
| --- | --- |
| 命令成功 | 回显 **stdout**（普通命令最多 30 行；构建类命令最多 200 行，超出截断并说明总行数）；stdout 为空而 stderr 有内容时回显 **stderr**——git 的克隆进度、Maven 的告警都走 stderr，非 TTY 会话下 git 进度默认静默、stdout 恒为空，只读 stdout 会显示成「（命令无输出）」，容易被误读成命令没生效 |
| 构建命令执行中 | **实时逐行回传**（上限 500 行）：Maven 每产出一行就落一条日志，页面能看到进度滚动。原来输出要等通道关闭才读取，命中超时则缓冲区全部丢弃，页面上只剩一句「执行超时」 |
| 构建命令成功 | 只记一条汇总（`构建命令执行成功：耗时 N 秒，共 M 行输出`），不再整段重打 stdout——输出已经实时落过一遍，重复回显等于同一段日志出现两次；行数超过实时回传上限时补录末尾 200 行 |
| 克隆成功 | 显式记一条 `代码拉取成功：{仓库地址}`（地址经脱敏），随后记 `代码拉取完成，当前提交：{commit}`；不再依赖命令输出判断成败 |
| 命令失败 | stderr **完整**写入日志（普通命令最多 40 行、构建类最多 200 行，超出截断），异常消息只保留首行摘要供列表页展示。Java 类错误（如 `NoSuchMethodError`）首行只有一句「找不到方法」，点名具体类与 jar 的 `at xxx.yyy(Zzz.java:行号)` 全在后续行里，只留首行等于没有定位信息 |
| 命令超时 | 已收到的输出按上述上限落日志，并补记最后一行与「超时前没有任何输出」的判定；异常消息给出超时秒数与放宽键名（`build_config_json.command_timeout_seconds`） |
| 构建命令为 Maven | 执行前额外记一条 `构建工具链版本：`，内容为 `{token} -v` 的输出（Maven 版本 + Maven home + **实际使用的 JDK 版本**）。这是「JDK 版本错配」类问题的唯一自证信息，探测失败不影响构建 |

需要固定写进日志的两类信息（因此不依赖用户手动复现）：

- **构建工具链版本**（`logBuildToolchain`）：`mvn -v` 的输出同时给出 Maven 版本与它运行所依赖的 JVM。例如 `NoSuchMethodError: java.nio.ByteBuffer.mark()Ljava/nio/ByteBuffer;` 的根因是「用 JDK 9+ 编译的类跑在 JDK 8 上」——JDK 9 给 `ByteBuffer` 增加了返回 `ByteBuffer` 的 `mark()` / `flip()` / `clear()` / `position(int)` / `limit(int)` / `reset()` / `rewind()` 协变重载，JDK 8 上这些方法仍来自父类 `Buffer`，方法描述符不匹配即链接失败。报错本身不会说明是哪个 jar、哪个 JVM 导致的，版本日志是唯一线索；
- **失败输出的完整上下文**：构建失败时先写完整 stderr 再抛异常。

#### 6.2.4 构建命令的超时与终止

构建命令以 `setsid -w sh -c '<脚本>'` 的方式启动，脚本内容为「把进程组组长 PID 写入 `/tmp/light-deploy-build-{taskId}.pid`」+「cd 到执行目录 + 环境前缀 + 用户构建命令」：

- **为什么用 setsid**：命令进入独立会话后，组长 PID 就是进程组 PGID，超时可以用 `kill -9 -PGID` 连 `mvn` 及其 fork 出的子进程一起终止。否则「任务已判失败、远端还在往即将被删除的工作区里写」，清理工作区会与残留进程互相干扰；
- **为什么带 `-w`**：进程组组长场景下 `setsid` 会 fork，不带 `-w` 时父进程立刻退出、通道提前关闭，构建会被误判成「瞬间成功」；
- **构建机没有 setsid 时降级**：改以普通方式重跑一次，并如实记一条「本次构建超时后无法终止远端进程组」，不让用户对着一句 `setsid: command not found` 发懵；
- **超时判定**：`exec` 命中超时 → 先终止进程组与删 PID 文件，再落已收到的输出，最后抛出 `构建命令执行超时（N 秒，可在 build_config_json.command_timeout_seconds 放宽上限）`；终止失败不覆盖超时结论，只补一条说明；
- **超时预算**：项目级 `build_config_json.command_timeout_seconds` 优先，未配置时用 `light-deploy.ssh.long-command-timeout-seconds`（默认 1800 秒）。首次全量构建与增量构建可能差一个数量级，所以不做「一个全局值打天下」。

克隆仓库同样走长命令超时（大仓库可达几分钟），超时时把 git 写在 stderr 的进度落日志。

### 6.2.5 compose 文件快照：存在发布版本记录里，而不是构建机

DOCKER 项目如果打算用 `docker compose` 启动（`runtime_config_json.deploy_form=COMPOSE`），
就把编排文件放进仓库、在 `build_config_json.compose_file_path` 指路径。
构建成功后执行器会把文件**原文**读到 `release_record.compose_content`，发布时直接下发到目标机。

**为什么是快照到库里，而不是随产物落到构建机持久目录**：

| | 走构建机产物目录 | 存发布版本记录（采用） |
| --- | --- | --- |
| 落盘成本 | 每个版本多一个目录，还要进配额、要回收 | 无磁盘产物，不占配额 |
| 取回成本 | 发布要两跳（构建机→平台→目标机） | 平台直接 `cat` 到目标机，一跳 |
| 粒度 | 按版本号能取回 | 同样按版本号精确回溯 |
| 一致性风险 | 产物与版本记录可能不同步 | 版本记录即唯一来源 |

compose 是几 KB 的**编排描述**，不是可分发制品。把它当产物落盘，
等于为一个文本文件付出「配额计算 + 回收 + 两跳传输」的全部代价。
这里也连带保持了「DOCKER 版本不占构建机磁盘」这条配额判据（见 §6.7）依然成立。

**读取规则（两种失败语义不同，必须区别对待）**：

| 情形 | 行为 | 理由 |
| --- | --- | --- |
| 显式配了 `compose_file_path` 却读不到 | **构建失败**，报错指出路径 | 用户明确说有这个文件，静默跳过会把错误推迟到发布阶段才爆 |
| 没配路径且默认 `docker-compose.yml` 不存在 | 静默跳过（`compose_content` 为空） | 多数 `docker run` 项目根本不用 compose，不能因缺可选文件让构建失败 |
| 读到内容但缺 `${IMAGE_TAG}` 占位符 | **构建失败**，报错给出写法示例 | 缺占位符 = 容器永远拉同一个 tag，发布报成功而线上没变化，属于最难发现的一类故障 |

**平台不对快照内容做任何改写**：改 ComposeInjection 也不做插值替换，
原样写进目标机的 `docker-compose.yml`。版本号走独立的变量文件注入（见 [发布模块.md](发布模块.md)）——
这样运维上机看到的文件与仓库里逐字一致，排障时「文件里写的是啥」永远可信。

代价要写清楚：**compose 变了必须重新构建**才能发布。它描述的是「这个版本怎么跑」，
不属于运行时可以随便覆盖的参数；反过来，正因为随版本固化，回滚才能精确回到当时的编排。

### 6.3 状态维护与发布版本
- 构建状态只能由执行链路通过 `startBuild`（→ 构建中）、`completeSuccess`（→ 成功）、`completeFailure`（→ 失败）维护，普通更新接口不能写 status；
- `completeSuccess` 同时：置成功 + 写结束时间 + 落全部产物 + 创建「可发布」的 `release_record`（版本号在克隆后由 `resolveReleaseVersion` 一次性定稿，见 §6.6）；
- 仅终态构建允许删除，避免删除正在执行 / 排队中的记录导致任务悬空（与任务模块同一守卫思路）。

### 6.4 构建机解析与防重

- 构建机解析顺序：**请求 `buildServerId` 显式指定 → 项目档案 `project.build_server_id` → 系统默认
  `light-deploy.build.server-id`（application.yaml，默认空）**；三者皆空则直接拒绝触发。
  中间这一级是 2026-09-26 加的：项目档案里记下「这个项目固定在哪台机器上构建」，
  新建构建即可默认带出该机器，同时让「项目连通性测试」与真实构建落在同一台机器上（见 [项目模块.md](项目模块.md) §6.7）；
- 同一项目已有 `排队中 / 构建中` 构建时禁止重复触发，避免抢占构建机与产物混乱；
- 项目列表页「构建」按钮默认带出项目档案的构建机，仍可清空或改选。

### 6.5 「重新构建」的语义：新建而非重放

构建列表行上的「重新构建」**不是重放那次构建**，而是**针对同一项目重新触发一次全新构建**。它在业务上等价于「对同一个项目再点一次构建」，与那行记录的版本、提交、构建机都没有关系。

链路（`views/build/index.vue` → `BuildService.createAndTrigger` → `BuildTaskHandler`）：

```ts
// 前端只取 projectId；旧记录的 commit / 版本 / 构建机一律不参与
await createBuild({ projectId: row.projectId })
```
```java
// 执行器工作区按 buildId 隔离，注释原文「每次全新创建，避免旧产物污染」
final String workspacePath = workspaceBase + "/" + project.getCode() + "_" + buildId;
prepareWorkspace(task, session, workspacePath);
// 克隆只带分支（branchOrEmpty），不带提交；全程无 checkout
"git clone " + branchOrEmpty(project) + gitUrl + " " + workspacePath
```

因此：

| 疑问 | 结论 |
| --- | --- |
| 会重建旧记录那次的包吗？ | **不会**。新 build 记录、新工作区、新 BUILD 任务，产物与版本号都是新的 |
| 会读旧记录的 `git_commit` 吗？ | **完全不读**。`build.git_commit` 目前全项目 0 个读取点 |
| 那构建的是哪份代码？ | 克隆当前 `project.git_branch`（未配置则仓库默认分支）的**最新 HEAD** |
| 版本号怎么来的？ | 克隆后 `git rev-parse HEAD` 回填 commit，版本号 = `项目编码-v{序号}-短commit`（`resolveReleaseVersion`）；序号每次构建递增，所以重复构建**不会**互相覆盖（见 §6.6） |
| 会改写旧记录吗？ | 不会。旧记录一字不动，只是列表里多出一条新记录 |

**推论：当前无法「按指定 commit 重建历史包」。** 一旦构建机上的产物被清理、或镜像标签被新版本覆盖，旧构建记录就只剩「曾经构建过」的溯源信息，无法再从构建侧复现。要复现旧代码只能走部署侧——回滚或重发旧的 `release_record` 版本。

**若后续要支持「按 commit 重建」**：`build.git_commit` 已在库中可直接利用，把克隆命令改成 `git fetch --all && git checkout <commit>`（或把 `--branch` 换成指定 ref），并在记录上标识「本次为历史版本重建」。需同时处理分支被 force push 后旧 commit 不可达的情形——那时 Git 侧也拿不到代码，只能依赖已持久化的产物。

### 6.6 发布版本号的生成：一处定稿、四处共用

发布版本号格式固定为 **`{项目编码}-v{版本序号}-{提交短码}`**，例如 `auth-7888-v3-887b603c`（无提交时提交部分退化为 `yyyyMMddHHmmss` 时间戳）。序号是版本号必须包含的段：只凭 `项目编码-提交短码` 无法回答「这是第几个版本」，也无法排序。

生成点全项目只有一处——`BuildService.resolveReleaseVersion(projectId, projectCode, gitCommit, manualSeq)`，调用时机是**克隆拿到 commit 之后**：

```java
int seq = (manualSeq != null && manualSeq > 0)
        ? manualSeq
        : releaseRecordMapper.selectMaxVersionSeq(projectId) + 1;
return new ReleaseVersion(seq, projectCode + "-" + VERSION_SEQ_PREFIX + seq + "-" + versionCommitPart(gitCommit));
```

这个字符串被**四处共用**，因此必须在构建开始时一次性定稿、全程传递，绝不中途重算：

| # | 使用点 | 形式 |
| --- | --- | --- |
| 1 | Docker 镜像 tag | `{imageRepo}:{版本号}`，分层构建另有基础镜像 tag `base-{版本号}` |
| 2 | 构建机产物持久目录 | `{build_artifact_dir}/{项目编码}/{版本号}`（JAR / STATIC 转存，部署时 SFTP 回取） |
| 3 | 产物目录下的 `VERSION` 标识文件 | `{build_artifact_dir}/{项目编码}/{版本号}/VERSION`，含 `version=` 行的 `key=value` 文本 |
| 4 | `release_record.version` | 版本记录本体，部署侧据此选版本与回滚 |

四处一旦不一致，就会出现「版本列表里有这个名字，但镜像或产物目录里没有」，部署时才在目标机上炸。实现上 `BuildTaskHandler` 在 clone 后把版本号当参数往下传，`assembleRelease` 不再自行取号。

**第 3 处（产物版本标识）为什么必需**：产物文件本身不带任何平台标识——`auth-tool.jar` 里既没有版本号也没有提交号。平台可达时看版本列表即可，但平台宕机、或运维在构建机上直接找产物时，只能靠目录名或回平台反查。`BuildTaskHandler.writeArtifactVersionMarker` 在产物转存后写一份 `VERSION`，内容含 `version` / `commit` / `runtime` / `artifact` / `built_at`，让产物自己带上版本。

**标识一律用外部文件，禁止重写 jar 的 `MANIFEST.MF`**：Spring Boot fat jar 的嵌套 jar 依赖 ZIP 的 STORED 布局，用 `jar --update` 重打包一旦改变压缩方式会静默产出「启动即失败」的产物；且重打包会改变 SHA256，与 `build_artifact.artifact_digest` / `release_record.sha256` 的语义冲突。写标识失败**只记日志、不影响构建结论**——它是辅助信息，不该挡住一次已经成功的构建。完整约束（含目标机侧的两处同名标识）见 AGENTS §24.7。

**取号规则**

- **自动取号**：`MAX(version_seq) + 1`。这个查询**刻意不过滤软删除**——若过滤，删掉 v3 后新建又会拿到 v3，出现两个 v3，排序与追溯同时失效。
- **人工指定**：走 `build.version_seq`（项目页「触发构建」对话框可选填）。校验发生在**创建构建时**而非构建收尾，`requireVersionSeqAvailable` 只看未删除记录，口径与唯一键 `uk_release_project_version` 一致——避免配置错误拖到构建跑完才失败、白占一次构建机。

**为什么必须加序号（不只是可读性问题）**

改造前版本号只有「项目编码 + 提交短码」，同一 commit 重复构建时上述三处全部同名：镜像被第二次 push 覆盖、产物目录被 `cp -r` 覆盖，并在 `release_record` 上撞唯一键。而 `BuildService.completeSuccess` **没有事务**，顺序是「置 build 成功 → 插产物 → 插版本」，异常炸在最后一步——结果是**构建记录显示成功、任务显示失败、版本列表里没有它**，镜像已推送、产物已落盘，这个包却永远发不出去。序号让每次构建的产物彼此独立，从根本上消除这种半成功状态。

**历史版本号不改写**：`release_record.version`、`deployment_target.old_version / new_version`、历史镜像 tag 里存的是旧格式字符串，改名会让部署记录与镜像、产物目录全部对不上。因此新格式**只对新构建生效**，版本列表新旧格式并存是预期现象；升级脚本会按 `create_time` 给老数据回填序号 1..N，让新构建从 N+1 继续编号。发布侧把版本号当作不透明字符串处理，不受影响（见 [发布模块.md](发布模块.md) §6.1）。

### 6.7 发布版本保留策略：磁盘产物与版本记录一起回收

`project.retain_release_count`（项目页「保留版本数」，最小 1，默认 5）此前**只落库、无任何消费方**——既没把历史版本置为「已废弃」，也没删过构建机上的产物目录，因此构建机的 `{构建产物持久目录}/{项目编码}/` 只增不减。本轮把它接进**构建成功后的收尾**。

**触发点与顺序**：`BuildTaskHandler` 在 `completeSuccess` 之后调用 `applyRetentionPolicy`，顺序固定为 **先删磁盘产物，再置记录废弃**。反过来会让记录已不可见、磁盘却还占着，运维只能上机手工找目录。

**按版本自己的构建机删**：`release.build_server_id` 是构建完成时从 build 记录复制的**快照**。产物是磁盘文件，只在当初那台机器上存在——若按项目当前绑定的构建机去找，历史版本会全部找不到包。因此回收时逐条读它自己的 `build_server_id`，必要时额外开 SSH 连到另一台老构建机（`resolveSession`：本次构建机复用会话，其它机器按需新开并缓存，用完统一关闭）。

**两条安全边界**

| 边界 | 说明 |
| --- | --- |
| 保护窗口 | 最近 20 次部署引用过的版本**一律不回收**。回滚是按 `old_version` 重新发布，把某台机器正跑着的版本清掉会让回滚与新发同时断掉。宁可少删，不可错删 |
| 路径白名单 | 待删目录只能由「构建机产物持久目录 / 项目编码 / 版本号」三段拼成，版本号须匹配 `[A-Za-z0-9._-]`。版本号来自库记录而非用户输入，但 `rm -rf` 的目标仍做一次校验，杜绝路径穿越 |

**镜像类版本（DOCKER）不参与配额与回收**：它的产物是镜像仓库里的 tag，构建不往产物持久目录落任何文件，`artifactDir()` 恒返回 null，走完流程也只是「置废弃、删了个空气」——省不下一字节磁盘，却让一个镜像仍在仓库、随时可再次发布的版本从下拉里消失。配额只对**占用构建机磁盘**的文件类版本计数，且过滤必须发生在配额计算之前，否则 DOCKER 版本会挤占名额把文件类版本提前清掉。详见 [产物分发链路.md](产物分发链路.md) §8.9.1。

**失败口径**：回收**不是构建成功的必要条件**。算不出清单、连不上构建机、`rm` 失败都只记日志（未预期异常 ERROR 带堆栈），**不影响本次构建结论**——否则会把「磁盘清理不顺」误报成「构建失败」。目录无法确定（构建机缺失 / 未配产物目录 / 版本号不安全）时只废弃记录，**不猜路径删**。

**语义变更**：此前「历史版本永不置已废弃，始终可在新建部署里选到」。接进保留策略后，**超出保留数且不在保护窗口内的版本会被置为 `DEPRECATED` 并从版本下拉中消失**（下拉只列「可发布」）。这是用户显式配置保留数的正常语义，但「手工换包后补一次新建部署重发对应版本」要趁那个版本还在窗口内做。

**遗留**：① 只在**下次构建成功时**触发，存量目录不会立刻减少，想马上清理需手工删（只删 `release_record` 里查不到的孤儿目录，删前务必核对）；② 库里查不到记录的旧格式目录不会被自动回收；③ 保留数为 null 或 ≤0 时**不做任何回收**。

### 6.8 产物上传链路（`ArtifactUploadService`）

面向「代码不从仓库来、产物在本地已经构建好」的项目：项目来源 `UPLOAD` + 构建模式 `ARTIFACT_ONLY` + 运行时 `JAR` / `STATIC`。典型场景是前端 `npm run build` 后打包上传，或本机打好的 jar 直接上传。平台**不做任何构建**，只负责存产物与登记版本，之后走与正常构建产物完全相同的发布链路。

三个准入条件缺一不可：来源是 `UPLOAD`、构建模式是 `ARTIFACT_ONLY`、运行时是 `JAR` / `STATIC`。**DOCKER 不支持上传**——它的产物是镜像，必须由镜像仓库承载，上传一个文件无法变成可发布的镜像。

**产物必须落到构建机，不能只存在平台本地**：发布执行器下载产物时强制要求 `release_record.build_server_id`，走的是「构建机 → 平台 → 目标机」两跳。只存平台本地会让发布阶段直接报「未记录构建机」。构建机在这里是产物暂存与分发中心，不是构建中心。

落盘位置与构建链路完全一致：`{构建机产物持久目录}/{项目编码}/{版本号}/{文件名}`，并写入同格式的 `VERSION` 标识文件，运维在构建机上找上传产物与找构建产物是同一套找法。

版本号走既有的退化格式 `{编码}-v{序号}-yyyyMMddHHmmss`（无 Git 提交场景，`BuildService.resolveReleaseVersion` 已支持）。人工指定序号时**在上传前先校验占用**：等到落库撞唯一键，产物已经传到构建机了，用户看到的是「换个序号再来一次」，而远端多了一份永远不会被引用的文件。

**为什么用编程式事务**：上传天然分成两段——SFTP 传输是分钟级远程 IO，落库是三张表（build / build_artifact / release_record）。AGENTS.md §4.6 要求事务方法内禁止远程调用与耗时 IO，因此事务边界只能包住落库；而同一个 bean 内自调用 `@Transactional` 方法不经过代理、事务不会生效，这里改用 `TransactionTemplate` 显式划定边界，比拆一个只为过代理的类更直白。

受支持的格式：`.zip` / `.tar.gz` / `.tgz` / `.jar`。文件名在服务端过滤掉路径分隔符与空白后再拼进远程路径，防止 `../` 把产物写到构建机的任意位置。

`spring.servlet.multipart` 上限已放宽到 500MB（Spring Boot 默认单文件 1MB，前端 dist 几十 MB 会直接被拒）。

**`ARTIFACT_ONLY` 项目不能发起构建任务**：`BuildService.createAndTrigger` 与 `BuildTaskHandler` 都会在入口拦住并提示走 `/build/upload`。让它占住构建机排队、跑到执行阶段才失败，对用户毫无意义。

**上传也要参与版本保留策略**：回收动作原先只写在 `BuildTaskHandler` 内部，产物上传不走构建任务，于是上传登记的版本在构建机磁盘上只增不减。现已抽出 `ReleaseRetentionExecutor`（`release/service` 包），把「算清单 → `rm -rf` 产物目录 → 置记录废弃」做成一条链路，构建收尾与上传登记**共用同一份实现**——「删哪些、能不能删」这类带安全阀的逻辑在全局必须只有一处定义，漏掉安全阀比没有回收更危险。

上传侧的调用是**异步**的：本次 HTTP 请求已经承担了一次 SFTP 传输，回收还可能要再连另一台构建机，SSH 握手或超时的时间是分钟级，塞进同步响应会让上传页面长时间转圈。而回收本来就不是上传成功的必要条件——漏做一次不影响结果，下一次构建或上传还会再触发。

调用方可传入自己已认证的那个 SSH 会话复用（`try-with-resources` 的生命周期仍由调用方掌握），为一个删除动作重新握手不划算；产自其它机器的版本由执行器按需单开会话，用完即关。

**前端入口**：构建列表页的「上传产物」按钮（`src/views/build/index.vue`）打开 `720px` 对话框，调用 `uploadArtifact()`（`src/api/build.ts`）。项目下拉在打开时才拉取，并**只保留满足后端准入条件的项目**（来源 `UPLOAD` + 构建模式 `ARTIFACT_ONLY` + 运行时 `JAR`/`STATIC`）——把不满足条件的项目放进下拉，用户选完提交才被拒，是一次纯粹的浪费。

### 6.2.2 JAR_PREBUILD（B1）构建流程

面向「项目是 Java 应用、但不想在目标机装 maven/JDK 工具链」的 DOCKER 运行时项目。平台先用 Maven 构建镜像在构建机打出 jar，再用项目提供的极简 Dockerfile 包成镜像推仓库，目标机只做纯 `docker run`。

前置条件（`build_config_json`）：
- `artifact_path`：**必填**，jar 相对仓库根路径（找不到再按 `module_dir` 回落）；
- `dockerfile_path`：**必填**，项目提供的极简 Dockerfile（如 `FROM eclipse-temurin:8-jre` + `COPY app.jar` + `COPY *.yml`）；
- `settings_path`：选填，Maven `settings.xml` 相对路径，用于切阿里云镜像加速依赖下载。

流程：① Maven 构建镜像挂载 `~/.m2` 缓存与工作区跑 `build_command` 出 jar；② 定位 jar；③ `docker build -f {dockerfile_path}`（构建上下文为工作区根）出 `imageRepo:tag`；④ 推仓库 + 取 digest + 登记 `release_record`。
**不产出构建上下文 tarball**：目标机无源码也无 maven，应急上机重建无意义；RUN 形态本就不下发。发布侧复用 `DockerDeployService`（pull + run / compose up）。

## 7. 与其他模块的关系

| 方向 | 关系 |
| --- | --- |
| → 任务模块 | 每次构建生成一条 BUILD 任务（`bizId = build.id`），由 `TaskExecutor` + `BuildTaskHandler` 驱动；实时日志复用 `lds_task_log` 与 `GET /taskLog/pull` |
| → SSH 执行层 | 构建机连接、Git 凭据解密、命令脱敏全部走 `com.lx.deploy.ssh`（见 [SSH执行层.md](SSH执行层.md)） |
| → 项目模块 | 消费 `project.runtime_type` / `build_mode` / `build_config_json` / `registry_id`；校验运行时 × 构建模式组合 |
| → 服务器模块 | 构建机是 server 表中的一台启用中的机器 |
| → 凭据 / 镜像仓库模块 | Git 令牌 / 私钥、镜像仓库登录密码来自这两个模块的凭据表，构建层只短暂解密 |
| → 发布模块（后续） | 构建成功自动生成的 `release_record` 是发布的数据源；`deployment_id` 预留为「为某次部署定向构建」的回流字段 |
| ← 前端 | 项目管理页「构建」按钮触发并打开实时日志对话框；构建管理页（构建列表）查询 / 查看产物 / 重新构建 / 删除，日志与项目页共用 `/taskLog/pull` 增量拉取 |

## 8. 已知边界与后续演进

- **已开放**：`ARTIFACT_ONLY` 构建模式与 `UPLOAD` 来源（见 §6.8 产物上传链路，已落地）；`dependency_hash` 依赖缓存未计算；`deployment_id` 定向构建未回填；
- **构建产物不可按提交复现**：`build.git_commit` 只用于溯源与版本号生成，全项目无读取点；「重新构建」永远克隆分支最新 HEAD（见 §6.5），所以**不能按历史 commit 重建产物**。产物可复现性实际依赖构建机持久目录与镜像仓库的保留策略（见 [发布模块.md](发布模块.md) §8）；
- **构建机单点**：v1 由一台专用构建机（或系统默认）承担全部构建，未做构建机集群与负载均衡；
- **真机验证待进行**：构建执行链路（克隆 / 构建 / 推送 / 产物登记 / 发布版本生成）已编码完成并通过编译，需在真实构建机（如 47.103.12.12 同类环境）跑通端到端；
- **镜像仓库无预检**：仓库连通性 / 登录正确性要到首次推送才暴露（与镜像仓库模块同源遗留）；
- **凭据仅构建机使用**：Git 与镜像仓库凭据只在该构建机建连 / 登录瞬间解密，日志与响应不出现明文（AGENTS.md §7）。
