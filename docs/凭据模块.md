# 凭据模块文档

> 模块包：`com.lx.deploy.credential` ｜ 对应数据表：`credential` ｜ 状态：已完成，真机验证通过（含引用保护）

## 1. 模块定位

凭据模块保存**外部系统**的登录凭据：Git 拉取用的令牌 / 私钥、镜像仓库登录用的用户名密码。

- 本模块提供：凭据的加密落库、类型区分、引用查询、删除前的引用保护；
- 本模块不提供：加解密算法（统一委托 `CredentialCrypto`）、凭据的使用（Git 拉取与镜像推送执行时由消费方解密）；
- **服务器 SSH 凭据不走本表**：`server` 表直接保存自己的密文字段（AGENTS.md §6、§7），本表只服务于 Git 与 registry；
- 凭据是全局资源，不属于某个项目或环境，因此页面挂在「系统设置」下。

## 2. 数据表结构（`credential`）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | VARCHAR(32) | 主键，MyBatis-Plus `ASSIGN_UUID` 生成 |
| name | VARCHAR(100) | 凭据名称，必填，与 is_deleted 组成唯一键 |
| type | VARCHAR(30) | 凭据类型编码：GIT_TOKEN / SSH_KEY / REGISTRY / SSH_PASSWORD |
| encrypted_value | TEXT | **AES-GCM 加密后的明文凭据，禁止存明文** |
| metadata_json | JSON | 非敏感元数据，**仅供页面展示**（如给凭据备注一个账号名），不参与登录或克隆；禁止放密码、令牌、私钥 |
| create_time / update_time / is_deleted | - | BaseEntity 统一审计字段，软删除 |

唯一键：`uk_credential_name (name, is_deleted)` —— 同名凭据软删除后可重新创建。

## 3. 枚举设计（`com.lx.deploy.common.enums.credential`）

| 枚举 | 取值 | 用途 |
| --- | --- | --- |
| CredentialType | GIT_TOKEN | HTTPS 形式仓库地址的用户名 + 访问令牌 |
| | SSH_KEY | SSH 形式仓库地址（`git@`）使用的部署私钥 |
| | REGISTRY | 登录私有镜像仓库的用户名 + 密码 |
| | SSH_PASSWORD | **保留类型**，当前没有消费方（服务器 SSH 密码在 server 表里） |

`CredentialType.isGitType()` 返回 true 的只有 GIT_TOKEN 与 SSH_KEY —— 项目绑定 Git 凭据时用它判断类型是否可用。

**「用户名 + 令牌」里的令牌是当密码用的**，不是登录密码：Gitee 的私人访问令牌（Personal Access Token）与账号密码是两个东西，账号密码在 HTTPS 克隆里已被平台拒绝。具体填法与示例见 §6.6。

## 4. 代码结构

```text
com.lx.deploy.credential
├── controller/CredentialController.java   # /credential 标准六接口
├── mapper/CredentialMapper.java           # BaseMapper，无自定义 SQL
├── model/
│   ├── Credential.java                    # 持久化实体（含 encrypted_value）
│   ├── dto/CredentialDto.java             # 请求对象（credential 明文只写）
│   └── vo/CredentialVo.java               # 响应对象（**不含密文**）
└── service/CredentialService.java         # 加密边界 + 唯一性 + 引用保护
```

跨模块依赖：`CredentialService` → `ProjectMapper` / `RegistryMapper`（删除前统计引用），
两个消费方（ProjectService / RegistryService）→ `CredentialMapper`（校验引用）。
全部走 Mapper，不注入对方 Service，避免 Service 之间形成循环依赖。

## 5. 接口清单

统一前缀 `/credential`，统一返回 `ApiResponse<T>` 并携带 `requestId`。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/credential/page` | 条件分页查询（name / type 等值过滤） |
| GET | `/credential/list` | 条件列表查询（前端下拉用，如 `?type=REGISTRY`） |
| GET | `/credential/detail/{id}` | 主键查询，不存在抛 DATA_NOT_FOUND(4004) |
| POST | `/credential/create` | 新增，`credential`（明文）必填 |
| PUT | `/credential/update/{id}` | 修改，`credential` 选填（留空保留旧密文） |
| DELETE | `/credential/delete/{id}` | 逻辑删除，被项目或仓库引用时拒绝 |

## 6. 核心业务规则与代码逻辑

### 6.1 明文只写不读（最核心）

```text
前端提交明文 credential（CredentialDto.credential，标注 WRITE_ONLY）
        │
        ▼  CredentialService.create / update
CredentialCrypto.encrypt()   ← AES/GCM/NoPadding，key 来自 LIGHT_DEPLOY_AES_KEY
        │
        ▼
写入 credential.encrypted_value（数据库只存密文）
        │
        ▼  后续消费方（Git 拉取 / 镜像推送，构建模块落地后）
CredentialCrypto.decrypt()   ← 仅在建立连接前短暂解密，用后不缓存
```

三条结构性保证：

1. **DTO 只有明文入参**：`CredentialDto` 声明 `credential` 并标注
   `@JsonProperty(access = WRITE_ONLY)` + `@Schema(accessMode = WRITE_ONLY)`，
   调用方无法提交密文，也不会在响应里看到它；
2. **VO 没有密文字段**：`CredentialVo` 根本不声明 `encryptedValue`，
   从类型结构上排除「查询接口回显密文」，与 server 模块的 `ciphertext` 处理同口径；
3. **密文只由 Service 产生**：`toEntity()` 属性复制无法把请求内容写进 `encrypted_value`，
   该字段只在 `create` / `update` 里由 `encrypt()` 赋值。

实测：`GET /credential/page` 的响应 JSON 中既没有明文也没有密文字段。

### 6.2 修改语义

- `credential` 选填：不传（或空串）→ **保留原密文**，支持只改名称 / 元数据；
- 传了新明文 → 重新加密覆盖旧密文（密文 SHA256 前后变化已实测）；
- `type` 允许修改，但类型与实际凭据内容不符会导致后续连接失败，界面按「换类型就重填凭据」使用。

### 6.3 校验规则（与前端表单镜像）

| 规则 | 不满足时的响应 |
| --- | --- |
| 名称必填、长度 ≤ 100 | VALIDATION_ERROR(4001) |
| 类型必须是 CredentialType 取值 | VALIDATION_ERROR(4001)「凭据类型必须为 GIT_TOKEN、SSH_KEY 或 REGISTRY」 |
| 明文凭据新增必填 | VALIDATION_ERROR(4001)「凭据内容不能为空」 |
| metadata_json 必须是合法 JSON | VALIDATION_ERROR(4001) |
| 名称不能与未删除记录重复 | DATA_CONFLICT(4005) |

### 6.4 引用保护（删除前检查）

```java
// 项目引用：project.git_credential_id
Long projectCount = projectMapper.selectCount(
        new LambdaQueryWrapper<Project>().eq(Project::getGitCredentialId, id));
// 镜像仓库引用：registry.credential_id
Long registryCount = registryMapper.selectCount(
        new LambdaQueryWrapper<Registry>().eq(Registry::getCredentialId, id));
```

任一引用大于 0 就抛 `DATA_CONFLICT(4005)` 并给出具体数量与解除路径。这是**最后一道防线**：
消费方各自也有引用校验（ProjectService / RegistryService），但删除侧必须自己再查一次，
否则会出现「页面删掉了凭据、项目的 git_credential_id 变成悬空外键」。

### 6.5 查询规则

- `name` / `type` 参与等值查询；
- `metadata_json` 与 `encrypted_value` **不参与任何查询**：前者是自由文本、参与查询没有业务价值，
  后者是密文，参与查询等于给自己开一条侧信道；
- 列表按 `create_time` 倒序。

### 6.6 各类凭据的填写口径与示例

`credential` 字段的名字叫「明文凭据内容」，但**四类凭据往里填的东西完全不同**，填错的表现也不一样：填错 GIT_TOKEN 会克隆失败，填错 REGISTRY 会 `docker login` 失败，而**填错 SSH_PASSWORD 则毫无反应**——因为没有任何代码读它。下表是唯一的填写口径。

| 类型 | 明文内容格式 | 示例 | 谁在读、怎么用 |
| --- | --- | --- | --- |
| `GIT_TOKEN` | `用户名:令牌`，或只填令牌（平台以 `oauth2` 补用户名位） | `wangan2022:a1b2c3d4e5f6...` 或 `a1b2c3d4e5f6...` | `BuildTaskHandler.buildCloneCommand`：拼进 HTTPS 仓库地址 |
| `SSH_KEY` | **完整 PEM 私钥**，含首尾标识行、保留换行 | `-----BEGIN OPENSSH PRIVATE KEY-----` 起的整段文本 | 同上：写入构建机临时文件，经 `GIT_SSH_COMMAND` 引用 |
| `REGISTRY` | `用户名:密码`，按**第一个**冒号切分 | `light-deploy:Abc123456` | 构建链路 `dockerPush` 与项目连通性测试共用 `RegistryAuthSupport`：`docker login <仓库地址> -u <冒号前> --password-stdin`（密码经临时文件走 stdin，不进命令行） |
| `SSH_PASSWORD` | —— | —— | **没有消费方**，填了也不会被使用；服务器 SSH 密码在「服务器管理」里单独维护 |

**四类凭据的配套要求：**

- **`GIT_TOKEN` 只能配 HTTPS 仓库**：项目的 Git 地址必须是 `https://gitee.com/组/仓库.git`。代码里有硬校验，地址不是 `https://` 开头直接抛「GIT_TOKEN 凭据仅适用于 HTTPS 协议仓库」。
- **`SSH_KEY` 只能配 SSH 仓库**：地址形如 `git@gitee.com:组/仓库.git`。除了这份私钥，还要把**对应公钥**加到代码平台（Gitee：仓库 → 管理 → 部署公钥；部署公钥默认只读，需要推送权限就加到账号级公钥）。
- **`REGISTRY` 的 `registry_url` 与登录用户名不要弄混**：`registry_url` 在「镜像仓库管理」里配置（如 `registry.cn-hangzhou.aliyuncs.com`），凭据里填的是登录**用户名与密码**；元数据里也可以写一份用户名用于页面展示，但**登录只认明文里的用户名**。
- **`SSH_PASSWORD` 不要选**：保留编码仅为兼容既有 DDL 注释。

**`GIT_TOKEN` 的令牌放在哪一位，决定了成不成功。** HTTPS 形式的仓库地址由三段组成：

```text
https:// <用户名> : <密码> @ <主机>/<路径>
          └── 这两段合称 userinfo ──┘
```

令牌是**当密码用**的，必须落在冒号后面那一段：

```bash
# 正确：令牌在密码位（Gitee 官方形式）
git clone https://oauth2:<私人令牌>@gitee.com/wangan2022/auth-system-Iteration.git
git clone https://wangan2022:<私人令牌>@gitee.com/wangan2022/auth-system-Iteration.git

# 错误：令牌只放在用户名位，URL 里没有密码段
git clone https://<私人令牌>@gitee.com/wangan2022/auth-system-Iteration.git
# → fatal: could not read Password for 'https://xxx@gitee.com': No such device or address
```

最后那种写法是 GitHub 的习惯（`https://<PAT>@github.com` 可用），**Gitee 不认**：git 看到「有用户名、无密码」会转去交互式索要密码，而构建机上的克隆跑在 SSH 通道里没有终端，于是直接报 `No such device or address`。

> **修复记录（2026-09-26）**：此前 `buildCloneCommand` 生成的正是最后那种错误形态（`"https://" + 明文 + "@"`，令牌落在用户名位），已修复为「只填令牌时补 `oauth2` 占位」；同时补上了协议双向校验、`GIT_TERMINAL_PROMPT=0` 与克隆成功后的 remote url 复位。详见 `docs/疑问与解答.md` Q-14。

### 6.7 三个平台的凭据设置入口对照

同一件事在三个平台上叫法不同、入口不同，下面的对应关系用于照着点。**平台侧只负责签发凭据，平台里填的永远是凭据本身，不是平台账号密码。**

**访问令牌（`GIT_TOKEN`）**

| 平台 | 平台侧叫法 | 设置入口 | 需要的权限 | 有效期 |
| --- | --- | --- | --- | --- |
| Gitee | 私人令牌（Personal Access Token） | 头像 → 设置 → 安全设置 → 私人令牌 → 生成新令牌 | 勾 `projects`（仓库读；要推送需含写权限） | 可设置，建议 1 年 |
| GitLab | Personal Access Token | 头像 → Edit profile → Access tokens | `read_repository`（只读克隆）；推送加 `write_repository` | 新版强制填过期日期 |
| GitHub | Personal access token（classic / fine-grained） | Settings → Developer settings → Personal access tokens → Tokens (classic) 或 Fine-grained tokens | classic 勾 `repo` 才能读私有仓库；fine-grained 选 `Contents: Read-only` | 可设置 |

三家的共同点：**令牌只在生成时显示一次**，关掉页面就再也看不到，必须当场复制并填进平台的凭据里；**令牌是当密码用的**，填法与地址形态见上一节。Gitee 开启双因素认证后，HTTPS 推拉只能用私人令牌，账号密码直接失效——这也是私有仓库改用令牌的常见起因。

**Git 私钥（`SSH_KEY`）**

| 平台 | 平台侧叫法 | 设置入口 | 只读 / 读写 | SSH 地址形态 |
| --- | --- | --- | --- | --- |
| Gitee | 部署公钥（单仓库）/ SSH 公钥（账号级） | 仓库 → 管理 → 部署公钥管理；账号级：设置 → 安全设置 → SSH 公钥 | 部署公钥**固定只读**；账号级公钥可读写 | `git@gitee.com:组/仓库.git` |
| GitLab | Deploy keys（单项目）/ SSH Keys（账号级） | 项目 → Settings → Repository → Deploy keys；账号级：User settings → SSH Keys | Deploy key 默认只读，可勾 `Grant write permissions` | `git@gitlab.com:组/仓库.git` |
| GitHub | Deploy keys（单仓库）/ SSH and GPG keys（账号级） | 仓库 → Settings → Deploy keys；账号级：Settings → SSH and GPG keys | Deploy key 默认只读，可勾 `Allow write access` | `git@github.com:用户/仓库.git` |

三个要点：

1. **私钥与公钥不要搞反**：`ssh-keygen` 生成两个文件，填进平台凭据的是**私钥文件**（`~/.ssh/ld_deploy`，无后缀那个）的完整内容；上传到代码平台的是**公钥**（`~/.ssh/ld_deploy.pub`）。凭据里粘贴私钥时**必须包含 `-----BEGIN` / `-----END` 两行**，换行原样保留。
2. **优先用「部署公钥 / Deploy key」而不是账号级公钥**：前者只对单个仓库生效、默认只读，泄露影响面最小；本项目只拉代码不推送，用只读的就够。平台侧配置私钥时也不要把带口令（passphrase）的私钥放进去——克隆过程没有输入口令的环节。
3. **HTTPS 与 SSH 是两条独立通道，凭据类型必须与仓库地址形态一致**：`GIT_TOKEN` ↔ `https://…`，`SSH_KEY` ↔ `git@主机:…`。平台在拼装克隆命令时会校验这一点，配错会直接报「不适用于该协议」，不会等到克隆时才失败。

**该选哪一种**：能配 SSH 就优先 `SSH_KEY` + 部署公钥——凭据不进 URL、不落工作区的 `.git/config`，只对单个仓库生效；只有在 HTTPS 是唯一出网通道（或平台侧不方便维护 SSH 公钥）时才用 `GIT_TOKEN`。

**为什么 `SSH_KEY` 用起来没有「用户名」的困扰**：SSH 协议的认证身份就是密钥本身，不存在把凭据塞进 URL 的环节；私钥由平台写入构建机 `/tmp/ld_git_key_{项目编码}_{任务ID}`（`chmod 600`），只在这一条 `GIT_SSH_COMMAND` 里使用，不落库、不落日志。

## 7. 与其他模块的关系

| 方向 | 关系 |
| --- | --- |
| ← project 模块 | `project.git_credential_id` 引用本表；ProjectService 校验存在性且类型必须可用于 Git |
| ← registry 模块 | `registry.credential_id` 引用本表；RegistryService 校验存在性且类型必须是 REGISTRY |
| → 后续构建模块 | Git 拉取、镜像推送时按引用取出密文并解密使用（构建模块落地后实现） |
| → common.crypto | 加解密统一委托 `CredentialCrypto`，本模块不实现算法 |
| ← 前端 | 系统设置 → 凭据管理页面；项目表单的 Git 凭据下拉、镜像仓库表单的凭据下拉都读本模块的 list 接口 |

## 8. 已知边界与后续演进

- **没有凭据「使用记录 / 最近使用时间」**：页面无法看出某份凭据是否还在被使用，只能靠删除时的引用提示；如果后续需要，可在解密处打点；
- **轮换凭据需人工操作**：修改凭据内容后立即生效（下次连接即用新凭据），没有版本历史与回滚；
- **SSH_PASSWORD 类型保留但无消费方**：与既有 DDL 注释保持一致，新增凭据时不要选用；
- **凭据不区分环境**：同一份凭据可被测试与生产项目共用，环境隔离依赖项目 / 环境的划分，本模块不做限制；
- 明文只在请求体与加密瞬间存在，**日志中不打印任何凭据字段**（包括长度），排障时只能看到凭据名称与类型。
