# 环境与部署目标：发布到底发到哪台机器

> 面向运维的操作手册与原理说明。项目模块.md §6.8 有一版精简结论，本文是完整版。
> 相关硬约束见 AGENTS.md §24.5（版本方向）与本文 §7（陷阱字段）。

---

## 1. 一句话结论

**环境不决定发到哪台机器，部署目标才决定。**

发布时选环境，平台只是拿 `(项目ID, 环境ID)` 去 `project_environment_target` 表查「这个项目在这个环境下绑定了哪几台启用的服务器」，再按策略裁剪，快照进 `deployment_target`。

环境本身只提供三样东西：环境名称/编码、**默认部署策略与批次大小**、以及一个**完全不起作用**的「默认服务器」字段。

---

## 2. 三层模型

```
project（项目）
  └── project_environment_target（部署目标）  ← 唯一的发布依据
        ├── environment_id → environment（环境：dev/test/prod，全局共享）
        └── server_id      → server（服务器：SSH 凭据、IP、部署根目录）
```

| 层 | 表 | 回答什么问题 | 谁私有 |
|---|---|---|---|
| 环境 | `environment` | 这是「生产」还是「测试」；默认用什么策略发 | **全局**，所有项目共用同一批环境 |
| 部署目标 | `project_environment_target` | 这个项目在这个环境下，**具体发哪几台、按什么顺序、谁主谁从** | 项目私有 |
| 服务器 | `server` | 怎么连上这台机器（host/端口/凭据/部署根目录） | 全局资产 |

关键点：

- **机器不归环境管。** 一台服务器不会因为「环境标签是生产」就自动成为生产环境的发布目标，也不会因为环境叫 prod 就被发到。
- **同一环境同一服务器只能绑一次**（唯一键 `uk_project_env_server`），主目标在同一项目环境内互斥（最多一个）。
- **环境是全局的**：A 项目在 prod 环境绑了 3 台，B 项目在 prod 环境可以绑完全不同的 5 台。区别在于各自的目标绑定，不在环境本身。

## 3. 发布时的读取路径（代码坐标）

入口 `DeploymentService.createAndTrigger`：

```java
// ① 取候选全集：项目 + 环境 + 启用，按发布顺序升序
List<ProjectEnvironmentTarget> bindings = projectEnvironmentTargetMapper.selectList(
        new LambdaQueryWrapper<ProjectEnvironmentTarget>()
                .eq(ProjectEnvironmentTarget::getProjectId, project.getId())
                .eq(ProjectEnvironmentTarget::getEnvironmentId, environment.getId())
                .eq(ProjectEnvironmentTarget::getStatus, EnableStatus.ENABLED)
                .orderByAsc(ProjectEnvironmentTarget::getDeployOrder)
                .orderByAsc(ProjectEnvironmentTarget::getCreateTime));
if (bindings.isEmpty()) {
    throw new DeployException(VALIDATION_ERROR, "该项目在环境 X 下没有启用的部署目标，请先在部署目标中绑定服务器");
}

// ② 按策略裁剪
List<ProjectEnvironmentTarget> selected = targetPlanner.selectByStrategy(bindings, strategy);

// ③ 推断每台机器当前版本，作为 old_version（回滚依据）
Map<String, String> currentVersions = targetPlanner.resolveCurrentVersions(project.getId(), environment.getId());

// ④ 快照进 deployment_target：serverId / deployOrder / oldVersion / newVersion
```

**策略裁剪**（`DeploymentTargetPlanner.selectByStrategy`）：

| 策略 | 实际发几台 |
|---|---|
| `SINGLE_TARGET` | **1 台**：优先主目标（`is_primary=1`）；没有主目标时取 `deploy_order` 最小的那台 |
| `ALL_AT_ONCE` | 全部启用绑定 |
| `ROLLING` | 全部启用绑定，按 `batch_size` 分批 |

⚠️ **最大的误发风险就在这里**：绑了 5 台、策略是 `SINGLE_TARGET`，平台只会发主目标那 1 台，其余 4 台不动——而日志里不会有任何「另外 4 台没发」的提示，因为对平台来说它们根本不在本次目标集里。

**顺序随快照固化**：`deployment_target.deploy_order` 在创建时从绑定表写死，之后改绑定表不影响当次发布。执行器与页面明细一律 `orderByAsc(deployOrder).orderByAsc(createTime)`，禁止只用 `create_time`（秒级 DATETIME 并列时会退化成随机序）。

## 4. 「看起来像配置、实际不起作用」的字段

这是运维最容易踩的坑：字段**在 UI 上能设、能看到，但对发布零影响**。

| 字段 | 在哪设 | 是否影响发布 | 真相 |
|---|---|---|---|
| `environment.default_server_id`<br>环境管理页「默认服务器」 | —— | ❌ **已移除** | 2026-09-28 从表、实体、DTO/VO、Service 校验、环境页表格与表单中全部删除。移除理由不只是「没用」：**环境是全局共享的，被多个项目引用，而各项目在该环境下绑哪些机器由部署目标决定，「某个环境的默认服务器」这个语义本身不成立** |
| `server.env_tag`<br>服务器管理页「环境标签」（1开发/2测试/3生产） | 服务器 → 编辑 | ❌ **完全不消费** | 只用于服务器列表的搜索筛选与表格 tag 着色。它与 `environment` 表**没有外键、没有一致性校验**——把 `env_tag=1（开发）` 的机器绑到 prod 环境，平台不会拒绝也不会警告 |

**真正起作用的开关只有这几个**：

| 字段 | 作用 |
|---|---|
| `project_environment_target.status` | 0 停用 = 该机器**不参与**这个环境的发布（保留绑定关系，可随时启用） |
| `project_environment_target.is_primary` | 决定 `SINGLE_TARGET` 发哪台 |
| `project_environment_target.deploy_order` | 决定多目标的发布顺序 |
| `project_environment_target.runtime_config_json` | 该机器的差异化运行配置（覆盖项目默认），如端口、内存 |
| `environment.deploy_strategy` / `batch_size` | 新建部署时的**默认值**，请求可覆盖 |
| `server.status` | 0 停用时，若它被选中参与发布，`createAndTrigger` **直接抛错**：「部署目标服务器 X 已停用，不允许发布」——是**失败，不是跳过** |
| `project.build_server_id` | 构建机，**与发布目标无关**，只决定在哪构建、产物存在哪 |

## 5. 运维操作指南

### 5.1 新项目接入（一次性）

1. **服务器管理**建档案：host、SSH 端口、用户名、认证方式、部署根目录。连通性测试必须通过。
   - `env_tag` 随手填，它只是个展示标签；**真正区分环境靠的是部署目标绑到哪个 environment**。
2. **环境管理**确认环境存在（dev/test/prod 是全局的，通常已建好）。
   - ⚠️ **不要给每台服务器各建一个环境**。后果：版本链割裂（`old_version` 按「项目+环境」推断，两套链路互不可见）、防重失效（两个环境可同时发）、历史记录碎片化。
   - ⚠️ 「默认服务器」可以留空，设了也没用。
3. **部署目标**绑定：`项目 → 环境 → 服务器`，逐台添加。
4. 设**主目标**（1 个）与**发布顺序**。
5. 确认环境的**默认策略**：只发一台用 `SINGLE_TARGET`；多台用 `ROLLING` 并设 `batch_size`。

### 5.2 新增一台机器

1. 服务器管理建档案 → 连通性测试。
2. 部署目标新增绑定，**先设为停用**。
3. 确认配置无误后启用绑定 → 下次发布覆盖到它。
4. 首次发布建议：策略临时用 `SINGLE_TARGET` 且临时把主目标切到新机器，发完再切回——避免一上来就全量。

### 5.3 摘除一台机器（临时/永久）

- ✅ **正确：停用绑定**（部署目标 → 状态改停用）。保留绑定关系与差异化配置，随时可恢复。
- ❌ 停用服务器（`server.status=0`）：会影响**所有项目**对该机器的引用，且被选中时是**发布失败**而不是跳过。
- ❌ 删除绑定：丢失差异化配置，历史记录里的 `server_id` 仍指向它，追溯会断。

### 5.4 换机器 IP / 换机器

先摘除（停用绑定）→ 改档案或新建档案 → 重新绑定 → 启用。

⚠️ 一个追溯上的坑：`deployment_target` **只存 `server_id`，不存 host 快照**。改了服务器档案的 IP 后，历史部署记录里显示的 IP 会跟着变成新的——「这次发布到底发到了哪个 IP」在事后无法从平台确认。所以**换 IP 前先摘除**，让历史记录停在一个确定的状态。

### 5.5 发布前三查

| # | 检查项 | 怎么看 | 不通过的表现 |
|---|---|---|---|
| 1 | 环境下拉显示的「N 台」是不是我预期的台数 | 新建部署 → 选环境下拉，选项形如「生产环境（2 台）」 | 台数为 0 时该环境根本不出现在下拉里 |
| 2 | 策略是不是 `SINGLE_TARGET` | 新建部署表单的策略项，默认取环境配置 | 绑 5 台只发 1 台，且无人提示 |
| 3 | 目标集是不是我要的那几台 | 跑 §6 的预演 SQL | 多发/漏发 |

### 5.6 发布后核对

任务日志里这三行必须对得上：

```
#2 INFO[准备]开始执行部署 xxx，策略 ROLLING，目标数 2        ← 目标数
#3 INFO[分发]开始第 1/2 批，含 1 个目标                      ← 分批
#4 INFO[分发]开始在 阿里云轻量服务器(47.103.12.12) 上发布 …  ← 机器名 + IP
```

**`目标数` 与 `第 x/y 批` 是第一道防线**——它们在执行开始前就打出来了，看到数字不对立刻取消（`QUEUED`/`DEPLOYING` 可取消），比发完再回滚便宜得多。

## 6. 核对用 SQL

```sql
-- ① 预演：某项目某环境下，发布候选全集（按实际执行顺序）
SELECT t.deploy_order, t.is_primary, t.status AS bind_status,
       s.server_name, s.host, s.ssh_port, s.status AS server_status
FROM project_environment_target t
JOIN `server` s ON s.id = t.server_id
WHERE t.project_id = '<项目ID>'
  AND t.environment_id = '<环境ID>'
  AND t.is_deleted = 0
  AND t.status = 1
ORDER BY t.deploy_order, t.create_time;
```

- 策略 `SINGLE_TARGET` → 实际只发 `is_primary=1` 那行；没有主目标就发 `deploy_order` 最小的那行。
- 策略 `ALL_AT_ONCE` / `ROLLING` → 全部行，按 `deploy_order` 顺序。

```sql
-- ② 存量库清理 default_server_id（可选，不执行也不影响运行）
--    先查有没有值，确认无人依赖后再 DROP：
SELECT COUNT(*) FROM environment WHERE is_deleted = 0 AND default_server_id IS NOT NULL;

--    确认后手工执行（平台部署链路无 DDL 能力，必须手工）：
--    ALTER TABLE environment DROP COLUMN default_server_id;
```

```sql
-- ③ 找出「机器被绑到了与它 env_tag 不符的环境」：平台不校验，靠人工
SELECT p.code AS project_code, e.code AS env_code,
       s.server_name, s.host, s.env_tag
FROM project_environment_target t
JOIN project p     ON p.id = t.project_id
JOIN environment e ON e.id = t.environment_id
JOIN `server` s    ON s.id = t.server_id
WHERE t.is_deleted = 0 AND t.status = 1
  AND ((e.code LIKE '%prod%' AND s.env_tag <> 3)
    OR (e.code LIKE '%dev%'  AND s.env_tag <> 1));
```

```sql
-- ④ 服务器已停用但绑定仍启用：会让发布直接失败而不是跳过
SELECT p.code, e.code, s.server_name, s.host
FROM project_environment_target t
JOIN project p     ON p.id = t.project_id
JOIN environment e ON e.id = t.environment_id
JOIN `server` s    ON s.id = t.server_id
WHERE t.is_deleted = 0 AND t.status = 1 AND s.status = 0;
```

## 7. 相关：`old_version` 推断方向取反（2026-09-28 修复）

**现象**：每次发布后点回滚都提示「本次发布为首次发布，目标机上没有平台纳管的历史版本，无法回滚」，但目标机上明明有备份。

**自证线索**：备份名形如 `aiops_bak_20260928030145`，**缺版本段**。版本段取自 `ctx.currentVersion()` = `deployment_target.old_version`，缺即说明 `old_version` 为空。

**根因**：推断「这台机器现在跑什么版本」的两处代码调错了方向——

```java
targetVersionOf  = rollingBack ? old_version : new_version   // 动作结束后机器在跑的 ← 正确
currentVersionOf = rollingBack ? new_version : old_version   // 本次被换掉的（备份命名用）← 用错了
```

首次发布那次 `old_version` 本就为空 → 取反后推断到的仍是它 → 之后**永远为空** → 永远判「首次发布」，备份名也永远不带版本段（回滚快路径按 `*_bak_*_{版本}` 同样永远命中不了）。

**修复**：`DeploymentTargetPlanner.resolveCurrentVersions` 与 `DeploymentVoAssembler.resolveCurrentVersion` 改回 `targetVersionOf`；`DeployContext` 两个取法补互指警示。硬约束见 AGENTS.md §24.5。

⚠️ **修复不回填历史数据**：存量的 `deployment_target.old_version` 仍是空值，需要**新建一次部署**才会带上正确值；且推断只扫最近 10 条 `status in (2 成功, 6 已回滚)` 的部署，若该环境近期全是失败记录，修完仍推断不出。

**「平台纳管」的定义**：= 这台机器在这条项目环境下有过 `status=2/6` 的部署目标行。**与磁盘上有没有 jar、备份、VERSION 文件完全无关**——手工跑 `jar-init.py` 初始化目录、手工传包上线，平台都不会因此认为它纳管了。
