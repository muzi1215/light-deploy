# 发布模块

> 模块包名：`com.lx.deploy.deployment`（执行器另含 `com.lx.deploy.deployment.executor`）
> 对应数据表：`deployment`、`deployment_target`（消费 `release_record`、`project_environment_target`、`project`、`environment`、`server`）
> 当前状态：已完成并编译通过（后端 + 前端 typecheck 通过），端到端真机验证待进行

## 1. 模块定位

发布模块回答平台的最后一公里问题：**把某个已经构建好的版本，发到某个环境绑定的机器上，并在出问题时退回去。**

它在整条链路中的位置：

```text
构建模块（代码 → 可发布版本 release_record）
        │
        ▼
发布模块（版本 + 项目拓扑 → 目标机器上的运行实例）
        │
        ▼
AIops（发布期间告警静默、风险建议，v1 仅占位）
```

与构建模块的分工边界很清晰：构建产出「可发布的东西」，发布负责「把它变成正在跑的服务」。因此本模块不关心代码怎么编译，只消费 `release_record`（镜像标签或产物路径 + 构建机）与项目环境拓扑（`project_environment_target`）。

三条运行时链路全部真实可用：

| 运行时 | 发布动作 | 分发方式 |
| --- | --- | --- |
| DOCKER | `docker pull` + `docker rm -f` + `docker run -d` | 目标机直接从镜像仓库拉取 |
| JAR | 固定工作目录原地替换：备份旧 jar → 投放新 jar → `systemctl restart`；systemd 单元仅在首次部署生成 | 构建机 → 平台 → 目标机中转 |
| STATIC | SFTP 上传归档 + 解压到 Nginx 根目录 + `nginx -s reload` | 构建机 → 平台 → 目标机中转 |

## 2. 数据表结构

### 2.1 deployment（部署主任务）

| 列 | 说明 |
| --- | --- |
| project_id / environment_id | 发什么项目、发到哪个环境，创建时校验存在性（项目须启用） |
| release_id | 本次发布的版本，必须为「可发布」状态，且属于该项目 |
| strategy | 部署策略快照，取自环境默认或请求覆盖 |
| status | 0 排队 / 1 发布中 / 2 成功 / 3 失败 / 4 已取消 / 5 回滚中 / 6 已回滚 |
| operator_id / operator_name | 操作者留痕，接入权限中心后由认证信息填充 |
| aiops_silence_id | AIops 静默窗口 ID，v1 仅占位 |
| started_at / finished_at / error_message | 由状态流转维护，不允许普通更新接口修改 |

### 2.2 deployment_target（部署目标任务）

| 列 | 说明 |
| --- | --- |
| deployment_id / server_id | 所属部署与目标服务器 |
| status | 0 排队 / 1 发布中 / 2 成功 / 3 失败 / 4 已取消 / 5 已跳过 |
| old_version / new_version | 发布前后版本，old_version 是回滚依据 |
| image_tag | DOCKER 运行时本次实际部署的镜像 |
| health_status | 0 未检查 / 1 健康 / 2 不健康，允许为 NULL |
| error_message / started_at / finished_at | 目标级失败原因与时间 |

**为什么目标要快照而不是实时关联拓扑**：部署记录必须忠实反映「当时发了哪些机器」。如果实时关联 `project_environment_target`，后续改一次拓扑，历史部署的目标列表就变了，回滚会发到错误的机器上。

### 2.3 本轮新增列：release_record.build_server_id

JAR / STATIC 没有镜像仓库，产物文件只存在于构建机的某个绝对路径上。`release_record` 与 `build` 之间没有外键（设计上刻意松耦合），发布链路无法反查构建机，因此把构建机 ID 冗余到发布版本上。

- 升级脚本（幂等）：`src/main/resources/db/upgrade-release-build-server.sql`
- 只读校验脚本：`src/main/resources/db/verify-release-build-server.sql`
- 历史版本该列为空，发布时会给出「未记录构建机，请重新构建」的明确提示，而不是静默失败。

## 3. 枚举设计

本模块不新增枚举，状态全部沿用 AGENTS.md §4.5 的数字编码常量（禁止用枚举表达状态）：

| 常量类 | 取值 |
| --- | --- |
| `DeploymentStatus` | 0 排队 / 1 发布中 / 2 成功 / 3 失败 / 4 已取消 / 5 回滚中 / 6 已回滚 |
| `DeploymentTargetStatus` | 0 排队 / 1 发布中 / 2 成功 / 3 失败 / 4 已取消 / 5 已跳过 |
| `HealthStatus` | 0 未检查 / 1 健康 / 2 不健康 |

沿用既有枚举表达「分类」：

- `DeployStrategy`（SINGLE_TARGET / ALL_AT_ONCE / ROLLING）：环境默认策略，请求可覆盖；
- `RuntimeType`（DOCKER / JAR / STATIC）：决定发布动作分支。

前端映射集中在 `lighit-deploy-ui/src/constants/deploymentStatus.ts`，状态字段全部 `number`，与后端编码一一对应。

## 6. 核心业务规则与代码逻辑

### 6.1 创建即快照：目标列表与 old_version

`createAndTrigger` 一次做完四件事：校验、选目标、推断旧版本、落快照。

```java
// 策略：请求覆盖优先，否则取环境默认，都没配退化为单目标
String strategy = resolveStrategy(dto.getStrategy(), environment);

// 单目标只发一台：优先主目标，没有主目标时取发布顺序最靠前的一台
List<ProjectEnvironmentTarget> selected = selectByStrategy(bindings, strategy);

// 推断每台机器当前生效的版本，作为回滚依据
Map<String, String> currentVersions = resolveCurrentVersions(project.getId(), environment.getId());
```

`resolveCurrentVersions` 是回滚能否成立的关键。它回溯该项目环境最近 10 次历史部署，按时间从新到旧遍历，**成功的部署取 new_version、已回滚的部署取 old_version**（回滚之后机器跑的就是旧版本），每台机器只取第一次命中的结果。首次发布时为空，表示这台机器此前没有平台纳管的版本。

版本号（`old_version` / `new_version`）在发布侧一律当作**不透明字符串**处理：只做存储、展示与相等判断，不解析格式。因此构建侧把版本号升级为 `{项目编码}-v{序号}-{提交短码}`（见 [构建模块.md](构建模块.md) §6.6）不影响发布与回滚链路，历史部署记录里的旧格式版本号也无需迁移。

`createAndTrigger` 与 `rollback` 都带 `@Transactional(rollbackFor = Exception.class)`：`deployment`、`deployment_target` 与 DEPLOY 任务是一次发布的三个组成部分，必须同生共死。

> 这条约束来自一次真实事故：早期没有事务，`deployment_target` 表尚未建好时目标快照插入失败，主记录却已经落库，留下一条**永远不会有关联任务**的孤儿部署；更麻烦的是它的排队中状态会命中「该项目环境下已有进行中的部署」防重判断，把后续所有发布都挡在门外，只能人工取消才能恢复。

**目标从哪来：三层拓扑，不是「环境 = 机器」。** 模型是 **项目 → 环境 → 部署目标**：`project_environment_target` 是 `项目 × 环境 × 服务器`（唯一键 `uk_project_env_server`），**环境是全局逻辑环境（dev/test/prod），不是项目私有、也不代表机器**。要让多台机器一起发同一个版本，必须在**同一个环境**下绑多条部署目标，策略选全量或滚动；给每台机器各建一个环境，则新建部署只能选一个环境、一次只覆盖一台。

分成两个环境的代价：① 版本链割裂（`resolveCurrentVersions` 按「项目 + 环境」推断，两套链路互不可见）；② 防重失效（`inProgress` 同样按项目 + 环境判定，两个环境可同时发）；③ 历史记录碎片化。

**新建部署表单没有目标勾选**：只有 `projectId / environmentId / releaseId / strategy` 四个字段，目标集完全由「环境下的启用绑定 + 策略」决定。只发一台只能靠 ① 策略覆盖为 `SINGLE_TARGET`（发主目标那台）；② 在部署目标页停用另一台（影响后续所有部署）。

**新机器不需要预先有任何产物。** 产物链路是「平台 SFTP 从**构建机**下载到平台本地临时文件 → 再上传到**目标机**」；首次部署时 `ensureInitialized` 会 `mkdir -p {工作目录}/exec` → 投放三份 py 脚本 → 探测工作目录里有没有 jar → 没有就跑 `jar-init.py` 建目录并注册 systemd unit。真实失败点按顺序是：服务器档案没填部署根目录 → 该目录在机器上不存在或不可写（**平台不自动创建**）→ 目标机无 python3 → 目标机无 java（兜底 `/usr/bin/java`，unit 建了但服务起不来，这种最坑）→ 构建机上该版本产物不在 → `release.build_server_id` 为空。

### 6.2 批次编排：策略差异体现在「失败后要不要停」

```java
if (failedInBatch > 0 && isRolling(deployment.getStrategy())) {
    aborted = true;
    skipRemaining(task, batches, batchIndex + 1);
}
```

- **SINGLE_TARGET**：只发主目标（或顺序最靠前的一台），一批；
- **ALL_AT_ONCE**：全部目标一批，不因单个失败中止——全量的语义是「整体替换」，中途停下会让集群处于更混乱的半新半旧状态；
- **ROLLING**：按 `environment.batch_size` 切批，任一批失败即中止，剩余目标置为 **已跳过（5）**。

「已跳过」不是「失败」：它表示这台机器本次没动过。回滚时据此排除（`DeploymentTargetStatus.isUntouched`），不会把从未更新过的机器回退到旧版本。

### 6.3 三条运行时链路

**DOCKER**：`docker pull` → `docker rm -f`（容器名是发布幂等的关键）→ `docker run -d --restart=always`。启动后立刻 `docker inspect` 确认容器仍处于运行态，避免把「启动即退出」报成成功。

**JAR**：固定工作目录 + 原地替换（对齐 `jar_linux.py` 的存量约定，也贴合「jar 与 application.yml 分离部署」的真实仓库形态）。

首次部署时，平台把内置的 `jar-init.py` / `jar-update.py` / `jar-fallback.py` 上传到目标机工作目录的 `exec/` 下并执行初始化：建立 `logs` / `exec` / `exec/bak` / `config` 四级目录，写入 systemd 单元（`--spring.config.location` 显式指向 config 目录），并把三个脚本留在机器上供运维手工应急。

三个脚本**每次发布都会重新投放**（与是否首次无关）：脚本是平台资产，版本必须随平台走。只在首次投放会让目标机长期停留在一份旧脚本上，而运维应急发版/回滚恰恰依赖这几份脚本。初始化日志同时会回显目标机的 `python3 --version`，脚本本身也会拒绝低于 3.5 的解释器并给出明确提示。

> **脚本必须兼容 Python 3.5+**：目标机的 `python3` 常见是 3.6（CentOS 7 一类），脚本里禁止使用 3.7 才有的参数（`subprocess` 的 `capture_output` / `text`）。真实事故：`run()` 用了 `capture_output=True, text=True`，在老机器上抛 `__init__() got an unexpected keyword argument 'capture_output'`，初始化在最后一步 `systemctl daemon-reload` 前中断，整台目标被判失败。

之后每次发布按固定时序走：**备份旧 jar 到 `exec/bak`（备份名内嵌被替换包的版本号）→ 投放新 jar（先传 `.uploading` 再 `mv -f` 覆盖）→ 复核 SHA256 → 写 `VERSION` → 刷新 `exec/deploy.conf` 的 `version=` 行 → `systemctl restart` → `is-active` 确认**。

时序不是随意的，两点必须记住：**校验放在重启之前**（jar 已上盘、服务尚未重启，此刻发现损坏可以无损还原）；**版本标识放在重启之前**（磁盘上已是新 jar，标识必须与磁盘一致，写在重启之后会在重启失败时停在旧版本、与磁盘错位）。**systemd 单元只在首次生成、不再随版本重写**，运维手工调整过的启动参数不会被平台覆盖。

```text
/lx/jarapps/auth-tool-7888
├── auth-tool.jar                       # 每次发版原地替换，目录不变
├── VERSION                             # 本机当前版本标识（key=value，含 version= 行）
├── config/application.yml              # 配置与 jar 分离，平台不覆盖已存在的配置
├── logs/                               # 应用日志（journal_app.log / journal_error.log）
└── exec/
    ├── deploy.conf                     # 服务名 / jar 名 / 工作目录 / 当前版本，供下面两个脚本读取
    ├── VERSION                         # 待投放版本的标识：手工更新时随 jar 一起放进来，用完即删
    ├── jar-init.py                     # 初始化脚本（平台上传，可手工重跑）
    ├── jar-update.py                   # 手工应急更新：把新 jar 放进本目录后执行
    ├── jar-fallback.py                 # 手工应急回滚：从 bak 中选一个历史包恢复
    └── bak/
        └── auth-tool_bak_20260925222851_auth-7888-v6-c9bb25d3.jar
```

备份命名为 `{jar名}_bak_{时间戳}_{版本号}.jar`，例如 `auth-tool_bak_20260925222851_auth-7888-v6-c9bb25d3.jar`。名称以「`{jar名}_bak_` + 14 位时间戳」打头，因此**字典序即时间序**；末尾保留 `.jar`，与机器上手工执行 `jar-update.py` 产生的备份混在同一目录里，应急时手工跑 `fallback.py` 也能回滚平台发过的版本。

**版本号必须内嵌在备份文件名里**：备份名里的时间戳是「执行替换的时刻」，指向的是**替换者**而不是包里的版本——`auth-tool_bak_20260925203000v1.jar` 装的是「20:30 那次发布换下去的那个包」。只留时间戳的话，事后 `ls` 一眼看不出某个备份属于哪个平台版本，只能靠 SHA256 反查或时间线推断。版本段取自目标机的 `VERSION`（**磁盘事实，不取平台库快照**——库快照在手工换包后会失真）；取不到时省略该段、退化为 `{jar名}_bak_{时间戳}.jar`，**不猜**。**不采用「另存一个 `{备份名}.version` 伴随文件」的做法**：信息虽等价，但 `ls` 看不见、要多养一个文件，而且 `.version` 挂在 `.jar` 后面看起来像包的后缀，容易被误读。**版本段逐字保留平台版本号，不把其中的连字符换成下划线**：文件名里的 `auth-7888-v7-1521739f` 必须与 `release_record.version`、Docker 镜像 tag、`VERSION` 文件字面一致，才能直接复制去查库、搜日志、比对镜像。若为「统一下划线」把 `-` 换成 `_`，读回时就得按段回译，而项目编码本身允许含 `_`，回译不再双射——拿一个隐式约定换一点视觉整齐，不划算。文件名里 `-` 与 `_` 混用**是有意为之**：`_` 分隔备份名的结构段，`-` 属于版本号本身。写入文件名前版本段会清洗为 `[A-Za-z0-9._-]`，防止被改脏的 `VERSION` 带出 `/` 把备份写到别的目录。

**版本标识一律用外部文件，不重写 jar 的 `MANIFEST.MF`**：Spring Boot fat jar 的嵌套 jar 依赖 ZIP 的 STORED 布局，用 `jar --update` 重打包一旦改变压缩方式会静默产出「启动即失败」的产物，且会改变 SHA256，与登记的摘要语义冲突。两处 `VERSION` 文件加备份名版本段的读入口径与完整约束见 AGENTS §24.7；手工回退时的版本识别顺序（SHA256 比对 > 备份名版本段 > 时间戳反查）同样见该节。

**手工识别备份版本**（完整操作见 `docs/疑问与解答.md` Q-11）：

```bash
cd {workdir}
ls -1 exec/bak                      # 名字里直接带版本号，一眼可读
sha256sum {jar名} exec/bak/*.jar    # 需要严肃确认时再算摘要
```

改造前产生的备份名里没有版本段，此时才需要拿摘要去构建机 `sha256sum {build_artifact_dir}/{项目编码}/*/{jar名}`（**产物目录名就是版本号**）或平台 `release_record.sha256` 对照。三点必须记住：**`cp -p` 会保留源 jar 的 `mtime`**，`ls -l` 显示的是「包当初被发布的时刻」而非备份时刻，判断最新备份要看**文件名时间戳**（`fallback.py --steps` 也按文件名时间戳排序，不按 `mtime`）；**版本段有一次发布的预热期**——工作目录里还没有 `VERSION` 时本次备份得不到版本段，属预期；**改造前的历史备份永远没有版本段**，只能走 SHA256 或时间戳反查。

回滚与发布走完全相同的路径，只是投放的是 `old_version` 的 jar（同样原地替换，目录不变）。`work_dir` 未配置时回落到「目标机部署根目录 `/apps` / 项目编码」。

> DOCKER 链路不受本方案影响：仍按 `dockerfile_path` 构建镜像、`docker pull + run` 发布，
> 不使用工作目录与上述三个脚本；`config_paths` 也只在 JAR / STATIC 的脚本构建分支消费。

**STATIC**：目录型产物（前端 dist）先在构建机上 `tar -czf` 打成单文件（SFTP 只传文件，避免逐文件握手开销），目标机解压到 Nginx 根目录后 `nginx -t && nginx -s reload`；目标机没有 nginx 时只告警不失败。

分发统一走「构建机 → 平台 → 目标机」中转，而不是服务器间直传：目标机不需要持有构建机的免密通道，凭据与网络策略都收敛在平台侧。

### 6.4 健康检查：不健康就是失败

```java
if (healthConfig != null) {
    HealthChecker.HealthCheckResult result = healthChecker.check(healthConfig, server.getHost());
    healthStatus = result.healthy() ? HealthStatus.HEALTHY : HealthStatus.UNHEALTHY;
    if (!result.healthy()) {
        throw new DeployException(ResponseCode.REMOTE_EXECUTION_ERROR, "健康检查不通过（" + result.detail() + "）");
    }
}
```

探测在**平台侧**发起（`HttpClient` / `Socket`），不在目标机上 `curl`：探测逻辑与超时控制完全由平台掌握，不依赖目标机装了什么；代价是平台需要能访问目标机的业务端口。HTTP 把 2xx 视为健康，TCP 只验证端口可连通；默认 3 次探测、间隔 3 秒，用于容忍应用启动慢。

发布动作成功但健康检查不通过时，目标**判为失败**：服务起不来的发布对用户而言就是失败，只是失败原因不同，因此统一收敛为失败、由 `health_status` 区分细节。

### 6.5 回滚：复用同一批目标，靠主任务状态切换方向

**入口先判定能不能回滚。**「状态成功」只是必要条件而不是充分条件——还要有历史版本、且历史版本的记录与产物仍在。判定收在 `DeploymentService.evaluateRollback` 一处，按优先级给出唯一原因：

| 档位 | 条件 | 原因文案 |
|---|---|---|
| ① | 状态不是「成功」 | 当前状态为 X，只有发布成功的部署允许回滚 |
| ② | 变更过的目标全都没有 `old_version` | 本次发布为首次发布，目标机上没有平台纳管的历史版本，无法回滚 |
| ③ | 有 `old_version` 但版本记录查不到，或该版本缺分发所需信息（DOCKER 缺 `image_tag`；JAR/STATIC 缺 `build_server_id` / `artifact_path`） | 历史版本 X 的发布记录或构建产物已不存在，无法回滚 |

判定结果同时用于两处，保证「按钮能不能点」与「接口会不会拒」永远一致：`rollback()` 不可回滚时**抛 `DeployException`**，`toVo` 把同一结论填进 `rollbackable` / `rollbackBlockReason` 供前端置灰与提示。

**不可回滚时禁止静默成功。**早先的做法是「一个目标都回滚不了时直接把状态置为已回滚」：

```java
// 旧实现（已删除）：rollbackCount == 0 时直接收敛为已回滚
deployment.setStatus(DeploymentStatus.ROLLED_BACK);
updateById(deployment);
return toVo(deployment);
```

使用者看到「已回滚」，机器上却一个字节都没变，页面上也找不到任何说明。现在改为直接拒绝，把原因返回给页面。

```java
// 判定只做一次：inspectTargets 产出逐目标明细，rollback 与回滚预览消费同一份
RollbackEvaluation evaluation = evaluateRollback(deployment, targets);
if (!evaluation.rollbackable()) {
    throw new DeployException(ResponseCode.DATA_CONFLICT, evaluation.blockReason());
}
for (RollbackDecision decision : evaluation.decisions()) {
    DeploymentTarget target = decision.target();
    if (!decision.rollbackable()) {
        // 首次发布 / 历史版本产物已不存在，记为跳过而不是失败
        skipForRollback(target, decision.skipReason());
        continue;
    }
    target.setStatus(DeploymentTargetStatus.QUEUED);
    // ...重置健康检查与起止时间，随后生成 DEPLOY 任务，执行器按 ROLLING_BACK 改发 old_version
}
```

**允许部分回滚**：有过变更且有历史版本的机器正常退回去，其余标记为「已跳过」并写明原因、保持原版本不动——不判失败，也不把从未更新过的机器回退。

**提交前先预览**：`GET /deployment/rollback-preview/{id}` 是只读接口，返回总结论与逐目标明细（服务器名/地址、`当前版本 → 将回滚到的版本`、是否可回滚、跳过原因），前端在回滚确认弹窗里逐台展示。关键是**与提交共用同一份判定**——逐目标明细由 `inspectTargets` 产出一次，`rollback()` 的目标重置与预览清单都消费它，因此不存在「预览说能退、提交说退不了」。列表侧另有 `rollbackTargetCount` / `rollbackSkippedCount`（判定时已算出、零额外查询），供按钮 tooltip 直接给出台数。

**版本字段的展示口径：`version` 是快照，「当前版本」另算**

`deployment.version`（经 `release_id` 关联 `release_record.version`）回答的是「这次动作针对哪个发布版本」，属于**记录创建时的快照，回滚后也不改写**——改了就与发布日志、产物路径、`release_record` 全部对不上。而「机器上现在跑的是哪个版本」是另一个事实，由 `DeploymentVo.currentVersion` 单独承载：`DeploymentService.resolveCurrentVersion` 在 `toVo` 里复用**已加载的目标列表**算出（零额外查询），发布成功取各目标的 `new_version`、已回滚取 `old_version`（回滚就是把机器退回老版本），**只有全部成功目标一致时才返回值**，多目标不一致（部分回滚、部分首次发布）时返回 null，页面不显示。

页面据此分两层展示：

- **部署列表版本列**：已回滚时在版本号下方补一行「当前 xxx」，tooltip 写明「本次发布版本 X；机器当前实际运行 Y」；其他状态不补——要么 `version` 就是当前版本，要么还没有确定结论；
- **目标明细的版本对照**：统一写成「当前 → 目标」，两种场景都自解释、方向永远与事实一致。发布是 `old_version → new_version`，回滚是 `new_version → old_version`（**回滚执行的恰恰是把 `new_version` 换回 `old_version`**）。直接按字段顺序拼 `oldVersion → newVersion` 会让回滚那行箭头反向，而字段名本身不含角色信息，看的人只能猜「哪个是现在的」；
- 回滚预览接口里 `currentVersion` / `targetVersion` 的取法与此同源，**三处口径必须一致**（详见 AGENTS.md §24.5）。

**关于目标机 `exec/bak`（重要澄清）**：平台回滚走的是「重新发布 `old_version`」，依赖**版本记录 + 构建机上的产物**（`resolveVersionRelease` → `downloadArtifact`），**不读** `exec/bak` 里的备份包。原因是备份包属于目标机本地、改造前产生的备份名里更没有版本信息（旧格式 `{jar名}_bak_{时间戳}v{序号}.jar`，末尾 `v{序号}` 是防撞名序号而不是版本号），不足以作为回滚依据；`exec/bak` 的定位是运维断网/平台不可用时手工应急（`jar-fallback.py`）。所以「能不能回滚」的判据是历史版本产物是否还在，而不是目标机上有没有备份包。

发布与回滚共用同一个 `DeployTaskHandler`，靠 `deployment.status == ROLLING_BACK` 区分「这次该发 new_version 还是 old_version」。回滚时按 `old_version` 反查对应版本的 `release_record`，拿到该版本的镜像标签或产物路径——否则无从知道「旧版本到底是什么」。

**回滚日志必须能独立交代这次回滚做了什么**，六个要素缺一不可（详见 AGENTS.md §24.5）：

```text
[准备] 开始回滚部署 <id>，开始时间 2026-09-25 17:53:00
[准备] 回滚策略 ROLLING，本次回滚 2/3 个目标，另有 1 个目标无历史版本或本次未变更，保持原版本不变
[分发] 回滚目标 阿里云轻量服务器(1.2.3.4)：当前版本 auth-tool-abc123 → 回滚到 auth-tool-9f8e7d，开始时间 2026-09-25 17:53:04
[启动] 重启 systemd 服务 auth-tool
[启动] 服务 auth-tool 启动成功（systemctl is-active = active）
[收尾] 目标 阿里云轻量服务器 回滚成功，服务启动正常（当前版本 auth-tool-9f8e7d）
[收尾] 回滚成功：已成功回滚 2 个目标到历史版本，服务启动正常；另有 1 个目标保持原版本不变，完成时间 2026-09-25 17:53:19
```

| 要素 | 落点 |
|---|---|
| 开始回滚 + 开始时间 | 开场日志（`STAGE_PREPARE`） |
| 当前版本 / 回滚到什么版本 | 目标级「当前版本 X → 回滚到 Y」，X 取 `new_version`、Y 取 `old_version` |
| 时间 | 目标级起始时间 + 收尾完成时间，格式 `yyyy-MM-dd HH:mm:ss`，**写进正文** |
| 回滚成功 / 失败 | 收尾单独一条结论（成功走 INFO，失败走 ERROR 并提示人工确认当前版本） |
| 是否启动成功 | `restartService` 通过后写「服务 X 启动成功（systemctl is-active = active）」，成功也留痕 |

失败时收尾写「回滚失败：…完成时间…请人工确认目标机当前版本」，并继续按 §6.1 的口径让部署记录与 DEPLOY 任务**同时失败**。**禁止**只靠目标行零散的 INFO 加上执行器结尾那句「任务执行成功」充当回滚结论——那句话不区分发布与回滚。

回滚中不允许取消：中途取消会让目标停留在新旧版本混合状态。

### 6.6 状态流转由 Service 收口

执行器只回调、不直接写业务状态（与 `BuildTaskHandler → BuildService` 的分工一致）：

```java
deploymentService.markDeploying(deploymentId);      // 排队→发布中（回滚中保持回滚中）
deploymentService.markTargetRunning(targetId);
deploymentService.markTargetSuccess(targetId, healthStatus);
deploymentService.markTargetFailed(targetId, reason, healthStatus);
deploymentService.skipTarget(targetId, reason);
deploymentService.markSuccess / markFailed / markRolledBack / markRollbackFailed(...);
```

单个目标的异常在执行器内被捕获并落为「目标失败」，不会冒泡中断其余目标——**「哪台机器失败、为什么失败」始终有记录**，而是否中止后续批次交给策略决定。

但「每台机器的失败不冒泡」不等于「整次部署不算失败」：所有批次跑完后按汇总结果收敛，**只要存在失败目标，部署记录与 DEPLOY 任务同时置为失败**，任务失败原因取第一条失败目标的原因：

```java
String failureSummary = failed > 0 ? buildFailureSummary(deploymentId, failed, total) : null;
finishDeployment(deploymentId, rollingBack, failureSummary);   // markFailed / markRollbackFailed
if (failureSummary != null) {
    throw new DeployException(ResponseCode.REMOTE_EXECUTION_ERROR, failureSummary);
}
```

早先这里只收敛了部署状态、处理器仍正常返回，于是任务管理里显示「成功」，任务日志最后一行是「任务执行成功」，中间却夹着目标级的 ERROR——自相矛盾。任务状态是运维盯发布结果的第一入口，不能与部署记录给出两个结论。失败原因形如「共 1 个目标，其中 1 个失败：阿里云轻量服务器 → 工作目录初始化失败：…」，只有一行，完整清单仍以目标明细为准。

### 6.7 本轮顺带修复的构建侧缺陷

`BuildTaskHandler` 在构建结束后会 `rm -rf` 工作区，而 `release_record.artifact_path` 原本指向工作区内的产物路径——发布阶段下载到的会是一个已被删除的路径。修复方式是在清理工作区之前把产物转存到持久目录（构建机档案的 `build_artifact_dir`，服务器页面按机器配置，默认 `/opt/light-deploy/artifacts`）：

```java
String persistDir = artifactBase + "/" + project.getCode() + "/" + version;
session.exec("mkdir -p " + persistDir + " && cp -r " + actualFile + " " + persistDir + "/");
// 登记 persistedPath 而不是工作区路径
artifact.setMetadataJson("{\"path\":\"" + persistedPath + "\"}");
```

### 6.8 为什么没有「重新发布」：部署记录是执行快照，不是可重跑的作业

部署记录行的操作只有「目标明细 / 发布日志 / 回滚 / 取消 / 删除」，**没有「重新发布」**。这不是遗漏，而是数据模型把 `deployment` 定义成**一次执行的不可变快照**的必然结果（见 §6.1 与类注释）：

> 关键设计：目标列表在创建时快照。发布记录必须忠实反映「当时发了哪些机器」，后续修改项目拓扑不能追溯性地改变已有部署记录，否则回滚会发到错误的机器上。

在原记录上重跑会同时撞上三处：

| 冲突 | 说明 |
| --- | --- |
| **首次执行结果被覆盖** | 重跑要把目标行重置为排队并清空 `health_status` / `started_at` / `finished_at`；`targetTotal` / `targetSuccess` / `targetFailed`、主状态与起止时间都会被第二次执行覆写，第一次执行的结论永久丢失 |
| **回滚语义失效** | `old_version` 与 `new_version` 变成同一个值。`createAndTrigger` 正是靠这两个字段做「发布前版本 → 本次版本」的对照，相等之后目标行再也说不清「从哪来、到哪去」，`historyArtifactAvailable` 的可用性判定会指向自己 |
| **当前版本推断自指** | `resolveCurrentVersions` 靠扫描该项目历史部署（`OLD_VERSION_SCAN_LIMIT = 10`）反推每台机器当前版本，其前提是「一条记录 = 一次真实且不重复的状态迁移」 |

回滚能在同一条记录上执行，是因为它被显式定义为**同一批目标的状态切换**（`ROLLING_BACK` → `ROLLED_BACK`），并非第二次独立执行——两者不可类比。

**这不是能力缺失。** 重发同版本等价于「拿同一个 `release_record` 再建一次部署」，而「新建部署」的项目 → 环境 → 版本三级联动已经支持选择任意历史版本：`deploy/index.vue` 取版本用 `listReleases({ projectId, status: 1 })`。

> **口径变更（保留策略接入后）**：早期这里写的是「代码中没有任何位置把版本置为已废弃，所以历史版本永远处于可发布」。**该表述已不成立**——`ReleaseRetentionService` 会在构建收尾时把超出保留数且不在保护窗口内的版本置为 `DEPRECATED`（见 [构建模块.md](构建模块.md) §6.7）。因此准确说法是：**处于「可发布」状态的版本都可以手选重发**，能否选到取决于它是否还在保留范围内。这同时避免了「下拉看得到、点了却发不了」。

**正确的「重新发布」形态（后续演进）**：以原记录为模板**复制出一条新部署**——新建 `deployment` + 复制目标快照 + 生成新 DEPLOY 任务，旧记录一字不动。这样历史结论不受污染，还能天然复用「同项目环境防重」带来的串行保障，以及 `historyArtifactAvailable` 的产物可用性判定。实施前需拍板两点：

1. 目标集取「当时的目标快照」还是「当前项目的启用绑定」——前者才是忠实复现，但机器换过之后点重发会发到已下线的机器，需在确认框里提示差异；
2. 该版本产物已不存在时的拒绝提示（直接复用 `historyArtifactAvailable` 的判定结论）。

### 6.9 版本下拉带构建机名 + 提交前产物存在性预检

**问题**：版本记录存在 ≠ 产物还在。换过构建机、产物被保留策略回收、历史版本压根没记构建机，都会让「下拉看得到、点了发不了」——而失败要等到任务跑到「下载产物」阶段才暴露，那时部署记录与目标快照都已落库，页面上看像一次失败的发布。

**第一处：下拉带出构建机名。** `ReleaseRecordVo` 增加 `buildServerName`，由 `ReleaseService.toVos` **批量回填**（按构建机 ID 去重后一次 `selectBatchIds`，避免把一次列表放大成 N 次查询）。页面显示 `auth-7888-v7-1521739f · 构建机 build-01`；构建机为空的历史版本标注「未记录构建机（多为历史版本）」，在点发布前就能看出它发不了。

版本号与构建机是选项里的两行内容，所以这个下拉（以及同样两行的「部署策略」下拉）必须用 `popper-class="strategy-option-popper"` 放开 Element Plus 选项 34px 的固定行高——不放开的表现为描述行被选项下边界裁掉、并与下一项标题挤在一起（规则见 AGENTS.md §20.2，排查过程见 [疑问与解答.md](疑问与解答.md) Q-23 第三层）。

**第二处：提交前预检。** 新增 `ArtifactProbe.requireExists`，在 `createAndTrigger` 中、版本状态校验之后调用：连到版本记录的构建机执行 `test -e <artifact_path>`，不存在直接抛 `VALIDATION_ERROR`，原因写明「可能已被保留策略回收或构建机已更换，请重新构建后再发布」。

两个口径固定：

- **只校验落盘产物**（JAR / STATIC）。Docker 版本的产物是镜像仓库里的 tag，目标机 `docker pull` 时才真正判定，平台侧探了也不代表目标机拉得到，因此不预检；
- **连不上构建机时不能放行**。放行等于把「未知」当成「存在」，任务照样会失败，只是更晚。

| 构建模块 | 消费构建成功生成的 `release_record`；本轮为其补充 `build_server_id` 与产物持久目录 |
| 项目模块 | 消费 `project`（运行时、运行/健康检查配置）与 `project_environment_target`（目标拓扑与差异化配置） |
| 服务器模块 | 目标服务器与构建机的连接配置来源，凭据解密由 `SshSessionFactory` 收口 |
| 任务模块 | 一条部署对应一条 DEPLOY 任务，`DeployTaskHandler` 通过 `TaskHandler` SPI 注册 |
| SSH 执行层 | 远程命令执行与 SFTP 传输（`SshSession.sftpDownload` / `sftpUpload` 为本轮新增） |
| AIops | `deployment.aiops_silence_id` 占位，v1 不发起真实调用 |
| 前端 | 「发布管理 → 部署记录」二级菜单；列表 + 新建对话框（项目/环境/版本联动）+ 目标抽屉 + 实时日志抽屉 |

## 8. 已知边界与后续演进

1. **全量发布在批次内串行执行**：`ALL_AT_ONCE` 的语义是「不做批次中止」，但批次内的目标仍按顺序发布。真正的并发发布需要解决日志顺序、并发状态写入与失败收敛，留待后续。
2. **健康检查在平台侧发起**：平台需要能访问目标机的业务端口。若部署环境存在网络隔离，后续可增加「在目标机上 curl」的探测方式。
3. **AIops 静默窗口未接通**：字段已预留，需要 `aiops_event` 表与幂等重试机制一起落地（静默必须带自动过期时间）。
4. **备份无回收策略**：JAR 每次发版都会往目标机 `exec/bak` 追加一个备份，长期发布只增不减，需要保留策略；
5. **产物持久目录无回收策略**：构建机上的产物持久目录（`build_artifact_dir`，默认 `/opt/light-deploy/artifacts`）会随构建次数增长，同样需要保留策略。
6. **操作者信息为空**：过渡期没有登录态，`operator_id` / `operator_name` 待接入统一权限中心后填充。
7. **端到端真机验证待进行**：三条运行时链路均按真实 SSH/SFTP 命令实现，但尚未在真机上跑通完整发布与回滚。
8. **无「一键重新发布」入口**：部署记录不可原地重跑（原因见 §6.8），重发同版本目前需在「新建部署」里手选历史版本。若要补「以某条记录为模板再发一次」，实现形态应为**复制出新部署记录**，而非在原记录上重跑。
