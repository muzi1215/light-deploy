# 架构与调用链路总入口（讲解文档）

> 模块包：`com.lx.deploy.*` ｜ 定位：全平台代码阅读与链路追踪的**总入口**
> 当前状态：已完成并编译通过

## 0. 一句话心智模型（最重要，先读这段）

整个平台**没有消息队列、没有 Spring 事件（`@EventListener` 全文 0 处）、没有 `@Async`**。
所有「构建 / 发布 / 回滚 / 连通性测试」这类长耗时任务，统一由**数据库轮询调度器**驱动：

```text
前端页面（点按钮）
   │  axios 请求
   ▼
Controller（收参 → 调用 Service → 只做一件事：插一条 status=0 的 lds_task 排队记录 + 业务主记录）
   │  立即返回 taskId / taskNo，连接断开，请求结束
   ▼  （此处链路"断开"——请求线程已经走完了）
后台 TaskExecutor（独立线程，每 1 秒轮询一次 lds_task）
   │  listQueued 抢到排队中的任务 → 原子 markRunning 抢占 → 提交到 worker 线程池
   ▼
Handler.execute(task)   ← 真正干活的代码，跑在 TaskExecutor 的 worker 线程里
   │  SSH 连构建机 / 目标机、执行命令、传文件、写 lds_task_log
   ▼
前端再用 GET /taskLog/pull 轮询拉日志，看到实时进度
```

**核心结论：你在 `DeployTaskHandler` 里找不到「被谁调用」，是因为它唯一的直接调用方是
`TaskExecutor.executeTask()` 的第 411 行（`handler.execute(task)`，详见 §1.2）。** Controller 永远不直接调用 Handler，Dao 也不调用。
请求路径与执行路径通过 `lds_task` 这张表解耦——这就是你"看代码看不懂"的根因，不是你的问题，是这套架构
刻意的"请求与执行分离"。

本平台所有模块文档都遵循同一套写法：**每个模块都有一节「调用链路（前端 → 后端 → 执行器）」，
精确到 前端api函数 → HTTP方法+URL → Controller.方法@行号 → Service.方法@行号 → 任务类型 → Handler.方法@行号 → 实际动作**。
看文档时先翻到那一节，就能从前端一路定位到具体代码行。

### 1.2 TaskExecutor 的 start() 到底被谁触发？——你卡住的根因（重点）

你原话："我根本就没看到 TaskExecutor 的方法被触发调用的代码，都没有定时任务什么的。"
这句话点中本平台最反直觉的地方：**确实没有任何 `@Scheduled`、没有任何一处显式调用 `taskExecutor.start()`**。下面把"它怎么启动、每秒怎么跑、怎么扇出到构建/部署"一次讲透。

#### 1.2.1 触发点：不是定时器，是 Spring 容器生命周期（SmartLifecycle）

`TaskExecutor` 的类签名：

```java
@Component
public class TaskExecutor implements SmartLifecycle { ... }
```

`SmartLifecycle` 是 Spring 的**生命周期接口**。Spring 在 **`ApplicationContext` 刷新完成（`finishRefresh`）之后**，由容器内部的 `DefaultLifecycleProcessor` 自动遍历所有 `SmartLifecycle` Bean，逐个调用 `start()`。

所以：

- **`TaskExecutor.start()` 的调用方是 Spring 容器本身**，不是任何 Controller / Service / 定时器；
- 你在业务代码里 grep `taskExecutor.start()` 搜不到——它从没被业务代码调用；
- 你搜 `@Scheduled` 也搜不到——本平台的轮询**不是**用 `@Scheduled` 注解实现的。

> 直觉等价：把"应用启动后自动跑一次 `start()`"交给容器生命周期托管。如果用 `@Scheduled(fixedDelay=1000)` 注解在方法上，那是 Spring 另一种调度写法；本项目**不用它**，是为了对手搓调度器做精细控制（线程命名、守护线程、异常隔离、与容器生命周期联动的优雅停机）。下面的 `poller` 就是手搓版的"每秒调度器"。

#### 1.2.2 轮询引擎：手搓的 `lds-task-poller` 守护线程（你看到的那段代码）

`start()` 内部（`:207`）创建调度器：

```java
poller = Executors.newSingleThreadScheduledExecutor(runnable -> {
    Thread thread = new Thread(runnable, "lds-task-poller");
    thread.setDaemon(true);     // 守护线程
    return thread;
});
```

接着（`:225`）注册周期任务：

```java
poller.scheduleWithFixedDelay(this::pollOnce, 0L, pollIntervalMs, TimeUnit.MILLISECONDS);
```

这就是"每 1 秒轮询一次 `lds_task`"的**真正来源**：

- `ScheduledExecutorService` 是 JDK 自带的调度线程池；`newSingleThreadScheduledExecutor` 取单线程版本；
- `scheduleWithFixedDelay(...)` = **上一轮 `pollOnce` 跑完之后，再等 `pollIntervalMs`（默认 1000ms）才开始下一轮**；`initialDelay=0` 表示应用一启动立刻跑第一轮；
- 线程名叫 `lds-task-poller`，`jstack` / `top -H` 一眼能认出这是任务轮询线程。

几个**为什么这样设计**（正是你"看不懂"那段代码的理由）：

| 设计点 | 代码 | 原因 |
| -- | -- | -- |
| 单线程调度 | `newSingleThreadScheduledExecutor` | 轮询串行，绝不出现"两轮 `pollOnce` 并发拉同一批任务"导致重复消费。真正干活的并发交给另一个 `workerPool`（大小 6） |
| 守护线程 | `thread.setDaemon(true)` | JVM 退出时不阻塞；代价是被强杀不会走完当前轮，所以配套 `stop()` 优雅停机 |
| `scheduleWithFixedDelay` | `:225` | 上一轮结束后再等间隔，避免某轮 DB 慢查询卡 30s 后 `FixedRate` 连发追赶造成雪崩 |
| `pollOnce` 全量 try-catch | `:295-317` | ⚠️ **致命坑**：`ScheduledExecutorService` 中若 task 抛未捕获异常，**后续调度会被静默取消**（poller 从此装死不报错）。`pollOnce` 必须自己兜住所有异常 |

#### 1.2.3 扇出全貌：从 `start()` 到 `BuildTaskHandler` / `DeployTaskHandler`

```text
Spring 容器启动（ApplicationContext 刷新完成）
  │  DefaultLifecycleProcessor 自动调用所有 SmartLifecycle Bean 的 start()
  ▼
TaskExecutor.start()                              // TaskExecutor.java:174
  ├─ recoverInterruptedTasks()         @472       // ① 收敛上次残留的"执行中"任务
  ├─ running = true                    @191       // ② 开运行开关（volatile，跨线程可见）
  ├─ poller = newSingleThreadScheduledExecutor(...)  @207   // ③ 建"lds-task-poller"守护线程
  └─ poller.scheduleWithFixedDelay(pollOnce, 0, 1000ms)  @225  // ④ 注册每秒轮询
        │
        │  ═══ 此后每秒自动跑一次 pollOnce()，无需任何外部触发 ═══
        ▼
pollOnce()                                      // :291
  └─ for (task : taskService.listQueued(limit))        @300   // 查 status=0 排队任务，按 create_time 升序
        └─ trySubmit(task)                             // :326
              ├─ handler = handlers.get(task.getTaskType())   @327  // 按 task_type 查 Handler
              ├─ 取 Semaphore 并发令牌 + 抢 busyLockKeys 互斥键（同服务器串行）
              └─ workerPool.execute(() -> runTask(...))      @347   // 交给 6 线程 worker 池
                    ▼
runTask()                                       // :366
  └─ executeTask(taskId, handler)               // :391
        ├─ taskService.markRunning(id)          @394   // 原子抢占 status 0→1（条件更新）
        └─ handler.execute(task)                @411   // ★ 真正干活的 Handler（Build / Deploy / ...）
                    │
        ┌───────────┴───────────────┬────────────────────────┐
        ▼                           ▼                        ▼
BuildTaskHandler             DeployTaskHandler          ServerTest / ProjectTest
.execute(task)               .execute(task)            TaskHandler.execute(task)
（连构建机构建）             （连目标机发布/回滚）       （SSH 只读探活）
bizId = build.id             bizId = deployment.id
```

**一句话总结扇出**：`TaskExecutor` 是唯一中央调度器，它**不认识**构建和部署业务；它只认 `lds_task.task_type` 这个字符串，按字符串从 `handlers` Map 查出对应 Handler 调 `execute(task)`。构建和部署**从来不被"调用"**，它们只是"往 `lds_task` 插了一条对应类型的排队记录"。

#### 1.2.4 "其它编排调度器"是什么层级？（解决"怎么调用其它编排调度器"）

你问的"构建和部署发布阶段又是怎么调用其它的编排调度器的"——答案是：**它们不调用，是 `TaskExecutor` 统一扇出。** 层级是三层：

| 层级 | 角色 | 成员 | 职责 |
| -- | -- | -- | -- |
| 中央调度器 | `TaskExecutor`（唯一） | 实现 `SmartLifecycle` | 轮询 `lds_task`、原子抢占、并发令牌、同服务器互斥、状态收敛、日志落库 |
| 域编排器（4 个 `Handler`） | 各管一种 `task_type` | `BuildTaskHandler`(`BUILD`) / `DeployTaskHandler`(`DEPLOY`) / `ServerTestTaskHandler`(`SERVER_TEST`) / `ProjectConnectTestTaskHandler`(`PROJECT_TEST`) | 拿到"已进入执行中"的任务后按本域语义把事做完；再按运行时 `switch` 分发给具体执行器 |
| 域内执行器 | Handler 内部再委托 | `DockerBuilder`/`JarPrebuildBuilder`/`ScriptBuildService`；`DockerDeployService`/`JarDeployService`/`StaticDeployService` | 真正连机器干活（SSH/SFTP/构建/启动/健康探测） |

> `TaskExecutor` 与 4 个 Handler **不是继承、也不是互相 `@Autowired` 调用**。Handler 在 `TaskExecutor` 构造函数里被 `List<TaskHandler>` 自动收集进 Map（`:122-131`）；运行时 `executeTask()` 按 `task.getTaskType()` 取出调 `execute(task)`（`:411`）。新增一种任务类型，只需新建 `TaskHandler` 实现并注册成 Bean，调度代码一行都不用改。

#### 1.2.5 构建 / 部署业务代码只"插任务"，不"调 Handler"

这是把"触发"与"执行"彻底解耦的关键，也是你"没看到 TaskExecutor 被触发调用"的原因——**触发发生在数据库插入那一刻，执行发生在后台轮询线程，两者在代码里不相邻**：

- `BuildService.createAndTrigger(dto)`（`:176`，`@Transactional`）：校验 → 落 `build` 记录 → `taskService.create(...)` 插一条 `BUILD` 任务（`bizId=build.id`）→ **立即返回 `BuildVo`（含 taskId）**。它**完全不认识 `BuildTaskHandler`** 这个类。
- `DeploymentService.createAndTrigger(dto)`（`:245`）：校验 → 落 `deployment` 主记录 + `deployment_target` 快照 → `createDeployTask(id)` 插一条 `DEPLOY` 任务（`bizId=deployment.id`）→ 返回 `DeploymentVo`。它**也完全不认识 `DeployTaskHandler`**。

耦合只发生在 **`lds_task.task_type` 字符串** 与 **Handler 的 `taskType()` 返回值** 之间：

- 前端点"构建" → `BuildController` → `BuildService.createAndTrigger` → **插库** → 请求结束；
- 1 秒后 `TaskExecutor` 轮询到这条 `BUILD` 记录 → `markRunning` 抢占 → `BuildTaskHandler.execute(task)`，`task.getBizId()` 拿到 `build.id` → 加载 Build → 连构建机干活；
- 发布同理，只是 `task_type=DEPLOY`、Handler 换成 `DeployTaskHandler`。

> 回头看 §0 的图：在 `Controller` 返回之后、后台 `Handler` 执行之前，链路有一个"断点"——这个断点就是 `lds_task` 这张表 + 后台轮询线程。理解了这个"断点"，你就不会再去找"谁调了 Handler"。

### 1.3 调度追踪日志标记与排障对照（备查）

为了解决"日志里只有 taskId、看不出走到哪一步"的问题，平台在 **中央调度器 + 四个域编排器** 全链路埋了统一的日志前缀标记。
排障时**先用 `grep '<标记>'` 把对应业务维度的日志抽出来**，再顺着阶段序号定位卡点。

#### 1.3.1 标记总表（前缀 → 含义 → 位置 → 触发时机）

| 日志前缀标记 | 所属类 @ 行 | 业务维度 | 触发时机 / 含义 |
| --- | --- | --- | --- |
| `[中央调度中枢]` | `TaskExecutor.java:241` | 中央调度器 | **应用启动、调度器上线时打印一次**：输出并发上限、轮询间隔(ms)、已注册的四个编排器类名。没看到这行 = 调度器没起来（`SmartLifecycle` 未触发 / 启动异常） |
| `[中央调度分发]` | `TaskExecutor.java:420` | 中央调度器 | **每领到一个任务并抢占成功后打印一次**：`taskId → 编排器类名(taskType) , bizId=...`。这是"中央→域"扇出的唯一铆点；有这行说明任务已出队进入执行 |

#### 1.3.2 排障套路

```bash
# 1) 看调度器是否上线（启动日志里应有且仅有一行）
grep '\[中央调度中枢\]' app.log

# 2) 抽某条 task 的"分派"行（把 <taskId> 换成实际 id），拿到 bizId
grep '\[中央调度分发\]' app.log | grep '<taskId>'
#   真正的阶段日志在对应编排器前缀里，用上面拿到的 bizId 追：
grep '\[部署编排器\]' app.log | grep '<bizId>'

# 3) 按业务维度整条拉（构建 / 发布 / 服务器测试 / 项目测试 任选其一）
grep -E '\[构建编排器\]|\[中央调度分发\]' app.log
grep -E '\[部署编排器\]|\[中央调度分发\]' app.log
grep -E '\[服务器测试编排器\]|\[中央调度分发\]' app.log
grep -E '\[项目测试编排器\]|\[中央调度分发\]' app.log
```

> 关键约定：**阶段日志不带 `taskId`，只带 `bizId`（业务主键：`buildId` / `deploymentId` / `serverId` / `projectId`）**。`[中央调度分发]` 那一行**同时带 taskId 和 bizId**，是两者之间的"桥"。排障时先靠 `taskId` 在分发行锁定 `bizId`，再用 `bizId` 去对应编排器前缀里追阶段。

#### 1.3.4 卡点速查

| 现象 | 可能原因 | 看哪行日志 / 数据 |
| --- | --- | --- |
| 点了构建/发布，页面一直"排队中" | 调度器没启动，或任务没插库 | 搜 `[中央调度中枢]` 是否存在；查 `lds_task where status=0` |
| 有 `[中央调度中枢]` 但无 `[中央调度分发]` | 任务卡 `status=0` 没被领走（并发令牌 `Semaphore` 满、或 `busyLockKeys` 被同服务器别的任务占着） | 看 `TaskExecutor.trySubmit` 抢占逻辑；确认同服务器是否有"执行中"任务 |
| 有分发行但没有编排器阶段日志 | Handler `execute` 开头就抛异常（连不上机、SSH 密钥错等） | 看 `[中央调度分发]` 之后紧跟的 ERROR / 任务终态 `markFailed` |
| `[部署编排器] 阶段③` 之后断 | 某目标发布中途失败（健康探测不过、文件投放失败） | 紧跟的 ERROR + `lds_task_log` 该目标明细 + `deployment_target` 各目标 status |
| 阶段日志有 `阶段④` 没 `阶段⑤` | `finishDeployment` 汇总前某目标未达成 | 同上，核对 `deployment_target` 各目标 status |

## 3. 为什么 DeployTaskHandler 看起来「无主」？（解码你的困惑）

你原话："我根本不知道 DeployTaskHandler 被什么调用，在哪里调用，怎么触发的。"

答案分三层：

1. **它在哪被实例化**：`DeployTaskHandler` 是个 `@Component`（`DeployTaskHandler.java:75`），由 Spring 注入所有依赖。
   它实现 `TaskHandler` 接口，`TaskExecutor` 的构造函数接收 `List<TaskHandler>`，启动时把它收进
   `handlers` Map（`TaskExecutor.java:122-131`）。这一步只是"登记"，不是"调用"。

2. **它在哪被调用**：`grep -rn "DeployTaskHandler"` 全文，除了定义、`@Component`、构造函数、类注释，
   **没有任何业务代码 new 它或调它**。它唯一的运行入口是 `TaskExecutor.executeTask()` 第 411 行
   `handler.execute(task)`——`handler` 是从 Map 里按 `task.getTaskType()` 查出来的。

3. **它怎么被触发**：不是前端、不是 Controller、不是事件，而是 **`lds_task` 表里出现一条
   `task_type=DEPLOY` 且 `status=0` 的记录**。`DeploymentService.createAndTrigger`（`DeploymentService.java:245`）
   在事务里插这条记录并立即返回；之后 `TaskExecutor` 每秒轮询到它，抢占执行，才轮到 `DeployTaskHandler`。

   换句话说：**触发点是「数据库里多了一条排队任务」，不是「某段代码调了某方法」。** 这正是解耦架构的代价——
   链路在代码里不是一条直连的调用栈，而是"写库 + 后台轮询"。本平台所有模块文档的「调用链路」一节，
   都会把这条"断开又接上"的链路画清楚。

## 4. 顺着代码读的正确顺序（给第一次读代码的人）

不要从 `DeployTaskHandler` 往回找调用方——你会卡住。正确顺序：

1. **从前端入口读**：`lighit-deploy-ui/src/api/*.ts` 找你要跟的 api 函数（如 `createDeployment`）；
2. **到 Controller**：`src/main/java/com/lx/deploy/**/controller/*.java` 找对应 `@PostMapping`/`@PutMapping`，
   确认 URL 与方法，确认它只做"收参 + 调 Service"；
3. **到 Service**：看它落了哪些业务表、是否调了 `taskService.create(...)` 插异步任务；
4. **到 TaskExecutor**：确认任务类型，再看 §1.1 映射表找到对应 Handler；
5. **到 Handler**：`execute(task)` 里才是真正 SSH 连目标机干活的代码；
6. **回前端**：用返回的 `taskId` 调 `GET /taskLog/pull` 看实时进度。
