> 模块包：`com.lx.deploy.*` ｜ 定位：全平台代码阅读与链路追踪的**总入口**
> 当前状态：已完成并编译通过

## 0. 一句话心智模型（最重要，先读这段）

整个平台**没有消息队列、没有 Spring 事件（`@EventListener` 全文 0 处）、没有 `@Async`**。
所有「构建 / 发布 / 回滚 / 连通性测试」这类长耗时任务，统一由**数据库轮询调度器**驱动：

```text
前端页面（点按钮）
   │  axios 请求
   ▼
Controller（收参 → 调用 Service → 只做一件事：插一条 status=0 的 lds_task 排队记录 + 业务主记录）
   │  立即返回 taskId / taskNo，连接断开，请求结束
   ▼  （此处链路"断开"——请求线程已经走完了）
后台 TaskExecutor（独立线程，每 1 秒轮询一次 lds_task）
   │  listQueued 抢到排队中的任务 → 原子 markRunning 抢占 → 提交到 worker 线程池
   ▼
Handler.execute(task)   ← 真正干活的代码，跑在 TaskExecutor 的 worker 线程里
   │  SSH 连构建机 / 目标机、执行命令、传文件、写 lds_task_log
   ▼
前端再用 GET /taskLog/pull 轮询拉日志，看到实时进度
```

**核心结论：你在 `DeployTaskHandler` 里找不到「被谁调用」，是因为它唯一的直接调用方是
`TaskExecutor.executeTask()` 的第 411 行（`handler.execute(task)`，详见 §1.2）。** Controller 永远不直接调用 Handler，Dao 也不调用。
请求路径与执行路径通过 `lds_task` 这张表解耦——这就是你"看代码看不懂"的根因，不是你的问题，是这套架构
刻意的"请求与执行分离"。

本平台所有模块文档都遵循同一套写法：**每个模块都有一节「调用链路（前端 → 后端 → 执行器）」，
精确到 前端api函数 → HTTP方法+URL → Controller.方法@行号 → Service.方法@行号 → 任务类型 → Handler.方法@行号 → 实际动作**。
看文档时先翻到那一节，就能从前端一路定位到具体代码行。

### 1.1.1 Handler 是如何被收集并按 taskType 路由的（Spring 注入 + 构造函数建 Map）

你原话："只是定义了 `String taskType()`，怎么拿到的不同的任务类型给到 TaskExecutor 的？" 答案分五步，核心就一句：
**`taskType()` 本身不"给" TaskExecutor 任何类型，它只是每个 Handler 自报家门的一个标签；真正把"类型 → Handler"凑成一张表的是 Spring 的依赖注入 + 构造函数里的一次性建 Map。**

#### ① 接口只定契约

`TaskHandler` 接口（`task/executor/TaskHandler.java:25`）只声明方法签名，不关心实现：

```java
public interface TaskHandler {
    String taskType();   // 该处理器负责任务类型编码，如 "BUILD" / "DEPLOY" / ...
    String lockKey(Task task);
    void execute(Task task);
}
```

#### ② 每个 Handler 各自返回自己的常量（引用同一枚举，防拼错）

```java
// build/executor/BuildTaskHandler.java:51-52, 116-119
private static final String TASK_TYPE = TaskType.BUILD.getCode();   // 来自枚举，不是手写字符串
@Override
public String taskType() { return TASK_TYPE; }   // 返回 "BUILD"
```

其余三个同理，只换 `TaskType.DEPLOY / SERVER_TEST / PROJECT_TEST`。**`TaskType` 枚举是"单一事实来源"**——Handler 的 `taskType()` 和 Service 插库时写的 `task_type` 都从它取 `.getCode()`，保证两边字符串一致。

#### ③ Spring 自动把所有实现收成 List 注入（关键！）

```java
// TaskExecutor.java:113  —— 构造函数参数
public TaskExecutor(..., List<TaskHandler> handlerList, ...) {
```

这是 Spring 的标准能力：**注入 `List<某接口>` 时，Spring 会把容器里所有实现了该接口的 Bean 自动收集成一个 List 塞给你**。四个 Handler 都是 `@Component`（Spring Bean）且 implements `TaskHandler`，所以启动时被自动打包成 `List` 传入——`TaskExecutor` 一行"扫描"代码都不用写。

#### ④ 构造函数把 List 拍成 Map（仅构造期一次，并显式打印路由表）

```java
// TaskExecutor.java:122-145
// 路由本质：Map<taskType字符串, 对应 Handler 实例>；来源是 Spring 注入的 handlerList；
// 约定：handler.taskType() 必须与 lds_task 里写入的 task_type 完全一致，否则运行期查不到 Handler。
Map<String, TaskHandler> handlerMap = new HashMap<>();
StringBuilder routeInfo = new StringBuilder();
for (TaskHandler handler : handlerList) {                    // :129 遍历全部 Handler
    TaskHandler exists = handlerMap.put(handler.taskType(), handler);  // :131 用 taskType() 当 key 建映射
    if (exists != null) {
        throw new IllegalStateException("任务类型 " + handler.taskType() + " 存在多个处理器：...");  // :134 重复类型启动即炸
    }
    routeInfo.append(handler.taskType()).append('=').append(handler.getClass().getSimpleName());
}
this.handlers = Map.copyOf(handlerMap);                      // :143 不可变路由表，运行期只查不改
log.info("[中央调度中枢] 任务类型路由表（type → 编排器）：{}", routeInfo);  // :145 启动即打印路由表
```

启动后日志会看到一行（排障一眼可见平台支持哪些类型）：

```text
[中央调度中枢] 任务类型路由表（type → 编排器）：BUILD=BuildTaskHandler, DEPLOY=DeployTaskHandler, SERVER_TEST=ServerTestTaskHandler, PROJECT_TEST=ProjectConnectTestTaskHandler
```

#### ⑤ 运行期按 task_type 字符串反查（最终落点）

```java
// TaskExecutor.trySubmit（:346）→ 运行期路由查表（核心落点）
TaskHandler handler = handlers.get(task.getTaskType());      // :350 用任务里存好的 task_type 反查编排器
if (handler == null) {
    // 库里出现本平台未实现的任务类型：没有 Handler 能处理，必须领取并立即失败，否则会永远停在排队中
    log.warn("[中央调度分发] 未找到任务类型 {} 对应的编排器，任务将标记失败：taskId={}", task.getTaskType(), task.getId());  // :353
}
// executeTask（:423）→ markRunning 抢占后
log.info("[中央调度分发] 分派 taskId={} → 编排器 {} (taskType={})，业务主键 bizId={}", ...);  // :446
handler.execute(task);                                       // :451 真正执行
```

> 注意：**`handler.taskType()` 只在构造时各调一次**用来当 Map 的 key；运行期路由根本不再调 `taskType()`，而是直接拿 `lds_task` 表里存好的 `task_type` 字符串去 `handlers.get(...)`。所以"类型对得上"不是靠 Handler 实时自报，而是靠**建表时的 key 与插库时的字符串约定一致**。

#### 两个设计红利（为什么这么设计）

| 红利 | 说明 |
| --- | --- |
| **扩展零改调度代码** | 新增一种任务，只要新建一个 `@Component` 实现 `TaskHandler` 并写好 `taskType()`，Spring 自动加进 `handlerList`，构造函数循环自动收进 Map——`TaskExecutor` 一行都不用动 |
| **重复类型启动即炸** | `:134` 的 `IllegalStateException`：两个 Handler 返回同样的 `taskType()` 时 `put` 检测到 `exists != null` 立刻抛异常，应用启动失败，而不是静默把一种任务路由错 Handler |

### 1.1.2 `lockKey(task)`：互斥键——"同一服务器同一时刻只跑一个任务"的落地

接口里 `lockKey` 的契约（`task/executor/TaskHandler.java:37`）：返回形如 `<前缀>:<业务主键>` 的字符串，**相同互斥键的任务在平台内串行执行**，用于落实 AGENTS.md §1「同一服务器同一时刻只执行一个任务」。

#### 调用链路（谁在什么时候算这个键）

```text
pollOnce() @311
  └─ trySubmit(task) @346
        ├─ handler.lockKey(task) @357        ← 由 Handler 按业务维度算互斥键
        ├─ busyLockKeys.add(lockKey) @364      ← 真正串行互斥的闸门
        │     └─ 已被占用（同锁键任务执行中）→ 打 DEBUG 日志 @365 并跳过本轮，下轮再试
        └─ 占用成功 → workerPool.execute(runTask) @375
```

> 关键点：**互斥粒度由 Handler 自己决定**，调度器只负责"算出来 → 放进 `busyLockKeys` 集合 → 占不到就跳过"。连构建机、连目标机这种以"机器"为操作对象的任务，自然用 `server:<id>` / `build-server:<id>` 做键；而部署以"一次部署"为粒度，用 `deploy:<deploymentId>`。

#### 四个 Handler 的实际键格式（来自真实代码）

| Handler | `lockKey()` 实现 | 实际键格式 | 互斥粒度 |
| --- | --- | --- | --- |
| `BuildTaskHandler` | `LOCK_KEY_PREFIX + build.getBuildServerId()` @131 | `build-server:<构建机ID>` | 按**构建机**维度（同构建机上的构建串行；读不到构建机时回落 build.id） |
| `DeployTaskHandler` | `LOCK_KEY_PREFIX + task.getBizId()` @216 | `deploy:<deployment.id>` | 按**一次部署**维度（发布与回滚互相串行） |
| `ServerTestTaskHandler` | `LOCK_KEY_PREFIX + task.getBizId()` @150 | `server:<server.id>` | 按**目标服务器**维度 |
| `ProjectConnectTestTaskHandler` | 优先 `BUILD_SERVER_LOCK_PREFIX + 项目构建机ID`，读不到回落 `PROJECT_LOCK_PREFIX + project.id` @202 | `build-server:<构建机ID>` 或 `project-test:<project.id>` | 优先与构建任务共用同一构建机键，使"同机构建与测试串行" |

#### 日志（本次新增）

互斥键被占用、任务本轮跳过时打印（DEBUG 级，避免正常并发刷屏）：

```text
[中央调度分发] 任务 taskId=3072 跳过本轮：互斥键 server:12 被占用（同锁键任务执行中），下轮重试
```

> ✅ **已修复（2026-11-03）**：原 `lockKey` 返回 `build-server:<build.id>`，实为「按构建记录」互斥，与类注释"同一台构建机上的构建必须串行执行"不一致——同一构建机并发两个不同构建**不会**被串行化。已改为先读 build 取 `build.getBuildServerId()` 做键（读不到构建机时回落 build.id），现在同一构建机上的并发构建会被串行化；且与 `ProjectConnectTestTaskHandler` 共用同一 `build-server:<构建机ID>` 键，**同构建机上的构建与项目测试也会互斥**（落实 AGENTS.md §1「同一服务器同一时刻只执行一个任务」）。实现见 `BuildTaskHandler.java:131`。

### 1.1.3 `execute(task)`：真正干活的入口——调用链路与日志

接口里 `execute` 的契约（`task/executor/TaskHandler.java:48`）：拿到一条**已进入执行中**的任务后把事做完；通过 `TaskService.updateProgress` 汇报阶段、通过 `TaskLogService` 写执行日志；抛异常即视为失败（异常消息作失败原因，**不得携带凭据等敏感信息**）。

#### 调用链路（从轮询到真正干活）

```text
pollOnce() @311
  └─ trySubmit(task) @346
        └─ workerPool.execute(() -> runTask(taskId, lockKey, handler)) @375   ← 交给 6 线程 worker 池（不阻塞 1s 轮询线程）
              ▼
runTask(taskId, ...) @398          ← worker 线程入口，保证令牌/互斥键一定释放
  └─ executeTask(taskId, handler) @423
        ├─ taskService.markRunning(taskId) @426        ← 原子抢占 status 0→1（条件更新）
        ├─ [中央调度分发] 分派日志 @446                 ← 打印 编排器类名 + taskType + bizId
        └─ handler.execute(task) @451                  ← ★ 真正进入具体 Handler 干活（在 worker 线程，可长耗时 SSH）
              └─ 各 Handler 内部打 [xxx编排器] 阶段日志 → 返回 → markSuccess / 抛异常 → failTask
```

#### 四个 Handler 的 `execute` 入口与既有追踪日志

| Handler | `execute()` 入口 | 业务维度 | 既有追踪日志前缀 |
| --- | --- | --- | --- |
| `BuildTaskHandler` | @142 | 构建 | `[构建编排器]`（5 阶段：收派→连构建机→克隆→定稿版本号→分发 Builder→完成） |
| `DeployTaskHandler` | @232 | 发布/回滚 | `[部署编排器]`（5 阶段：收派→开静默窗→标部署中→分批/按运行时分发→收敛→关静默窗） |
| `ServerTestTaskHandler` | @164 | 服务器连通性测试 | `[服务器测试编排器]`（3 阶段：收派→连服务器→逐项只读探活→部署目录可写性→完成） |
| `ProjectConnectTestTaskHandler` | @224 | 项目连通性测试 | `[项目测试编排器]`（5 阶段：收派→连构建机→工具链→代码仓库→镜像仓库→目标机 java→通过） |

#### 日志与异常收敛

- 进入 `execute` 之前：`[中央调度分发]` 分派日志 @446（已在 §1.3.1 登记）。
- 执行中：各 Handler 内部的 `[xxx编排器]` 阶段日志（阶段日志只带 `bizId`，见 §1.3）。
- 执行后：`execute` 正常返回 → `markSuccess`；抛异常 → `executeTask` 的 catch 块按"业务失败 WARN 不带堆栈 / 未预期异常 ERROR 带堆栈"记日志并 `failTask`（详见 `TaskExecutor.java:451` 之后的 catch 段）。
- 因为 `execute` 跑在 `workerPool` 线程里，**长耗时的 SSH 构建/发布不会阻塞 1 秒轮询线程**，调度器吞吐不受影响。

### 1.2 TaskExecutor 的 start() 到底被谁触发？——你卡住的根因（重点）

你原话："我根本就没看到 TaskExecutor 的方法被触发调用的代码，都没有定时任务什么的。"
这句话点中本平台最反直觉的地方：**确实没有任何 `@Scheduled`、没有任何一处显式调用 `taskExecutor.start()`**。下面把"它怎么启动、每秒怎么跑、怎么扇出到构建/部署"一次讲透。

#### 1.2.1 触发点：不是定时器，是 Spring 容器生命周期（SmartLifecycle）

`TaskExecutor` 的类签名：

```java
@Component
public class TaskExecutor implements SmartLifecycle { ... }
```

`SmartLifecycle` 是 Spring 的**生命周期接口**。Spring 在 **`ApplicationContext` 刷新完成（`finishRefresh`）之后**，由容器内部的 `DefaultLifecycleProcessor` 自动遍历所有 `SmartLifecycle` Bean，逐个调用 `start()`。

所以：

- **`TaskExecutor.start()` 的调用方是 Spring 容器本身**，不是任何 Controller / Service / 定时器；
- 你在业务代码里 grep `taskExecutor.start()` 搜不到——它从没被业务代码调用；
- 你搜 `@Scheduled` 也搜不到——本平台的轮询**不是**用 `@Scheduled` 注解实现的。

> 直觉等价：把"应用启动后自动跑一次 `start()`"交给容器生命周期托管。如果用 `@Scheduled(fixedDelay=1000)` 注解在方法上，那是 Spring 另一种调度写法；本项目**不用它**，是为了对手搓调度器做精细控制（线程命名、守护线程、异常隔离、与容器生命周期联动的优雅停机）。下面的 `poller` 就是手搓版的"每秒调度器"。

#### 1.2.2 轮询引擎：手搓的 `lds-task-poller` 守护线程（你看到的那段代码）

`start()` 内部（`:221`）创建调度器：

```java
poller = Executors.newSingleThreadScheduledExecutor(runnable -> {
    Thread thread = new Thread(runnable, "lds-task-poller");
    thread.setDaemon(true);     // 守护线程
    return thread;
});
```

接着（`:239`）注册周期任务：

```java
poller.scheduleWithFixedDelay(this::pollOnce, 0L, pollIntervalMs, TimeUnit.MILLISECONDS);
```

这就是"每 1 秒轮询一次 `lds_task`"的**真正来源**：

- `ScheduledExecutorService` 是 JDK 自带的调度线程池；`newSingleThreadScheduledExecutor` 取单线程版本；
- `scheduleWithFixedDelay(...)` = **上一轮 `pollOnce` 跑完之后，再等 `pollIntervalMs`（默认 1000ms）才开始下一轮**；`initialDelay=0` 表示应用一启动立刻跑第一轮；
- 线程名叫 `lds-task-poller`，`jstack` / `top -H` 一眼能认出这是任务轮询线程。

几个**为什么这样设计**（正是你"看不懂"那段代码的理由）：

| 设计点 | 代码 | 原因 |
| -- | -- | -- |
| 单线程调度 | `newSingleThreadScheduledExecutor` | 轮询串行，绝不出现"两轮 `pollOnce` 并发拉同一批任务"导致重复消费。真正干活的并发交给另一个 `workerPool`（大小 6） |
| 守护线程 | `thread.setDaemon(true)` | JVM 退出时不阻塞；代价是被强杀不会走完当前轮，所以配套 `stop()` 优雅停机 |
| `scheduleWithFixedDelay` | `:239` | 上一轮结束后再等间隔，避免某轮 DB 慢查询卡 30s 后 `FixedRate` 连发追赶造成雪崩 |
| `pollOnce` 全量 try-catch | `:295-317` | ⚠️ **致命坑**：`ScheduledExecutorService` 中若 task 抛未捕获异常，**后续调度会被静默取消**（poller 从此装死不报错）。`pollOnce` 必须自己兜住所有异常 |

#### 1.2.3 扇出全貌：从 `start()` 到 `BuildTaskHandler` / `DeployTaskHandler`

```text

  │  DefaultLifecycleProcessor 自动调用所有 SmartLifecycle Bean 的 start()
  ▼
```

**一句话总结扇出**：`TaskExecutor` 是唯一中央调度器，它**不认识**构建和部署业务；它只认 `lds_task.task_type` 这个字符串，按字符串从 `handlers` Map 查出对应 Handler 调 `execute(task)`。构建和部署**从来不被"调用"**，它们只是"往 `lds_task` 插了一条对应类型的排队记录"。

#### 1.2.4 "其它编排调度器"是什么层级？（解决"怎么调用其它编排调度器"）

你问的"构建和部署发布阶段又是怎么调用其它的编排调度器的"——答案是：**它们不调用，是 `TaskExecutor` 统一扇出。** 层级是三层：

| 层级 | 角色 | 成员 | 职责 |
| -- | -- | -- | -- |
| 中央调度器 | `TaskExecutor`（唯一） | 实现 `SmartLifecycle` | 轮询 `lds_task`、原子抢占、并发令牌、同服务器互斥、状态收敛、日志落库 |
| 域编排器（4 个 `Handler`） | 各管一种 `task_type` | `BuildTaskHandler`(`BUILD`) / `DeployTaskHandler`(`DEPLOY`) / `ServerTestTaskHandler`(`SERVER_TEST`) / `ProjectConnectTestTaskHandler`(`PROJECT_TEST`) | 拿到"已进入执行中"的任务后按本域语义把事做完；再按运行时 `switch` 分发给具体执行器 |
| 域内执行器 | Handler 内部再委托 | `DockerBuilder`/`JarPrebuildBuilder`/`ScriptBuildService`；`DockerDeployService`/`JarDeployService`/`StaticDeployService` | 真正连机器干活（SSH/SFTP/构建/启动/健康探测） |

> `TaskExecutor` 与 4 个 Handler **不是继承、也不是互相 `@Autowired` 调用**。Handler 在 `TaskExecutor` 构造函数里被 `List<TaskHandler>` 自动收集进 Map（`:122-145`）；运行时 `executeTask()` 按 `task.getTaskType()` 取出调 `execute(task)`（`:451`）。新增一种任务类型，只需新建 `TaskHandler` 实现并注册成 Bean，调度代码一行都不用改。

#### 1.2.5 构建 / 部署业务代码只"插任务"，不"调 Handler"

这是把"触发"与"执行"彻底解耦的关键，也是你"没看到 TaskExecutor 被触发调用"的原因——**触发发生在数据库插入那一刻，执行发生在后台轮询线程，两者在代码里不相邻**：

- `BuildService.createAndTrigger(dto)`（`:176`，`@Transactional`）：校验 → 落 `build` 记录 → `taskService.create(...)` 插一条 `BUILD` 任务（`bizId=build.id`）→ **立即返回 `BuildVo`（含 taskId）**。它**完全不认识 `BuildTaskHandler`** 这个类。
- `DeploymentService.createAndTrigger(dto)`（`:245`）：校验 → 落 `deployment` 主记录 + `deployment_target` 快照 → `createDeployTask(id)` 插一条 `DEPLOY` 任务（`bizId=deployment.id`）→ 返回 `DeploymentVo`。它**也完全不认识 `DeployTaskHandler`**。

耦合只发生在 **`lds_task.task_type` 字符串** 与 **Handler 的 `taskType()` 返回值** 之间：

- 前端点"构建" → `BuildController` → `BuildService.createAndTrigger` → **插库** → 请求结束；
- 1 秒后 `TaskExecutor` 轮询到这条 `BUILD` 记录 → `markRunning` 抢占 → `BuildTaskHandler.execute(task)`，`task.getBizId()` 拿到 `build.id` → 加载 Build → 连构建机干活；
- 发布同理，只是 `task_type=DEPLOY`、Handler 换成 `DeployTaskHandler`。

> 回头看 §0 的图：在 `Controller` 返回之后、后台 `Handler` 执行之前，链路有一个"断点"——这个断点就是 `lds_task` 这张表 + 后台轮询线程。理解了这个"断点"，你就不会再去找"谁调了 Handler"。

### 1.2.6 为什么调度器启动后，要等你点构建/测试/发布才"看到"它运行？（空闲轮询模型）

这是 §1.2 的延续，也是你最初"看不懂触发"的另一半困惑。结论先说：

**中央调度器从应用一启动就一直在跑了（每秒轮询一次 `lds_task`），并不是等你点构建/测试/发布才"启动"。你点那几个按钮时真正发生的，只是往 `lds_task` 表里插了一条 `status=0` 的排队记录。调度器早就"在岗"，只是之前每次轮询都查无任务，所以你没看到它干活的日志。**

#### 时序还原（关键：调度器一直转，任务行才是"触发器"）

```text
T0  应用启动（Spring 刷新完成）
    │  DefaultLifecycleProcessor 自动调 TaskExecutor.start()
    ▼
  [中央调度中枢] TaskExecutor 已启用 …        ← 你看到的这行，只打一次（TaskExecutor.java:188）
    │  poller 启动，从此每 1 秒跑一次 pollOnce()
    ▼
T0+1s, T0+2s, … T0+Ns：
    pollOnce() @311 → taskService.listQueued(limit) @314
    │   SELECT … WHERE status=0  →  返回空
    │   循环体不执行 → 不打任何日志（刻意不打"空闲"日志，避免刷屏）
    ▼   看起来"没动静"，其实线程一直在转

T_user 点「构建」：
    HTTP → Controller → BuildService.createAndTrigger @176
    │   只做一件事：taskService.create(...) 插一条 BUILD 任务(status=0)
    │   请求立刻返回 taskId，连接断开
    ▼  （这一步和调度器毫无关系，只是写了库）

≤1 秒后某次轮询：
    pollOnce() 查到这条 status=0 → markRunning 抢占 @426
    → [中央调度分发] @446（分派行出现）
    → handler.execute(task) @451
    → [构建编排器] 阶段①…②…③…   ← 你这才"看到"调度在跑
```

#### 为什么是"这几个环节"才触发

因为**全平台只有这四种动作会写 `lds_task` 排队记录**（其余都是请求线程内同步完成的纯 CRUD，从不插任务）：

| 动作 | 插任务的位置 | `task_type` |
| --- | --- | --- |
| 构建 | `BuildService.createAndTrigger`（`BuildService.java:176`） | `BUILD` |
| 发布 / 回滚 | `DeploymentService.createAndTrigger` / `rollback` | `DEPLOY` |
| 服务器测试 | `ServerService.submitConnectivityTest` | `SERVER_TEST` |
| 项目测试 | `ProjectService.submitConnectivityTest` | `PROJECT_TEST` |

而服务器 / 项目 / 环境 / 凭据这些**纯 CRUD 模块**从头到尾从不插任务，所以调度器对它们"永远没活干"，你自然看不到任何调度日志。

#### 一句话心智模型

> 调度器是"7×24 轮询一张表"，不是"被某个业务事件叫醒"。你点按钮 = 往表里扔了张工单；调度器下一秒扫到工单才开工。它不认识"构建/发布"这些概念，只认识 `lds_task.task_type` 这个字符串。

#### 排障推论（判断调度器是否真的"活着"）

不要靠"它有没有在构建时跑"来判断，而要看：

1. 启动日志里有没有那一行 `[中央调度中枢]`（`TaskExecutor.java:188`）；
2. `jstack` / `top -H` 里有没有 `lds-task-poller` 这个守护线程——它一直在，和有没有任务无关。

如果启动日志有中枢行、但又没有 `[中央调度分发]`、且页面一直"排队中"，问题**不在调度器没启动**，而在**任务没被领走**：要么 `lds_task` 里没插进 `status=0` 的记录（业务 Service 插库失败），要么同服务器有"执行中"任务占着 `busyLockKeys`、或并发令牌 `Semaphore` 已耗尽。具体见 §1.3.4 卡点速查。

### 1.3 调度追踪日志标记与排障对照（备查）

为了解决"日志里只有 taskId、看不出走到哪一步"的问题，平台在 **中央调度器 + 四个域编排器** 全链路埋了统一的日志前缀标记。
排障时**先用 `grep '<标记>'` 把对应业务维度的日志抽出来**，再顺着阶段序号定位卡点。

#### 1.3.1 标记总表（前缀 → 含义 → 位置 → 触发时机）

| 日志前缀标记 | 所属类 @ 行 | 业务维度 | 触发时机 / 含义 |
| --- | --- | --- | --- |
| `[中央调度中枢]` | `TaskExecutor.java:145` / `:188` | 中央调度器 | **应用启动阶段打印两次**（均在启动期，先于任何任务）：①构造函数建好路由表后打印「任务类型路由表（type → 编排器）：BUILD=BuildTaskHandler, …」@145，排障一眼可见平台支持哪些类型；②`start()` 打印「已启用：并发上限/轮询间隔/已注册编排器」@188。两者都看不到 = 调度器没起来（`SmartLifecycle` 未触发 / 启动异常 / 路由表构建抛 `IllegalStateException`） |
| `[中央调度分发]` | `TaskExecutor.java:353` / `:446` | 中央调度器 | **两类**：①运行期路由查表时发现 `lds_task.task_type` 在本平台无对应 Handler → 打印 WARN「未找到任务类型 X 对应的编排器，任务将标记失败」@353（任务会立即以失败收尾，避免永远排队）；②正常领到任务且 `markRunning` 抢占成功后打印「分派 taskId → 编排器类名(taskType)，bizId」@446，这是"中央→域"扇出的唯一铆点，有这行说明任务已出队进入执行 |

#### 1.3.2 排障套路

```bash
# 1) 看调度器是否上线（启动日志里应有且仅有一行）
grep '\[中央调度中枢\]' app.log

# 2) 抽某条 task 的"分派"行（把 <taskId> 换成实际 id），拿到 bizId
grep '\[中央调度分发\]' app.log | grep '<taskId>'
#   真正的阶段日志在对应编排器前缀里，用上面拿到的 bizId 追：
grep '\[部署编排器\]' app.log | grep '<bizId>'

# 3) 按业务维度整条拉（构建 / 发布 / 服务器测试 / 项目测试 任选其一）
grep -E '\[构建编排器\]|\[中央调度分发\]' app.log
grep -E '\[部署编排器\]|\[中央调度分发\]' app.log
grep -E '\[服务器测试编排器\]|\[中央调度分发\]' app.log
grep -E '\[项目测试编排器\]|\[中央调度分发\]' app.log
```

> 关键约定：**阶段日志不带 `taskId`，只带 `bizId`（业务主键：`buildId` / `deploymentId` / `serverId` / `projectId`）**。`[中央调度分发]` 那一行**同时带 taskId 和 bizId**，是两者之间的"桥"。排障时先靠 `taskId` 在分发行锁定 `bizId`，再用 `bizId` 去对应编排器前缀里追阶段。

| --- | --- | --- |
| 点了构建/发布，页面一直"排队中" | 调度器没启动，或任务没插库 | 搜 `[中央调度中枢]` 是否存在；查 `lds_task where status=0` |
| 有 `[中央调度中枢]` 但无 `[中央调度分发]` | 任务卡 `status=0` 没被领走（并发令牌 `Semaphore` 满、或 `busyLockKeys` 被同服务器别的任务占着） | 看 `TaskExecutor.trySubmit` 抢占逻辑；确认同服务器是否有"执行中"任务 |
| 有分发行但没有编排器阶段日志 | Handler `execute` 开头就抛异常（连不上机、SSH 密钥错等） | 看 `[中央调度分发]` 之后紧跟的 ERROR / 任务终态 `markFailed` |
| `[部署编排器] 阶段③` 之后断 | 某目标发布中途失败（健康探测不过、文件投放失败） | 紧跟的 ERROR + `lds_task_log` 该目标明细 + `deployment_target` 各目标 status |
| 阶段日志有 `阶段④` 没 `阶段⑤` | `finishDeployment` 汇总前某目标未达成 | 同上，核对 `deployment_target` 各目标 status |

## 3. 为什么 DeployTaskHandler 看起来「无主」？（解码你的困惑）

你原话："我根本不知道 DeployTaskHandler 被什么调用，在哪里调用，怎么触发的。"

答案分三层：

1. **它在哪被实例化**：`DeployTaskHandler` 是个 `@Component`（`DeployTaskHandler.java:75`），由 Spring 注入所有依赖。
   它实现 `TaskHandler` 接口，`TaskExecutor` 的构造函数接收 `List<TaskHandler>`，启动时把它收进
   `handlers` Map（`TaskExecutor.java:122-145`）。这一步只是"登记"，不是"调用"。

2. **它在哪被调用**：`grep -rn "DeployTaskHandler"` 全文，除了定义、`@Component`、构造函数、类注释，
   **没有任何业务代码 new 它或调它**。它唯一的运行入口是 `TaskExecutor.executeTask()` 第 411 行
   `handler.execute(task)`——`handler` 是从 Map 里按 `task.getTaskType()` 查出来的。

3. **它怎么被触发**：不是前端、不是 Controller、不是事件，而是 **`lds_task` 表里出现一条
   `task_type=DEPLOY` 且 `status=0` 的记录**。`DeploymentService.createAndTrigger`（`DeploymentService.java:245`）
   在事务里插这条记录并立即返回；之后 `TaskExecutor` 每秒轮询到它，抢占执行，才轮到 `DeployTaskHandler`。

   换句话说：**触发点是「数据库里多了一条排队任务」，不是「某段代码调了某方法」。** 这正是解耦架构的代价——
   链路在代码里不是一条直连的调用栈，而是"写库 + 后台轮询"。本平台所有模块文档的「调用链路」一节，
   都会把这条"断开又接上"的链路画清楚。

## 4. 顺着代码读的正确顺序（给第一次读代码的人）

不要从 `DeployTaskHandler` 往回找调用方——你会卡住。正确顺序：

1. **从前端入口读**：`lighit-deploy-ui/src/api/*.ts` 找你要跟的 api 函数（如 `createDeployment`）；
2. **到 Controller**：`src/main/java/com/lx/deploy/**/controller/*.java` 找对应 `@PostMapping`/`@PutMapping`，
   确认 URL 与方法，确认它只做"收参 + 调 Service"；
3. **到 Service**：看它落了哪些业务表、是否调了 `taskService.create(...)` 插异步任务；
4. **到 TaskExecutor**：确认任务类型，再看 §1.1 映射表找到对应 Handler；
5. **到 Handler**：`execute(task)` 里才是真正 SSH 连目标机干活的代码；
6. **回前端**：用返回的 `taskId` 调 `GET /taskLog/pull` 看实时进度。
