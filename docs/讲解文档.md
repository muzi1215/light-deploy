## 0. 一句话定位（开场必讲）

**Light Deploy 是面向中小企业的轻量化部署发布平台。把「手工 SSH 登录服务器、跑脚本发版」这件事，变成平台化、可审计、团队都能安全使用的操作。**

- 技术形态：Spring Boot 4 单体 + Vue3 前端，**通过 SSH/SFTP 纳管多台 Linux 目标服务器**，支持 **DOCKER / JAR / STATIC** 三种运行时的构建与发布。
- 解决的痛点：运维手动发版没有记录、容易误操作、无法回滚、凭据明文散落、多台机器并行发版靠人盯。
- 我的角色：个人独立开发的运维工具型项目，后端 Java + 前端 Vue 全程自己写。

> 🎯 追问「为什么不用 Jenkins / GitLab CI + Ansible？」
> 答：那两套偏企业级、学习/维护成本高，且 Ansible 仍要人写 playbook、Jenkins 流水线对非运维不友好。这个项目定位是「中小团队、轻量、页面点一点就发」，不重复造企业级 CI，而是把「构建产物 → 安全发布到目标机 → 回滚」这条最后一公里做成带审计和监控的闭环。构建还是交给 Git + Maven/Docker，平台只做编排与分发。

## 1. 整体架构与分层

```text
┌──────────────────────────────────────────────────────────────┐
│                      运维 浏览器                               │
│              Vue3 前端（Vite :9850 / Nginx 托管 dist）          │
└───────────────────────────────┬──────────────────────────────┘
                                │  HTTP  /api  →  :2027/deploy
                                ▼
┌──────────────────────────────────────────────────────────────┐
│              Light Deploy 平台（Spring Boot 单体）              │
│  Controller(DTO/VO) ─ Service(业务规则/加解密边界) ─ Mapper(MP)   │
│  任务执行器（轮询+并发令牌+互斥键）  凭据AES-GCM加密              │
│  构建机调度(BuildTaskHandler)    发布编排(DeployTaskHandler)     │
└───────┬───────────────────────────────────┬──────────────────┘
        │ SSH/SFTP                          │ HTTP（预留）
        ▼                                   ▼
┌──────────────────┐  ┌────────────────────┐  ┌─────────────────┐
│ 专用构建机        │  │ 6+ 台目标 Linux    │  │  AIops（告警联动）│
│ Maven/Docker 构建 │  │ 服务器（D/J/S 运行）│  │   v1 仅占位      │
└──────────────────┘  └────────────────────┘  └─────────────────┘
```

- **数据**：MySQL（业务表 + `lds_` 任务域表）+ Redis（任务状态/分布式锁/实时进度）。
- **远端能力全部收敛到一层**：`com.lx.deploy.ssh`（SSH 执行层），构建/发布/健康检查/回滚最终都走它，不各自写 SSH 代码。
- **长耗时操作全是异步任务**：连通性测试、构建、发布都建模成 `lds_task`，由任务执行器调度，页面用 `GET /taskLog/pull` 增量拉实时日志。

> 🎯 追问「为什么单体不拆微服务？」
> 答：按团队规模和阶段，单体最划算——部署简单、事务好做（构建记录+任务、部署记录+任务都靠本地事务同生共死）。微服务要满足团队≥10人+边界稳定+运维到位三条才上，当前明显不满足。架构服务于业务，不过度设计。

## 2. 核心领域模型（讲流程前先认对象）

| 概念 | 表 | 一句话 |
| --- | --- | --- |
| 服务器 server | `server` | 纳管的 Linux 机器（含 SSH 凭据密文、部署根目录、构建工作区） |
| 凭据 credential | `credential` | Git 令牌/私钥、镜像仓库密码，加密落库 |
| 镜像仓库 registry | `registry` | 镜像推送目标，**只服务 DOCKER 运行时** |
| 项目 project | `project` | 一个可部署的服务模块；含 runtime_type / source_type / build_mode |
| 环境 environment | `environment` | dev/test/prod，**全局共享**，不是项目私有 |
| 部署目标 pet* | `project_environment_target` | 项目×环境×服务器，**发布的唯一依据** |
| 发布版本 release | `release_record` | 构建成功自动生成「可发布」记录（镜像tag/产物路径/SHA256） |
| 任务 task | `lds_task` / `lds_task_log` | 异步任务生命周期 + 实时日志 |

**拓扑关键认知（必考）**：环境 ≠ 机器。发布选环境，平台拿 `(项目ID, 环境ID)` 去 `project_environment_target` 查「这个项目在该环境下绑了哪几台启用的服务器」，按策略裁剪后**快照**进 `deployment_target`。
- 同一环境同一服务器只能绑一次（唯一键）；主目标在一个项目环境内互斥。
- 环境只是全局逻辑环境，**不持有机器**；真正决定发哪台的是部署目标。
- 不要把每台机器各建一个环境——会割裂版本链、让防重失效、历史碎片化。

> 🎯 追问「为什么部署目标要快照而不是实时关联拓扑？」
> 答：部署记录必须忠实反映「当时发了哪些机器」。如果实时关联，后面改一次拓扑，历史部署的目标集就变了，回滚会发到错误的机器上。同理 `old_version`/`new_version`、`deploy_order` 都在创建部署时固化。

## 3. 核心流程一：构建（代码 → 可发布产物）

### 3.1 触发与异步

```
POST /build/create
  → 校验项目/运行时×构建模式/DOCKER必须绑registry
  → 解析构建机（请求指定 → 项目档案 build_server_id → 系统默认，皆空则拒）
  → 防重（同项目已有 排队/构建中 则拒）
  → @Transactional：落 build(status=0排队) + 生成 BUILD 异步任务   ← 同生共死
  → 立即返回 BuildVo(taskId/taskNo)
```

**为什么事务包住「记录+任务」**：任务建不起来时，构建记录也不能留下，否则出现「既没有日志、也不会被调度」的孤儿构建。

### 3.2 执行器在构建机上做什么（BuildTaskHandler）

```
1. 准备工作区：构建机 build_workspace_dir 下为本次构建建隔离目录（按 buildId 隔离）
2. 克隆代码：
   - HTTPS+GIT_TOKEN：令牌注入 URL 的【密码位】 https://oauth2:令牌@host/path
     （克隆后立刻 git remote set-url 复位，否则令牌写进 .git/config）
   - SSH+SSH_KEY：写临时私钥文件，GIT_SSH_COMMAND 指向它
   - 命令前加 GIT_TERMINAL_PROMPT=0（非交互会话，避免 git 转去索要密码被误报认证失败）
3. 按运行时构建：
   - DOCKER：Dockerfile 由【项目仓库提供】，平台不生成模板
   - JAR/STATIC：执行 build_config_json.build_command，定位产物
4. 产出与登记：DOCKER 推送取 digest；文件类算 sha256sum
   → completeSuccess：落 build_artifact + 自动生成 release_record（版本号一处定稿四处共用）
```

### 3.3 两个值得讲的工程细节

- **构建命令的非交互坑**：SSH 非交互会话不加载 `/etc/profile`，Maven 常在 PATH 里缺。平台先 `. /etc/profile` 再拼构建机档案的 `build_env_script`，并用**相同前缀**预检「命令首词是否可执行」（`command -v`/`test -x`），预检不通过直接判失败并给出三种处理方式，而不是只甩一句 `command not found`。
- **超时与进程组**：构建命令以 `setsid -w sh -c '...'` 启动，超时用 `kill -9 -PGID` 连 mvn 及其子进程一起杀掉（否则任务判失败、远端还在往即将被删的工作区写）。命中超时先终止进程组、落已收输出、再抛明确异常。
- **产物必须先转存到持久目录再清理工作区**：工作区任务收尾 `rm -rf`，若直接登记工作区路径，发布阶段会下载到一个已删除的路径（历史缺陷已修）。

> 🎯 追问「构建的版本号怎么生成、为什么重要？」
> 答：格式 `{项目编码}-v{序号}-{提交短码}`（如 `auth-7888-v3-887b603c`），**全项目只有一处**生成（`resolveReleaseVersion`，克隆拿到 commit 后定稿），被**四处共用**：① Docker 镜像 tag；② 构建机产物持久目录名；③ 产物目录内 `VERSION` 标识文件；④ `release_record.version`。四处一旦不一致，就会出现「版本列表有名字、镜像/产物目录却没有」，部署时才炸。序号用 `MAX(version_seq)+1` 且**不过滤软删除**，避免删了 v3 又新建出第二个 v3 撞唯一键；早期无序号时同 commit 重复构建会撞唯一键导致「构建记录成功、任务失败、版本列表没有它」的半成品状态。

### 3.4 五种构建模式（重点，逐一讲清楚）

| 模式 | 运行时 | 做法 |
| --- | --- | --- |
| `PROJECT_DOCKERFILE` | DOCKER | 用项目自带单个 Dockerfile 构建 |
| `LAYERED_DOCKER` | DOCKER | `Dockerfile.base + Dockerfile.app` 分层（基础镜像推仓库，业务镜像基于它） |
| `JAR_PREBUILD` | DOCKER | 平台先在构建机用 Maven 镜像打 jar，再用项目提供的极简 Dockerfile 包成镜像——**目标机只做纯 docker run，不用装工具链** |
| `SCRIPT_DEPLOY` | JAR/STATIC | 执行项目自带构建命令，产出 jar / 静态文件 |
| `ARTIFACT_ONLY` | JAR/STATIC | 不构建，只登记并发布**已存在的产物**（配合 `UPLOAD` 来源走页面上传链路） |

**运行时 × 模式矩阵**（规则唯一来源 `RuntimeType.supports`）：DOCKER 三种镜像模式；JAR/STATIC 两种文件模式。DOCKER 必须绑 `registry_id`，否则无处推镜像。

**`PLATFORM_TEMPLATE` 已整体下线**：早期平台猜测语言生成 Dockerfile，结果「能构建成功、运行即崩」，失败点离原因极远，所以砍掉——保留这条注记是为了解释历史代码与文档。

> 🎯 追问「JAR_PREBUILD 为什么单独做一种模式？」
> 答：很多 Java 项目不想在目标机装 Maven/JDK 工具链。这种模式下平台用 Maven 构建镜像在构建机把 jar 打出来，再用项目给的极简 Dockerfile（`FROM jre + COPY jar + COPY yml`）包成镜像推仓库，目标机零工具链只跑 `docker run`。前置是 `artifact_path`/`dockerfile_path` 必填、`settings_path` 选填（阿里云镜像加速）。

> 🎯 追问「ARTIFACT_ONLY 为什么不能发起构建任务？」
> 答：它本质是不构建、只登记版本，让它占构建机排队、跑到执行阶段才失败毫无意义，入口直接拦下提示走 `/build/upload`。上传的产物也必须落到**构建机**（不是平台本地），因为发布执行器下载产物强制要求 `release_record.build_server_id`，走的是两跳中转。

## 4. 核心流程二：分发 / 发布（版本 → 目标机上的运行实例）

### 4.1 入口与快照

```
POST /deployment/create（创建即快照）
  → 校验项目/环境/版本（release 必须「可发布」且属于该项目）
  → 选目标：selectByStrategy（策略覆盖优先，否则取环境默认）
  → resolveCurrentVersions：回溯该项目环境最近10次部署，成功取new_version、已回滚取old_version → 作为 old_version（回滚依据）
  → 快照 deployment_target（serverId/deployOrder/oldVersion/newVersion）
  → @Transactional：deployment + deployment_target + DEPLOY 任务 同生共死
```

**为什么"创建即快照"是硬约束**：早期没事务，目标表还没建好时插入失败、主记录却落库，留下一条永远不会有关联任务的孤儿部署，还会命中防重把后续发布全挡住。

### 4.2 批次编排（策略差异只在"失败后停不停"）

```
if (failedInBatch>0 && isRolling) { 中止剩余批次，未发的置「已跳过(5)」 }
```

- `SINGLE_TARGET`：只发主目标（无主目标取顺序最靠前的）一台。
- `ALL_AT_ONCE`：全部一批，不因单台失败中止（整体替换语义，中途停更混乱）。
- `ROLLING`：按 `batch_size` 切批，任一批失败即中止，剩余置「已跳过」。「已跳过」≠失败——表示这台本次没动过，回滚时排除。

**顺序来源**：`deploy_order` 在创建部署时从绑定表固化。绝不用 `create_time` 排（秒级 DATETIME 同一次插入并列，MySQL 不保证稳定顺序，会退化成随机主键序，表现为"配了顺序1却先发顺序2"）。

### 4.3 三运行时链路（发布动作各自独立）

`DeployTaskHandler` 只做编排，三种运行时各是一个独立 Service，统一 `deploy(DeployContext)`：

```java
switch (runtimeType) {
  case DOCKER  -> dockerDeployService.deploy(ctx);
  case JAR     -> jarDeployService.deploy(ctx);
  case STATIC  -> staticDeployService.deploy(ctx);
}
```

**拆开的原因**：三者入参、产物形态、回滚方式完全不同（JAR 备份单文件、STATIC 换整目录、DOCKER 不备份）。原先挤在一个 1600 行处理器里，改 Docker 容易误伤 JAR。

#### DOCKER
- RUN（默认）：`docker pull` → `docker rm -f {容器名}`（幂等关键，不删 run 直接失败）→ `docker run -d --restart=always` → `docker inspect` 确认 Running（把"启动即退出"挡在成功前）。
- COMPOSE：下发两个小文件——`docker-compose.yml`（构建期快照的**原文逐字节**，不经构建机中转）+ `.env.light-deploy`（只有一行 `IMAGE_TAG=本次tag`）。**版本号用变量注入而非替换占位符**，运维上机看到的文件与仓库逐字一致；缺 `${IMAGE_TAG}` 占位符在构建期与发布期各校验一次，命中即报错（否则容器永远拉同一个 tag，发布报成功线上没变，最难发现）。平台不代目标机 `docker login`（由运维预置）。

#### JAR（固定工作目录 + 原地替换）
首次部署：上传内置 `jar-init.py/jar-update.py/jar-fallback.py` 并执行初始化（建 `logs/exec/exec-bak/config` 目录、写 systemd 单元、注册 `--spring.config.location`）。之后每次发版固定时序：
```
备份旧jar到 exec/bak（备份名内嵌被换包的版本号）
→ 投放新jar（先传 .uploading 再 mv -f 覆盖）
→ 复核 SHA256（不符先还原备份再抛异常）
→ 写 VERSION + 刷 exec/deploy.conf 的 version=
→ systemctl restart → is-active 确认
```
**时序不可乱**：校验与写标识都在 `restart` 之前（此刻发现损坏可无损还原；标识晚于重启会停留"磁盘新版本+标识旧版本"错位）。**systemd 单元只首次生成、不再重写**（尊重运维手工调过的 `-Xmx` 等）。**版本号内嵌在备份文件名**（`auth-tool_bak_20260925..._auth-7888-v6-xxx.jar`），`-`与`_`混用是有意的（`_`分隔结构段、`-`属于版本号本身）。

#### STATIC（只换目录内容，绝不换目录）
`static_root` 是 nginx 的 `root`，平台只替换它**里面的文件**。
```
构建机必要时 tar -czf 打包 → 下载到平台临时文件 → SFTP 上传目标机 /tmp
→ 解压到旁路暂存 static-new-{时间戳} → 剥壳/非空校验
→ 把 static_root 内条目整体搬进 backupDir（MOVE_CONTENTS，目录本身不动）
→ 把暂存目录条目搬进 static_root → rmdir 暂存 + 记 inode 前后值
```
**为什么不换目录**：`static_root` 常作 Docker bind mount 源，而 bind mount 是容器启动时按路径解析一次并绑定 inode，目录被 rename 走后容器仍握旧 inode → 容器内空目录 → nginx 全站 403，且 `nginx -s reload` 无效（reload 不重新挂载），只能重建容器。代价是切换有极短目录为空窗口，但"瞬时404自愈"远优于"容器失效挂载必须重建"。**不执行 nginx reload**（平台不碰 nginx 配置，且 nginx 未必由目标机那个二进制跑）。**产物为空必须中止**（内容替换语义下空包=站点被清空却报成功）。

### 4.4 两跳中转模型（高频）

**文件类运行时（JAR/STATIC）走"构建机 → 平台 → 目标机"两跳，不做服务器间直传。**

```
构建机 {build_artifact_dir}/{项目}/{版本}/xxx.jar|dist
   │ ① SFTP get（sftpDownload）
   ▼
平台本地临时文件 /tmp/ld-deploy-{部署ID}-{文件名}   ← 由调用方 finally 清理
   │ ③ 投放：JAR 走 exec 流式管道（cat > 文件），异常回落 SFTP；STATIC 走 SFTP
   ▼
目标机 {workDir} / {static_root}
```

**为什么中转不给目标机直连构建机**：目标机不需要持有构建机免密；网络与凭据收敛在平台侧（跨机房/VPC 场景尤其重要）。代价是多一跳带宽、平台本地磁盘峰值 = 单产物 × 并发目标数。

**传输层抉择**：JAR 大文件先试流式管道（`cat > 远端`），抛异常回落 SFTP（个别加固机器禁 exec 写 stdin）；流式管道由 TCP 自流控，高延迟链路上远快于逐包确认的 SFTP（实测 74MB SFTP 要 325s，管道约 18s）。**每一步先临时名后 `mv`**，中途失败不在服务目录留半截产物。

> 🎯 追问「平台本地临时文件会不会泄露凭据/产物？」
> 答：临时文件只在单个目标生命周期内存在，finally 里 `deleteQuietly` 清理；远程输出统一 `maskSecrets` 脱敏后才进日志；凭据只在 SSH 层建连前解密、不缓存不进日志。产物临时文件是构建机上的 jar/dist，不含明文凭据。

### 4.5 健康检查：不健康就是失败

默认在**目标机本地**探测（`probe_from=TARGET`）：平台 SSH 到目标机，TCP 用 `ss -lntn`、HTTP 用 python3 请求 127.0.0.1。理由——平台连业务端口不通只能证明链路不通，无法区分"应用没起/只监听127.0.0.1/防火墙"，**在本机探测才直接回答"服务到底起没起"**。默认 3 次、间隔 3s。发布动作成功但健康检查不通过 → 目标判失败（"发布成功但服务起不来"对用户就是失败）。JAR 无论成败都额外输出 systemd 状态留证。

## 5. 核心流程三：回滚

### 5.1 入口先判定能不能回滚（evaluateRollback）

发布与回滚**共用同一个 `DeployContext` 和 `deploy()`**，靠 `deployment.status == ROLLING_BACK` 区分方向。但入口先判定（按优先级给唯一原因）：

| 档位 | 条件 | 文案 |
| --- | --- | --- |
| ① | 状态不是"成功" | 只有发布成功的部署允许回滚 |
| ② | 变更过的目标全无 `old_version` | 首次发布，机器上没有平台纳管的历史版本 |
| ③ | 有 `old_version` 但版本记录查不到，或 JAR/STATIC 缺 `build_server_id`/`artifact_path`、DOCKER 缺 `image_tag` | 历史版本产物已不存在 |

**不可回滚直接拒绝，禁止静默成功**：早期做法是"一个目标都回滚不了就直接置已回滚"，用户看到"已回滚"机器上一个字节没变。现在改为抛异常 + 前端置灰。

### 5.2 版本方向集中换算（防错位的关键）

发布与回滚方向在 `DeployContext` 两个方法集中，运行时 Service 一律取用，不再自行判断 `rollingBack`：
```java
targetVersion()  // 本次要写到磁盘的：发布=new_version，回滚=old_version
currentVersion() // 正被换掉的（仅备份命名用）：发布=old_version，回滚=new_version
```
构造时做一次对齐校验：目标快照版本与 `release_record.version` 不一致直接抛"版本记录与部署快照不一致"。（干净数据上恒真，是防历史脏数据/人工改库的数据一致性断言。）

### 5.3 三种运行时的回滚差异

| 运行时 | 回滚产物从哪来 | 是否读本机备份 | 网络依赖 |
| --- | --- | --- | --- |
| DOCKER | 镜像仓库，按 `old_version` 的 `image_tag` 重新 pull | 无本机备份 | 仓库可达即可 |
| JAR | **构建机，100%**（与发布走一模一样的两跳） | **否**（平台不用，仅运维上机手工救） | 平台↔构建机、平台↔目标机 |
| STATIC | **先查目标机 static-bak，命中 `cp -a` 快路径；未命中回落构建机** | **是** | 命中时只需平台↔目标机 |

**核心认知**：能否回滚由 `release_record` + 入口判定单点决定；本机备份只决定"多快回滚"和"平台不可用时运维能不能手工救"。JAR 回滚 100% 走构建机 → 本机 `exec/bak` 清到 0 份照样成功；STATIC 本机备份清空也只是从秒级退化为分钟级。反过来，本机备份留再多也救不了一个 `release_record` 不可用的版本（入口早拦下）。

### 5.4 回滚日志必须能独立交代（六要素）

开始回滚+开始时间、参与范围、当前版本→回滚到什么版本、时间写进正文、回滚成功/失败、是否启动成功。失败时部署记录与任务同时失败，禁止"日志说失败、任务说成功"。

> 🎯 追问「为什么没有一键重新发布？」
> 答：部署记录被设计成"一次执行的不可变快照"，目标列表/版本/顺序创建时固化。在原记录上重跑会覆盖首次执行结论、让 `old_version=new_version` 使回滚语义失效、让当前版本推断自指。正确形态是"以原记录为模板复制出新部署"——新建 deployment + 复制目标快照 + 新 DEPLOY 任务，旧记录一字不动。而重发同版本现在就能做：新建部署时版本下拉选任意历史版本即可。

## 6. 异步任务调度（平台怎么"不阻塞地"跑构建/发布）

### 6.1 模型

- `lds_task`（任务）：task_no 唯一、`task_type`（SERVER_TEST/BUILD/DEPLOY…）、`biz_id`（关联业务主键）、`status`（0排队/1执行中/2成功/3失败/4取消）、`current_stage`/`progress`/`error_message`。
- `lds_task_log`（日志）：`sequence_no`（服务端 max+1 分配，单调递增，唯一键保证连续）、`stage`/`level`/`content`。

### 6.2 执行器调度（TaskExecutor）

```
定时轮询（poll-interval-ms 默认 1000）
  → listQueued 按 create_time 升序取排队中
  → 取并发令牌（Semaphore = pool-size 默认 6）  ← 池内不堆排队任务
  → 按 lockKey 抢占互斥键（busyLockKeys）      ← 同服务器同时只跑一个任务
  → 提交线程池 → markRunning（带 status=0 条件的原子更新，抢不到就跳过）
  → handler.execute → 正常返回=成功 / 抛异常=失败
  → finally：markSuccess/markFailed + 释放互斥键与令牌
```

**关键设计点**：
1. **领取是原子抢占**：`update ... eq(status,QUEUED).set(status,RUNNING)`，影响行数 0 区分"不存在/状态冲突"。
2. **三重去重**：内存 `submittedTaskIds` + `busyLockKeys` 服务器级互斥 + 数据库条件更新兜底（为将来多实例预留）。
3. **并发上限=6**：对应"至少纳管6台服务器、不同服务器可并行"的规模基线；先取令牌再提交，线程池不堆积等待。
4. **重启收敛僵尸任务**：进程重启后停在"执行中"的任务不可能续跑，启动把残留执行中任务统一标失败（"平台重启导致中断，请重提"）。
5. **日志写入失败只 WARN**：日志是留痕，不能成为任务失败原因。
6. **失败结论必须与业务记录一致**：处理器表达失败的唯一方式是抛异常；禁止"写ERROR却正常返回"——否则任务管理显示成功、日志末尾却夹着 ERROR。

### 6.3 实时日志增量拉取

```
GET /taskLog/pull?taskId=&lastSeq=&limit=200
→ { status, finished, currentStage, progress, errorMessage, logs[], lastSeq }
```
锚点用 `sequence_no`（主键是 UUID 不单调）。**停止条件**：`finished === true` 且本批条数 `< limit`（满页说明还有剩余，必须再拉一次把尾部取完）。

> 🎯 追问「为什么任务处理器不直接写业务状态，而靠执行器回调？」
> 答：状态流转收口在 Service（markDeploying/markTargetSuccess…），执行器只回调。单目标异常被捕获落为"目标失败"不冒泡中断其余目标，但所有批次跑完按汇总收敛——只要存在失败目标，部署记录与任务同时置失败，任务状态是运维盯结果的第一入口，不能和部署记录给两个结论。

## 7. 安全设计（常问）

- **凭据 AES-GCM 加密落库**：`server.ciphertext` 只写不读；`SshSessionFactory` 是明文唯一出现点——建连前才 `CredentialCrypto.decrypt`，认证完不再持有明文引用，不缓存、不进日志、不进异常消息。AES key 只通过环境变量 `LIGHT_DEPLOY_AES_KEY` 注入，**绝不提交 Git**。
- **输出脱敏**：所有远程输出返回前统一 `maskSecrets`（`https://***@` 等），异常消息不含凭据。
- **Git 令牌注入密码位**：`https://oauth2:令牌@host`，克隆后立刻 `git remote set-url` 复位（否则令牌写进 `.git/config`）；命令前 `GIT_TERMINAL_PROMPT=0` 防非交互会话被误报认证失败。
- **已知安全债（诚实交代）**：① SSH **未做主机密钥校验**（SSHD 默认放行，内网可信可接受，公网需补 `ServerKeyVerifier`）；② 私钥只支持**未加密**的 OpenSSH/PKCS#8，带口令的会明确提示；③ 健康检查默认从目标机本地发起，平台自身不需访问业务端口。

> 🎯 追问「凭据明文会不会出现在日志/响应里？」
> 答：不会。DTO 只有明文入参、VO 不声明密文字段；密文只在 SSH 层执行前短暂解密；远程输出经 `maskSecrets` 脱敏；`build`/`deployment` 的业务状态也只能由 Service 流转方法维护，普通更新接口改不了。

## 8. 版本保留策略（细节加分项）

- `project.retain_release_count`（默认 5）：构建成功收尾时触发 `applyRetentionPolicy`，**先删磁盘产物、再置记录废弃**（顺序反了会"记录不可见、磁盘还占着"）。
- **按版本自己的构建机删**：产物是磁盘文件，只在当初那台机器上，回收时逐条读 `release.build_server_id` 按需新开 SSH。
- **两条安全边界**：① 保护窗口——最近 20 次部署引用过的版本一律不回收（回滚按 old_version 重新发布，清掉会让回滚与新发同时断）；② 路径白名单——待删目录只能由"构建机产物目录/项目编码/版本号"三段拼成，版本号匹配 `[A-Za-z0-9._-]` 防路径穿越。
- **DOCKER 版本不进配额**：镜像在仓库，构建不落文件，`artifactDir()` 恒 null，只置废弃不删字节；若让不占磁盘的版本占名额，会把文件类版本提前挤掉（配额过滤放 Java 侧、不写进 SQL，避免 `runtime_type` 为 NULL 三值逻辑漏行）。
- **本机备份（exec/bak、static-bak）不受 `retain_release_count` 管理**，有独立 `scripts/cleanup-bak.sh`（份数+天数双上限，强制保留最近1份，默认 dry-run）。

## 10. 高频追问速答

**Q：你这个项目最大的技术难点是什么？**
A：三运行时三种发布链路的状态一致性。发布与回滚共用同一批代码，方向靠 `rollingBack` 标志切换，版本号"要写上去的/被换掉的"在两端相反，一旦散落多处算错不会报错、只会在回滚时才暴露退不到想要的版本——所以我把换算集中到 `DeployContext` 两个方法，并做了快照对齐断言。另一个是 STATIC 的 bind mount inode 陷阱（换目录导致容器全站 403），最后定死"只换内容不换目录"的硬约束。

**Q：为什么不用 k8s / 容器编排平台？**
A：定位是中小企业轻量场景，目标机很多是单机 Docker 或裸机 systemd，引入 k8s 运维成本远超收益。平台对 DOCKER 同时支持 `docker run` 和 `docker compose` 两种形态，覆盖单容器到多容器编排，不绑定特定编排平台。

**Q：构建机和发布机之间怎么保证产物一致性？**
A：产物在构建机转存到持久目录（工作区会 rm-rf，必须先转存），发布时按 `artifact_path` 下载并**复核 SHA256**；JAR 还做"目标机已是本次包则跳过备份与上传"。版本号一处定稿四处共用，镜像 tag/产物目录/VERSION/版本记录保持字面一致。

**Q：如果构建机挂了，已发布的版本还能回滚吗？**
A：分运行时。DOCKER 回滚只依赖镜像仓库，不受影响；JAR 回滚 100% 走构建机，构建机不可达或产物被保留策略回收 → 无法回滚（与目标机留多少备份无关）；STATIC 本机 `static-bak` 命中快路径则秒级回滚、未命中才回落构建机。

**Q：你一个人做的？怎么保证质量？**
A：是。靠几条硬纪律：修改 Java 后必跑 `mvn -o -q -DskipTests compile`；每个模块交付同步中文模块文档（docs/ 下，与代码同批）；状态字段统一 TINYINT 数字编码 + 常量类，禁止枚举/字符串表达状态；核心流程（构建/分发/回滚）都有详尽的设计文档和事故修复记录（如 inode 陷阱、版本方向取反、孤儿部署事务）。
