# 平台不可用应急手册

> **底线**：服务可用性高于平台功能完整。平台不可用时，运维必须能凭目标机现场已有的少量素材，用命令把服务救回来，**不依赖平台、不依赖构建机回连、不需要源码**。
> 本文按运行时与部署形态给出命令级步骤。平台恢复后，凡手工动过目标机的，**必须补一次新建部署重发对齐**（平台记录与线上状态脱节）。

---

## 1. 30 秒判断：你面对的是哪一类

| 运行时 / 形态 | 目标机现场素材 | 自救入口 | 本手册章节 |
| --- | --- | --- | --- |
| DOCKER + `JAR_PREBUILD`（B1）· COMPOSE | `<work_dir>/build-context/`：`<产物名>.jar`（如 `auth-tool.jar`）、`Dockerfile.hotfix`、`docker-compose.hotfix.yml`、`config/`、`README.md` | §2 | 两条命令 `up -d --build` |
| DOCKER + `JAR_PREBUILD`（B1）· RUN | 同上（无 compose 文件） | §2.3 | `docker build` + `docker run` |
| DOCKER + `PROJECT_DOCKERFILE` / `LAYERED_DOCKER` | `<work_dir>/build-context/`：源码 + Dockerfile | §3 | `docker build` 后 `compose up` |
| JAR（systemd） | `{workDir}`：`auth-tool.jar`、`VERSION`、`config/`、`exec/bak/` 备份 | §4 | `cp` 备份 → `systemctl restart` |
| STATIC（Nginx） | `{static_root}`、同级 `static-bak/` 备份 | §5 | `cp -a` 还原内容 |

> 判断依据：登录目标机看 `<work_dir>/build-context/` 是否存在，以及目录里是 `<产物名>.jar`（B1，名字沿用项目产物，如 `auth-tool.jar`）还是源码（标准 DOCKER）。

## 2. DOCKER + JAR_PREBUILD（B1）——重点

平台每次发布都会把「热修包」下发到目标机 `<work_dir>/build-context/`，平铺结构：

```text
build-context/
├── auth-tool.jar            # 本次版本已构建好的 jar，名字沿用项目产物原名
├── Dockerfile.hotfix        # 平铺上下文（COPY *.jar），项目提供
├── docker-compose.hotfix.yml# 热修编排，项目提供（RUN 形态可能没有）
├── config/application.yml   # 配置，通过目录挂载生效
└── README.md                # 命令级指引（平台生成）
```

### 2.1 一键（推荐）

```bash
cd <work_dir>/build-context
docker compose -p <项目编码> -f docker-compose.hotfix.yml up -d --build
```

- `-p <项目编码>` 必须与平台发布时一致（否则会叠出第二套栈）。项目编码见版本号前缀，如 `auth-tool-v7-cf2434d5` → `auth-tool`。
- `--build` 会用 `Dockerfile.hotfix` + 目录里的那个 jar 就地构建镜像，**不访问镜像仓库、不访问平台**。

### 2.2 分两步（便于单独看构建日志）

```bash
docker build -f Dockerfile.hotfix -t <项目编码>:hotfix .
docker compose -p <项目编码> -f docker-compose.hotfix.yml up -d
```

### 2.3 RUN 形态（项目未提供 hotfix compose）

```bash
docker build -f Dockerfile.hotfix -t <项目编码>:hotfix .
# 先取旧容器的端口/挂载/环境变量，照抄即可
docker inspect <容器名> --format '{{json .HostConfig.PortBindings}} {{json .Mounts}} {{json .Config.Env}}'
docker rm -f <容器名>
docker run -d --restart=always --name <容器名> <按上面结果的端口/挂载参数> <项目编码>:hotfix
```

### 2.4 改配置

配置走 `./config` 目录挂载（`docker-compose.hotfix.yml` 里 `./config:/app/config:z`），**改完执行**：

```bash
docker compose -p <项目编码> -f docker-compose.hotfix.yml restart
```

> `<work_dir>/config/`（正常发布时 compose 挂载的那份）由平台在首次发布时投放配置初稿，
> **已存在则不覆盖**。平台不可用时直接改这个目录里的文件再 `up -d` 即可，与 `build-context/config/`
> 是两份互不影响的位置：前者给正在跑的容器用，后者给热修重建用。

> Spring 只在启动时读配置，`restart` 才生效。
> `:z` 是 SELinux 标签；CentOS 上漏了会出现「挂载不生效但容器照常启动」的静默错配（跑的是 jar 内默认配置）。

### 2.5 只换 jar（开发给你一个新包）

不用重新下发素材，把新 jar 覆盖进 `build-context/` 再重建即可：

```bash
cd <work_dir>/build-context
ls *.jar                        # 先确认目录里只有一个 jar，记住它的名字（如 auth-tool.jar）
mkdir -p bak && mv auth-tool.jar bak/auth-tool.jar.$(date +%Y%m%d%H%M%S)   # 旧包挪出当前目录
cp /path/to/new.jar ./auth-tool.jar                                        # 新包必须沿用原文件名
docker compose -p <项目编码> -f docker-compose.hotfix.yml up -d --build
```

> **文件名必须与原来一致**：`Dockerfile.hotfix` 用 `COPY *.jar` 定位 jar，一个目录里出现两个 `.jar`
> 会让 `docker build` 直接报 `more than one source file`——这是故意的，宁可报错也不要悄悄打进旧包。
> 旧的包挪到 `bak/` 子目录（或改成非 `.jar` 后缀），不要留在当前目录旁边。

### 2.6 镜像仓库可用时的等价做法（更贴近平台原路径）

若只是平台挂了、镜像仓库仍可用，也可以不动本地构建，直接产镜像再拉起：

```bash
docker build -f Dockerfile.hotfix -t <仓库>/<镜像名>:hotfix-YYYYMMDD .
docker push <仓库>/<镜像名>:hotfix-YYYYMMDD
# 目标机
IMAGE_TAG=<仓库>/<镜像名>:hotfix-YYYYMMDD docker compose -p <项目编码> -f docker-compose.hotfix.yml up -d
```

### 2.7 前提与缺口

- 项目必须在 `dockerfile_path` 同目录提供 `Dockerfile.hotfix`；**没有该文件时平台不下发热修包**（构建日志会写明），此时只能走 §2.6 或让开发补文件。
- 基础镜像 `eclipse-temurin:8-jre` 需目标机本地已有或可拉取；离线环境请提前 `docker save/load`。
- 手工构建的镜像 tag（`<项目编码>:hotfix`）平台不认识；平台恢复后必须补一次正规部署对齐。

## 3. DOCKER 源码构建（PROJECT_DOCKERFILE / LAYERED_DOCKER）

这类项目的 `build-context/` 里是**源码 + Dockerfile**（标准 DOCKER 且配置了 `work_dir` 时下发）：

```bash
cd <work_dir>/build-context
docker build -f <dockerfile 相对路径> -t <项目编码>:hotfix .
docker compose -p <项目编码> -f <work_dir>/docker-compose.yml up -d
# 或按原有 docker run 参数重跑
```

> 注意：源码上下文体积大（几十 MB 起），且目标机需要有构建能力（基础镜像、磁盘）。这也是 B1 改发「jar 热修包」的原因。

### 3.1 LAYERED_DOCKER 的稳定基础镜像（重点）

分层构建的基础层一旦构建并推送后，长期留在镜像仓库、tag 固定为 `{仓库}/{镜像名}:base`（**不随版本号变化**）。
绝大多数发布只重建应用层、复用这个稳定 base——所以纯手工重建应用镜像时，**不用再构建基础层**：

```bash
docker pull <仓库>/<镜像名>:base                    # 稳定基础镜像，从仓库拉（或目标机本地已有）
docker pull <仓库>/<镜像名>:<版本号>                 # 若只是要回退/重拉某个已发布的应用镜像，直接拉它即可
# 必须就地重建应用镜像时（如改了应用层源码）：
cd <work_dir>/build-context
docker build -f <dockerfile 相对路径> --build-arg BASE_IMAGE=<仓库>/<镜像名>:base -t <仓库>/<镜像名>:<版本号> .
docker compose -p <项目编码> -f <work_dir>/docker-compose.yml --env-file <work_dir>/.env.light-deploy up -d
```

> 要点：
> - `BASE_IMAGE` 必须指向**稳定 base 的完整引用**（含仓库地址，如 `registry.cn-hangzhou.aliyuncs.com/lx_relife/aiops-platform:base`），
>   与平台构建期一致；不要写成版本化的 base tag（平台已不再使用 `base-<版本号>` 这种写法）。
> - 若仓库里**还没有** `:base`（首次使用前没勾选过「重新构建基础镜像」），先按 §9.4 或平台跑一次带「重建基础镜像」的构建创建它；
>   否则 `docker build` 会因 `FROM $BASE_IMAGE` 拉不到而失败。
> - 基础层极少变化，本地 `docker pull :base` 一次后基本长期复用，离线目标机请提前 `docker save/load`。

## 4. JAR（systemd 原地替换）

现场素材：`{workDir}/auth-tool.jar`、`VERSION`、`config/`、`exec/bak/` 历史备份（文件名含被替换包的版本号）。

### 4.1 回退到上一版（最快）

```bash
cd <workDir>/exec/bak
ls -1t *              # 看文件名里的 14 位时间戳，判断最新备份（不要只看 ls -l 的 mtime，cp -p 会保留源时间）
cp -p <备份jar> ../../auth-tool.jar
cd ../..
systemctl restart <服务名>
systemctl is-active <服务名>
```

### 4.2 手工投放新 jar

```bash
cp /tmp/new.jar <workDir>/auth-tool.jar
sha256sum <workDir>/auth-tool.jar          # 与开发给的摘要比对
echo "<版本号>" > <workDir>/VERSION
sed -i "s/^version=.*/version=<版本号>/" <workDir>/exec/deploy.conf
systemctl restart <服务名>
systemctl is-active <服务名>
```

> 手工换包后平台状态脱节，恢复后补一次新建部署重发。

## 5. STATIC（Nginx 只换内容，绝不换目录）

现场素材：`{static_root}` 当前内容、同级 `static-bak/` 下历史备份目录。

```bash
# 1) 备份当前内容（目录内条目，目录本身不动）
cd <static_root> && mkdir -p <备份目录>/手动_$(date +%Y%m%d%H%M%S)
mv * .[!.]* ..?* <备份目录>/手动_$(date +%Y%m%d%H%M%S)/ 2>/dev/null

# 2) 新内容就位（从解压目录搬条目，不要 mv 整个 static_root）
cp -a /tmp/new-dist/. <static_root>/

# 3) 校验
ls <static_root>/index.html
```

**红线**：不要 `rm -rf` 或 `mv` 掉 `static_root` 本身。容器 bind mount 按 inode 绑定，目录被换掉会导致容器内看到空目录、全站 403，`nginx -s reload` 无效，只能重建容器。
**不要执行 `nginx -s reload`**：内容替换后即时生效；reload 失败会把「文件已替换」误判成发布失败。

---

## 6. 平台恢复后对齐

1. 目标是手工改过的，**补一次新建部署**（不要原地重跑，部署记录不可重跑）；
2. 核对 `deployment.status`、`release_record` 与线上镜像/文件是否一致；
3. 若手工构建过镜像，正规部署会重新 `pull` 仓库镜像并覆盖，完成对齐。

## 7. 自检清单（每季度确认一次）

| 检查项 | 期望 |
| --- | --- |
| B1 项目目标机 `<work_dir>/build-context/` | 存在 `<产物名>.jar`（如 `auth-tool.jar`）+ `Dockerfile.hotfix` + `README.md`，且该 jar 可 `sha256sum`；**目录内只能有一个 `.jar`** |
| B1 项目仓库 | `Dockerfile.hotfix` 已提交；`docker-compose.hotfix.yml` 已提交（COMPOSE 形态） |

| JAR 项目 `exec/bak/` | 至少有 1 份可回退备份 |
| STATIC 项目 `static-bak/` | 至少有 1 份可回退备份，且位于 web 根之外 |
| 运维手上 | 本手册 + 各项目 `work_dir` / 服务名 / 容器名清单 |

## 8. 已知边界

- **B1 热修包依赖项目提供 `Dockerfile.hotfix`**：未提供时平台跳过下发（日志明确记录），该版本无现场重建素材。
- **热修包随版本保留策略清理**：`retain_release_count` 回收版本时会连带删除构建机上的包，但**目标机已下发的副本不受影响**，仍可自救。
- **RUN 形态无 compose**：只能用 §2.3 的 `docker run`，参数需从旧容器 `docker inspect` 取。
- **配置挂载的静默回落**：`./config` 缺失或被 SELinux 拦截时，容器会用 jar 内默认配置启动，healthcheck 仍可能通过——务必确认 `docker inspect` 的 Mounts 与启动日志里的配置来源。

## 9. 目标机日常管理（COMPOSE 标准形态：平台下发的 docker-compose.yml）

平台按 COMPOSE 形态发布时，会在目标机 `<work_dir>/` 下写出两份文件：

```text
<work_dir>/
├── docker-compose.yml      # 项目自带 compose 原样下发（含 build: 段，来自仓库「一份两用」文件）
└── .env.light-deploy       # 平台生成的版本变量，注入 IMAGE_TAG=仓库地址:版本号
```

这份 compose **完全可以在目标机做容器管理、重启、看日志、停服**，与「平台发布 / 构建」不冲突。唯一要当心的只有 `build` / `up -d` 这两条会触发构建的命令。

### 9.1 日常改配置重启（最常见，不构建）

配置走 bind mount（compose 里 `./config:/app/config`，镜像不烘配置）。改了宿主机 `./config/application.yml` 后，**不用重建镜像**，重启容器进程让它重读配置即可：

```bash
docker restart <容器名>          # 最简单；容器名见 compose 的 container_name（auth-tool 即 auth-tool）
# 等价写法（显式带项目名，不影响，也不会构建）：
docker compose -p <项目编码> -f <work_dir>/docker-compose.yml --env-file <work_dir>/.env.light-deploy restart
```

> `restart` / `stop` / `start` / `logs` / `ps` / `down` 这些管理命令**都不碰 build**，compose 里的 `build:` 段对它们无影响。直接 `docker restart <容器名>` 即可，无需 `--env-file`、无需 `up -d`。Spring 只在启动时读配置，`restart` 才生效。

### 9.2 看日志 / 查状态

```bash
docker ps | grep <项目编码>                    # 确认容器在跑、IMAGE 是期望版本
docker logs -f <容器名>                        # 跟踪日志
docker compose -p <项目编码> -f <work_dir>/docker-compose.yml --env-file <work_dir>/.env.light-deploy logs -f
```

### 9.3 ⚠️ 坑：不要敲「裸 up -d」

**错误示范**：

```bash
docker compose -f docker-compose.yml up -d     # 没带 --env-file
```

compose 里 `image: ${IMAGE_TAG:-auth-tool:dev}`——不带 `--env-file` 时 `IMAGE_TAG` 为空，镜像名退化成 `auth-tool:dev`，本地根本没有这个镜像 → Docker 一看镜像缺失、又有 `build:` 段 → 转去**构建** → 构建上下文（仓库「一份两用」compose 的 `../..`，或手改的绝对路径如 `/lx/auth-tool`）在目标机上不存在 → 报错：

```text
! auth-tool Warning Get "https://registry-1.docker.io/v2/": context deadline exceeded              # 非致命：阿里云机器常连不上 Docker Hub
docker-container:multiarch-builder resolve : lstat /lx/auth-tool: no such file or directory        # 致命：build 上下文不存在
```

平台自己跑的是 `docker compose -p <项目编码> -f <work_dir>/docker-compose.yml --env-file <work_dir>/.env.light-deploy up -d`：`.env` 把 `IMAGE_TAG` 指到**已经 pull 下来的仓库镜像**，镜像在本地，`up -d` 不触发 build。

### 9.4 需要（重新）拉起整个服务时

用平台那套带 `--env-file` 的完整命令（镜像名正确 → 先 pull 已存在的仓库镜像 → 不再 build）：

```bash
docker compose -p <项目编码> -f <work_dir>/docker-compose.yml --env-file <work_dir>/.env.light-deploy up -d
```

> 只有「想重建镜像」才用 build（如 §2 B1 的 `up -d --build`、§3 的 `docker build` 后再 `up -d`）。目标机日常运维一律走 9.1 / 9.2 的管理命令，避免误触构建。

### 9.5 防呆（可选）

若担心手滑敲裸 `up -d`，可在目标机另存一份**去掉 `build:` 段**的「管理专用 compose」（只留 `image:` + 容器配置），日常用那份 `restart` / `up -d`；应急重建仍用 `<work_dir>/build-context/` 里的素材。非必须。
