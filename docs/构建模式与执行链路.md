# 构建模式与执行链路

> 适用范围：Light Deploy 全部构建/发布链路。  
> 权威来源：后端 `com.lx.deploy.common.enums.project.BuildMode`（模式清单）、  
> `RuntimeType.supportedBuildModes()`（合法组合）、前端 `constants/projectConfig.ts` 的  
> `BUILD_MODE_OPTIONS`（页面清单）。本文档只做解释与索引，**不新增规则**。  
> 最后更新：2026-10-31（§2 扩充为「运行时 vs 构建模式」完整概念澄清；新增 §5–§7，源自 auth-tool v9 构建失败事故）。
>
> **第一次读这份文档，请从 §2 开始**：它解释「运行时」与「构建模式」是两个阶段的两把开关。  
> 跳过这一节直接看 §1 的 5 种模式，很容易误以为「Java 项目都必须用 JAR 预构建」。

---

## 1. 一页结论

现在一共 **5 种构建模式**，全部由平台唯一的分支点 `BuildTaskHandler.execute()`（约 358–440 行）  
按「运行时 + 构建模式」两把开关分发。

> 下表列的是**构建模式**（产物怎么来）。**运行时**（产物怎么跑）只有 3 个：  
> `DOCKER` / `JAR` / `STATIC`。两者不是一回事，区别见 §2。

| # | 构建模式                 | 平台做什么                                          | 产物             | 目标机怎么发                                      | 代码入口                  |
| - | -------------------- | ---------------------------------------------- | -------------- | ------------------------------------------- | --------------------- |
| 1 | `PROJECT_DOCKERFILE` | **不做任何预先构建**，直接 `docker build -f <dockerfile>` | 镜像             | `docker pull` + `compose up` / `docker run` | `buildDocker()`       |
| 2 | `LAYERED_DOCKER`     | 同上，但拆两跳：先建 base 层并推送，再基于它建应用层                  | 镜像（含 base 镜像）  | 同上                                          | `buildDocker()` 分层分支  |
| 3 | `JAR_PREBUILD`       | **平台先跑 Maven 打 jar**，再交给极简 Dockerfile 包镜像      | 镜像 + jar + 热修包 | 同上                                          | `buildJarPrebuild()`  |
| 4 | `SCRIPT_DEPLOY`      | 在构建机执行项目自带构建命令（不产出镜像）                          | jar / 静态目录     | JAR：systemd 原地替换；STATIC：目录内容替换              | `buildFileArtifact()` |
| 5 | `ARTIFACT_ONLY`      | **什么都不做**，产物由页面直接上传                            | jar / 压缩包      | 同 `SCRIPT_DEPLOY`                           | 入口直接拒绝构建（见 §3.5）      |

一句话记忆：**前三种产物是镜像（过 registry），后两种产物是文件（不过 registry）。**

## 2. 运行时与构建模式：先分清这两件事

> 这一节是整篇的地基。搞混这两个概念，后面所有判断都会错——包括 2026-10-31 那次    
> 「auth-tool 构建失败」和「为什么页面上从来看不到 JAR 预构建」。

### 2.1 各自回答什么问题

|          | 运行时 `RuntimeType`      | 构建模式 `BuildMode`     |
| -------- | ---------------------- | -------------------- |
| **回答**   | 产物到了目标机，**怎么跑起来**      | 这次要用的产物，**怎么来**      |
| **决定**   | 发布阶段的动作                | 构建阶段的动作              |
| **取值**   | 3 个                    | 5 个                  |
| **存放**   | `project.runtime_type` | `project.build_mode` |
| **权威定义** | `RuntimeType` 枚举       | `BuildMode` 枚举       |

一条发布链路是**两段流水线**：

```text
构建机 ──[构建阶段]──► 产物 ──[发布阶段]──► 目标机
            ↑构建模式决定            ↑运行时决定
```

**运行时只有 3 个**，差别在产物形态与「谁托管它」：

| 运行时      | 产物        | 目标机动作                                       | 回滚方式                  |
| -------- | --------- | ------------------------------------------- | --------------------- |
| `DOCKER` | 容器镜像      | `docker pull` + `compose up` / `docker run` | 拉回旧 tag 重跑            |
| `JAR`    | `.jar` 文件 | 备份旧 jar → 投新 jar → `systemctl restart`      | 投放 `exec/bak` 里的旧 jar |
| `STATIC` | 目录        | 替换 `static_root` 的**内容**（目录不动）              | `static-bak` 还原内容     |

两者**正交**：构建模式不改变产物形态，只改变「产物由谁、在哪一步做出来」。正交不等于任意搭配，  
合法组合由 §4 的矩阵约束。

### 2.2 怎么选：先问一句「Dockerfile 自己能不能产出 jar」

这是最容易搞错的地方，也是本项目真实踩过的坑。

```text
你的 Dockerfile 里有没有 mvn / npm 这类构建步骤？
├─ 有（多阶段构建，FROM maven AS builder ...）
│   └─ 选 PROJECT_DOCKERFILE（或拆了 base 层就选 LAYERED_DOCKER）
│      平台只负责 docker build，编译发生在镜像构建过程内部。
│
└─ 没有（只 FROM jre + COPY xxx.jar，jar 是外部产物）
    └─ 选 JAR_PREBUILD
       平台先用 Maven 容器把 jar 打出来放在宿主机工作区，
       再让这份「极简 Dockerfile」把已存在的 jar COPY 进镜像。
```

**把「只 COPY 的极简 Dockerfile」配成 `PROJECT_DOCKERFILE`，必然报 `COPY ... : not found`**  
——因为平台在该模式下不跑 Maven，而 jar 是构建产物、不随 Git 进仓库，刚 clone 下来的工作区里根本没有它。  
日志特征是 `transferring context: 2B`（上下文里除了 `.dockerignore` 什么都没有）。

### 2.3 三组易混对照

| 容易混                                      | 区别                                                             |
| ---------------------------------------- | -------------------------------------------------------------- |
| `PROJECT_DOCKERFILE` vs `LAYERED_DOCKER` | 都在 Dockerfile 内编译，区别只是有没有拆出可复用的 base 层（依赖不变时 base 层可复用，省排队时间）。 |
| `PROJECT_DOCKERFILE` vs `JAR_PREBUILD`   | 编译发生在哪一步：Dockerfile 内部 vs 平台先跑 Maven。产物都是镜像，**选错必失败或白跑一遍**。    |
| `SCRIPT_DEPLOY` vs `ARTIFACT_ONLY`       | 前者平台**执行** `build_command` 生成产物；后者平台**不执行任何命令**，产物由人上传。        |

### 2.4 「JAR 预构建」到底换来什么

它的价值**不在于多一份 Dockerfile**，而在于让 jar 成为可以脱离镜像独立存在的东西：

> **多阶段构建里，jar 是镜像的中间产物，构建完就没了；  
> JAR 预构建里，jar 是成品，镜像只是它的包装之一。**

两条链路并排：

```text
【多阶段 Dockerfile → 项目自带 Dockerfile】
docker build .
  ├─ 阶段1  FROM maven:3.9
  │         mvn package → /app/target/auth-tool.jar   （只存在于镜像层）
  └─ 阶段2  FROM jre
            COPY --from=阶段1 /app/target/auth-tool.jar
结果：构建机磁盘上只有一个镜像，jar 随中间层一起丢弃。

【极简 Dockerfile → JAR 预构建】
① 平台先跑  docker run maven ... mvn package
            → /lx/light-deploy/workspace/auth-tool_xxx/auth-tool/linux/auth-tool-7888/auth-tool.jar
               ↑ 真真实实落在构建机磁盘上
② 再跑      docker build -f Dockerfile.jre .   （只 COPY 那个 jar）
            → 镜像
结果：磁盘上有 jar + 有镜像，jar 可以单独拿走。
```

换来三样东西：

| 收益              | 具体含义                                                                                                                                                                                      |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **目标机上有救命素材**   | 平台把 jar 打进 `hotfix-kit.tar.gz`，下发到 `<work_dir>/build-context/`。平台与仓库同时不可用时，运维 cd 进去 `up -d --build` 就能把服务救回来。多阶段构建做不到——目标机上只有镜像层，想把 jar 挖出来得 `docker create` + `docker cp`，真出事没人记得住镜像内路径。 |
| **jar 可校验、可归档** | 能算 SHA256 写进 `release_record`，能按版本留存与清理。镜像内的 jar 做不到。                                                                                                                                     |
| **增量构建复用依赖缓存**  | Maven 容器挂载构建机的 `~/.m2`，第二次构建不必全量下载。多阶段构建的 `/root/.m2` 在容器内部，除非 Dockerfile 特意写 `--mount=type=cache`。                                                                                       |

代价也要认清：极简 Dockerfile 必须与多阶段那份**产出等价镜像**（改 `JAVA_OPTS` / `ENTRYPOINT`  
时两处都要改），否则会出现「平台发的是这个行为、应急重建出来是另一个行为」——比没有更危险。

### 2.5 一个反直觉点：走 JAR 预构建不需要维护两份 Dockerfile

很多人以为选了 `JAR_PREBUILD` 就得同时维护多阶段与极简两份、还要保证同步。**不必。**

走 `JAR_PREBUILD` 时，项目里**只留那一份极简 Dockerfile 就够了**，编译交给平台。多阶段那份可以删掉，  
或保留作为「不依赖平台也能自己 build」的兜底手段——保留才需要同步，删掉就没有同步成本。

auth-tool 现在两份都在，是因为当初要拿它做两种模式的对照验证，不是模式要求的。

### 2.6 Docker 运行时下 Java 服务的默认口径（团队规则）

```text
DOCKER + Java 服务：
  默认   用「JAR_PREBUILD」，配「只 COPY jar 的极简 Dockerfile」。
  例外   项目 Dockerfile 是多阶段、且明确不愿把编译交给平台 → 用「PROJECT_DOCKERFILE」。
  禁止   把极简 Dockerfile 配成「PROJECT_DOCKERFILE」。
```

为什么要写「禁止」这一条：`DOCKER` + `PROJECT_DOCKERFILE` 是**合法组合**，`ProjectService` 的  
组合校验必然放行——它只能判断「这个组合允不允许」，判断不了「这份 Dockerfile 属于哪一种」。  
这类错误只会在 `docker build` 阶段暴露，校验拦不住，只能靠规则 + 文档 + §8 的排障表。

### 2.7 命名说明：`Dockerfile.jre` 这个名字不贴切

`jre` 指的是基础镜像（`eclipse-temurin:8-jre`），不是这份文件的职责。它真正的职责是  
**只打包、不编译**，叫 `Dockerfile.pack` 之类会更贴切。目前保持原名以免打断既有配置；  
若要改名，需同步 `build_config_json.dockerfile_path`、`Dockerfile.hotfix` 的注释与本文档。

## 3. 逐个模式的实际执行链路

> **三种 DOCKER 构建模式（`PROJECT_DOCKERFILE` / `LAYERED_DOCKER` / `JAR_PREBUILD`）都会多做一件事：
> 把 `build_config_json.config_paths` 指到的配置文件转存到 `{构建产物持久目录}/{项目编码}/{版本}/config`
> （`BuildTaskHandler.persistVersionConfig`）。** 镜像类产物的 `artifact_path` 是 null、不落构建机磁盘，
> 走不到 `buildFileArtifact` 那条「产物 + 配置一起落盘」的路径；不单独补这一步，目标机上 compose 挂的
> `./config` 永远是空目录，容器会静默回落到镜像内配置（发布照样报成功）。配置缺失不阻断构建，
> 只在日志里写一行「随版本转存配置文件 …」。发布端怎么用见 [产物分发链路.md](产物分发链路.md) §6.4。

### 3.1 `PROJECT_DOCKERFILE`（项目自带 Dockerfile）

| 步骤 | 实际动作                                                                                                     | 失败点                                    |
| -- | -------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| 1  | 建工作区 → `git clone`（令牌注 URL 密码位，日志脱敏）                                                                     | 仓库不可达 / 鉴权失败                           |
| 2  | `docker build -f <dockerfile_path> -t <imageRepo>:<version> .`（上下文 = 仓库根）                                | **Dockerfile 内 COPY 找不到文件**（本项目事故就是这个） |
| 3  | `dockerRunVerify`：构建机本地 `timeout -k 5 <N>s docker run --rm`，窗口内存活即通过（`docker_verify_on_build` 可关，默认 30s） | 镜像能构建但一启动就崩                            |
| 4  | `docker push` + 取 digest                                                                                 | registry 鉴权 / 网络                       |
| 5  | `readComposeFile`：把项目 compose 原文快照进 `release_record.compose_content`                                     | 显式配了 `compose_file_path` 却读不到 → 直接失败   |
| 6  | `captureBuildContext`：仅 COMPOSE + 配了 `work_dir` 时，把源码上下文打成 tarball 落构建机供下发                               | 非致命                                    |

前置校验：`dockerfile_path` 必填。

### 3.2 `LAYERED_DOCKER`（分层构建）

与 3.1 同链路，仅第 2 步拆成两跳：

```bash
docker build -f <base_dockerfile_path> -t <imageRepo>:base-<version> .
docker push  <imageRepo>:base-<version>
docker build -f <dockerfile_path> --build-arg BASE_IMAGE=<imageRepo>:base-<version> -t <imageRepo>:<version> .
```

应用层 Dockerfile 必须声明 `ARG BASE_IMAGE` 并用它做 `FROM`。前置校验：`base_dockerfile_path` 与  
`dockerfile_path` 都必填。

### 3.3 `JAR_PREBUILD`（B1：平台先打 jar 再包镜像）

| 步骤 | 实际动作                                                                                                          | 说明                                     |
| -- | ------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| 1  | Maven 容器构建 jar：`mvn -B [-s <settings>] -f <moduleDir>/pom.xml package -DskipTests`（挂载 `~/.m2` 缓存，输出实时回传）      | 不需要构建机裸装 maven/JDK                     |
| 2  | `locateJarArtifact` 按 `artifact_path` 定位 jar（仓库根优先、模块目录回落，支持 `*` 通配）                                          | 找不到直接失败并指向 artifact_path               |
| 3  | `docker build -f <dockerfile_path>`                                                                           | 这份 Dockerfile **只 COPY jar**，自己不具备构建能力 |
| 4  | 启动级验证 → push                                                                                                  | 同 3.1                                  |
| 5  | `captureHotfixKit` 产 `hotfix-kit.tar.gz`（jar 沿用产物原名 + `Dockerfile.hotfix` + hotfix compose + config + README） | **平台不可用时的现场重建素材**，失败不阻断构建              |
| 6  | `persistVersionConfig` 把 `config_paths` 指到的文件转存到版本目录 `config/`，供发布期投放到目标机                          | 缺配置 / 找不到文件只记日志，不阻断构建                   |

jar 名口径：**包内沿用构建产物自己的文件名**（如 `auth-tool.jar`），由 `fileNameOf()` 从  
`artifact_path` 定位到的路径取 basename。不从 pom 的 `<finalName>` 反推（要处理属性插值、模块/根 pom  
优先级），也不再加一个 `jar_name` 配置项（会与 `artifact_path` 构成两个真相来源）。

对应 `Dockerfile.hotfix` 用 `COPY *.jar /app/app.jar`，与名字解耦；代价是平铺目录里只能有一个 jar。

### 3.4 `SCRIPT_DEPLOY`（脚本部署）

| 步骤 | 实际动作                                                                |
| -- | ------------------------------------------------------------------- |
| 1  | 校验 `build_command` 与 `artifact_path` 都已配置                           |
| 2  | 命令前缀 `. /etc/profile` + 机器级环境初始化脚本（非交互 SSH 不加载 profile，PATH 常缺 mvn） |
| 3  | `checkBuildCommandExecutable` 先探首词是否可执行，区分「没装」与「没配 PATH」            |
| 4  | `logBuildToolchain` 自证 JDK/Maven 版本（版本错配类报错只能靠这条定位）                 |
| 5  | 执行 `build_command`（长命令超时 + 逐行回传 + 超时杀远端进程组）                         |
| 6  | 按 `artifact_path` 定位产物 + 算 SHA256 + 转存 `config_paths` 指到的配置文件       |

目标机发布：`JAR` 走「备份旧 jar → 投放新 jar → 复核 SHA256 → 写 VERSION → `systemctl restart`」；  
`STATIC` 走「旧内容搬到 `static-bak` → 新内容搬进来」，**不换目录、不 reload nginx**。

### 3.5 `ARTIFACT_ONLY`（仅发布已有产物）

**本模式不会真正执行构建。** `BuildTaskHandler.execute()` 在解析出该模式后立即抛错：

```
构建模式 ARTIFACT_ONLY（仅发布产物）不发起构建任务，请通过产物上传接口 POST /build/upload 登记版本
```

正确入口是页面「上传产物」→ `POST /build/upload`（单文件：`.jar` / `.zip` / `.tar.gz` / `.tgz`），  
平台只登记版本、不连构建机。这样可以避免「点了构建、跑了几分钟、才在最后失败」的浪费。

## 4. 运行时 × 构建模式：合法组合矩阵

唯一来源是 `RuntimeType` 枚举常量上声明的 `supportedBuildModes`，前后端都不得另写一套判断  
（AGENTS.md §23.4）。

| 运行时      | 允许的构建模式                                                  | 理由                                               |
| -------- | -------------------------------------------------------- | ------------------------------------------------ |
| `DOCKER` | `PROJECT_DOCKERFILE` / `LAYERED_DOCKER` / `JAR_PREBUILD` | 产物是镜像，必须经过 registry（JAR_PREBUILD 虽先打 jar，终态仍是镜像） |
| `JAR`    | `SCRIPT_DEPLOY` / `ARTIFACT_ONLY`                        | 产物是文件，交付到目标机由 systemd 托管                         |
| `STATIC` | `SCRIPT_DEPLOY` / `ARTIFACT_ONLY`                        | 产物是目录，交付到目标机由 Nginx 托管                           |

不存在的组合（如 `JAR` + `PROJECT_DOCKERFILE`）由 `ProjectService`（约 285–297 行）在保存时拒绝，  
错误信息会带上该运行时的可选模式列表。

> **注意**：这条校验只保证「组合合法」，**不保证「选对了」**。  
> `DOCKER` + `PROJECT_DOCKERFILE` 永远是合法组合——哪怕项目的 Dockerfile 其实是只 COPY 的极简版。  
> 选错的后果要到 `docker build` 阶段才暴露（见 §7）。这也是 §2 的决策树必须存在的理由。

## 5. 三处数据必须一致：枚举 / 前端常量 / 数据库

| 位置                                   | 角色                              | 缺了会怎样                                    |
| ------------------------------------ | ------------------------------- | ---------------------------------------- |
| 后端 `BuildMode` 枚举                    | **唯一权威**，决定分发分支是否认识这个编码         | 不认识的编码在 `execute()` 入口直接报「不受支持」          |
| 后端 `RuntimeType.supportedBuildModes` | 合法组合的唯一来源                       | 组合校验失效，非法搭配能存进库                          |
| 前端 `BUILD_MODE_OPTIONS`              | 页面**唯一清单**，表单下拉、搜索下拉、列表文案全部从它派生 | 该模式在页面上「消失了」：下拉里选不到、列表显示原始编码             |
| 数据库 `project.build_mode`             | 存量事实                            | 与枚举脱节（如遗留 `PLATFORM_TEMPLATE`）会在构建时被明确拒绝 |

派生关系（必须单向）：

```text
BuildMode 枚举 ──(手工同步)──► BUILD_MODE_OPTIONS ──派生──► BUILD_MODE_MAP（列表/详情文案）
                        └──────派生──► 搜索下拉选项
                        └──────派生──► 编辑页按运行时过滤后的下拉
```

**禁止在任何页面里再手写一份模式清单。** `build/index.vue` 曾自己维护过一份映射，与常量模块  
不同步、漏掉了 `JAR_PREBUILD`，直接导致了 §7 的事故。

## 6. 变更检查清单（新增 / 修改 / 下线构建模式时逐条过）

1. **后端枚举** `BuildMode`：加/改常量，`code` 与数据库存值一致，`message` 是页面与日志的中文名；
2. **后端组合规则** `RuntimeType.supportedBuildModes`：在对应运行时里声明；
3. **后端分发分支** `BuildTaskHandler.execute()`：新模式在这里必须有明确去处，不允许落到 `else` 里被  
   `buildDocker` 的兜底分支拒绝——要么实现，要么在入口给出「该用哪个模式」的指引；
4. **前端唯一清单** `constants/projectConfig.ts` 的 `BUILD_MODE_OPTIONS`：`value / label / shortLabel /
   runtimes` 四个字段齐全，**漏 `runtimes` 等于该模式在所有运行时下都选不到**；
5. **不要新增第二份清单**：列表页、搜索下拉、详情页一律从 `BUILD_MODE_OPTIONS` / `BUILD_MODE_MAP` 派生；
6. **文档**：本文档 §1、§3、§4 三处 + `AGENTS.md` §23.4；
7. **存量数据**（MySQL 变更一律手工执行）：下线模式必须先把库里旧值订正掉，订正 SQL **必须带限定条件**


   （`WHERE code = '...'` 或 `WHERE id = '...'`），禁止无条件 `UPDATE`；
8. **验证三件套**：`mvn -o -q -DskipTests compile`、`npm run build` + `npx vue-tsc --noEmit`、
   真机跑一次该模式的构建。

## 7. 事故复盘：auth-tool v9 构建失败（2026-10-31）

**现象**：构建日志显示 `模式 PROJECT_DOCKERFILE`，`docker build` 在 `Dockerfile.jre:34` 报
`COPY auth-tool/linux/auth-tool-7888/auth-tool.jar ...: not found`，上下文只有 2B。

**因果链**：

1. auth-tool 的 `dockerfile_path` 指向 `Dockerfile.jre`——一份「只 COPY 预构建 jar」的极简 Dockerfile，
   它必须配 `JAR_PREBUILD`；
2. 但前端 `BUILD_MODE_OPTIONS` 漏登记了 `JAR_PREBUILD`，编辑页按运行时过滤后只剩
   「项目自带 Dockerfile / 分层构建」两项；
3. 打开编辑页时，`formData.buildMode` 的现值 `JAR_PREBUILD` 不在选项里，下拉显示空白；
4. 更严重的是 `handleRuntimeTypeChange()` 里的联动：
   `BUILD_MODE_OPTIONS.find(v => v.value === formData.buildMode)?.runtimes.includes(runtimeType)`
   对未知编码求值为 `undefined`，`!undefined === true`，于是**静默回退到第一个选项**
   ——`PROJECT_DOCKERFILE`；
5. 保存后 `build_mode` 被改掉，下一次构建必然失败。

**为什么组合校验没拦住**：`DOCKER` + `PROJECT_DOCKERFILE` 是完全合法的组合，`ProjectService`
的校验只能判断「组合是否允许」，判断不了「项目的 Dockerfile 属于哪一种」。这类错误只能靠
「模式语义 + Dockerfile 形态」的对应关系来防（§2）。

**修复内容**（2026-10-31）：

- `constants/projectConfig.ts`：补齐 `JAR_PREBUILD`，并给每个模式写明「平台会做什么」；
- `views/build/index.vue`：删掉本地手写映射，改为从常量模块导入；
- `views/project/edit.vue`：`handleRuntimeTypeChange` 区分两种情况——「值在表里但运行时不支持」
  才自动回退并提示；「值根本不在表里」保留原值 + 告警，绝不静默替换；
- 后端 `BuildMode` / `ProjectVo`：JavaDoc 补齐每个模式的执行入口与分界线；
- 数据库：auth-tool 的 `build_mode` 改回 `JAR_PREBUILD`。

## 8. 排障速查：看日志就能定位

| 日志特征 | 结论 | 处理 |
| --- | --- | --- |
| `（模式 PROJECT_DOCKERFILE）` 且没有 `Maven 构建 jar` 这一行 | 平台没跑构建，直接 build | 确认 Dockerfile 能否自行产出产物；不能就换 `JAR_PREBUILD` |
| `transferring context: 2B` / 很小 | 构建上下文里没文件（被 `.dockerignore` 排掉，或产物本来就不在仓库） | 查 `.dockerignore`；查是不是把「构建产物」当成了仓库文件 |
| `COPY ... : not found` | Dockerfile 要的东西不在上下文里 | 同 §2 决策树 |
| `项目的构建模式「XXX」不受支持` | 库里是已下线的编码，枚举不认识 | 按提示改成现有模式 |
| `构建模式 ARTIFACT_ONLY（仅发布产物）不发起构建任务` | 用错了入口 | 改用「上传产物」 |
| `脚本部署（SCRIPT_DEPLOY）必须在 build_config_json.build_command 中显式给出构建命令` | 少配 `build_command` | 补配置 |
| `bash: mvn: command not found`（但机器上装了） | 非交互 SSH 未加载 PATH | 配机器级环境初始化脚本，或改用 `JAR_PREBUILD`（走 Maven 容器） |
| `镜像构建完成` 后紧接 `启动级验证失败` | 构建成功但一启动就崩 | 看验证窗口内的容器日志；必要时临时 `docker_verify_on_build=false` 排查 |
