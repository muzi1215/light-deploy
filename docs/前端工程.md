# 前端工程文档

> 工程目录：`lighit-deploy-ui`（与后端同仓库） ｜ 技术栈：Vue3 + Vite + TypeScript + Element Plus + Pinia ｜ 状态：已完成并构建通过

## 1. 模块定位

前端工程是 Light Deploy 平台的操作入口，当前完成第一版管理页面：

- 过渡期假登录（前端 mock，不依赖后端登录接口）；
- 静态菜单（不依赖后端菜单 JSON）；
- 服务器 / 项目 / 环境 / 部署目标 / 任务 / 凭据 / 镜像仓库七个管理页面，对接后端已完成的标准六接口；服务器列表已提供连通性测试入口与实时日志抽屉；
- 生产环境由 Nginx 托管 `dist/` 静态文件并反向代理后端（未配置，待部署阶段）。

## 3. 关键适配点

### 3.1 代理链路

```text
浏览器 → http://localhost:9850/api/xxx
       → vite proxy 重写 /api → /deploy
       → http://localhost:2027/deploy/xxx（Spring Boot，context-path=/deploy）
```

### 3.2 响应契约

`utils/request.ts` 判定 `code === 200` 为成功（与后端 `ResponseCode.SUCCESS` 一致），业务码非 200（如 4001 参数错误、4004 数据不存在、4005 唯一冲突）时以 `ElMessage` 弹出后端 message 并 reject —— 页面无需重复处理错误提示。requestId 已在响应中返回，反馈问题时可直接提供。

### 3.3 假登录与静态菜单

- `api/user.ts` 的 login/getInfo/logout 均为前端 mock，任意用户名密码可登录，token 为 `mock_token_时间戳` 存 Cookie；
- `getInfo` 返回 `routers: []`，`permission.ts` 据此走静态路由模式；
- 四个业务页面注册在 `router/index.ts` 的 `constantRoutes` 中；
- 对接真实登录时，只需按 `api/user.ts` 底部注释切换为真实 API 调用。

### 3.4 列表搜索区的创建时间区间

带搜索区的列表统一在时间筛选上使用同一套实现，约定见 AGENTS.md §10.4：

- 模板放 `<CreateTimeRange v-model="timeRange" />`（组件内含 `el-form-item` 与 `el-date-picker`，
  默认时刻固定为开始 `00:00:00`、截止 `23:59:59`——不设置时选同一天会查不到当天数据）；
- 请求参数用 `...splitTimeRange(timeRange.value)` 展开为 `createTimeBegin` / `createTimeEnd`；
- 重置时 `timeRange.value = []`；
- 列表必须有「创建时间」列：筛选项与展示列对不上，用户无法核对筛选是否生效
  （发布 / 构建 / 任务三个流水型页面原先只有开始、结束时间列，已补创建时间列）。

列表页的 keep-alive 缓存与刷新策略（AGENTS.md §20.10）：页面由 `AppMain` 的 `<keep-alive :include="cachedViews">` 缓存，切走再切回**不重跑 setup**，因此必须显式决定「回来时要不要重新拉数据」：

- **数据由服务端/平台自己产生**（任务列表、构建列表、部署记录）→ 在 `onActivated` 里无条件重新拉一次。任务列表尤其明显：构建一次、发布一次各建一条任务，「任务管理里没有记录」几乎都是这个原因造成的；
- **数据只被本站自己的编辑页改动**（项目列表）→ 用 `store/pageRefresh.ts` 的标记 + `consumeDirty`，编辑页保存成功后 `markDirty`，激活时命中才刷新，普通切标签不产生多余请求；
- 两种写法都要处理「首次挂载后会紧接着触发一次 `onActivated`」：初次已在 setup / `onMounted` 拉过数据，用一个只跳过一次的标记避免重复请求（`ProjectList` 因为走 `consumeDirty` 天然规避，其余页面显式跳过）。

复杂配置字段（三段 JSON 等）在表单 label 后加「?」图标 + `el-tooltip` 展示完整示例，示例常量与输入框 `placeholder` 共用一份；`.form-tip`、`.form-label-tip`、`.tooltip-json` 统一定义在全局 `styles/index.scss`（AGENTS.md §20.2）。

实时日志是平台里出现次数最多的交互，共 5 处：任务列表（`el-dialog`）、构建列表（`el-drawer`）、发布列表（`el-drawer`）、服务器连通性测试（`el-drawer`）、项目触发构建（`el-dialog`）。它们**共用 `composables/useTaskLogViewer.ts`**，页面只渲染控制台与外层容器：

```ts
const { bodyRef, logs, task, running, downloading, progressStatus, start, stop, download, beforeClose } =
  useTaskLogViewer({ onFinished: fetchData })   // onFinished 可选，用于任务结束时刷新列表

// 打开时 start(种子)，容器 @closed 时 stop，下载按钮接 download，关闭拦截接 beforeClose
start({ taskId: row.taskId, taskNo: row.taskNo, status: row.status, progress: row.progress })
```

三条硬规则（完整约定见 AGENTS.md §20.9）：

- **容器宽度统一 800px，日志区自动滚到底部**，任务状态 / 进度 / 阶段 / 失败原因同屏展示（失败原因用 `el-alert`），刷新一律走 `GET /taskLog/pull` 增量拉取，控制台样式只在全局 `styles/index.scss` 定义一份；
- **任务执行中（状态 0/1）锁死容器关闭入口**：`before-close` 兜底 + 隐藏 ✕ + 禁用 ESC + 页脚按钮走同一拦截，同时给出安全阀——首次拉取失败时按「未知」处理并放行关闭，避免把用户永久关在弹窗里；
- **下载日志走 `GET /taskLog/export/{taskId}`**，`responseType: 'blob'` 且必须自己判断响应类型（异常时后端返回 JSON，直接存会得到一个装着报错信息的「日志文件」），文件名以 `Content-Disposition` 为准；这把 `utils/request.ts` 里早已预留的 blob 分支真正用了起来。

> 任务列表的日志查看曾是独占实现：`/taskLog/list` 一次性拉取 + 手动「刷新」按钮，既没有刷新时机也无法表达进度。现已统一到增量拉取，手动刷新按钮随之移除——1.5 秒轮询下它是一块死 UI。

状态类字段全部使用数字编码：前端类型为 `number`，下拉与标签映射按数字取值，标签颜色遵循统一口径（启用/成功 `success`、停用/未知 `info`、进行中 `primary`、警告/已取消 `warning`、失败/危险 `danger`），环境标签颜色唯一维护在 `constants/tagStyle.ts`（AGENTS.md §4.5、§20.7）。

## 6. 蓝色渐变背景按钮配色规范（幽灵按钮）

> **背景（为什么写这一节）：** 2026-11-03 修复首页「查看发布记录」按钮在白色主题下文字不可见的问题。根因是原样式 `.hero-actions .el-button { --el-button-text-color: #fff; }` 把白字强加给了 **白底** 的默认按钮，导致浅色主题下白字白底、完全看不见。同类问题会随蓝色背景复用再次出现，故固化为规范，避免二次返工。

### 6.1 规则

任何放在 **深色/蓝色/渐变背景** 上的 Element Plus 按钮，**禁止直接使用默认白底样式**（默认按钮在浅色主题是白底深字，一旦被强制白字就会隐形）。必须显式覆盖 CSS 变量，分两类：

| 按钮 | 背景 | 文字/边框 | 关键 CSS 变量 |
| --- | --- | --- | --- |
| **主按钮**（`type="primary"`） | 白色 `#ffffff` | 蓝字 `#1677ff` | `--el-button-bg-color` / `--el-button-border-color` / `--el-button-text-color` / `--el-button-hover-*` |
| **次按钮/默认按钮**（无 type） | 透明 `transparent` | 白字 + 白边 | `--el-button-bg-color: transparent` / `--el-button-border-color: rgba(255,255,255,.85)` / `--el-button-text-color: #fff` / `--el-button-hover-bg-color: rgba(255,255,255,.15)` |

即：**主按钮「白底蓝字」、次按钮「透明底 + 白边 + 白字」的幽灵样式**，两者在浅色/深色主题下都清晰，不再依赖主题默认值。

### 6.2 落地写法（首页 hero 的现有实现）

```scss
.hero-actions {
  .el-button--primary {           /* 主按钮：白底蓝字 */
    --el-button-bg-color: #ffffff;
    --el-button-border-color: #ffffff;
    --el-button-text-color: #1677ff;
    --el-button-hover-bg-color: #f0f5ff;
    --el-button-hover-border-color: #f0f5ff;
    --el-button-hover-text-color: #1677ff;
  }
  .el-button:not(.el-button--primary) {  /* 次按钮：幽灵样式 */
    --el-button-bg-color: transparent;
    --el-button-border-color: rgba(255, 255, 255, 0.85);
    --el-button-text-color: #ffffff;
    --el-button-hover-bg-color: rgba(255, 255, 255, 0.15);
    --el-button-hover-border-color: #ffffff;
    --el-button-hover-text-color: #ffffff;
  }
}
```

### 6.3 适用范围

- **目前仅首页 hero（`.hero-card` 蓝色渐变）** 属于「深色背景 + 按钮」，已按上述规范处理。
- 登录页左侧品牌区（`.login-left` 蓝色渐变）**只有文字，没有按钮**，暂无需处理；若后续在该区加按钮，必须套用同一规范。
- 白色卡片上的按钮（如 AIops 状态卡的「前往 AIops 平台」）**不要**套幽灵样式——白底上用普通 `type="primary" link` 或默认按钮即可，否则会白底白字。

### 6.4 与演示只读开关的关系

首页 hero 的两个按钮（「开始管理项目」「查看发布记录」）都是**导航**而非写操作，因此 **不加** `v-readonly`；演示只读开关只锁编辑/删除类写操作按钮，不影响首页导航。
