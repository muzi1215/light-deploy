# 项目模块文档

> 模块包：`com.lx.deploy.project` ｜ 对应数据表：`project`、`environment`、`project_environment_target` ｜ 状态：已完成并编译通过

## 1. 模块定位

项目模块是发布链路的起点，回答三个问题：

1. **发布什么** —— `project` 表登记项目的运行时（DOCKER/JAR/STATIC）、代码来源与构建模式；
2. **发到哪** —— `environment` 表定义部署环境（dev/test/prod）与部署策略（单目标/全量/滚动）；
3. **具体发到哪台机器** —— `project_environment_target` 表把「项目 × 环境」绑定到具体服务器，形成完整发布拓扑。

**「一个 project = 一个可部署的服务模块」是本模块的建模基准**（见 AGENTS.md §23.1）：`project` 登记的是一条可独立构建、独立发布、独立回滚的发布单元记录，不是「一个 Git 仓库一条记录」。因此多模块仓库（如 `auth-system-Iteration` 下的 `auth-system` / `auth-rest` / `auth-tool`）在同一 `git_url` + `git_branch` 下会创建多条 project，靠 `build_config_json.module_name` 区分（见 §2.3.1），唯一性只由 `code` 保证。

三表关系：

```text
project ────┐
            ├──▶ project_environment_target ──▶ server（服务器模块）
environment ┘
```

## 2. 数据表结构

### 2.1 `project`（部署项目）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| code | VARCHAR(64) | 项目编码，唯一键，`^[A-Za-z0-9_-]{2,64}$` |
| name | VARCHAR(100) | 项目名称 |
| runtime_type | VARCHAR(20) | 运行时：DOCKER / JAR / STATIC |
| source_type | VARCHAR(20) | 代码来源：GIT / UPLOAD，默认 GIT |
| git_url / git_branch / git_credential_id | - | Git 来源信息；凭据指向独立 credential 表 |
| build_mode | VARCHAR(30) | 构建模式，默认 PLATFORM_TEMPLATE；与 runtime_type 的组合受约束（见 §6.5） |
| registry_id | VARCHAR(32) | 镜像仓库 ID，仅 DOCKER 运行时可绑定，指向 registry 表；JAR / STATIC 必须为空 |
| build_config_json / runtime_config_json / health_config_json | JSON | 三段配置（当前只做格式校验、不解析语义）；键名 schema 与完整示例见 [§2.3](#23-三段-json-配置字段约定构建--运行--健康检查) |
| retain_release_count | INT | 保留发布版本数，默认 5 |
| status | TINYINT | 状态：0 停用 / 1 启用，默认 1 |

### 2.2 `environment`（部署环境）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| code | VARCHAR(32) | 环境编码（dev/test/prod），`^[a-z][a-z0-9-]{1,31}$` |
| name | VARCHAR(100) | 环境名称 |
| deploy_strategy | VARCHAR(30) | SINGLE_TARGET / ALL_AT_ONCE / ROLLING，默认 SINGLE_TARGET |
| batch_size | INT | 滚动发布批次大小，默认 1 |
| default_server_id | VARCHAR(32) | 默认目标服务器（可选，存在性校验） |
| aiops_enabled | TINYINT | 是否启用 AIops 联动（发布静默窗口），默认 0 |

### 2.3 三段 JSON 配置字段约定（构建 / 运行 / 健康检查）

`project` 表用三段 JSON 描述「怎么构建、怎么运行、怎么判定可用」。当前 `ProjectService` 只校验其是否为合法 JSON（见 §6.1），**不做语义解析**；语义校验、默认值填充与兼容处理由后续构建 / 发布 / 健康检查模块消费。为避免各模块实现时字段语义漂移、前后端口径不一致，此处先行锁定 schema，作为下游模块的开发契约。

> **核心原则**：一个 project = 一个发布单元（见 AGENTS.md §23.1）。三段 JSON 只描述「本发布单元自身」的构建与运行细节，不重复承载仓库地址、分支、目标环境等已落在 `git_url` / `git_branch` / `environment` / `project_environment_target` 的信息。

- 键名统一 `snake_case`，与数据库列命名风格一致，禁止在同一份配置里混用驼峰；
- 三段 JSON 均为可选字段，但一旦填写必须是合法 JSON；
- 三段 JSON 都允许清空：表单提交空串时 Service 归一为 `null`，实体用 `updateStrategy = FieldStrategy.ALWAYS` 保证真的写入 NULL（否则会出现「能设置、不能清空」，见 AGENTS.md §10.1）；
- 未填写的键由消费方模块按本文档给出的默认值处理，Service 层不介入；
- 表单直接编辑原始 JSON 文本，前端只做 JSON 语法校验，不做语义校验（与后端一致）。

#### 2.3.1 `build_config_json`（构建模块消费）

回答「仓库拉取之后，如何定位子模块并构建出本项目的产物」。

| 键 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `module_name` | string | 多模块仓库必填 | 子模块名，如 `auth-tool`。同时是默认 `-pl` 参数、默认模块目录名与默认镜像名的来源 |
| `module_dir` | string | 否 | 子模块相对仓库根的目录，默认等于 `module_name`；单模块仓库可省略（默认仓库根目录） |
| `pom_path` | string | 否 | Maven 构建入口 pom 路径，默认 `{module_dir}/pom.xml`；单模块仓库默认 `pom.xml` |
| `build_tool` | string | 否 | `MAVEN` / `GRADLE` / `NPM`，默认按仓库根文件探测（`pom.xml` / `build.gradle` / `package.json`） |
| `build_command` | string | 否 | 完整构建命令；填写后覆盖 `build_tool` 的推导结果，如 `mvn clean package -pl auth-tool -am -DskipTests` |
| `dockerfile_path` | string | `PROJECT_DOCKERFILE` / `LAYERED_DOCKER` 必填 | Dockerfile 相对仓库根路径，如 `auth-tool/Dockerfile` |
| `base_dockerfile_path` | string | `LAYERED_DOCKER` 必填 | 分层构建的基础层 Dockerfile 路径，如 `Dockerfile.base` |
| `artifact_path` | string | `JAR` / `STATIC` 运行时必填 | 构建产物相对路径，支持 `*` 通配，如 `auth-tool/target/auth-tool-*.jar` |
| `image_repository` | string | `DOCKER` 运行时建议填写 | 业务镜像仓库地址（不含 tag），如 `registry.cn-hangzhou.aliyuncs.com/lx/auth-tool` |
| `image_tag_pattern` | string | 否 | 镜像 tag 模板，默认 `{version}`；可用变量 `{version}`、`{projectCode}` |

**单模块仓库（默认，可极简）：**

```json
{
  "build_tool": "MAVEN",
  "build_command": "mvn clean package -DskipTests",
  "artifact_path": "target/auth-app-*.jar"
}
```

**Maven 多模块仓库（同一仓库含多个可独立发布子模块）：**

`auth-system-Iteration` 是父工程（`packaging=pom`），其下 `auth-system` / `auth-rest` / `auth-tool` 是三个独立可发布子模块。**不需要拆 Git 仓库，也不需要改 project 表结构**：在同一 `git_url` + `git_branch` 下建三条 project 记录，各自通过 `module_name` 指向不同子模块即可。

```json
{
  "module_name": "auth-tool",
  "module_dir": "auth-tool",
  "build_command": "mvn clean package -pl auth-tool -am -DskipTests",
  "dockerfile_path": "auth-tool/Dockerfile",
  "artifact_path": "auth-tool/target/auth-tool.jar"
}
```

```json
{
  "module_name": "auth-rest",
  "module_dir": "auth-rest",
  "build_command": "mvn clean package -pl auth-rest -am -DskipTests",
  "dockerfile_path": "auth-rest/Dockerfile",
  "artifact_path": "auth-rest/target/auth-rest.jar"
}
```

```json
{
  "module_name": "auth-system",
  "module_dir": "auth-system",
  "build_command": "mvn clean package -pl auth-system -am -DskipTests",
  "artifact_path": "auth-system/target/auth-system-*.jar"
}
```

**执行流程**：拉取代码 → 解析 `build_config_json` → 进入 `module_dir`（或直接用 `-pl` 指定模块）执行 `build_command` → 按 `artifact_path` 取产物 → 按 `runtime_type` 生成镜像或上传产物。

**多模块解析约定**（完整规则见 AGENTS.md §23.3）：

1. 仓库只拉一次：同一 `git_url` + 分支的子模块共享一次 `git clone` 与工作区缓存，产物目录按 `project.code` + 版本号隔离；
2. 按 `module_dir` / `-pl` 局部构建，避免每次构建整个仓库；
3. 每个子模块 project 独立登记 `release_record`、独立走 `deployment`，互不影响，支持各自回滚；
4. 模块间依赖由 Maven / Gradle 依赖图保证（`-am` 会一并构建被依赖模块），project 表不表达模块依赖关系。

#### 2.3.2 `runtime_config_json`（发布模块消费）

回答「产物在目标服务器上怎么跑起来」。按 `runtime_type` 读取对应键，其他键忽略。

| 键 | 类型 | 适用运行时 | 说明 |
| --- | --- | --- | --- |
| `deploy_dir` | string | 全部 | 目标服务器上的部署目录，如 `/opt/apps/auth-tool`；JAR / STATIC 必填 |
| `container_name` | string | DOCKER | 容器名，默认 `{project_code}` |
| `compose_file` | string | DOCKER | 仓库内 compose 文件相对路径，如 `auth-tool/docker-compose.yml`；填写后走 compose 启动 |
| `ports` | string[] | DOCKER | 端口映射列表，如 `["8080:8080"]` |
| `env` | object | DOCKER | 容器环境变量键值对，如 `{"SPRING_PROFILES_ACTIVE": "prod"}` |
| `restart_policy` | string | DOCKER | 容器重启策略，默认 `unless-stopped` |
| `service_name` | string | JAR | systemd 服务名，默认 `{project_code}` |
| `jar_name` | string | JAR | 部署后的 jar 文件名，默认沿用产物名，如 `auth-tool.jar` |
| `jvm_opts` | string | JAR | JVM 启动参数，如 `-Xms512m -Xmx1024m -Dfile.encoding=UTF-8` |
| `start_command` | string | JAR / STATIC | 自定义启动命令；填写后覆盖默认的 systemd / Nginx 行为 |
| `nginx_server_name` | string | STATIC | Nginx `server_name`，如 `tool.example.com` |
| `nginx_root` | string | STATIC | 静态站点根目录，默认 `{deploy_dir}/dist` |
| `nginx_extra_config` | string | STATIC | 追加到 server 块的 Nginx 配置片段（location、proxy_pass 等） |

Docker 容器（对应 `runtime_type=DOCKER`）：

```json
{
  "deploy_dir": "/opt/apps/auth-tool",
  "container_name": "auth-tool",
  "compose_file": "auth-tool/docker-compose.yml",
  "ports": ["8080:8080"],
  "env": { "SPRING_PROFILES_ACTIVE": "prod" },
  "restart_policy": "unless-stopped"
}
```

Java JAR（对应 `runtime_type=JAR`，systemd 托管）：

```json
{
  "deploy_dir": "/opt/apps/auth-rest",
  "service_name": "auth-rest",
  "jar_name": "auth-rest.jar",
  "jvm_opts": "-Xms512m -Xmx1024m -Dfile.encoding=UTF-8"
}
```

前端静态产物（对应 `runtime_type=STATIC`，Nginx 托管）：

```json
{
  "deploy_dir": "/opt/www/auth-tool-web",
  "nginx_server_name": "tool.example.com",
  "nginx_root": "/opt/www/auth-tool-web/dist",
  "nginx_extra_config": "location /api { proxy_pass http://127.0.0.1:8080; }"
}
```

#### 2.3.3 `health_config_json`（健康检查消费）

回答「发布后怎么判定服务可用」。未配置时按 TCP 端口探活兜底。

| 键 | 类型 | 说明 |
| --- | --- | --- |
| `type` | string | `HTTP` / `TCP` / `COMMAND` / `NONE`，默认 `TCP`；`NONE` 表示只校验进程存活、不探活 |
| `port` | int | 探活端口，如 `8080`；默认取 `runtime_config_json.ports` 中的容器内端口 |
| `path` | string | HTTP 探活路径，如 `/actuator/health`，仅 `HTTP` 使用 |
| `expected_status` | int | HTTP 期望状态码，默认 200 |
| `command` | string | `COMMAND` 方式执行的探活命令，退出码 0 视为健康 |
| `interval_seconds` | int | 检查间隔秒数，默认 10 |
| `timeout_seconds` | int | 单次检查超时秒数，默认 3 |
| `retries` | int | 连续失败多少次判定为不健康，默认 3 |
| `start_period_seconds` | int | 发布后的观察期秒数，期间失败不计入 `retries`，默认 30 |

```json
{
  "type": "HTTP",
  "port": 8080,
  "path": "/actuator/health",
  "expected_status": 200,
  "interval_seconds": 10,
  "timeout_seconds": 3,
  "retries": 3,
  "start_period_seconds": 30
}
```

探活结果写入 `deployment_target.health_status`：`0 未检查 / 1 健康 / 2 不健康`。

#### 2.3.4 `retain_release_count`（保留发布版本数）

| 项 | 说明 |
| --- | --- |
| 含义 | 该项目在目标服务器上保留的历史版本数量，供回滚使用 |
| 默认值 | `5`，合法范围 `1-100`，前后端一致（前端 `el-input-number` 限制同范围） |
| 生效时机 | 一次发布成功后清理历史版本，只保留最近 `retain_release_count` 个可回滚版本，超出的版本连同镜像 / 产物一起清理 |
| 与回滚的关系 | 保留数量直接决定可回滚深度；调小不会立即删除已有版本，下一次发布成功时才收敛 |
| 与状态的关系 | 被清理的版本记录状态置为 `release_record.status = 2 已废弃`，不物理删除 |

### 2.4 `project_environment_target`（项目环境部署目标）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| project_id / environment_id / server_id | VARCHAR(32) | 三方外键，组成唯一键 `uk_project_env_server` |
| is_primary | TINYINT | 是否主目标（同项目环境内互斥，最多一个） |
| deploy_order | INT | 多目标发布顺序，默认 1 |
| runtime_config_json | JSON | 目标差异化运行配置（结构与 project.runtime_config_json 一致，见 §2.3.2） |
| status | TINYINT | 状态：0 停用 / 1 启用，默认 1 |

## 3. 枚举设计（`com.lx.deploy.common.enums.project`）

| 枚举 | 取值 | 使用场景 |
| --- | --- | --- |
| RuntimeType | DOCKER / JAR / STATIC | project.runtime_type |
| SourceType | GIT / UPLOAD | project.source_type |
| BuildMode | PLATFORM_TEMPLATE / PROJECT_DOCKERFILE / LAYERED_DOCKER / SCRIPT_DEPLOY / ARTIFACT_ONLY | project.build_mode；AIops 项目用 LAYERED_DOCKER |
| DeployStrategy | SINGLE_TARGET / ALL_AT_ONCE / ROLLING | environment.deploy_strategy |

状态类字段不建枚举：`project.status`、`project_environment_target.status` 使用 `com.lx.deploy.common.constants.EnableStatus` 常量（`0 停用 / 1 启用`），规则见 AGENTS.md §4.5、§22.4。

枚举取值与《需求设计文档》§306-308、§520-521 对齐，数据库存字符串编码，业务代码走 `fromCode()`。

## 5. 接口清单

三张表各自提供标准六接口（page / list / {id} / POST / PUT / DELETE），前缀分别为 `/project`、`/environment`、`/projectEnvironmentTarget`，统一 `ApiResponse<T>` + requestId。

典型查询示例：

```text
GET /projectEnvironmentTarget/list?projectId={id}&environmentId={id}
→ 返回该项目在该环境下绑定的全部目标服务器（按发布顺序升序）

GET /project/page?pageNum=1&pageSize=10&runtimeType=DOCKER&buildMode=LAYERED_DOCKER
→ 项目列表支持的查询条件：code / name / runtimeType / sourceType / gitBranch / buildMode（以上均为非空字符串等值匹配）、status（数字编码等值匹配）
```

`/project/page` 的构建模式条件是**等值过滤**，配合前端「运行时 + 构建模式」两个下拉可以快速筛出「Docker 分层构建」这类项目。注意 `runtime_type` 与 `build_mode` 是两个独立的**过滤**维度（过滤时不联动），但两者的**组合**在新增/修改时受约束（见 §6.5）。

## 6. 核心业务规则与代码逻辑

### 6.1 ProjectService

**新增/修改校验链**（`validateBusinessRule`，修改时 `excludeId` 排除自身）：

1. code / name 必填，code 匹配 `^[A-Za-z0-9_-]{2,64}$`；
2. runtimeType 必填且必须是 RuntimeType 枚举值；
3. sourceType / buildMode 选填但必须是合法枚举值，status 选填但必须是数字 0 或 1（`EnableStatus.isValid` 校验）；
4. **GIT 来源强制填写 gitUrl**（UPLOAD 来源不强制）；
5. retainReleaseCount ≥ 1；
6. 三个 JSON 配置字段用 Jackson `readTree()` 做格式校验（只校验合法 JSON，不校验内部结构 —— 语义校验留给后续构建/健康检查模块按 runtimeType 解析）；
7. code 唯一性预检，冲突抛 `DATA_CONFLICT(4005)`。

**默认值填充**（`applyDefaultValue`）：sourceType=GIT、buildMode=PLATFORM_TEMPLATE、status=1（启用）、retainReleaseCount=5。显式填充而非依赖数据库 DEFAULT，保证新增接口返回的 VO 与库内数据一致。

**删除保护**：删除项目前统计 `project_environment_target` 中引用该项目的记录数，存在引用则抛 DATA_CONFLICT「项目仍被部署目标引用，请先删除或迁移部署目标」。

### 6.2 EnvironmentService

校验链：code 必填且小写格式、name 必填、deployStrategy / batchSize / aiopsEnabled 取值合法、**defaultServerId 存在性校验**（注入 ServerMapper 查询）、code 唯一。

删除保护：同样检查部署目标引用。

### 6.3 ProjectEnvironmentTargetService（本模块业务核心）

**三方存在性校验**：

```text
project_id   → ProjectMapper.selectById   → 不存在抛「项目不存在」
environment_id → EnvironmentMapper.selectById → 不存在抛「环境不存在」
server_id    → ServerMapper.selectById    → 不存在抛「目标服务器不存在」
             → server.status != 1          → 抛「目标服务器已停用，不允许绑定」
```

**绑定唯一性**：同一项目 + 环境 + 服务器只能绑定一次（对齐数据库唯一键 `uk_project_env_server`），修改场景排除自身。

**主目标互斥**（`demoteOtherPrimary`，事务内执行）：

```java
// 当前目标 is_primary = 1 时，将同项目同环境下其他目标的 is_primary 清零
update(new LambdaUpdateWrapper<ProjectEnvironmentTarget>()
        .eq(getProjectId, entity.getProjectId())
        .eq(getEnvironmentId, entity.getEnvironmentId())
        .eq(getIsPrimary, 1)
        .ne(getId, entity.getId())
        .set(getIsPrimary, 0));
```

保证任一「项目 × 环境」组合下最多一个主目标；create/update 均标注 `@Transactional(rollbackFor = Exception.class)`，避免出现双主目标或无主目标的中间状态。

**查询排序**：结果按 `create_time DESC, deploy_order ASC` 排列，同一项目环境下的目标按发布顺序展示。

### 6.4 跨模块依赖方式

校验他表数据时**注入对方 Mapper 而非 Service**：

```java
public ProjectEnvironmentTargetService(ProjectMapper projectMapper,
                                       EnvironmentMapper environmentMapper,
                                       ServerMapper serverMapper) { ... }
```

理由：若 Service 之间互相注入（如 ProjectService 注入 ProjectEnvironmentTargetService），极易形成循环依赖；Mapper 是无状态的纯数据访问层，跨模块引用安全。这是全项目的既定约定。

### 6.5 运行时与构建模式的组合校验（2026-09-23 落地）

规则的唯一来源是 `RuntimeType` 枚举常量上声明的 `supportedBuildModes`，以及 `supports(BuildMode)`：

| 运行时 | 允许的构建模式 | 理由（产物形态） |
| --- | --- | --- |
| `DOCKER` | `PLATFORM_TEMPLATE` / `PROJECT_DOCKERFILE` / `LAYERED_DOCKER` | 产物是镜像，必须推送镜像仓库 |
| `JAR` | `SCRIPT_DEPLOY` / `ARTIFACT_ONLY` | 产物是 JAR 文件，脚本产出或直接发布已有产物 |
| `STATIC` | `SCRIPT_DEPLOY` / `ARTIFACT_ONLY` | 产物是静态目录（dist） |

```java
// ProjectService.validateBusinessRule
RuntimeType runtimeType = RuntimeType.fromCode(dto.getRuntimeType());
BuildMode buildMode = BuildMode.fromCode(dto.getBuildMode());
if (runtimeType != null && buildMode != null && !runtimeType.supports(buildMode)) {
    throw new DeployException(ResponseCode.VALIDATION_ERROR,
            "运行时 " + runtimeType.getCode() + " 不支持构建模式 " + buildMode.getCode()
                    + "，该运行时的可选构建模式为：" + runtimeType.supportedBuildModeCodes());
}
```

- 拒绝时把该运行时的**全部可选模式**回给调用方（`supportedBuildModeCodes()` 按枚举声明顺序输出，文案稳定）；
- 前端用同一份矩阵做下拉联动：运行时变化时，若当前构建模式不被支持，自动切到第一个可选模式；
- 历史数据中的非法组合不会被自动修正，但再次保存时会被拦下。

### 6.6 凭据与镜像仓库的引用校验

项目有两个外部引用，都在保存前校验、且都受「删除保护」呼应：

| 字段 | 校验内容 | 不满足时的响应 |
| --- | --- | --- |
| `git_credential_id` | 凭据存在，且类型为 GIT_TOKEN 或 SSH_KEY | 4001（不存在 / 类型不符） |
| `registry_id` | **仅 DOCKER 运行时**可填；仓库存在且状态为启用 | 4001（运行时不符 / 不存在 / 已停用） |

- 校验统一注入对方 Mapper（`CredentialMapper` / `RegistryMapper`），不注入对方 Service，避免 Service 循环依赖；
- 两个字段都标注 `updateStrategy = FieldStrategy.ALWAYS`：**清空 / 换绑能真正落库**。
  这一条是实测出来的——未标注时 DOCKER 项目改成 JAR 后 `registry_id` 仍残留仓库绑定，
  形成「运行时是 JAR 却挂着镜像仓库」的自相矛盾数据（详见 AGENTS.md §10.1）。

## 7. 与其他模块的关系

| 方向 | 关系 |
| --- | --- |
| ← server 模块 | target.server_id 引用 server 表；删除服务器时本模块的引用数据可能悬空（见 §8） |
| → 后续构建/发布模块 | build / deployment / deployment_target 按 project_id + environment_id 消费本模块定义的发布拓扑；`build_config_json`（§2.3.1）是构建模块解析「仓库 → 产物」的输入契约，多模块仓库通过 `module_name` / `module_dir` 区分子模块 |
| → credential 模块 | `project.git_credential_id` 指向 credential 表，类型必须是 GIT_TOKEN / SSH_KEY；凭据被本项目引用期间不允许删除（见 [凭据模块.md](凭据模块.md)） |
| → registry 模块 | `project.registry_id` 指向 registry 表，仅 DOCKER 运行时项目有值；仓库被本项目绑定期间不允许删除（见 [镜像仓库模块.md](镜像仓库模块.md)） |

## 8. 已知边界与后续演进

- **删除顺序依赖人工遵守**：项目/环境删除有引用保护，但 server 删除无反向保护，规范操作顺序为「先删部署目标 → 再删服务器」；
- **JSON 配置只做格式校验**：`build_config_json` / `runtime_config_json` / `health_config_json` 的内部结构（如 `module_name` / `artifact_path`）待构建、发布、健康检查模块落地时按 `runtimeType` 解析消费；三段 schema 与 Maven 多模块仓库的解析约定已在 [§2.3](#23-三段-json-配置字段约定构建--运行--健康检查) 先行锁定，作为下游模块的开发契约，避免前后端口径漂移；
- **凭据与仓库引用已校验**（2026-09-23）：`git_credential_id` 与 `registry_id` 在保存时校验存在性与类型，删除凭据 / 仓库时反向拦截（见 §6.6）；
- **`registry_id` 只在 DOCKER 运行时可绑定**：脚本部署与仅发布产物没有镜像推送目标；运行时从 DOCKER 改成 JAR / STATIC 时该字段会被清空（字段策略 `ALWAYS`），不会残留矛盾绑定；
- **三段 JSON 的内部键名仍未校验**：`registry_id` 解决的是「推到哪个仓库」，镜像名 / 标签仍由 `build_config_json` 与构建逻辑决定；
- **环境编码枚举约束**：设计上约定 dev/test/prod，当前只做格式校验未做白名单 —— 保留灵活性，允许用户自定义环境（如 staging），符合轻量定位。
