# 项目模块文档

> 模块包：`com.lx.deploy.project` ｜ 对应数据表：`project`、`environment`、`project_environment_target` ｜ 状态：已完成并编译通过

## 1. 模块定位

项目模块是发布链路的起点，回答三个问题：

1. **发布什么** —— `project` 表登记项目的运行时（DOCKER/JAR/STATIC）、代码来源与构建模式；
2. **发到哪** —— `environment` 表定义部署环境（dev/test/prod）与部署策略（单目标/全量/滚动）；
3. **具体发到哪台机器** —— `project_environment_target` 表把「项目 × 环境」绑定到具体服务器，形成完整发布拓扑。

**「一个 project = 一个可部署的服务模块」是本模块的建模基准**（见 AGENTS.md §23.1）：`project` 登记的是一条可独立构建、独立发布、独立回滚的发布单元记录，不是「一个 Git 仓库一条记录」。因此多模块仓库（如 `auth-system-Iteration` 下的 `auth-system` / `auth-rest` / `auth-tool`）在同一 `git_url` + `git_branch` 下会创建多条 project，靠 `build_config_json.module_name` 区分（见 §2.3.1），唯一性只由 `code` 保证。

三表关系：

```text
project ────┐
            ├──▶ project_environment_target ──▶ server（服务器模块）
environment ┘
```

## 1.1 调用链路（前端 → 后端）

项目模块大部分是**同步 CRUD**（Controller → Service → Mapper，不触发 `lds_task`、不连 SSH）。唯一异步入口是「项目连通性测试」。

```text
项目 CRUD：
lighit-deploy-ui/src/api/project.ts
  ├─ 列表/详情/新增/修改/删除 → GET|POST|PUT|DELETE /project/* → ProjectController
  │     （project/controller/ProjectController.java，detail@74 / create@87 / test@121）
  │     → ProjectService / EnvironmentService / ProjectEnvironmentTargetService → Mapper 直写三张表
  └─ testProjectConnectivity(id)            // project.ts:45
        │  POST /project/test/{id}
        ▼
      ProjectController.test()              // ProjectController.java:121
        ▼
      ProjectService.submitConnectivityTest(id)  // project/service/ProjectService.java:123
        │  hasUnfinishedTask 防重 → taskService.create(dto) 插 PROJECT_TEST 任务（task_type=PROJECT_TEST）
        ▼  （立即返回 taskId）
┄┄┄┄┄┄┄┄┄┄┄┄ TaskExecutor 轮询 ┄┄┄┄┄┄┄┄┄┄┄┄
      ProjectConnectTestTaskHandler.execute(task)  // task/executor/ProjectConnectTestTaskHandler.java:224
        │  SSH 连 build_server_id 指向的构建机，校验 Git/镜像仓库/工具链
        ▼
      lds_task_log（实时日志，前端 GET /taskLog/pull 拉取）
```

环境、部署目标同理为同步 CRUD：`EnvironmentController` / `ProjectEnvironmentTargetController`（见 `project/controller/`）。发布时由 `DeploymentService.createAndTrigger` 消费它们的拓扑（见 [环境与部署目标.md](环境与部署目标.md)）。

## 2. 数据表结构

### 2.1 `project`（部署项目）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| code | VARCHAR(64) | 项目编码，唯一键，`^[A-Za-z0-9_-]{2,64}$` |
| name | VARCHAR(100) | 项目名称 |
| runtime_type | VARCHAR(20) | 运行时：DOCKER / JAR / STATIC |
| source_type | VARCHAR(20) | 代码来源：GIT / UPLOAD，默认 GIT |
| git_url / git_branch / git_credential_id | - | Git 来源信息；凭据指向独立 credential 表 |
| build_mode | VARCHAR(30) | 构建模式，默认 PROJECT_DOCKERFILE；与 runtime_type 的组合受约束（见 §6.5） |
| registry_id | VARCHAR(32) | 镜像仓库 ID，仅 DOCKER 运行时可绑定，指向 registry 表；JAR / STATIC 必须为空 |
| build_server_id | VARCHAR(32) | 构建机（服务器 ID，选填），指向 server 表；见 [§6.7 构建机绑定与项目连通性测试](#67-构建机绑定与项目连通性测试) |
| build_config_json / runtime_config_json / health_config_json | JSON | 三段配置（当前只做格式校验、不解析语义）；键名 schema 与完整示例见 [§2.3](#23-三段-json-配置字段约定构建--运行--健康检查) |
| retain_release_count | INT | 保留发布版本数，默认 5 |
| status | TINYINT | 状态：0 停用 / 1 启用，默认 1 |

### 2.2 `environment`（部署环境）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| code | VARCHAR(32) | 环境编码（dev/test/prod），`^[a-z][a-z0-9-]{1,31}$` |
| name | VARCHAR(100) | 环境名称 |
| deploy_strategy | VARCHAR(30) | SINGLE_TARGET / ALL_AT_ONCE / ROLLING，默认 SINGLE_TARGET |
| batch_size | INT | 滚动发布批次大小，默认 1 |
| aiops_enabled | TINYINT | 是否启用 AIops 联动（发布静默窗口），默认 0 |

> **环境表不含任何服务器字段，这是刻意的。** 原 `default_server_id`（「默认服务器」）已于
> 2026-09-28 移除：环境是全局共享的，一个环境被多个项目引用，而各项目在该环境下绑定哪些机器由
> `project_environment_target` 决定，环境层面给不出有意义的「默认服务器」。
> 需要表达「主要发这一台」用部署目标的 `is_primary`。硬约束见 AGENTS §24.11。

### 2.3 三段 JSON 配置字段约定（构建 / 运行 / 健康检查）

> 前端编辑形态：项目新增 / 编辑页（`views/project/edit.vue`）对三段配置提供「表单 / JSON」双模式编辑，
> 表单模式按 `lighit-deploy-ui/src/constants/projectConfig.ts` 的 schema 常量分组渲染并按运行时 / 构建模式联动显隐；
> schema 外的自定义键保存时原样合并、不静默丢弃。**键名变更必须同步该常量文件与本节**（示例唯一来源规则见 AGENTS.md §20.2）。

`project` 表用三段 JSON 描述「怎么构建、怎么运行、怎么判定可用」。当前 `ProjectService` 只校验其是否为合法 JSON（见 §6.1），**不做语义解析**；语义校验、默认值填充与兼容处理由后续构建 / 发布 / 健康检查模块消费。为避免各模块实现时字段语义漂移、前后端口径不一致，此处先行锁定 schema，作为下游模块的开发契约。

> **核心原则**：一个 project = 一个发布单元（见 AGENTS.md §23.1）。三段 JSON 只描述「本发布单元自身」的构建与运行细节，不重复承载仓库地址、分支、目标环境等已落在 `git_url` / `git_branch` / `environment` / `project_environment_target` 的信息。

- 键名统一 `snake_case`，与数据库列命名风格一致，禁止在同一份配置里混用驼峰；
- 三段 JSON 均为可选字段，但一旦填写必须是合法 JSON；
- 三段 JSON 都允许清空：表单提交空串时 Service 归一为 `null`，实体用 `updateStrategy = FieldStrategy.ALWAYS` 保证真的写入 NULL（否则会出现「能设置、不能清空」，见 AGENTS.md §10.1）；
- 未填写的键由消费方模块按本文档给出的默认值处理，Service 层不介入；
- 表单直接编辑原始 JSON 文本，前端只做 JSON 语法校验，不做语义校验（与后端一致）。

#### 2.3.1 `build_config_json`（构建模块消费）

回答「仓库拉取之后，如何定位子模块并构建出本项目的产物」。

| 键 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `module_name` | string | 多模块仓库必填 | 子模块名，如 `auth-tool`。同时是默认 `-pl` 参数、默认模块目录名与默认镜像名的来源 |
| `module_dir` | string | 否 | 子模块相对仓库根的目录，默认等于 `module_name`；单模块仓库可省略（默认仓库根目录）。平台会先 `cd` 到该目录再执行构建命令，因此命令里**不要再写 `-pl` 指定同一模块**（见下方「`module_dir` 与 `-pl` 只能二选一」） |
| `pom_path` | string | 否 | Maven 构建入口 pom 路径，默认 `{module_dir}/pom.xml`；单模块仓库默认 `pom.xml` |
| `build_command` | string | `SCRIPT_DEPLOY` 必填 | 完整构建命令，在「执行目录」（`module_dir` → `module_name` → 仓库根）下执行。**只有脚本部署消费该键**：`PROJECT_DOCKERFILE` / `LAYERED_DOCKER` / `JAR_PREBUILD` 的构建命令由平台内置（`docker build` / Maven 容器），填了也不会执行。两种写法任选其一：填了 `module_dir` 用 `mvn -B clean package -DskipTests`，`module_dir` 留空用 `mvn -B clean package -pl auth-tool -am -DskipTests`。工具不在非交互式会话 PATH 里时，优先在服务器档案配「构建环境初始化脚本」 |
| `command_timeout_seconds` | int | 否 | 构建命令的等待上限（秒），不填用平台默认值（`light-deploy.ssh.long-command-timeout-seconds`，默认 1800）。首次构建要下载全部依赖属分钟级、增量构建通常几十秒，按项目给更贴合实际；超时后平台会终止远端构建进程组，并把卡住前已收到的输出留在任务日志里（见 [构建模块.md §6.2.4](构建模块.md)） |
| `dockerfile_path` | string | `PROJECT_DOCKERFILE` / `LAYERED_DOCKER` / `JAR_PREBUILD` 必填 | Dockerfile 相对仓库根路径；`JAR_PREBUILD` 指向项目提供的极简 Dockerfile（FROM jre + COPY jar） |
| `base_dockerfile_path` | string | `LAYERED_DOCKER` 必填 | 分层构建的基础层 Dockerfile 路径，如 `Dockerfile.base` |
| `artifact_path` | string | `JAR` / `STATIC` 运行时必填 | 构建产物相对路径，支持 `*` 通配；**相对仓库根优先**，未命中再按 `module_dir` 回落的口径查找，如 `auth-tool/linux/auth-tool-7888/auth-tool.jar` |
| `config_paths` | string | JAR 选填 | 随产物一起发布的配置文件相对路径，多个用英文逗号分隔，支持 `*` 通配；口径同 `artifact_path`，构建时转存到产物同级的 `config` 目录，如 `auth-tool/linux/auth-tool-7888/application.yml` |
| `image_repository` | string | `DOCKER` 运行时建议填写 | 业务镜像仓库地址（不含 tag），如 `registry.cn-hangzhou.aliyuncs.com/lx/auth-tool`。留空时回落 `registry 地址 + namespace + (module_name\|项目编码)`；**tag 由平台按 `{项目编码}-v{序号}-{提交短码}` 生成，不可配模板** |
| `maven_settings_path` | string | `JAR_PREBUILD` 选填 | Maven `settings.xml` 相对仓库根路径，如 `auth-tool/Docker/settings.xml`。填了平台打 jar 时加 `-s` 指向它（典型用途：切阿里云镜像加速）；留空走公网 Maven Central，内网构建机极慢 |
| `compose_file_path` | string | DOCKER 选填 | `docker-compose.yml` 相对仓库根路径，默认 `docker-compose.yml`；**想在目标机上用 `docker compose` 启动时填写**。构建成功会把文件**原文**快照进发布版本，发布时原样下发 → 改了这份文件**必须重新构建**才生效。随版本变化的镜像要写成 `image: 仓库地址/镜像名:${IMAGE_TAG}`，平台把本次版本号作为同名变量注入；**显式填了路径却读不到会直接构建失败**，没填且默认文件不存在则静默跳过（视为不用 compose） |
| `docker_verify_on_build` | bool | DOCKER 选填 | 构建期启动级验证开关（Plan C 闸门），默认 `true`。`docker build` 之后、`docker push` 之前以 `docker run -d` 起容器，窗口内逐秒 `docker inspect .State.Running` 判活，结束后读 `Running / ExitCode / OOMKilled` 定论（**不依赖退出码**，避免容器被 SIGKILL 时 sshd 只回 `exit-signal`、`getExitStatus()` 为 null 导致 `exit=-1` 误判）；应用启动依赖构建机不可达的外部资源（DB/HTTP）时设 `false` 跳过，完全依赖目标机业务级验证 |
| `docker_verify_timeout_seconds` | int | DOCKER 选填 | 启动级验证的存活窗口（秒），默认 `30`；启动慢的应用适当调大 |

**单模块仓库（默认，可极简）：**

```json
{
  "build_tool": "MAVEN",
  "build_command": "mvn clean package -DskipTests",
  "artifact_path": "target/auth-app-*.jar"
}
```

**Maven 多模块仓库（同一仓库含多个可独立发布子模块）：**

`auth-system-Iteration` 是父工程（`packaging=pom`），其下 `auth-system` / `auth-rest` / `auth-tool` 是三个独立可发布子模块。**不需要拆 Git 仓库，也不需要改 project 表结构**：在同一 `git_url` + `git_branch` 下建三条 project 记录，各自通过 `module_name` 指向不同子模块即可。

```json
{
  "module_name": "auth-tool",
  "module_dir": "auth-tool",
  "build_command": "mvn -B clean package -DskipTests",
  "dockerfile_path": "auth-tool/Docker/Dockerfile",
  "docker_verify_on_build": true,
  "docker_verify_timeout_seconds": 30,
  "artifact_path": "auth-tool/target/auth-tool.jar"
}
```

```json
{
  "module_name": "auth-rest",
  "module_dir": "auth-rest",
  "build_command": "mvn -B clean package -DskipTests",
  "dockerfile_path": "auth-rest/Dockerfile",
  "artifact_path": "auth-rest/target/auth-rest.jar"
}
```

```json
{
  "module_name": "auth-system",
  "module_dir": "auth-system",
  "build_command": "mvn -B clean package -DskipTests",
  "artifact_path": "auth-system/target/auth-system-*.jar"
}
```

> **`module_dir` 与 `-pl` 只能二选一**（AGENTS.md §23.3、[构建模块.md §6.2.1](构建模块.md)）：填了 `module_dir`，
> 平台会先 `cd {仓库根}/{module_dir}` 再执行构建命令，此时命令里再写 `-pl auth-tool -am`，Maven 从子模块
> pom 起构建、reactor 里没有名为 `auth-tool` 的模块，必然报 `Could not find the selected project in the reactor`。
> 上例用的是「`module_dir` + 模块内命令」这一种；若偏好仓库根 + `-pl`，则清空 `module_dir`、命令写
> `mvn -B clean package -pl auth-tool -am -DskipTests`。编辑页会直接拦截这种组合（表单模式提交时校验）。

**执行流程**：拉取代码 → 解析 `build_config_json` → 进入执行目录执行 `build_command`（执行目录 = `module_dir`，未填则 `module_name`，都没填则仓库根；**二选一，不要再叠加 `-pl`**）→ 按 `artifact_path` 取产物 → 按 `runtime_type` 生成镜像或上传产物。命令执行前平台会先引入登录态环境与构建机档案的「构建环境初始化脚本」，并预检命令首词是否可执行（见 [构建模块.md §6.2.2](构建模块.md)）。

**多模块解析约定**（完整规则见 AGENTS.md §23.3）：

1. 仓库只拉一次：同一 `git_url` + 分支的子模块共享一次 `git clone` 与工作区缓存，产物目录按 `project.code` + 版本号隔离；
2. 按 `module_dir` / `-pl` 局部构建，避免每次构建整个仓库；
3. 每个子模块 project 独立登记 `release_record`、独立走 `deployment`，互不影响，支持各自回滚；
4. 模块间依赖由 Maven / Gradle 依赖图保证（`-am` 会一并构建被依赖模块），project 表不表达模块依赖关系。

#### 2.3.2 `runtime_config_json`（发布模块消费）

回答「产物在目标服务器上怎么跑起来」。按 `runtime_type` 读取对应键，其他键忽略。

| 键 | 类型 | 适用运行时 | 说明 |
| --- | --- | --- | --- |
| `work_dir` | string | JAR | 目标机上的**固定**工作目录，如 `/lx/jarapps/auth-tool-7888`；**填了即完全覆盖服务器档案的部署根目录**（不拼接、不转换），留空才回落到「目标机部署根目录 `/apps` / 项目编码」。发版为原地替换 jar，systemd 单元只在首次部署生成。必须写**绝对路径**：平台按字面使用，相对路径会相对 SSH 登录用户的家目录解析 |
| `service_name` | string | JAR | systemd 服务名（不含 `.service`），默认 `{project_code}` |
| `jvm_options` | string | JAR | JVM 启动参数，如 `-Xms256m -Xmx512m` |
| `java_bin` | string | JAR | java 可执行文件绝对路径；留空时由平台在**每台目标机**探测 `command -v java`。**注意这是项目级配置，会套用到所有目标机**：各机器 JDK 路径不同时请留空，或在具体部署目标上单独覆盖（目标级配置按 key 覆盖项目级）。填错的表现是目标机 systemd 单元里 ExecStart 指向不存在的路径、服务以 `status=203/EXEC` 起不来，而**单元只在首次部署生成、之后不因配置变更重写** |
| `spring_profiles_active` | string | JAR | 传给 `-Dspring.profiles.active`，默认 `prod` |
| `config_dir` | string | JAR | 工作目录下的配置目录名，默认 `config` |
| `config_file` | string | JAR | 配置文件名，默认 `application.yml`，用于 `--spring.config.location` |
| `deploy_base` | string | — | **当前版本后端未消费**：`DeployTaskHandler.deployBase()` 只读 `server.agent_base_dir`，没有读这个键。字段保留只为兼容历史配置，要指定目录请填 `work_dir` |
| `deploy_form` | string | DOCKER | 部署形态：`RUN`（默认，平台拼 `docker run`）/ `COMPOSE`（用项目提供的 compose 文件启动）。选 `COMPOSE` 后 `container_name` / `port_mappings` / `extra_docker_args` **不再生效**——它们表达的是 `docker run` 的参数，硬套到 compose 上只会造成「配了却没生效」。可被部署目标级同名配置覆盖 |
| `container_name` | string | DOCKER | 容器名，默认 `{project_code}` |
| `port_mappings` | string | DOCKER | 端口映射，形如 `8080:8080`，多个用英文逗号分隔；留空表示不映射 |
| `extra_docker_args` | string | DOCKER | 附加 `docker run` 参数，原样拼到命令行 |
| `static_root` | string | STATIC | 静态产物发布根目录（Nginx root），默认 `/usr/share/nginx/html/{project_code}` |

> 历史契约里的 `deploy_dir` / `ports` / `env` / `jvm_opts` / `jar_name` 等键**从未被实现消费**，
> 填写后会被静默忽略。JAR 用 `work_dir` 这一组；DOCKER 的 RUN 形态用 `container_name` + `port_mappings` 这一组，COMPOSE 形态只认项目自己的 compose 文件（见 `deploy_form`）。

Docker 容器（对应 `runtime_type=DOCKER`）：

```json
{
  "container_name": "auth-tool",
  "port_mappings": "8080:8080",
  "extra_docker_args": "-e SPRING_PROFILES_ACTIVE=prod"
}
```

Java JAR（对应 `runtime_type=JAR`，systemd 托管，固定工作目录 + 原地替换）：

```json
{
  "work_dir": "/lx/jarapps/auth-tool-7888",
  "service_name": "auth-tool-7888",
  "java_bin": "/usr/lib/jdk1.8.0_121/bin/java",
  "jvm_options": "-Xmx512m",
  "spring_profiles_active": "prod",
  "config_dir": "config",
  "config_file": "application.yml"
}
```

前端静态产物（对应 `runtime_type=STATIC`，Nginx 托管）：

```json
{
  "static_root": "/usr/share/nginx/html/auth-tool-web"
}
```

#### 2.3.3 `health_config_json`（健康检查消费）

回答「发布后怎么判定服务可用」。**未配置（字段为空）时直接跳过健康检查**，不做任何兜底探测。

| 键 | 类型 | 说明 |
| --- | --- | --- |
| `type` | string | `HTTP` / `TCP`，默认 `HTTP`；2xx 视为健康（HTTP 只认状态码范围，不比对具体值） |
| `port` | int | 探活端口，必填：TCP 连该端口，HTTP 请求 `http://host:port/path` |
| `path` | string | HTTP 探活路径，默认 `/`，仅 `HTTP` 使用；TCP 忽略。**必须免鉴权且直接返回 200**，见下方重定向说明 |
| `timeout_seconds` | int | 单次探测超时秒数，默认 3 |
| `retry_count` | int | 最大探测次数（含首次），默认 3；任一次通过即健康 |
| `interval_seconds` | int | 两次探测之间的等待秒数，默认 3；给应用留出启动时间 |

```json
{
  "type": "HTTP",
  "port": 8080,
  "path": "/actuator/health",
  "timeout_seconds": 3,
  "retry_count": 10,
  "interval_seconds": 5
}
```

探测在**平台侧**发起（不是到目标机上 curl），因此平台必须能访问目标机的业务端口；探测逻辑见 `HealthChecker`，
不健康只会把部署目标判为失败并在日志写明「健康检查不通过」，不改变已完成的发布动作。

> **HTTP 探活不跟随重定向**：`HealthChecker` 用 JDK `HttpClient`，默认 `followRedirects = NEVER`。
> 因此 `path` 必须是一个**免鉴权、直接返回 200** 的接口——返回 302（典型如根路径跳登录页）、
> 401、403 都会被判为不健康。带登录态的系统要在拦截器/网关里显式放行该路径，
> 不要图省事填 `/`。探活端点建议只证明「进程活着」，不要级联查 DB/Redis，
> 否则依赖抖动会把一次正常的发布判成失败。

> 历史契约里的 `expected_status` / `command` / `start_period_seconds` / `retries` 等键**从未被实现消费**，
> 填写后会被静默忽略；`COMMAND` 远程命令探测当前不实现。

探活结果写入 `deployment_target.health_status`：`0 未检查 / 1 健康 / 2 不健康`。

#### 2.3.4 `retain_release_count`（保留发布版本数）

| 项 | 说明 |
| --- | --- |
| 含义 | 该项目保留多少个处于「可发布」状态的版本，超出部分连同构建机上的产物目录一起回收 |
| 默认值 | `5`，合法范围 `1-100`，前后端一致（前端 `el-input-number` 限制同范围） |
| 生效时机 | **构建成功后**（`BuildTaskHandler.applyRetentionPolicy`），不是发布成功后。顺序固定为「先删构建机磁盘产物，再置记录废弃」；回收失败只记日志，不影响构建结论 |
| 保护窗口 | 最近 20 次部署引用过的版本**一律不回收**：回滚按 `old_version` 重新发布，把某台机器正跑着的版本清掉会让回滚与新发同时断掉 |
| 与状态的关系 | 被回收的版本记录置 `release_record.status = 2 已废弃`，**不物理删除**，因此不再出现在新建部署的版本下拉里（下拉只列「可发布」） |
| 与回滚的关系 | 保留数量决定可回滚深度；调小不会立即删除已有版本，**下一次构建成功时才收敛** |
| 未配置时 | 值为 null 或 ≤ 0 时**不做任何回收**——没有明确配额就删东西风险太高 |

> **口径变更**：早期把这里写成「发布成功后清理」。实际消费方是构建链路（发布链路不删产物），且此前该字段**完全没有实现**、构建机产物只增不减。完整设计与两条安全边界见 [构建模块.md](构建模块.md) §6.7。

#### 2.3.5 一套可直接执行的验证样例（用 light-deploy 自身仓库自举）

新环境第一次跑通「构建 → 发布 → 健康检查」时，用本仓库当样例最省事：公开仓库、单模块 Maven、产物是可执行 jar，
不需要准备第二个业务项目。下表字段全部对应项目档案表单，三段 JSON 可直接粘贴。

| 表单字段 | 取值 |
| --- | --- |
| 项目编码 | `light-deploy`（服务名、工作目录默认值都由它推导） |
| Git 地址 | `https://gitee.com/wangan2022/light-deploy.git` |
| 分支 | `main` |
| Git 凭据 | 公开仓库可留空；私有仓库选已录入的 GIT_TOKEN / SSH_KEY 凭据 |
| 运行时类型 | `JAR` |
| 构建模式 | `SCRIPT_DEPLOY` |
| 构建机 | 已做过连通性测试、且装好 git / JDK 21 / Maven 的机器 |
| 镜像仓库 | 留空（脚本部署不产出镜像） |

构建配置 `build_config_json`：

```json
{
  "build_command": "mvn -B clean package -DskipTests",
  "artifact_path": "target/light-deploy-0.0.1-SNAPSHOT.jar",
  "config_paths": "src/main/resources/application.yaml"
}
```

- `module_name` / `module_dir` 留空：本仓库是单模块，`build_command` 在仓库根目录执行。
- `artifact_path` 写精确文件名而不用 `target/*.jar`：Spring Boot repackage 会同时产出 `xxx.jar.original`，
  通配取首个匹配虽然通常正确，但精确写死更可预期。
- `config_paths` 把 `application.yaml` 转存到产物同级的 `config` 目录，发布时投到目标机 `config` 子目录，
  jar 与配置分离——日常发版只换 jar，不碰配置。

运行配置 `runtime_config_json`：

```json
{
  "service_name": "light-deploy",
  "java_bin": "/usr/bin/java",
  "jvm_options": "-Xms256m -Xmx512m",
  "spring_profiles_active": "prod",
  "config_dir": "config",
  "config_file": "application.yaml"
}
```

- `work_dir` 留空即可，回落到「目标机部署根目录 `/apps/light-deploy`」；想指定就写绝对路径。
- `java_bin` 留空时平台在目标机 `command -v java` 探测；多 JDK 环境建议显式写绝对路径。
- `config_file` 必须与 `config_paths` 指向的文件名一致（本仓库是 `.yaml` 不是 `.yml`）。

健康检查 `health_config_json`（先用 TCP 探端口，起得来再换 HTTP）：

```json
{
  "type": "TCP",
  "port": 2027,
  "timeout_seconds": 3,
  "retry_count": 20,
  "interval_seconds": 5
}
```

前置条件与预期结果：

1. 构建机：`git`、`mvn`（或把命令换成 `./mvnw -B clean package -DskipTests`）、JDK 21；能访问 gitee。
2. 目标机：JDK 21、`systemd`（服务名 `light-deploy`）；MySQL（库 `deploy`）与 Redis 可用，
   否则应用启动会失败，健康检查判不健康——只想验证链路就先把 `health_config_json` 清空跳过检查。
3. 服务器档案：构建机填「构建工作区」「产物持久目录」，目标机填「部署根目录」（为空会在发布阶段直接报错）。
4. 首次发布：平台上传并执行 `jar-init.py` 生成 systemd 单元；之后每次发版走「备份 → 替换 jar → systemctl restart」，
   备份落在 `work_dir/exec/bak`，命名 `{jar}_bak_{时间戳}_{版本号}.jar`（版本号内嵌在文件名里，取不到时省略该段）。
   `exec/` 下的三份内置脚本每次发布都会重新投放（脚本版本随平台走，详见 [发布模块.md §6.3](发布模块.md)）。

## 6. 核心业务规则与代码逻辑

### 6.1 ProjectService

**新增/修改校验链**（`validateBusinessRule`，修改时 `excludeId` 排除自身）：

1. code / name 必填，code 匹配 `^[A-Za-z0-9_-]{2,64}$`；
2. runtimeType 必填且必须是 RuntimeType 枚举值；
3. sourceType / buildMode 选填但必须是合法枚举值，status 选填但必须是数字 0 或 1（`EnableStatus.isValid` 校验）；
4. **GIT 来源强制填写 gitUrl**（UPLOAD 来源不强制）；
5. retainReleaseCount ≥ 1；
6. 三个 JSON 配置字段用 Jackson `readTree()` 做格式校验（只校验合法 JSON，不校验内部结构 —— 语义校验留给后续构建/健康检查模块按 runtimeType 解析）；
7. code 唯一性预检，冲突抛 `DATA_CONFLICT(4005)`。

**默认值填充**（`applyDefaultValue`）：sourceType=GIT、buildMode=PROJECT_DOCKERFILE、status=1（启用）、retainReleaseCount=5。显式填充而非依赖数据库 DEFAULT，保证新增接口返回的 VO 与库内数据一致。

**删除保护**：删除项目前统计 `project_environment_target` 中引用该项目的记录数，存在引用则抛 DATA_CONFLICT「项目仍被部署目标引用，请先删除或迁移部署目标」。

### 6.2 EnvironmentService

校验链：code 必填且小写格式、name 必填、deployStrategy / batchSize / aiopsEnabled 取值合法、code 唯一。

> 该 Service **不依赖 ServerMapper**：环境不持有服务器，无需任何存在性校验（AGENTS §24.11）。

删除保护：同样检查部署目标引用。

### 6.3 ProjectEnvironmentTargetService（本模块业务核心）

**三方存在性校验**：

```text
project_id   → ProjectMapper.selectById   → 不存在抛「项目不存在」
environment_id → EnvironmentMapper.selectById → 不存在抛「环境不存在」
server_id    → ServerMapper.selectById    → 不存在抛「目标服务器不存在」
             → server.status != 1          → 抛「目标服务器已停用，不允许绑定」
```

**绑定唯一性**：同一项目 + 环境 + 服务器只能绑定一次（对齐数据库唯一键 `uk_project_env_server`），修改场景排除自身。

**主目标互斥**（`demoteOtherPrimary`，事务内执行）：

```java
// 当前目标 is_primary = 1 时，将同项目同环境下其他目标的 is_primary 清零
update(new LambdaUpdateWrapper<ProjectEnvironmentTarget>()
        .eq(getProjectId, entity.getProjectId())
        .eq(getEnvironmentId, entity.getEnvironmentId())
        .eq(getIsPrimary, 1)
        .ne(getId, entity.getId())
        .set(getIsPrimary, 0));
```

保证任一「项目 × 环境」组合下最多一个主目标；create/update 均标注 `@Transactional(rollbackFor = Exception.class)`，避免出现双主目标或无主目标的中间状态。

**查询排序**：结果按 `create_time DESC, deploy_order ASC` 排列，同一项目环境下的目标按发布顺序展示。

### 6.4 跨模块依赖方式

校验他表数据时**注入对方 Mapper 而非 Service**：

```java
public ProjectEnvironmentTargetService(ProjectMapper projectMapper,
                                       EnvironmentMapper environmentMapper,
                                       ServerMapper serverMapper) { ... }
```

理由：若 Service 之间互相注入（如 ProjectService 注入 ProjectEnvironmentTargetService），极易形成循环依赖；Mapper 是无状态的纯数据访问层，跨模块引用安全。这是全项目的既定约定。

### 6.5 运行时与构建模式的组合校验（2026-09-23 落地）

规则的唯一来源是 `RuntimeType` 枚举常量上声明的 `supportedBuildModes`，以及 `supports(BuildMode)`：

| 运行时 | 允许的构建模式 | 理由（产物形态） |
| --- | --- | --- |
| `DOCKER` | `PROJECT_DOCKERFILE` / `LAYERED_DOCKER` / `JAR_PREBUILD` | 产物是镜像，必须推送镜像仓库（JAR_PREBUILD 先打 jar 再包镜像） |
| `JAR` | `SCRIPT_DEPLOY` / `ARTIFACT_ONLY` | 产物是 JAR 文件，脚本产出或直接发布已有产物 |
| `STATIC` | `SCRIPT_DEPLOY` / `ARTIFACT_ONLY` | 产物是静态目录（dist） |

```java
// ProjectService.validateBusinessRule
RuntimeType runtimeType = RuntimeType.fromCode(dto.getRuntimeType());
BuildMode buildMode = BuildMode.fromCode(dto.getBuildMode());
if (runtimeType != null && buildMode != null && !runtimeType.supports(buildMode)) {
    throw new DeployException(ResponseCode.VALIDATION_ERROR,
            "运行时 " + runtimeType.getCode() + " 不支持构建模式 " + buildMode.getCode()
                    + "，该运行时的可选构建模式为：" + runtimeType.supportedBuildModeCodes());
}
```

- 拒绝时把该运行时的**全部可选模式**回给调用方（`supportedBuildModeCodes()` 按枚举声明顺序输出，文案稳定）；
- 前端用同一份矩阵做下拉联动：运行时变化时，若当前构建模式不被支持，自动切到第一个可选模式；
- 历史数据中的非法组合不会被自动修正，但再次保存时会被拦下。

### 6.6 凭据与镜像仓库的引用校验

项目有两个外部引用，都在保存前校验、且都受「删除保护」呼应：

| 字段 | 校验内容 | 不满足时的响应 |
| --- | --- | --- |
| `git_credential_id` | 凭据存在，且类型为 GIT_TOKEN 或 SSH_KEY | 4001（不存在 / 类型不符） |
| `registry_id` | **仅 DOCKER 运行时**可填；仓库存在且状态为启用 | 4001（运行时不符 / 不存在 / 已停用） |
| `build_server_id` | 服务器存在且状态为启用（选填，留空表示用系统默认构建机） | 4001（不存在 / 已停用） |

- 校验统一注入对方 Mapper（`CredentialMapper` / `RegistryMapper`），不注入对方 Service，避免 Service 循环依赖；
- 两个字段都标注 `updateStrategy = FieldStrategy.ALWAYS`：**清空 / 换绑能真正落库**。
  这一条是实测出来的——未标注时 DOCKER 项目改成 JAR 后 `registry_id` 仍残留仓库绑定，
  形成「运行时是 JAR 却挂着镜像仓库」的自相矛盾数据（详见 AGENTS.md §10.1）。

### 6.7 构建机绑定与项目连通性测试（2026-09-26 落地）

**为什么要有这个字段**。构建链路里最容易「第一次跑才暴雷」的三件事——Git 仓库不可达 / 凭据失效 / 分支名写错、
镜像仓库登录失败、构建机缺工具——只有在真正点「构建」时才会依次撞上，代价是一次失败的构建加上翻日志定位。
`project.build_server_id` 把「在哪台机器上构建」这件事落在项目档案上，从而可以在**构建之前**先测一遍。

**字段语义**

| 项 | 约定 |
| --- | --- |
| 是否必填 | 选填。留空表示构建时回落到系统默认构建机（`light-deploy.build.server-id`） |
| 构建机解析顺序 | 请求 `buildServerId` > 项目档案 `build_server_id` > 系统默认（见 [构建模块.md](构建模块.md) §6.1） |
| 保存校验 | 服务器必须存在且启用（`validateBuildServerReference`），与 §6.6 的另两个引用同口径 |
| 附加收益 | 项目列表页「构建」默认带出该机器，不必每次手选 |

**连通性测试**：`POST /project/test/{id}` → `ProjectService.submitConnectivityTest`，只建任务、立即返回，
真正的远程校验由 `ProjectConnectTestTaskHandler`（`TaskType.PROJECT_TEST`）异步完成。

| 阶段 | 校验项 | 失败是否判任务失败 |
| --- | --- | --- |
| 连接构建机 | SSH 登录 `build_server_id` 指向的服务器（服务器必须启用） | 是 |
| 工具链 | `git --version`（必需）、`docker --version`（仅 DOCKER 运行时必需）、`mvn -v`（仅提示） | 必需项失败即失败 |
| 代码仓库 | `GIT_TERMINAL_PROMPT=0 git ls-remote --heads <带凭据地址> [分支]` | 是 |
| 镜像仓库 | 有凭据：`docker login --password-stdin`；无凭据：探测 `/v2/` 端点 | 登录失败是，端点探测否 |
| 收尾 | 三条结论行（代码仓库 / 镜像仓库 / 工具链） | — |

**三条硬约束**

1. **必须在构建机上执行**，不能拿平台本机代替：平台机器常常不装 git / docker，网络策略也与构建机不同，
   在那上面测出来的结论说明不了构建能否成功。因此项目未绑定构建机时**直接拒绝提交**（而不是悄悄改测本机）；
2. **凭据拼装只有一份实现**：`GitAuthSupport` / `RegistryAuthSupport` / `SecretMasker`（`common/util`）被
   构建链路与测试处理器共用。两处各写一套必然在「谁补 `oauth2`」「密码怎么传」上分叉，
   表现为最难查的「测试通过、构建失败」；
3. **互斥键取构建机**（`build-server:{serverId}`，与 BUILD 同键）：测试期会执行 `docker login`
   写同机 `~/.docker/config.json`，与正在推送的构建并发会互相登出，必须串行。

用 `ls-remote` 而不是真克隆：它走完整的网络 + 认证链路，但不下载对象、不占磁盘、秒级返回。
分支不存在时 `git ls-remote --heads <url> <branch>` 会**成功返回且输出为空**，所以判空输出与判退出码同等重要。

### 6.8 环境、部署目标与服务器的关系（最容易误解的一处）

三层拓扑：**项目 → 环境 → 部署目标**，部署目标表是 `项目 × 环境 × 服务器`（唯一键 `uk_project_env_server`）。

- **环境是全局逻辑环境**（dev / test / prod），**不是项目私有，也不代表某台机器**。多个项目共用同一批环境，区别在各自绑了哪些目标；
- **机器不归环境管**，归部署目标管：一台服务器是绑到「某项目 + 某环境」这个组合下的；
- 同一环境同一服务器只能绑一次（唯一键），主目标在同一项目环境内互斥。

**常见误用**：给每台服务器各建一个环境，于是新建部署只能选一个环境、一次只覆盖一台。正确做法是**同一个环境下绑多条目标**，策略选全量或滚动（见 [发布模块.md](发布模块.md) §6.1 与 §6.2）。

分成两个环境的代价：① 版本链割裂（`resolveCurrentVersions` 按「项目 + 环境」推断 old_version，两套链路互不可见）；② 防重失效（进行中部署的判定同样按项目 + 环境，两个环境可同时发）；③ 历史记录碎片化。

**新建部署表单没有目标勾选**（只有 `projectId / environmentId / releaseId / strategy`）：目标集完全由「环境下的启用绑定 + 策略」决定。只发一台只能靠 ① 策略覆盖为 `SINGLE_TARGET`（发主目标那台）；② 在部署目标页停用另一台（影响该环境下后续所有部署）。

**新建部署的选环境下拉已按项目收敛**（2026-09-27）：`GET /projectEnvironmentTarget/env-options?projectId=`
只返回该项目**至少有一台启用绑定**的环境，选项形如「生产环境（2 台）」，台数只数启用绑定——
与发布模块展开目标的过滤条件一致，不会出现「下拉写着 2 台、提交后说没有启用目标」。
搜索区的环境下拉仍是全量（要能筛任何环境的历史记录），两者不共用数据，理由见 AGENTS §26.1。

**一个「设了也不生效」的字段**（运维最常踩，务必口头强调）：`server.env_tag`（服务器管理页的
「环境标签」）**不参与任何发布决策**——它只用于服务器列表的搜索筛选与 tag 着色，
与 `environment` 表无外键无校验。

> 原先这里还列了 `environment.default_server_id`（环境管理页「默认服务器」），该字段已于
> 2026-09-28 **移除**，环境表不再有任何服务器字段。
真正起作用的只有 `project_environment_target` 的 `status` / `is_primary` / `deploy_order`，
以及环境的 `deploy_strategy` / `batch_size`。硬约束见 AGENTS §24.11。

**完整原理与运维操作手册（含核对 SQL、发布前三查、摘机器/换 IP 的 SOP）见
[环境与部署目标.md](环境与部署目标.md)。**

## 7. 与其他模块的关系

| 方向 | 关系 |
| --- | --- |
| ← server 模块 | target.server_id 引用 server 表；删除服务器时本模块的引用数据可能悬空（见 §8） |
| → 后续构建/发布模块 | build / deployment / deployment_target 按 project_id + environment_id 消费本模块定义的发布拓扑；`build_config_json`（§2.3.1）是构建模块解析「仓库 → 产物」的输入契约，多模块仓库通过 `module_name` / `module_dir` 区分子模块 |
| → credential 模块 | `project.git_credential_id` 指向 credential 表，类型必须是 GIT_TOKEN / SSH_KEY；凭据被本项目引用期间不允许删除（见 [凭据模块.md](凭据模块.md)） |
| → registry 模块 | `project.registry_id` 指向 registry 表，仅 DOCKER 运行时项目有值；仓库被本项目绑定期间不允许删除（见 [镜像仓库模块.md](镜像仓库模块.md)） |
| → server 模块 | `project.build_server_id` 指向 server 表，是构建与[连通性测试](#67-构建机绑定与项目连通性测试)的执行位置 |
| → task 模块 | `POST /project/test/{id}` 提交 `PROJECT_TEST` 任务，日志走 `/taskLog/pull`（见 [任务模块.md](任务模块.md) §6.8） |

## 8. 已知边界与后续演进

- **删除顺序依赖人工遵守**：项目/环境删除有引用保护，但 server 删除无反向保护，规范操作顺序为「先删部署目标 → 再删服务器」；
- **JSON 配置只做格式校验**：`build_config_json` / `runtime_config_json` / `health_config_json` 的内部结构（如 `module_name` / `artifact_path`）待构建、发布、健康检查模块落地时按 `runtimeType` 解析消费；三段 schema 与 Maven 多模块仓库的解析约定已在 [§2.3](#23-三段-json-配置字段约定构建--运行--健康检查) 先行锁定，作为下游模块的开发契约，避免前后端口径漂移；
- **凭据与仓库引用已校验**（2026-09-23）：`git_credential_id` 与 `registry_id` 在保存时校验存在性与类型，删除凭据 / 仓库时反向拦截（见 §6.6）；
- **`registry_id` 只在 DOCKER 运行时可绑定**：脚本部署与仅发布产物没有镜像推送目标；运行时从 DOCKER 改成 JAR / STATIC 时该字段会被清空（字段策略 `ALWAYS`），不会残留矛盾绑定；
- **三段 JSON 的内部键名仍未校验**：`registry_id` 解决的是「推到哪个仓库」，镜像名 / 标签仍由 `build_config_json` 与构建逻辑决定；
- **环境编码枚举约束**：设计上约定 dev/test/prod，当前只做格式校验未做白名单 —— 保留灵活性，允许用户自定义环境（如 staging），符合轻量定位。
