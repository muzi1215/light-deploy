# 项目模块文档

> 模块包：`com.lx.deploy.project` ｜ 对应数据表：`project`、`environment`、`project_environment_target` ｜ 状态：已完成并编译通过

## 1. 模块定位

项目模块是发布链路的起点，回答三个问题：

1. **发布什么** —— `project` 表登记项目的运行时（DOCKER/JAR/STATIC）、代码来源与构建模式；
2. **发到哪** —— `environment` 表定义部署环境（dev/test/prod）与部署策略（单目标/全量/滚动）；
3. **具体发到哪台机器** —— `project_environment_target` 表把「项目 × 环境」绑定到具体服务器，形成完整发布拓扑。

三表关系：

```text
project ────┐
            ├──▶ project_environment_target ──▶ server（服务器模块）
environment ┘
```

## 2. 数据表结构

### 2.1 `project`（部署项目）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| code | VARCHAR(64) | 项目编码，唯一键，`^[A-Za-z0-9_-]{2,64}$` |
| name | VARCHAR(100) | 项目名称 |
| runtime_type | VARCHAR(20) | 运行时：DOCKER / JAR / STATIC |
| source_type | VARCHAR(20) | 代码来源：GIT / UPLOAD，默认 GIT |
| git_url / git_branch / git_credential_id | - | Git 来源信息；凭据指向独立 credential 表 |
| build_mode | VARCHAR(30) | 构建模式，默认 PLATFORM_TEMPLATE |
| build_config_json / runtime_config_json / health_config_json | JSON | 三段配置（格式校验但不解析语义）；`build_config_json` 的字段约定见 [§2.4](#24-build_config_json-约定) |
| retain_release_count | INT | 保留发布版本数，默认 5 |
| status | VARCHAR(20) | ENABLED / DISABLED |

### 2.2 `environment`（部署环境）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| code | VARCHAR(32) | 环境编码（dev/test/prod），`^[a-z][a-z0-9-]{1,31}$` |
| name | VARCHAR(100) | 环境名称 |
| deploy_strategy | VARCHAR(30) | SINGLE_TARGET / ALL_AT_ONCE / ROLLING，默认 SINGLE_TARGET |
| batch_size | INT | 滚动发布批次大小，默认 1 |
| default_server_id | VARCHAR(32) | 默认目标服务器（可选，存在性校验） |
| aiops_enabled | TINYINT | 是否启用 AIops 联动（发布静默窗口），默认 0 |

### 2.4 `build_config_json` 约定（构建模块消费，当前仅做格式校验）

`build_config_json` 是 `project` 表预留的构建描述字段，当前 `ProjectService` 只校验其是否为合法 JSON（见 §6.1），**不做语义解析**；内部结构由后续构建模块按 `runtime_type` / `build_mode` 解析消费。为避免构建模块落地时各字段语义漂移、前后端口径不一致，此处先行约定字段 schema 与多模块仓库的解析规则，作为构建模块开发的输入契约。

> **核心原则**：保持「一个 project = 一个发布单元」的模型不变。`build_config_json` 只描述「仓库拉取之后，如何定位并构建本项目的产物」，不承载仓库地址、分支等已落在 `git_url` / `git_branch` 的字段。

#### 2.4.1 通用字段（单模块仓库与多模块仓库共用）

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `moduleDir` | string | 否 | 子模块相对仓库根目录的路径，如 `auth-rest`；单模块仓库可省略，默认仓库根目录 |
| `pomPath` | string | 否 | Maven 构建入口 pom 路径；默认 `moduleDir/pom.xml`（单模块默认仓库根 `pom.xml`） |
| `mavenGoals` | string | 否 | Maven 构建目标，如 `clean package -DskipTests`；仅 `JAR` / `DOCKER` 运行时生效 |
| `artifactPath` | string | 否 | 构建产物相对路径（支持通配），构建后用于定位 jar / 静态资源，如 `auth-rest/target/auth-rest-*.jar` |
| `dockerfilePath` | string | 否 | Docker 构建使用的 Dockerfile 相对路径；不填则按 `build_mode` 走平台模板（`PLATFORM_TEMPLATE`）或项目自带（`PROJECT_DOCKERFILE`） |

字段默认值与缺失处理由构建模块负责，Service 层不介入。

#### 2.4.2 场景一：单模块仓库（默认）

仓库根即项目本身，`build_config_json` 可极简甚至为空：

```json
{
  "mavenGoals": "clean package -DskipTests",
  "artifactPath": "target/auth-app-*.jar"
}
```

#### 2.4.3 场景二：Maven 多模块仓库（一个仓库含多个可独立发布子模块）⭐

典型如 `auth-system-Iteration` 为父工程（空模块 / packaging=pom），其下 `auth-rest`、`auth-system`、`auth-tool` 为三个独立可发布子模块。**Light Deploy 不要求拆分仓库，也不要求拆分 project 表模型**——在同一 `git_url` 下创建多个 `project` 记录，各自通过 `moduleDir` 指向不同子模块即可。

三个 project 示例（`git_url` 全部为 `https://gitee.com/wangan2022/auth-system-Iteration.git`，`git_branch` 一致）：

```json
{
  "moduleDir": "auth-rest",
  "pomPath": "auth-rest/pom.xml",
  "mavenGoals": "clean package -DskipTests",
  "artifactPath": "auth-rest/target/auth-rest-*.jar",
  "dockerfilePath": "auth-rest/Dockerfile"
}
```

```json
{
  "moduleDir": "auth-system",
  "pomPath": "auth-system/pom.xml",
  "mavenGoals": "clean package -DskipTests",
  "artifactPath": "auth-system/target/auth-system-*.jar"
}
```

```json
{
  "moduleDir": "auth-tool",
  "pomPath": "auth-tool/pom.xml",
  "mavenGoals": "clean package -DskipTests",
  "artifactPath": "auth-tool/target/auth-tool-*.jar"
}
```

**构建模块的多模块解析约定**：

1. **仓库只拉一次**：同一 `git_url` 的不同子模块 project 共享一次 `git clone` / 缓存，避免重复拉取；构建工作区按 `git_url` + 分支缓存，按 `project.code` + 版本号区分产物目录；
2. **进入子模块目录构建**：执行器 `cd {workspace}/{moduleDir}` 后执行 `mavenGoals`，再按 `artifactPath` 取产物；
3. **独立发布单元**：每个子模块 project 独立登记 `release_record`、独立走 `deployment`，互不影响，支持各自回滚；
4. **依赖顺序由 Maven 保证**：若 `auth-rest` 依赖 `auth-system` 的 API 包，构建 `auth-rest` 前列出 `auth-system` 已 `install` 到本地仓库（或执行器先 `mvn install -pl auth-system -am` 再构建目标模块），具体由构建模块按 `pomPath` 依赖图编排，不在此处展开。

#### 2.4.4 场景三（可选，不推荐优先）：单 project 多产物强依赖构建

若多个子模块必须同一次发布（如 `auth-rest` 强依赖 `auth-system` 同一版本、不允许独立升级），可仅建一个 project，由构建模块一次 `mvn clean install` 后取多个产物分别生成镜像/包。该模式会让「一个 project → 多个 release/docker 镜像」突破当前 `project → release_record → deployment` 的一对多关系，复杂度上升，**建议先按场景二落地，确有强依赖需求再扩展**。

### 2.3 `project_environment_target`（项目环境部署目标）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| project_id / environment_id / server_id | VARCHAR(32) | 三方外键，组成唯一键 `uk_project_env_server` |
| is_primary | TINYINT | 是否主目标（同项目环境内互斥，最多一个） |
| deploy_order | INT | 多目标发布顺序，默认 1 |
| runtime_config_json | JSON | 目标差异化运行配置 |
| status | VARCHAR(20) | ENABLED / DISABLED |

## 3. 枚举设计（`com.lx.deploy.project.enums`）

| 枚举 | 取值 | 使用场景 |
| --- | --- | --- |
| RuntimeType | DOCKER / JAR / STATIC | project.runtime_type |
| SourceType | GIT / UPLOAD | project.source_type |
| BuildMode | PLATFORM_TEMPLATE / PROJECT_DOCKERFILE / LAYERED_DOCKER / ARTIFACT_ONLY | project.build_mode；AIops 项目用 LAYERED_DOCKER |
| DeployStrategy | SINGLE_TARGET / ALL_AT_ONCE / ROLLING | environment.deploy_strategy |

枚举取值与《需求设计文档》§306-308、§520-521 对齐，数据库存字符串编码，业务代码走 `fromCode()`。

## 5. 接口清单

三张表各自提供标准六接口（page / list / {id} / POST / PUT / DELETE），前缀分别为 `/project`、`/environment`、`/projectEnvironmentTarget`，统一 `ApiResponse<T>` + requestId。

典型查询示例：

```text
GET /projectEnvironmentTarget/list?projectId={id}&environmentId={id}
→ 返回该项目在该环境下绑定的全部目标服务器（按发布顺序升序）
```

## 6. 核心业务规则与代码逻辑

### 6.1 ProjectService

**新增/修改校验链**（`validateBusinessRule`，修改时 `excludeId` 排除自身）：

1. code / name 必填，code 匹配 `^[A-Za-z0-9_-]{2,64}$`；
2. runtimeType 必填且必须是 RuntimeType 枚举值；
3. sourceType / buildMode / status 选填但必须是合法枚举值；
4. **GIT 来源强制填写 gitUrl**（UPLOAD 来源不强制）；
5. retainReleaseCount ≥ 1；
6. 三个 JSON 配置字段用 Jackson `readTree()` 做格式校验（只校验合法 JSON，不校验内部结构 —— 语义校验留给后续构建/健康检查模块按 runtimeType 解析）；
7. code 唯一性预检，冲突抛 `DATA_CONFLICT(4005)`。

**默认值填充**（`applyDefaultValue`）：sourceType=GIT、buildMode=PLATFORM_TEMPLATE、status=ENABLED、retainReleaseCount=5。显式填充而非依赖数据库 DEFAULT，保证新增接口返回的 VO 与库内数据一致。

**删除保护**：删除项目前统计 `project_environment_target` 中引用该项目的记录数，存在引用则抛 DATA_CONFLICT「项目仍被部署目标引用，请先删除或迁移部署目标」。

### 6.2 EnvironmentService

校验链：code 必填且小写格式、name 必填、deployStrategy / batchSize / aiopsEnabled 取值合法、**defaultServerId 存在性校验**（注入 ServerMapper 查询）、code 唯一。

删除保护：同样检查部署目标引用。

### 6.3 ProjectEnvironmentTargetService（本模块业务核心）

**三方存在性校验**：

```text
project_id   → ProjectMapper.selectById   → 不存在抛「项目不存在」
environment_id → EnvironmentMapper.selectById → 不存在抛「环境不存在」
server_id    → ServerMapper.selectById    → 不存在抛「目标服务器不存在」
             → server.status != 1          → 抛「目标服务器已停用，不允许绑定」
```

**绑定唯一性**：同一项目 + 环境 + 服务器只能绑定一次（对齐数据库唯一键 `uk_project_env_server`），修改场景排除自身。

**主目标互斥**（`demoteOtherPrimary`，事务内执行）：

```java
// 当前目标 is_primary = 1 时，将同项目同环境下其他目标的 is_primary 清零
update(new LambdaUpdateWrapper<ProjectEnvironmentTarget>()
        .eq(getProjectId, entity.getProjectId())
        .eq(getEnvironmentId, entity.getEnvironmentId())
        .eq(getIsPrimary, 1)
        .ne(getId, entity.getId())
        .set(getIsPrimary, 0));
```

保证任一「项目 × 环境」组合下最多一个主目标；create/update 均标注 `@Transactional(rollbackFor = Exception.class)`，避免出现双主目标或无主目标的中间状态。

**查询排序**：结果按 `create_time DESC, deploy_order ASC` 排列，同一项目环境下的目标按发布顺序展示。

### 6.4 跨模块依赖方式

校验他表数据时**注入对方 Mapper 而非 Service**：

```java
public ProjectEnvironmentTargetService(ProjectMapper projectMapper,
                                       EnvironmentMapper environmentMapper,
                                       ServerMapper serverMapper) { ... }
```

理由：若 Service 之间互相注入（如 ProjectService 注入 ProjectEnvironmentTargetService），极易形成循环依赖；Mapper 是无状态的纯数据访问层，跨模块引用安全。这是全项目的既定约定。

## 7. 与其他模块的关系

| 方向 | 关系 |
| --- | --- |
| ← server 模块 | target.server_id 引用 server 表；删除服务器时本模块的引用数据可能悬空（见 §8） |
| → 后续构建/发布模块 | build / deployment / deployment_target 按 project_id + environment_id 消费本模块定义的发布拓扑；`build_config_json`（§2.4）是构建模块解析「仓库 → 产物」的输入契约，多模块仓库通过 `moduleDir` 区分子模块 |
| → credential 模块（未实现） | project.git_credential_id 将指向 credential 表的 GIT_TOKEN 类型凭据 |

## 8. 已知边界与后续演进

- **删除顺序依赖人工遵守**：项目/环境删除有引用保护，但 server 删除无反向保护，规范操作顺序为「先删部署目标 → 再删服务器」；
- **JSON 配置只做格式校验**：`build_config_json` 等的内部结构（如 `moduleDir` / `artifactPath` 字段）待构建模块落地时按 `runtimeType` 解析消费；其字段 schema 与 Maven 多模块仓库的解析约定已在 [§2.4](#24-build_config_json-约定) 先行锁定，作为构建模块的开发契约，避免前后端口径漂移；
- **gitCredentialId 存在性未校验**：credential 模块未实现，当前允许该字段指向尚不存在的凭据，待 credential 模块完成后补充校验；
- **环境编码枚举约束**：设计上约定 dev/test/prod，当前只做格式校验未做白名单 —— 保留灵活性，允许用户自定义环境（如 staging），符合轻量定位。
