# 项目创建与构建发布示例

> **本文定位**：给运维团队照抄用的「端到端配方」。每种**已验证跑通**的「运行时 + 构建模式」组合，
> 都给出：**创建项目参数（含三段 JSON）→ 构建 → 绑定环境与目标 → 发布**的完整示例，以及
> **前端字段 ↔ 后端字段/校验**的对照，避免参数写错。
>
> **当前覆盖**（五种「运行时 × 构建模式」组合全收录）：
> `PROJECT_DOCKERFILE`、`LAYERED_DOCKER`、`JAR_PREBUILD`、`SCRIPT_DEPLOY`、`ARTIFACT_ONLY`。
> 其中 `LAYERED_DOCKER` 参数按设计文档
> （`docs/Docker镜像构建发布方案评估.md` ADR-06 / `docs/构建模式与执行链路.md` §3.2）给出，
> 建议首次生产使用前先做小范围实测。
>
> 字段权威来源：前端 `lighit-deploy-ui/src/constants/projectConfig.ts`（`BUILD_MODE_OPTIONS` 与三段
> schema）、后端 `BuildConfig` / `DeployConfig` / `HealthConfig`（`@JsonProperty` 显式绑定 snake_case）。
> 两者不一致时以代码为准。

---

## 0. 先搞清三件事（写错参数多半栽在这）

### 0.1 运行时与构建模式是**受约束的合法组合**

| 运行时 `runtimeType` | 允许的 `buildMode` | 产物 | 发布去向 |
| -- | -- | -- | -- |
| `DOCKER`（Docker容器） | `PROJECT_DOCKERFILE`、`LAYERED_DOCKER`、`JAR_PREBUILD` | 镜像 | 推镜像仓库 → 目标机 `docker pull` |
| `JAR`（Java JAR） | `SCRIPT_DEPLOY`、`ARTIFACT_ONLY` | jar 文件 | 构建机产物目录 → 目标机固定 `work_dir`，systemd 托管 |
| `STATIC`（静态产物） | `SCRIPT_DEPLOY`、`ARTIFACT_ONLY` | 静态目录/压缩包 | 目标机 Nginx `static_root`（**只换内容不换目录**） |

约束由后端 `RuntimeType.supportedBuildModes()` 唯一决定，前端下拉也从同一份派生。**选到不支持的模式会被
Service 直接拒绝**；而「模式合法但和 Dockerfile 能力不匹配」则会拖到构建期才炸（见 §5）。

### 0.2 项目有三段 JSON 配置，各有唯一消费方

| 配置 | 落库列 | 后端解析类 | 消费时机 | 能否被目标覆盖 |
| -- | -- | -- | -- | -- |
| 构建配置 `buildConfigJson` | `project.build_config_json` | `BuildConfig` | 构建任务 | 否 |
| 运行配置 `runtimeConfigJson` | `project.runtime_config_json` | `DeployConfig` | 发布任务 | **能**（`project_environment_target.runtime_config_json` 按差异覆盖） |
| 健康检查 `healthConfigJson` | `project.health_config_json` | `HealthConfig` | 发布后探测 | 能（同上） |

> 键名一律 snake_case；schema 里没有的键后端会**静默忽略**（不报错但也不生效），所以别自己造键。
>
> **表单模式 vs JSON 模式**：编辑页的「表单模式」按 `runtimeType` / `buildMode` 联动渲染，
> **只显示当前模式真正消费的键**——例如 `build_command` 只在「脚本部署」出现，
> `dockerfile_path` 在三种 Docker 模式下都出现，`artifact_path` 只在脚本部署 / JAR 预构建出现。
> 所以「表单里没有某个输入框」＝ **该模式不消费这个键**，不是漏了；在 JSON 里硬填也不会生效。
> JSON 模式用于整段粘贴、或写 schema 外的自定义键。各示例的对照表都标了「页面可见」列，照着核对即可。

### 0.3 四步固定流程与对应页面/接口

| 步骤 | 页面（前端） | 接口（后端） |
| -- | -- | -- |
| ① 建项目 | 项目管理 → 新增：`views/project/edit.vue` | `POST /deploy/project/create` |
| ② 构建 | 构建管理 → 新建：`views/build/index.vue` | `POST /deploy/build/create`（`ARTIFACT_ONLY` 用 `POST /deploy/build/upload`） |
| ③ 绑环境与目标 | 部署目标：`views/deployTarget/index.vue`（环境：`views/environment/index.vue`） | `POST /deploy/environment/create` + `POST /deploy/projectEnvironmentTarget/create` |
| ④ 发布 | 发布管理 → 新建：`views/deploy/index.vue` | `POST /deploy/deployment/create` |

> 环境是**全局共享**的（一个环境可被多个项目引用）；「某项目在某环境发到哪台机器」由部署目标
> `project_environment_target` 决定，所以环境本身不配服务器（AGENTS §24.11）。

## 1. 示例一：项目自带 Dockerfile + Docker 容器（COMPOSE 发布）— `monitor_web`

真实项目：`gitee.com/wangan2022/system_monitor_web`（Python Flask，端口 5000）。**已实测构建 + 发布成功**。

### 1.1 创建项目参数

| 字段（`ProjectDto`） | 取值 | 说明 |
| -- | -- | -- |
| `code` | `monitor_web` | 项目编码，`^[A-Za-z0-9_-]{2,64}$`；镜像名/目录/容器默认名都由它派生 |
| `name` | `monitor_web` | 展示名 |
| `runtimeType` | `DOCKER` | 产出镜像 |
| `sourceType` | `GIT` | 从仓库克隆 |
| `gitUrl` | `https://gitee.com/wangan2022/system_monitor_web.git` | |
| `gitBranch` | `main` | |
| `gitCredentialId` | 已有 gitee 凭据 id | 公共仓库可留空 |
| `buildMode` | `PROJECT_DOCKERFILE` | Dockerfile 自己完成构建 |
| `registryId` | ACR 仓库 id | 推送/拉取都要登录 |
| `buildServerId` | 构建机服务器 id | 不填回落系统默认构建机 |
| `status` | `1` | 启用 |
| `retainReleaseCount` | `5` | 保留可回滚版本数 |

**构建配置 `buildConfigJson`**
```json
{
  "dockerfile_path": "Docker/Dockerfile",
  "compose_file_path": "Docker/docker-compose.yml",
  "image_repository": "registry.cn-hangzhou.aliyuncs.com/lx_relife/monitor_web",
  "docker_verify_on_build": true,
  "docker_verify_timeout_seconds": 30
}
```
要点：
- `dockerfile_path` **相对仓库根**，`PROJECT_DOCKERFILE` 必填（`DockerBuilder` 会校验，空则直接失败）。
- 构建上下文 = **仓库根**（平台执行 `cd <仓库根> && docker build -f <dockerfile_path> -t <img>:<tag> .`），
  所以 Dockerfile 里的 `COPY` 一律写相对仓库根的路径。
- 要 COMPOSE 发布就必须给 `compose_file_path`，且 compose 里随版本变化的镜像写成 `image: ...:${IMAGE_TAG}`。

**运行配置 `runtimeConfigJson`（项目级可留空，绑定目标时再写）**
```json
{ "deploy_form": "COMPOSE", "work_dir": "/lx/docker/monitor_web" }
```

**健康检查 `healthConfigJson`（可选）**
```json
{ "type": "HTTP", "probe_from": "TARGET", "port": 5000, "path": "/", "retry_count": 12, "timeout_seconds": 5, "interval_seconds": 3 }
```

### 1.2 构建

`POST /deploy/build/create`，body `{"projectId":"<id>"}`。链路与日志要点：

| 步骤 | 日志关键字 | 产物/结果 |
| -- | -- | -- |
| 克隆 | `git clone` | `build.git_commit` 回填（失败也能溯源） |
| 构建镜像 | `执行 docker build（输出实时回传）：cd <仓库根> && docker build -f Docker/Dockerfile -t <img>:<ver> .` | 镜像 |
| 启动级验证 | `启动级验证：构建机本地启动镜像 …` → `启动级验证通过：镜像在 30 秒窗口内持续运行` | 见 §0 与构建文档 §3.1.1 |
| 推送 | `推送镜像 …` + `Layer already exists` / `Pushed` | `build_artifact`（APP_IMAGE + digest） |
| 快照 compose | `已快照 compose 文件 Docker/docker-compose.yml（… 字符）` | `release_record.compose_content` |
| 收尾 | `构建完成，已生成发布版本 <version>` | `release_record`（可发布） |

实测：版本 `monitor_web-v2-5e820cf5`，镜像 `registry.cn-hangzhou.aliyuncs.com/lx_relife/monitor_web:monitor_web-v2-5e820cf5`，
`artifact_path=NULL`（镜像类产物不落盘），`context_artifact_path` 指向 `build-context.tar.gz`。

### 1.3 绑定环境与目标

① 建环境（若已有可复用）：
```json
{ "code": "prod", "name": "生产环境", "deployStrategy": "SINGLE_TARGET" }
```
② 绑定目标机（`runtime_config_json` 在这里覆盖项目级运行配置）：
```json
{
  "projectId": "<项目id>",
  "environmentId": "<环境id>",
  "serverId": "<目标机serverId>",
  "isPrimary": 1,
  "deployOrder": 1,
  "runtimeConfigJson": "{\"deploy_form\":\"COMPOSE\",\"work_dir\":\"/lx/docker/monitor_web\"}",
  "status": 1
}
```

### 1.4 发布

`POST /deploy/deployment/create`：
```json
{ "projectId": "<项目id>", "environmentId": "<环境id>", "releaseId": "<版本id>" }
```
> `releaseId` = `release_record.id`，用 `GET /deploy/release/list?projectId=<项目id>&status=1` 取最新一条
> （不是 `buildId`，`BuildVo` 不含该字段，详见 §7 的取法说明）。
日志顺序（COMPOSE）：目标机登录仓库 → `mkdir work_dir` → 下发 compose → 注入 `IMAGE_TAG=...` →
下发应急素材 `build-context` → `docker compose pull` → `docker compose up -d` → 运行态校验 →
`目标 xxx 发布成功`。成功判据：`deployment.status=2`、`currentVersion=<版本>`、`targetSuccess=targetTotal`。

### 1.5 前后端字段对应与校验点

| 页面字段（`projectConfig.ts`） | 键 | 页面可见 | 后端消费/校验 |
| -- | -- | -- | -- |
| Dockerfile 路径 | `dockerfile_path` | ✅ | `DockerBuilder` 校验非空；作为 `-f` 参数 |
| compose 文件路径 | `compose_file_path` | ✅ | `BuildSupport.readComposeFile` 读取并 `ComposeInjection.requireUsable` 校验 `${IMAGE_TAG}` |
| 镜像仓库地址 | `image_repository` | ✅ | 留空回落 `registry + namespace + (module_name\|code)` |
| 部署形态 | `deploy_form` | ✅ | `DockerDeployService`：`RUN` / `COMPOSE` |
| 固定工作目录 | `work_dir` | ✅ | 绝对路径；不填回落 `部署根目录/项目编码` |
| 容器名 / 端口映射 / 附加参数 | `container_name` / `port_mappings` / `extra_docker_args` | ✅ | **仅 RUN 形态生效**；COMPOSE 下由 compose 文件决定 |
| 启动级验证开关 / 窗口 | `docker_verify_on_build` / `docker_verify_timeout_seconds` | ✅ | 默认开启、窗口 30s；开关默认展示为**开**，不动它就不写进配置 |
| Maven settings | `maven_settings_path` | ❌ 本项目不显示 | 只在 `JAR_PREBUILD` 下出现，`PROJECT_DOCKERFILE` 无需配 |

## 2. 示例二：JAR 预构建镜像 + Docker（COMPOSE）— `auth-tool`

典型场景：**多阶段构建成本高/构建机没有 JDK 与 Maven**，让平台先用 Maven 容器打出 jar，再用
项目的**极简 Dockerfile（只 COPY jar）**包成镜像。**已实测构建 + 发布成功**。

### 2.1 创建项目参数

`runtimeType=DOCKER`、`buildMode=JAR_PREBUILD`、`sourceType=GIT`、`registryId`/`buildServerId` 同示例一。

**构建配置 `buildConfigJson`**
```json
{
  "module_dir": "auth-tool",
  "module_name": "auth-tool",
  "config_paths": "auth-tool/Docker/application.yml",
  "artifact_path": "auth-tool/linux/auth-tool-7888/auth-tool.jar",
  "dockerfile_path": "auth-tool/Docker/Dockerfile.jre",
  "image_repository": "registry.cn-hangzhou.aliyuncs.com/lx_relife/auth-tool",
  "compose_file_path": "auth-tool/Docker/docker-compose.yml",
  "maven_settings_path": "auth-tool/Docker/settings.xml",
  "docker_verify_on_build": true,
  "docker_verify_timeout_seconds": 60
}
```
要点：
- `artifact_path` **必填**：平台只负责打出 jar，得知道 jar 在哪（仓库根优先、模块目录回落，支持 `*`）。
- `dockerfile_path` 指向的 Dockerfile **只做 `COPY *.jar`**，自己不具备构建能力。
- `maven_settings_path` 可选，用于切阿里云 Maven 镜像加速。
- **与 `PROJECT_DOCKERFILE` 不可互换**：极简 Dockerfile 配 `PROJECT_DOCKERFILE` 必然 COPY 找不到 jar；
  多阶段 Dockerfile 配 `JAR_PREBUILD` 会构建两次、白等一半时间。

> 💡 **在页面上怎么填**：`buildMode` 选 `JAR_PREBUILD` 后，「Docker 构建」分组会显示
> Dockerfile 路径、compose 文件路径、镜像仓库地址、Maven settings 路径、启动级验证开关与窗口，
> 逐项填上面的值即可。启动级验证开关默认展示为**开**（后端默认开启），不动它就不会写进配置。

**运行配置 `runtimeConfigJson`**
```json
{ "work_dir": "/lx/docker/auth-tool-7888", "deploy_form": "COMPOSE" }
```

### 2.2 构建

日志关键行（按顺序）：
1. `执行构建命令（超时上限 1800 秒…）` —— 在 Maven 容器里 `mvn package` 打 jar；
2. `定位 jar 产物 …` —— 按 `artifact_path` 找 jar（仓库根优先、`module_dir` 回落、支持 `*`）；
3. `执行 docker build … -f auth-tool/Docker/Dockerfile.jre` —— 极简 Dockerfile 把 jar 包成镜像；
4. `启动级验证通过：镜像在 60 秒窗口内持续运行` —— 窗口取 `docker_verify_timeout_seconds`；
5. `推送镜像 …` —— 推到 `image_repository`；
6. `热修包已生成 <构建机产物目录>/auth-tool/<版本>/hotfix-kit.tar.gz（auth-tool.jar / Dockerfile.hotfix
   / docker-compose.hotfix.yml，平台不可用时下发目标机就地重建）` —— **B1 热修包**，见下；
7. 配置转存（`config_paths` → 版本目录 `config/`）。

产物：`build_artifact` 里有 `APP_IMAGE` + digest；`release_record.context_artifact_path` 指向
`hotfix-kit.tar.gz`；`artifact_path` 为 `NULL`（镜像不落盘）；版本目录下多一个 `config/`。

> **热修包是兜底素材，不是可选项**：它把「jar 原名 + 平铺 `Dockerfile.hotfix` + hotfix compose + `application.yml`
> + README」打成一个包，随发布下发到目标机 `<work_dir>/build-context/`。平台和 Git 仓库同时不可用时，
> 运维在目标机 `tar xzf` 后 `docker build` 就能把服务救回来，不依赖平台回连。
> 项目缺 `Dockerfile.hotfix`（与 `dockerfile_path` 同目录）时平台只记一条「跳过热修包」日志、不阻断构建，
> 但该版本**失去这条兜底路径**，建议补齐（`docs/平台不可用应急手册.md`）。

### 2.3 绑定环境与目标
同示例一，`runtimeConfigJson` 用 `{"deploy_form":"COMPOSE","work_dir":"/lx/docker/auth-tool-7888"}`。
若项目自带 `compose_file_path`，发布就用它；此时端口、卷、依赖全在 compose 里。

### 2.4 发布
同示例一（COMPOSE 链路）。实测版本 `auth-tool-v16-c8a298f4`，`compose_content` 已快照。

### 2.5 前后端对应与校验点

| 键 | 页面表单可见 | 后端消费 | 校验 / 坑 |
| -- | -- | -- | -- |
| `module_name` | ✅ 始终可见 | 多模块仓库的子模块名，默认镜像名来源 | 本项目 `auth-tool`；单模块仓库留空 |
| `module_dir` | ✅ 始终可见 | 平台先 `cd` 到该目录再执行命令 | 前端 `checks`：与 `build_command` 里的 `-pl` 冲突会拦提交 |
| `command_timeout_seconds` | ✅ JAR_PREBUILD 下显示 | Maven 容器构建的等待上限 | 留空用平台默认 1800s；首次构建下载依赖是分钟级 |
| `artifact_path` | ✅ JAR_PREBUILD 下显示 | `locateJarArtifact` 定位 jar | **必填**，找不到直接失败并指向该键 |
| `config_paths` | ✅ 始终可见 | `persistVersionConfig` 转存到版本 `config/` | 缺文件只记日志、不阻断 |
| `dockerfile_path` | ✅ JAR_PREBUILD 下显示 | `docker build -f` 参数 | **必填**，空则构建直接失败；填「只 COPY jar」的极简 Dockerfile |
| `compose_file_path` | ✅ JAR_PREBUILD 下显示 | 构建期快照进 `release_record.compose_content` | 要 COMPOSE 发布就必须配，且文件里要有 `${IMAGE_TAG}` |
| `image_repository` | ✅ JAR_PREBUILD 下显示 | 决定镜像推送到哪 | 留空回落 `registry + namespace + 项目编码`，本项目已显式配 |
| `maven_settings_path` | ✅ JAR_PREBUILD 下显示 | Maven `-s` 参数 | 可留空（留空走公网 Maven Central，内网构建机很慢） |
| `docker_verify_on_build` | ✅ JAR_PREBUILD 下显示（开关） | 构建机启动级验证开关 | 默认展示为**开**；不动就不写进配置，后端按开启处理 |
| `docker_verify_timeout_seconds` | ✅ JAR_PREBUILD 下显示 | 验证观察窗口 | 默认 30s；本项目实测用 60s（Maven 镜像冷启动偏慢） |

> 上表 11 个键就是 `JAR_PREBUILD` 下表单会渲染的**全部**输入框，可直接照着填、不需要切 JSON 模式。

## 3. 示例三：脚本部署 + JAR（systemd 托管）— `auth-rest-1991`

典型场景：项目自带构建脚本（Maven/Gradle/npm 均可），产物是 jar，目标机用 systemd 常驻。
**已实测构建 + 发布成功**。

### 3.1 创建项目参数

`runtimeType=JAR`、`buildMode=SCRIPT_DEPLOY`、`sourceType=GIT`。**不需要** `registryId`（JAR 不产出镜像，
填了会被 Service 拒绝，AGENTS §23.4）。

**构建配置 `buildConfigJson`**
```json
{
  "module_dir": "auth-rest",
  "module_name": "auth-rest",
  "config_paths": "auth-rest/auth-rest-1991/application.yml",
  "artifact_path": "auth-rest/auth-rest-1991/auth-rest.jar",
  "build_command": "JAVA_HOME=/usr/lib/jdk1.8.0_121 mvn -B clean package -DskipTests"
}
```
要点：
- `build_command` **必填**（脚本部署没有平台推导的默认命令）。
- 若填了 `module_dir`，平台会**先 cd 进去再执行**，命令里就不要再带 `-pl`（前端 `checks` 会拦截该冲突）。
- 构建机 PATH 里没有工具时，优先在服务器档案配「构建环境初始化脚本」，其次在命令前缀写绝对路径/JAVA_HOME。

**运行配置 `runtimeConfigJson`**（以下为该项目的实测值）
```json
{
  "work_dir": "/lx/jarapps/auth-rest-1991",
  "jvm_options": "-Xms256m -Xmx512m",
  "service_name": "auth-rest-1991",
  "spring_profiles_active": "prod"
}
```
要点：
- `work_dir` 必须绝对路径，jar、`config/`、启动脚本都落在这里。
- `config_dir` / `config_file` **有默认值**（`config` / `application.yml`）：不填时平台仍把 `config_paths`
  转存的配置投放到 `work_dir/config/`，并据此生成 `--spring.config.location`。只有想换目录名或文件名时才需要显式写。
- **`port_mappings` / `container_name` 在 JAR 运行时是无效键**（只对 Docker `RUN` 生效）。该项目的历史配置里残留
  这两个键，不影响发布，但别以为它们能改端口——JAR 的端口由应用自身配置决定，健康检查端口要与之对齐。
**健康检查 `healthConfigJson`**
```json
{ "type": "TCP", "probe_from": "TARGET", "port": 1991, "retry_count": 12, "timeout_seconds": 5, "interval_seconds": 2 }
```

### 3.2 构建
`执行构建命令` → `定位 jar 产物` → `转存产物`（记 SHA256）→ `转存配置文件`。产物：`JAR` 类型 artifact，
`artifact_path` 指向构建机持久目录下的 jar；`compose_content=NULL`、`context_artifact_path=NULL`
（JAR 运行时不产镜像、也不需要构建上下文下发）。

> 实测版本 `auth-rest-1991-v3-c8a298f4`，部署记录 `status=2`（成功）。`auth-7888` 同模式同样跑通。

### 3.3 绑定环境与目标
`runtimeConfigJson` 可写差异，例如某台机器 java 不在 PATH：
`{"java_bin":"/usr/lib/jdk1.8.0_121/bin/java"}`。
> **java_bin 是项目级配置**，填绝对路径等于要求每台目标机都有该文件；不确定就留空，由平台逐台
> `command -v java` 探测，个别机器再在目标上单独覆盖。

### 3.4 发布
单目标：上传 jar 到 `work_dir` → 首次生成 systemd 单元（之后不再重写）→ 写 `config/` 下配置 →
`systemctl daemon-reload && restart` → 健康检查。成功判据同前（`targetSuccess=targetTotal`）。
> systemd 单元**只在首次部署生成**，之后改 `service_name`/`java_bin` 不会自动重写已存在的单元。

### 3.5 前后端对应与校验点
| 键 | 页面可见 | 后端消费 | 校验/坑 |
| -- | -- | -- | -- |
| `build_command` | ✅ | 直接在构建机执行 | `SCRIPT_DEPLOY` 必填；页面上带 7 组可抄示例 |
| `artifact_path` | ✅ | 定位 jar | `JAR` 运行时必填；先按仓库根找、再按 `module_dir` 回落 |
| `module_dir` | ✅ | 先 `cd` 再执行命令 | 填了就不要在命令里写 `-pl`（前端 `checks` 拦） |
| `config_paths` | ✅ | 转存到版本 `config/` | 与运行配置的 `config_dir`/`config_file` 对齐 |
| `work_dir` | ✅ | 目标机固定目录 | 必须绝对路径（前端 `checks` 拦相对路径） |
| `service_name` | ✅ | systemd 单元名 | 默认项目编码；**已生成的单元不重写** |
| `jvm_options` / `spring_profiles_active` | ✅ | 写进 systemd `ExecStart` | 改这些同样不会重写已有单元 |
| `java_bin` | ✅ | systemd `ExecStart` 的 java 路径 | 项目级配置，对所有目标机生效；不确定就留空 |
| `config_dir` / `config_file` | ✅ | `--spring.config.location` | 有默认值（`config` / `application.yml`），一般不用填 |
| `port_mappings` / `container_name` | ✅ 显示但**无效** | JAR 链路不消费 | 只对 Docker `RUN` 生效，别指望它改端口 |
| `docker_verify_on_build` / `docker_verify_timeout_seconds` | ❌ `SCRIPT_DEPLOY` 下不显示 | 仅 DOCKER 运行时消费 | JAR 链路没有启动级验证环节，不用管 |

> 变体：`auth-7888` 与 `auth-rest-1991` 同模式，差异仅在 `work_dir=/lx/jarapps/auth-tool-7888`、
> `service_name=auth-tool-7888`、健康检查端口 `7888`。

## 4. 示例四：仅发布已有产物 + 静态产物（上传）— `aiops-vue`

典型场景：前端已经 `npm run build` 出 `dist/`，只想让平台发布到 Nginx，不在构建机跑构建。
**已验证跑通**（`aiops-vue`，最近成功部署 2026-10-22）。

### 4.1 创建项目参数

| 字段 | 取值 | 说明 |
| -- | -- | -- |
| `runtimeType` | `STATIC` | |
| `buildMode` | `ARTIFACT_ONLY` | **不做任何构建** |
| `sourceType` | `UPLOAD` | 无 `gitUrl`/`gitBranch`/`gitCredentialId` |
| `registryId` | 空 | STATIC 不涉及镜像；填了会被拒 |
| `buildConfigJson` | `null`（或空） | 该模式不消费构建配置 |

**运行配置 `runtimeConfigJson`**（以下为该项目的实测值）
```json
{
  "static_root": "/lx/docker/lx-nginx/www/html/aiops",
  "static_backup_dir": "/lx/docker/lx-nginx/backup"
}
```
要点：
- `static_root` 填到**站点文件所在那一层**（该目录里应直接是 `index.html`，不要再套一层 `dist/`）。
  留空时回落 `/usr/share/nginx/html/{项目编码}`。
- `static_backup_dir` 是**备份文件的实际落点，平台不会自动再拼一层项目子目录**，备份条目直接在里面，
  命名 `{站点目录名}_bak_{时间戳}_{版本}`。留空时回落到 `static_root 的上级目录/backup`。
- 备份目录建议配到 web 根之外（默认落在 nginx 可访问范围内，可能暴露 source map）。
- **发布只换目录内容、绝不换目录本身**（目录若是 Docker bind mount 的源，换 inode 会让容器全站 403）。

### 4.2 「构建」= 上传产物登记版本
`ARTIFACT_ONLY` **不发起构建任务**，改为 `POST /deploy/build/upload`（multipart）：
`projectId` + `versionSeq`（可空，自动取号）+ `file`（`.zip`/`.tar.gz`/`.tgz`；JAR 运行时用 `.jar`）。
上传完成即登记一个可发布版本，无 `build` 任务、无镜像。

### 4.3 绑定环境与目标
```json
{
  "projectId": "<项目id>", "environmentId": "<环境id>", "serverId": "<目标机serverId>",
  "isPrimary": 1, "deployOrder": 1, "status": 1,
  "runtimeConfigJson": "{\"static_root\":\"/lx/docker/lx-nginx/www/html/aiops\"}"
}
```

### 4.4 发布
上传的压缩包下发 → 解压到暂存目录 → 旧内容整体搬到 `static_backup_dir`（条目名 `{站点目录名}_bak_{时间戳}_{版本}`）→ 新内容投放 → 清理暂存 →
**不执行 nginx reload**（静态文件即时生效）。成功判据：`deployment.status=2`。
> **外壳目录会被自动剥掉**：`cd dist && zip -r app.zip .` 打出的平铺包直接用；
> `zip -r aiops.zip aiops` 这种多套一层的包，平台也会剥（日志出现「压缩包外层目录 xxx 已自动剥离」）。
> 剥离判据很窄：**暂存目录下恰好一个条目 + 该条目是目录 + 目录内有 `index.html`**，三条全中才剥，
> 所以根下只有 `assets/` 这类的包不会被误伤。剥完之后仍告警的情况说明包形态异常，按日志提示重打即可。

> **实测**：`aiops-vue` 最后一次成功部署是 2026-10-22（`deployment.status=2`）。
> 2026-09-27/28 曾连续因「Nginx reload 失败」「全站 403」翻车，正是后来改成
> **不 reload + 只换内容不换目录** 的原因——这两条不要为了「更彻底」再改回去。

### 4.5 前后端对应与校验点
| 键 | 页面可见 | 后端消费 | 坑 |
| -- | -- | -- | -- |
| `static_root` | ✅ | `StaticDeployService` | 填成 nginx 根会把别的站点一起搬走；换目录本身会致容器 403 |
| `static_backup_dir` | ✅ | 发布前整体搬迁旧内容、回滚优先从这里还原 | 与 `static_root` 同分区，否则退化成跨分区复制 |
| `deploy_form` / `work_dir` | ❌ STATIC 下不显示 | STATIC 链路不消费 | 只有 `DOCKER`（和 `JAR` 的 `work_dir`）才看这两个键 |

## 5. 常见错误对照表（照着排最省时间）

| 现象 / 报错 | 根因 | 正确做法 |
| -- | -- | -- |
| `PROJECT_DOCKERFILE 模式需要 build_config_json.dockerfile_path` | 漏配 `dockerfile_path` | 补上，路径**相对仓库根**（表单模式下该框在「Docker 构建」分组） |
| `COPY failed: ... not found` / 找不到 jar | **极简 Dockerfile 配了 `PROJECT_DOCKERFILE`**，或 COPY 写成 `../` | 极简 Dockerfile 用 `JAR_PREBUILD`；COPY 相对仓库根 |
| `项目的 compose 文件中找不到版本占位符 ${IMAGE_TAG}` | compose 里写死了镜像 tag | `image: ...:${IMAGE_TAG}`，中间件保持原样 |
| `docker compose pull 失败` | compose 镜像地址错 / 仓库未登录 | 平台会按项目 `registryId` 自动登录；确认 `image_repository` 与 compose 一致 |
| COMPOSE 下配了端口却不生效 | `port_mappings`/`container_name` 只对 RUN 生效 | 端口/容器名写进 compose 文件 |
| `Could not find the selected project in the reactor` | `module_dir` 与命令里的 `-pl` 同时存在 | 二选一（前端会拦） |
| `脚本部署（SCRIPT_DEPLOY）必须在 build_config_json.build_command 中显式给出构建命令` | 漏配 `build_command` | 补构建命令 |
| 配了 `build_command` 但构建没按它跑 | 该键**只有** `SCRIPT_DEPLOY` 消费 | Docker 类模式的命令由平台内置；`PROJECT_DOCKERFILE` 项目真正要的是 `dockerfile_path` |
| 健康检查失败但服务其实活着 | HTTP 路径跳登录（302/401/403 判不健康） | 填免鉴权返回 200 的路径，或用 TCP 探测 |
| STATIC 发布后全站 403 | 换了 `static_root` 目录（容器握旧 inode） | 只换内容不换目录；需重建容器才能恢复 |
| 构建机启动级验证失败且 `OOMKilled=true` | 应用内存超构建机 | 降内存 / 加构建机内存或 swap；或 `docker_verify_on_build=false` 由目标机兜底 |

> `exit=-1` 不是容器退出码，而是"没拿到退出码"的哨兵值。新版验证已改为 `docker inspect` 判活，
> 正常不会再因它误判；若仍出现，优先查构建机内存（详见 `构建模式与执行链路.md` §3.1.1）。

## 6. 参数速查（最小可用集）

| 构建模式 | `buildConfigJson` 必填 | `runtimeConfigJson` 关键 | 备注 |
| -- | -- | -- | -- |
| `PROJECT_DOCKERFILE` | `dockerfile_path` | `deploy_form`、`work_dir` | COMPOSE 还需 `compose_file_path` |
| `JAR_PREBUILD` | `dockerfile_path`、`artifact_path`（建议 `module_dir`+`image_repository`） | `deploy_form`、`work_dir` | Dockerfile 只 COPY jar |
| `SCRIPT_DEPLOY` | `build_command`、`artifact_path` | JAR：`work_dir`/`service_name`；STATIC：`static_root` | 可由脚本产出任意产物 |

| `LAYERED_DOCKER` | `dockerfile_path`、`base_dockerfile_path`（首次 `rebuild_base_image=true`） | `deploy_form`、`work_dir` | 应用层 Dockerfile 必须 `ARG BASE_IMAGE` + `FROM ${BASE_IMAGE}` |

## 7. 附录：`monitor_web` 全链路可复制请求体

> 三段配置在后端 DTO 里是 **String**，所以 HTTP body 里要**字符串化**（下面已转义好）。
> 命令行建议 `curl --data-binary @body.json`，避免 shell 转义踩坑。

**① 创建项目**（`POST /deploy/project/create`）
```json
{
  "code": "monitor_web",
  "name": "monitor_web",
  "runtimeType": "DOCKER",
  "sourceType": "GIT",
  "gitUrl": "https://gitee.com/wangan2022/system_monitor_web.git",
  "gitBranch": "main",
  "gitCredentialId": "<gitee凭据id>",
  "buildMode": "PROJECT_DOCKERFILE",
  "registryId": "<镜像仓库id>",
  "buildServerId": "<构建机serverId>",
  "buildConfigJson": "{\"dockerfile_path\":\"Docker/Dockerfile\",\"compose_file_path\":\"Docker/docker-compose.yml\",\"image_repository\":\"registry.cn-hangzhou.aliyuncs.com/lx_relife/monitor_web\",\"docker_verify_on_build\":true,\"docker_verify_timeout_seconds\":30}",
  "status": 1,
  "description": "Python Flask 系统监控 Web"
}
```

**② 构建**（`POST /deploy/build/create`）
```json
{ "projectId": "<上一步返回的 id>" }
```

**③ 建环境**（`POST /deploy/environment/create`）
```json
{ "code": "prod", "name": "生产环境", "deployStrategy": "SINGLE_TARGET" }
```

**④ 绑定目标**（`POST /deploy/projectEnvironmentTarget/create`）
```json
{
  "projectId": "<项目id>", "environmentId": "<环境id>", "serverId": "<目标机serverId>",
  "isPrimary": 1, "deployOrder": 1, "status": 1,
  "runtimeConfigJson": "{\"deploy_form\":\"COMPOSE\",\"work_dir\":\"/lx/docker/monitor_web\"}"
}
```

**⑤ 发布**（`POST /deploy/deployment/create`）
```json
{ "projectId": "<项目id>", "environmentId": "<环境id>", "releaseId": "<版本id>" }
```
> **`releaseId` 怎么取**：它是 `release_record.id`，**不是** `buildId`。注意 `GET /deploy/build/detail/{buildId}`
> 返回的 `BuildVo` 里**没有** `releaseId` 字段，照抄会拿到空值。正确做法：
> ```
> GET /deploy/release/list?projectId=<项目id>&status=1
> ```
> 返回该项目的可发布版本列表（`ReleaseRecordVo`），按 `versionSeq` 取最大的一条，
> 其 `id` 即 `releaseId`，`version` 即版本号（如 `monitor_web-v2-5e820cf5`）。
> 版本多时可用 `GET /deploy/release/page?projectId=<项目id>&pageNum=1&pageSize=10` 分页取（`pageSize` 上限 100）。
> 也可直接 `GET /deploy/release/detail/{releaseId}` 反查某版本详情。
>
> 可选 `strategy`（`SINGLE_TARGET` / `ALL_AT_ONCE` / `ROLLING`，不传取环境配置）、
> `forceOverwriteConfig`（`0` 默认存在即跳过 / `1` 先比对 MD5，不一致则把目标机旧文件备份为 `<文件名>_bak_<时间戳>` 后覆盖）。

## 8. 示例五：分层构建 + Docker（COMPOSE）— `aiops-app`（设计口径，建议首用前实测）

> 适用场景：基础依赖（系统包、语言运行时、公共库）体积大、几乎不变，想把它固化成稳定的 `base` 镜像，
> 业务层只叠加自己的产物，构建时复用 base、跳过依赖安装，省排队时间。
> 参数依据：`docs/构建模式与执行链路.md` §3.2、`docs/Docker镜像构建发布方案评估.md` ADR-06 与 §7.3。

### 8.1 创建项目参数
`runtimeType=DOCKER`、`buildMode=LAYERED_DOCKER`、`sourceType=GIT`、`registryId`/`buildServerId` 同示例一。

**构建配置 `buildConfigJson`**
```json
{
  "dockerfile_path": "Dockerfile.app",
  "base_dockerfile_path": "Dockerfile.base",
  "image_repository": "registry.cn-hangzhou.aliyuncs.com/lx_relife/aiops-app",
  "compose_file_path": "docker-compose.yml",
  "rebuild_base_image": true,
  "docker_verify_on_build": true,
  "docker_verify_timeout_seconds": 30
}
```
要点：
- `dockerfile_path`（应用层）与 `base_dockerfile_path`（基础层）**都必填**。
- 应用层 Dockerfile **必须**声明 `ARG BASE_IMAGE` 并用它做 `FROM`（如 `FROM ${BASE_IMAGE}`）；
  平台在构建时注入 `--build-arg BASE_IMAGE=<image_repository>:base`。基础层 Dockerfile 自己
  `FROM` 官方基础镜像并装依赖。
- `rebuild_base_image`：**默认 `false`（复用仓库里已有的稳定 `:base` 镜像）**。首次使用本模式、或基础层
  内容真的变了，必须**临时勾选 true**（或在构建弹窗选「重新构建基础镜像」）以创建/更新 `:base`；
  之后改回默认即可复用。**首次忘了开 true，会因仓库里没有 `:base` tag 而失败**。
- 与 `PROJECT_DOCKERFILE` 的区别：后者只用一个 Dockerfile 一步构建；分层是把「依赖安装」拆出来固化成
  可复用的 base。依赖不变时应优先选本模式提速。

**运行配置 `runtimeConfigJson`**
```json
{ "deploy_form": "COMPOSE", "work_dir": "/lx/docker/aiops-app" }
```
> 分层构建产出的业务镜像 tag 仍是 `<image_repository>:<版本>`，compose 里写
> `image: <image_repository>:${IMAGE_TAG}` 即可（base 镜像不进 compose、不随版本变）。

### 8.2 构建
日志关键行（按顺序）：
1. `执行 docker build -f Dockerfile.base -t <repo>:base .` → `推送基础镜像 <repo>:base`；
2. `执行 docker build -f Dockerfile.app --build-arg BASE_IMAGE=<repo>:base -t <repo>:<版本> .`；
3. `启动级验证通过` → `推送镜像 <repo>:<版本>`；
4. 配置转存（`config_paths` → 版本 `config/`）。
产物：`build_artifact` 含 `BASE_IMAGE`（`:base`）+ `APP_IMAGE`（`<版本>`，带 digest）。

> **ADR-06（v1）限制**：基础层不做依赖指纹复用，每次 `rebuild_base_image=true` 都是全量重装依赖，
> 没有缓存命中加速；`rebuild_base_image=false` 时直接跳过 base 构建、复用仓库现有 `:base`。
> 所以「要不要重建 base」按「依赖变没变」决定，不要每版都开。

### 8.3 绑定环境与目标 / 发布
同示例一（COMPOSE 链路），`runtimeConfigJson` 用 `{"deploy_form":"COMPOSE","work_dir":"/lx/docker/aiops-app"}`。

### 8.4 前后端对应与校验点
| 键 | 页面可见 | 后端消费 | 校验 / 坑 |
| -- | -- | -- | -- |
| `base_dockerfile_path` | ✅ LAYERED_DOCKER 下显示 | 构建基础层 `-f` 参数 | **必填**；空则构建失败 |
| `dockerfile_path` | ✅ LAYERED_DOCKER 下显示 | 应用层 `-f` 参数 | **必填**；应用层必须 `ARG BASE_IMAGE` + `FROM ${BASE_IMAGE}` |
| `image_repository` | ✅ | base 与 app 都推这里 | 留空回落 `registry+namespace+编码` |
| `rebuild_base_image` | ✅（开关） | 是否重建 base | 默认 **false**（复用 `:base`）；首次/依赖变更必须 true |
| `compose_file_path` | ✅ | 快照进 `release_record.compose_content` | COMPOSE 发布必配，含 `${IMAGE_TAG}` |
| `docker_verify_on_build` / `docker_verify_timeout_seconds` | ✅ | 启动级验证 | 默认开 / 30s |

## 9. 重要提醒：跨架构构建发布（本地 arm64 构建机 → amd64 目标机）

> 详见 `docs/Docker镜像构建发布方案评估.md` §11.1「跨架构构建发布限制（已知约束）」。

- **Docker 链路有架构绑定**：arm64 构建机打出的镜像在 amd64 目标机会报 `exec format error`。
  JAR / 脚本 / STATIC 部署不受影响（JVM 字节码跨架构、脚本与静态文件架构无关）。
- **生产无此问题**：生产构建机与目标机均为 amd64。冲突仅出现在本地「arm64 构建机（如 M 系列 Mac 上的
  arm64 虚拟机）→ amd64 服务器」的开发拓扑。
- **平台当前不支持跨架构构建发布**（构建命令走 `docker build`，未集成 QEMU 交叉构建）。
- **本地规避**：用 arm64 VM 作构建机时，Docker 镜像需在平台外用
  `docker buildx build --platform linux/amd64 --push` + 构建机注册 `tonistiigi/binfmt`（QEMU）
  交叉编成 amd64，再交给平台走推送 / 拉取 / 运行。
