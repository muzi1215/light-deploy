# 产物分发链路（构建机 → 平台 → 目标机）

> 范围：部署执行阶段「构建机上的产物如何到达目标机并生效」的完整内部逻辑，含回滚时的差异。
> 相关：`docs/发布模块.md` §6.3（三条运行时链路）、AGENTS.md §3.1 / §3.2（JAR / STATIC 形态）、§24.7（版本标识与完整性校验）、§24.10（回滚产物来源）。
> 本文按 2026-09-28 的代码实现撰写，与代码冲突时以代码为准。

---

## 1. 结论先行

- **文件类运行时（JAR / STATIC）走两跳中转**：构建机 → 平台本地临时文件 → 目标机。**不做服务器间直传**。
- **DOCKER 默认也不产文件**：目标机自己 `docker pull`，平台只下发命令。
  **唯一例外是 COMPOSE 形态**（`deploy_form=COMPOSE`）——它要下发两个小文件：项目自带的 `docker-compose.yml`（原文，构建期已快照到发布版本）与平台生成的版本变量文件，两者都只有几 KB，直接 `cat` 写过去，不走构建机中转，也**不修改任何一个字节的编排内容**。版本号以变量注入而非文本替换，理由见 §6.1。
- **B1（JAR_PREBUILD）额外下发一份「平铺热修包」**到 `<work_dir>/build-context/`（见 §6.1.1）：
  它不参与本次启动（启动仍是 pull + compose up），纯粹是**平台不可用时的现场重建素材**。
  B1 的目标机没有源码也没有 maven，源码上下文对它毫无意义，所以这份包收敛成
  `{产物名}.jar + Dockerfile.hotfix + docker-compose.hotfix.yml + config + README`，解包即可 `docker build`。
  jar 沿用产物自己的文件名（如 `auth-tool.jar`），不做重命名。
- **配置文件 JAR 与 DOCKER 都发**（见 §6.4）：`build_config_json.config_paths` 指到的文件在构建期转存到
  `{构建产物持久目录}/{项目编码}/{版本}/config`，发布期投放到目标机（JAR → `{workDir}/{configDir}`，
  DOCKER → `{workDir}/config`），**目标机已存在则跳过**。DOCKER 侧的产物是镜像、不落盘，
  转存由 `persistVersionConfig` 单独补一次，否则 compose 挂的 `./config` 永远是空目录。
- **两跳的传输方式不对称**：构建机 → 平台一律 SFTP 下载；平台 → 目标机在 JAR 上走 exec 流式管道（`cat > 文件`）并在异常时回落 SFTP，STATIC 仍是 SFTP。
- **每一步落盘都先写临时名再 `mv`，校验一律在「生效」之前**：JAR 在 `systemctl restart` 之前校验，STATIC 在替换目录内容之前校验。失败要么还原现场，要么中止在「还没碰过线上」的位置。

## 2. 全景

```text
             ┌──────────────── 平台（Spring Boot 进程）────────────────┐
             │ DeployTaskHandler：批次编排（策略、批次大小、中止/跳过）  │
             │   └─ deployTarget()：每台目标执行一次                    │
             │        └─ JarDeployService / StaticDeployService /      │
             │           DockerDeployService .deploy(DeployContext)     │
             └──────┬─────────────────────────────────────┬────────────┘
                    │ ① SFTP get                           │ ③ 投放 + 远程命令
                    │   sftpDownload()                     │   uploadLarge() / sftpUpload()
                    ▼                                     ▼
        ┌────────────────────────┐            ┌────────────────────────┐
        │ 构建机                  │            │ 目标机（N 台，串行）     │
        │ {build_artifact_dir}/   │            │ JAR:    {workDir}       │
        │   {项目编码}/{版本}/     │            │ STATIC: {static_root}   │
        │     xxx.jar | dist/     │            │ DOCKER: docker daemon   │
        │     config/  VERSION    │            └────────────────────────┘
        └────────────────────────┘                       ▲
                                                          │ ② 平台本地临时文件
                                                          │   /tmp/ld-deploy-{部署ID}-{文件名}
```

- ①②③ 是文件类运行时的完整路径；DOCKER 三条全不存在，只有一条命令通道。
  **COMPOSE 形态是这条规则的唯一例外**：它没有 ①②③（产物仍是镜像），但多一条「平台 → 目标机」的小文件通道（类型 ③ 的轻量版，见 §6.1）。
- **N 台目标 = N 遍 ①②③**：每台的产物下载彼此独立，平台不会为同一次部署复用已下载的临时文件（见 §9）。

## 3. 分发前的三个前提

分发本身不查拓扑、不算版本，它只消费三份已经定稿的数据。

### 3.1 `release_record`：东西在哪

| 字段 | 分发时的作用 |
| --- | --- |
| `artifact_path` | 构建机上产物的绝对路径（JAR / STATIC），分发起点 |
| `build_server_id` | 定位构建机。**为空直接报错**「未记录构建机（多为历史版本），请重新构建」——不在代码里猜机器 |
| `sha256` | 投放完成后回读校验；同时用于「目标机已经是这个包」的跳过判断 |
| `image_tag` | DOCKER 用，`docker pull` 的目标 |

产物路径形如 `{build_artifact_dir}/{项目编码}/{版本}/{文件名}`，两个来源：

- 构建产出：`BuildTaskHandler.buildFileArtifact` 在工作区构建完成后 `cp -r` 转存到持久目录，并写入 `VERSION`（`version/commit/runtime/artifact/built_at`）。**必须先转存**：工作区在任务收尾时被整体删除。
- 手工上传：`ArtifactUploadService` 把运维上传的压缩包直接放到同一约定的持久目录，同样写 `VERSION`、算 SHA256。

### 3.2 `deployment_target`：发到哪、从哪退

目标列表、发布顺序、`old_version` / `new_version` 都在**创建部署时固化成快照**。执行器只读快照，不实时关联 `project_environment_target`（AGENTS §24.9），否则改一次拓扑就会改变历史部署的目标集合。

### 3.3 `DeployContext`：这次到底发哪个版本

发布与回滚共用同一批分发代码，方向由上下文换算：

| 方法 | 发布 | 回滚 | 用途 |
| --- | --- | --- | --- |
| `targetVersion()` | `new_version` | `old_version` | 本次要写到磁盘的版本，`VERSION` 文件与日志都用它 |
| `currentVersion()` | `old_version` | `new_version` | **仅用于备份命名**——标记「被换下去的是哪个版本」 |

构造时做一次对齐校验：若目标快照声明的版本与 `release_record.version` 不一致，直接抛异常，不让磁盘上的 `VERSION` 与平台记录错位（错位要到「回滚时找不到能退的版本」才暴露）。

## 4. 通用中转模型

### 4.1 为什么不让目标机直接去构建机取

- 目标机不需要持有构建机的免密通道；
- **网络与凭据收敛在平台侧**：平台只要能连构建机、能连目标机即可，构建机与目标机之间不需要互通（跨机房、跨 VPC 场景尤其重要）；
- 代价是明确的：多一跳带宽、多一份平台本地磁盘占用（§9）。

### 4.2 平台本地临时文件

`DeploySupport.downloadArtifact` 用 `Files.createTempFile("ld-deploy-" + deploymentId + "-", "-" + fileName)` 落在系统临时目录，返回值交给调用方，**由调用方在 `finally` 里 `deleteQuietly` 清理**。生命周期是「单个目标」而不是「单次部署」。

### 4.3 会话与凭据

每次 `SshSessionFactory.open(server)` 建立一条独立会话（`SshClient` 随会话一起关闭），认证方式按 `server.auth_type` 走密码或私钥，密文在连接前才解密、不缓存、不进日志。

发一台目标的典型会话数：

| 运行时 | 会话 |
| --- | --- |
| JAR | 构建机 1 条（下载 jar；有配置文件时再 1 条）+ 目标机 1 条（投放 + 命令） |
| STATIC | 构建机 1–2 条（必要时打包 + 下载）→ 目标机 1 条 |
| DOCKER | 目标机 1 条 |

## 5. 传输层：两种通道与一次抉择

| 通道 | 实现 | 用在哪 |
| --- | --- | --- |
| SFTP | `SshSession.sftpDownload` / `sftpUpload` | 构建机 → 平台（全部）、平台 → 目标机的 STATIC 包与配置文件 |
| exec 流式管道 | `cat > 远端文件`，本地文件流写进通道 stdin | 平台 → 目标机的大文件（JAR） |

`SshSession.uploadLarge` 的抉择逻辑：**先试流式管道，抛异常则回落 SFTP**，并把最终方式（"流式管道" / "SFTP 回落"）返回给调用方写进任务日志。

为什么大文件不走 SFTP：SFTP 是有窗口与逐包确认的应用层协议，高延迟链路上吞吐被 RTT 压住——实测同一条链路上 74 MB 走 SFTP 要 325 s（约 0.23 MB/s），而裸管道由 TCP 自己做流控，通常能贴近实际带宽。保留回落是因为个别加固机器会禁掉 exec 写 stdin，此时退回 SFTP 至少还能发布成功。

三点通用保障：

- **超时**：普通命令 120 s（`light-deploy.ssh.command-timeout-seconds`），长命令 1800 s（`light-deploy.ssh.long-command-timeout-seconds`）；流式上传按长命令超时。超时抛 `SshCommandTimeoutException` 并带上已收到的输出快照，不停在「一句超时、日志空白」。
- **脱敏**：所有远程输出在 `SshCommandResult` 里统一 `maskSecrets` 后才进任务日志与异常消息。
- **先临时名后 `mv`**：JAR 传成 `{jar名}.uploading` 再 `mv -f`；STATIC 传到 `/tmp/{时间戳}-{包名}` 再解压。中途失败不会在服务目录里留下半截产物。

## 6. 三条链路逐步展开

### 6.1 DOCKER：默认无文件传输，COMPOSE 形态例外

#### RUN 形态（默认）

```
docker pull {image_tag}  →  docker rm -f {容器名}  →  docker run -d --restart=always  →  docker inspect 确认 Running
```

- 产物在构建阶段已推送到仓库，发布只发三条命令，全部按长命令超时等待。
- `docker rm -f` 不是可选项：容器名是发布幂等的关键，不删会让 `run` 直接失败；`|| true` 兜住首次发布没有旧容器的情况。
- 启动后必须再 `docker inspect -f '{{.State.Running}}'`：一次确认把「启动即退出」从「发布成功」里剔除。

#### COMPOSE 形态：下发两个小文件

```
登录仓库 → mkdir 工作目录 → 投放 config/（有配置时）→ 写 docker-compose.yml（原文快照）
→ 写 .env.light-deploy（IMAGE_TAG=本次标签）→ 下发热修包 → pull → up -d → ps 确认运行态
```

| 环节 | 内容 | 从哪来 |
| --- | --- | --- |
| `docker-compose.yml` | **项目仓库里的原文**，逐字节不变 | `release_record.compose_content`，构建阶段快照（见 [构建模块.md](构建模块.md) §6.2.5）；**不经构建机中转** |
| `.env.light-deploy` | 单行 `IMAGE_TAG={image_tag}` | 平台按本次版本号生成 |
| 落盘方式 | quoted heredoc（`cat > 文件 <<'LD_EOF'`） | 文件很小，一条命令写完，无临时文件中转 |

两条必须守住的边界：

1. **不对 compose 原文做任何替换**。用变量注入而不是把 `${IMAGE_TAG}` 替换成具体 tag，
   是为了让运维上机看到的文件与仓库里逐字一致——平台悄悄改过的文件，
   没人说得清哪部分是用户意图、哪部分是平台加工。heredoc 之所以用 quoted 形式（`<<'MARKER'`），
   同样是为了让 `${VAR}`、反引号、双引号全部保持字面：这份内容要经过 shell，
   少一层引号就会被 shell 提前吃掉变量，`ShellQuoteTests` 用真实 `sh -c` 把这条语义钉住了。
2. **缺 `${IMAGE_TAG}` 占位符就在构建期报错**（构建与发布两侧同一份判据）。
   缺了它容器永远拉同一个 tag：发布报成功、线上没变化，属于最难发现的一类故障。
- **不做 `docker login`**：登录只发生在构建机（推送）与连通性测试。目标机的仓库凭据是运维在该机器上预先配置好的，平台不代劳（现状如此，见 §9 边界第 4 条）。

#### 6.1.1 B1（JAR_PREBUILD）热修包：唯一一份含 jar 的应急素材

DOCKER 的产物是镜像，理论上「平台挂了也能 `docker pull` 起回来」——但前提是镜像仓库可达、且知道该拉哪个 tag。
一旦平台不可用且仓库也连不上，目标机上除了正在跑的容器什么都没有，**无法用一个新 jar 快速救火**。
B1 因此额外产出一份热修包，随正常发布落到目标机。

| 环节 | 行为 |
| --- | --- |
| 构建期 | `BuildTaskHandler.captureHotfixKit` 在 `buildJarPrebuild` 成功后，把 jar **按原名**（`fileNameOf` 取 `artifact_path` 定位到的文件名，如 `auth-tool.jar`）连同项目提供的 `Dockerfile.hotfix` / `docker-compose.hotfix.yml` / `application.yml` 与平台生成的 `README.md` 打成 `hotfix-kit.tar.gz`，落在 `{build_artifact_dir}/{项目编码}/{版本}/`，路径写入 `release_record.context_artifact_path` |
| 发布期 | `DockerDeployService.shouldDeliverKit` 对 `hotfix-kit.tar.gz` **一律返回 true**（B1 不要求配置 `work_dir`；未配置时落到「部署根目录/项目编码」），COMPOSE 与 RUN 两种形态都下发，解包到 `<work_dir>/build-context/` |
| 重建 | 运维 `cd build-context` → `docker compose -p <项目编码> -f docker-compose.hotfix.yml up -d --build`，全程不连平台、不连构建机、不需要源码 |
| 失败语义 | 热修包是应急素材：打包或下发失败只记日志，**不影响镜像构建/发布结论**；缺 `Dockerfile.hotfix` 视为项目未启用该能力，直接跳过 |

三个必须守住的边界：

1. **平台只打包、不生成**：`Dockerfile.hotfix` 与 `docker-compose.hotfix.yml` 均由项目仓库提供（约定与 `dockerfile_path` 同目录），平台不猜编排，与 §23.8「平台不生成 Dockerfile/compose」一致；
2. **平铺上下文**：`Dockerfile.hotfix` 用 `COPY *.jar /app/app.jar`（通配，与 jar 叫什么解耦），与 `Dockerfile.jre` 的仓库根相对路径不同。两份 Dockerfile 必须产出等价镜像——改 `JAVA_OPTS`/`ENTRYPOINT` 时须同步；镜像内路径固定为 `/app/app.jar`，包文件名怎么变都不影响启动；
3. **配置挂载、不烘进镜像**：`application.yml` 通过 `./config:/app/config:z` 挂载（`:z` 兼容 SELinux），未挂载时回落 jar 内 classpath 配置；这样改配置不必重建镜像。

> 完整命令级步骤与自检清单见 [平台不可用应急手册.md](平台不可用应急手册.md)。

### 6.2 JAR：固定工作目录 + 原地替换

| # | 动作 | 实现要点 |
| --- | --- | --- |
| 1 | 下载 jar 到平台临时文件 | `DeploySupport.downloadArtifact`，SFTP，日志记「已从构建机下载产物 {path}（74.02 MB（77607226 字节））」 |
| 2 | 下载随版本转存的配置文件 | 构建机产物同级的 `config/` 目录，`sftpDownload` 逐个拉回来 |
| 3 | 打开目标机会话 | 一台目标全过程复用这一条 |
| 4 | 投放内置脚本 + 必要时初始化 | `exec/` 下三份脚本**每次发布都重写**（平台资产，版本随平台走）；仅当工作目录里还没有 jar 时才跑 `jar-init.py` 建目录与 systemd 单元 |
| 5 | 投放配置文件到 `{workDir}/config` | **已存在同名文件就跳过，不覆盖**——配置由运维自己维护，平台不该每次发版覆盖现场改动 |
| 6 | 判断目标机是否已是本次要发的包 | `artifactUpToDate`：比对 `release.sha256` 与目标机 `sha256sum`。命中则**跳过备份与上传** |
| 7 | 备份旧 jar | `cp -p` 到 `exec/bak/{jar名}_bak_{时间戳}_{版本号}.jar`，版本段读目标机 `VERSION`（磁盘事实，不取库快照） |
| 8 | 上传新 jar | `uploadLarge` 传到 `{jar名}.uploading` → `mv -f` 覆盖 |
| 9 | **复核 SHA256** | 不一致 → 先 `cp -p` 还原备份再抛异常 |
| 10 | 写 `VERSION` + 刷新 `exec/deploy.conf` 的 `version=` | 两者失败只记日志不影响结论，但必须留痕 |
| 11 | `systemctl restart` + `is-active` 确认 | 重启按长命令超时；`is-active` 非 active 判失败 |
| 12 | 清理平台临时文件 | `finally` 里 `deleteQuietly` |

三个容易忽略的设计点：

- **第 6 步的跳过发生在备份之前**。重复发布同一版本、或发布失败后重试时，目标机上往往已经放着完全相同的包，此时再传一遍大文件纯属浪费（74 MB 在窄带上几分钟，而比对摘要只是一次目标机本地 `sha256sum`）。既然被替换者与替换者是同一个包，备份也没有意义，因此两步一起跳。三种情况一律按「需要上传」处理：版本未登记摘要、目标机上还没有 jar、目标机算不出摘要——保守方向。
- **jar 文件名沿用工作目录里已有的名字**（`resolveJarName`），同一实例只保留一个 jar，产物文件名带版本号时也不会在工作目录里越堆越多。
- **systemd 单元只在首次生成**，之后绝不重写：运维手工调过的 `-Xmx`、`--spring.config.location` 必须被尊重。

时序不可调换，尤其 **校验与写标识必须早于重启**：此刻发现 jar 损坏还能无损还原，一旦重启就变成线上事故；标识若晚于重启，重启失败时会停在「磁盘新版本 + 标识旧版本」的错位状态。

### 6.3 STATIC：只换目录内容，绝不换目录

| # | 动作 | 实现要点 |
| --- | --- | --- |
| 1 | （必要时）构建机上打包 | 产物已是 `.zip` / `.tar.gz` / `.tgz` 时原样传输；目录型产物才 `tar -czf /tmp/ld-static-{部署ID}.tar.gz -C {目录} .` |
| 2 | 下载到平台临时文件 | 同 JAR |
| 3 | 上传到目标机 `/tmp/{时间戳}-{包名}` | **走 `sftpUpload`**（未走流式管道，见 §9 边界第 1 条） |
| 4 | 解压到旁路暂存目录 `static-new-{时间戳}` | zip 先探测 `unzip` 是否存在；解压前 `rm -rf` 清掉上次失败残骸 |
| 5 | 剥壳 / 告警 / 非空校验 | `stripTopLevelDir`（三条判据全中才剥）→ `warnIfNested`（只告警）→ `ensureStagingNotEmpty`（**为空直接中止，站点此时还没被碰过**） |
| 6 | 备份当前内容 | `_ld_move {static_root} {backupDir}/{目录名}_bak_{时间戳}_{版本}` —— **搬的是目录内的条目，目录本身不动** |
| 7 | 新内容就位 | `_ld_move {stagedDir} {static_root}`，失败则立刻把备份搬回 `static_root` |
| 8 | 清理暂存目录 + 记录 inode | 用 `rmdir` 而非 `rm -rf`：有残留就让它留在原地被看见；日志输出 inode 前后值 |
| 9 | 不执行 nginx reload | 平台不改 nginx 配置，reload 失败会把「文件已替换」误判成发布失败 |

为什么要搬内容而不是换目录（2026-09-28 事故定论）：`static_root` 常作为 Docker bind mount 的源，而 bind mount 在容器启动时**按路径解析一次并绑定 inode**。目录被 rename 走之后容器仍握着旧 inode，容器内目录变空，nginx 报 `directory index ... is forbidden`、全站 403，`nginx -s reload` 无效，只能重建容器。因此切换动作由 `MOVE_CONTENTS`（shell 函数 `_ld_move`）完成，两个目录自身的 inode 全程恒定，代价是切换期间存在极短的目录为空窗口——两种失败模式不对等：瞬时 404 会自愈，容器失效挂载必须重建容器。

`_ld_move` 四条 shell 细节都不能改：进子 shell 用相对路径；非隐藏条目用 `set -- *` **整批** `mv`（逐个 mv 等于逐个 fork，上千文件会把窗口拖到分钟级）；`.[!.]* ..?*` 显式覆盖隐藏文件（`*` 不匹配点开头，会漏掉 `.env`、`.well-known`）；`if [ -e "$f" ]` 判存在（glob 无匹配时保留字面量），**不能写成 `[ -e "$f" ] && mv ... || exit 1`**——`&&` 短路会去执行 `|| exit 1`，把「没有隐藏文件」判成失败。

### 6.4 配置文件分发（JAR 与 DOCKER 共用）

构建阶段按 `build_config_json.config_paths` 把配置转存到版本目录的 `config/` 子目录；发布时：

1. `ls -1 {persistDir}/config` 列出文件名（无配置直接返回，不建立构建机会话）；
2. 逐个 `sftpDownload` 到平台临时文件；
3. 逐个 `sftpUpload` 到目标机配置目录。**默认已存在则跳过；勾选「强制覆盖」时内容不一致才覆盖（见下）。**

「默认不覆盖」是刻意设计：产物与配置分离的意义就在于配置由运维自己维护，平台不该在每次发版时用仓库里的配置盖掉现场改动。缺配置也不阻断发版——是否真的起得来由服务启动与运行态校验判定。

**显式开关 `force_overwrite_config`（部署记录上的列，创建部署时固化、异步任务再读）：**

- `0`（默认，保守）：目标机已存在同名文件则跳过、不覆盖——保护运维手动改过的现场配置（改库地址 / 账号等）。这是 JAR 与 DOCKER 共用的默认口径。
- `1`（强制）：勾选后平台先比对内容（MD5），**与本次版本一致则跳过；不一致则把目标机旧配置改名备份为 `<文件名>_bak_<时间戳>`（单文件、不建目录，与 JAR 备份约定同源）再写入新配置**。备份留退路，符合容灾底线。
- 为什么需要这个开关：配置本就是仓库管理的（如 `auth-tool/Docker/application.yml`），运维改了仓库配置 → 重建 → 重发，默认的「存在即跳过」会让新配置永远传不下去。开关把「要不要覆盖」这个有风险的决定显式交给操作者，平台不替你做。
- 开关只在「本次部署」生效，不是项目级长期配置；前端「新建部署」弹窗有对应勾选框。

两种运行时的差异只在**构建期谁负责转存**与**目标机放到哪个目录**：

| | JAR | DOCKER |
| --- | --- | --- |
| 构建期转存 | `buildFileArtifact` 顺手做（产物本来就要落盘） | `persistVersionConfig` 单独做（镜像不落盘，走不到上面那条路径） |
| 构建机上的位置 | `{build_artifact_dir}/{项目编码}/{版本}/config`，由 `artifact_path` 推得 | 同一位置，由约定拼接（DOCKER 的 `artifact_path` 为 null，`DeploySupport.versionConfigDir` 按 `构建产物持久目录 + 项目编码 + 版本` 拼） |
| 目标机目录 | `{workDir}/{configDir}`（`configDir` 取运行配置，默认 `config`） | `{workDir}/config` |
| 什么时候真正生效 | 平台把 `--spring.config.location` / `additional-location` 指过去（首次初始化时写进 systemd 单元） | compose 里挂了 `./config` 才生效（如 `- ./config:/app/config`） |

DOCKER 侧的三个设计点：

1. **投放必须早于 `up -d`**。`./config` 是 bind mount，容器创建那一刻就完成绑定；之后才往里放文件，容器已经按「空目录」起来了——表现为「宿主机有配置、容器里读不到」，`docker inspect` 也看不出异常。
2. **目录为空要显式告警**。compose 引用了 `./config` 而该目录没有文件时，发布日志里打一条「【注意】…容器将回落到镜像 / jar 内 classpath 的内置配置启动」。这类静默错配最危险的地方是：容器起得来、健康检查也过、平台报发布成功，实际连的却是镜像里的默认库。
3. **RUN 形态默认不落盘**。RUN 不挂载任何宿主目录，配置投放只对显式在 `extra_docker_args` 里写了 `-v .../config:/app/config` 的项目有意义；没有配置文件时这一步不创建任何目录，保持既有语义。

## 7. 失败与安全语义

| 环节 | 失败时的处理 | 理由 |
| --- | --- | --- |
| 产物下载（①） | 抛异常，目标判失败 | 磁盘尚未被触碰 |
| 上传中断（③） | 临时名残留，服务目录未变 | 先临时名后 `mv` |
| JAR 摘要不符 | **先 `cp -p` 还原备份再抛异常** | 否则停在「服务跑旧版、磁盘放坏包」，下次重启必然起不来 |
| JAR 还原失败 | 只记 ERROR，仍抛「完整性校验失败」 | 根因是校验失败，不能被还原异常覆盖 |
| STATIC 产物为空 | 中止发布 | 内容替换语义下，空包就位 = 站点被清空却报成功 |
| STATIC 新内容就位失败 | 把备份内容搬回 `static_root`，再抛异常 | 否则站点长时间空着 |
| 写 `VERSION` / 刷 `deploy.conf` 失败 | 只记日志，不影响结论 | 辅助信息，但必须留痕 |
| 平台临时文件清理失败 | 只 WARN | 不能让清理失败覆盖真正的发布结果 |

另外：

- **日志写入失败从不阻断发布**（`appendLog` 内部吞异常只告警）：发布动作可能已经改变了机器状态，一次日志库抖动不应把发布判成失败，否则会出现「记录说失败、磁盘已变更」的错位。
- **目标级失败不向外抛**：收敛成 `deployment_target.status + error_message`，由编排层决定策略（滚动中止剩余、全量跑完）。
- **脱敏在所有远程出口统一做**，异常消息里不含凭据。

## 8. 回滚时的分发差异

### 8.1 共同前提：改的是「取哪个版本」，不是「怎么发」

回滚与发布**共用同一个 `deploy()`**，代码路径逐行相同（`JarDeployService.deploy` / `StaticDeployService.deploy` / `DockerDeployService.deploy`）。差别只有两处：

| 差别 | 常规发布 | 回滚 |
| --- | --- | --- |
| `ctx.release()` 指向 | `new_version` 对应的版本记录 | `old_version` 对应的版本记录（编排层 `resolveVersionRelease` 换算） |
| `ctx.rollingBack()` | false | true（**只有 STATIC 消费这个标志**） |

其余全部一致：同一套下载、同一套投放、同一套校验、同一套重启与健康检查。因此**「回滚能不能成功」等价于「能否拿到那个版本的产物」**，而这完全由各运行时的产物来源决定。

### 8.2 JAR：100% 由平台重走两跳

先回答最常见的疑问：**是的，JAR 回滚就是平台按 `old_version` 反查版本记录，再从构建机把产物重新投放到目标机，与常规发布走一模一样的两跳。** `JarDeployService.deploy` 里**没有任何 `rollingBack()` 分支**——全文找不到一处。完整时序：

| # | 步骤 | 位置 | 说明 |
| --- | --- | --- | --- |
| 1 | 入口判定 | `DeploymentRollbackService.historyArtifactAvailable` | 要求目标版本的 `release_record` 同时有 `build_server_id` 与 `artifact_path`，缺一就在点按钮之前判「不可回滚」 |
| 2 | 复制出部署记录 | `DeploymentService`（`is_rollback=1`，`version` 记 `old_version`） | 部署记录不可原地重跑，必须新建（AGENTS §24.6） |
| 3 | 版本方向换算 | `DeployContext.targetVersionOf` | 回滚时「目标版本」= `old_version`；`currentVersion` 是正被换掉的 `new_version`，**只用于给备份命名** |
| 4 | 构建机下载 | `DeploySupport.downloadArtifact` | SFTP 拉 `artifact_path`，落到平台临时文件 |
| 5 | 目标机投放 | `SshSession.uploadLarge` | 流式管道优先、SFTP 回落；写 `{jar名}.uploading` 后 `mv -f` |
| 6 | SHA256 复核 | `verifyJarDigest` | 不符则先 `cp -p` 还原备份再抛异常 |
| 7 | 写标识 / 刷 conf / 重启 | `writeVersionMarker` → `refreshDeployConfVersion` → `restartService` | 与常规发布完全相同 |

**目标机 `exec/bak` 全程不参与**。它只在两种场合被使用：发布中途产物校验失败时平台自动还原（`restorePreviousJar`），以及运维上机手工 `cp` 回来。**回滚时平台不会去读它**——这是功能缺口而非不可行：备份名早已内嵌平台版本号，`DeploymentRollbackService` 的类注释里也写明了这一点。

推论：**JAR 的回滚能力完全取决于构建机产物目录是否还在。** 构建机不可达、或产物已被保留策略回收 → JAR 无法回滚，与目标机上留了多少份备份无关。

### 8.3 STATIC：两级来源，本机备份是「快路径」而非「兜底」

`StaticDeployService.deploy` 里唯一一处 `rollingBack()` 分支：

```java
boolean fromBackup = ctx.rollingBack()
        && restoreFromBackup(ctx, session, backupDir, dirName, ctx.targetVersion(), stagedDir);
if (!fromBackup) {
    // 常规路径：构建机 → 平台 → 目标机
}
```

| 分支 | 触发条件 | 动作 | 代价 |
| --- | --- | --- | --- |
| **快路径** | 回滚中，且备份目录里存在 `{静态目录名}_bak_*_{目标版本}` | `cp -a` 到暂存目录 | 不下载、不解压、不过构建机，秒级 |
| **回落** | 未命中（备份被清过，或该版本从未在这台机器跑过） | 完整两跳 + 打包/解压/剥壳/非空校验 | 分钟级 |

三个容易忽略的细节：

1. **用 `cp -a` 而不是 `mv`**：`restoreFromBackup` 的注释写明了原因——备份必须保留，否则回滚一次之后这个版本的备份就没了，再回滚同一版本只能重新走构建机。
2. **回滚自身也会产生新备份**：命中快路径后照样走 `switchDirectory`，旧内容会被搬进一个新的 `{目录名}_bak_{时间戳}_{版本号}/`。所以**回滚不是「消耗」一个备份，而是「消耗一个、生成一个」**，备份总数不会因回滚而下降。
3. **命中只看名字里的版本号**：`ls -d {backupDir}/{dirName}_bak_*_{version} | head -1` 取第一个；版本号先过 `SAFE_VERSION` 正则（`[A-Za-z0-9._-]`），不匹配直接走常规路径，避免把版本号当命令注入。

### 8.4 DOCKER：只换镜像标签

产物在镜像仓库，按 `old_version` 的 `image_tag` 重新 `docker pull` → `rm -f` → `run -d` → `inspect` 确认 Running。目标机不留任何历史副本，也不存在本机备份这一层。

### 8.5 三者对照

| 运行时 | 产物从哪来 | 是否消费本机备份 | 网络依赖 | 清理本机备份的后果 |
| --- | --- | --- | --- | --- |
| DOCKER | 镜像仓库 | 无本机备份 | 仓库可达即可 | — |
| JAR | **构建机，100%** | **否** | 平台↔构建机、平台↔目标机 | 回滚**不受影响**，只损失手工应急副本 |
| STATIC | **先查目标机本机备份，未命中回落构建机** | **是** | 命中时**只需平台↔目标机** | 回滚**仍会成功**，从秒级退化为分钟级 |

### 8.6 本机备份的真实角色：影响速度，不影响可行性

这是本节最容易被误解的一点。三条链路放在一起看，结论是反直觉的：

> **能否回滚，由 `release_record` + 入口判定单点决定；本机备份决定的是「多快回滚」，以及「平台不可用时运维能不能手工救」。**

- JAR 回滚 100% 走构建机 → 本机 `exec/bak` 被清到 0 份，回滚照样成功。
- STATIC 本机 `static-bak` 被清空 → 只是不再命中快路径，回落到构建机后照样成功。
- 反过来同样成立：**本机备份留再多，也救不了一个 `release_record` 已不可用（缺 `build_server_id` / `artifact_path`）的版本**——入口判定在点按钮之前就拦下了，本机备份根本轮不到出场。

因此本机备份的保留策略**可以安全地与 `project.retain_release_count` 解耦**，三条理由：

1. **语义不同**：`retain_release_count` 裁的是**版本号维度**（保留最近 N 个可发布版本）；本机备份是「某次发布时被换下去的那个包」，同一版本会重复出现（v6→v5→v6→v5 产生 4 份），按份数裁剪会错位。
2. **不能共因失效**：两者若联动清理，会在构建机产物被回收的同时清掉本机兜底，**两条恢复路径同时断**——而本机备份存在的意义恰恰是「构建机那条路断了」。
3. **它不承担可行性职责**：既然清掉也不影响回滚能否成功，就没必要跟版本保留策略绑死。

📌 **一处修正**：此前曾写「STATIC 的本机备份保留数须覆盖回滚需求，否则快路径形同虚设」——这句话只对一半。快路径确实会形同虚设，但**后果是回滚变慢，不是回滚失败**。保留数应按「能接受多慢」来定，而不是按「怕不能回滚」来定。

### 8.7 入口判定：为什么必须看版本状态

**已修（2026-09-28）**：`DeploymentRollbackService.probeRollbackArtifact` 已加入 status 判定，
并把「为什么不能回滚」按档拆开写清楚——笼统的「产物已不存在」对使用者没有任何行动价值。

| 情况 | 给出的原因 |
| --- | --- |
| 版本记录查不到 | 历史版本 X 的发布记录不存在，平台无法定位该版本的产物 |
| JAR / STATIC 且 `status ≠ 可发布`（含「已废弃」） | 历史版本 X 状态为「已废弃」，超出项目保留版本数后其 jar 产物 / 静态产物已从构建机回收，无法回滚：请重新构建该版本后再回滚 |
| JAR / STATIC 缺构建机或产物路径 | 历史版本 X 缺少构建机或产物路径记录，无法重新分发 |
| DOCKER 缺镜像标签 | 历史版本 X 未记录镜像标签，无法从镜像仓库重新拉取 |

修之前的缺陷是：`historyArtifactAvailable` 只检查 `buildServerId` / `artifactPath` 是否非空，
而 `ReleaseRetentionService` 在把版本置「已废弃」时会**删掉构建机上的产物目录却保留这两个字段的值**。
于是结论是「可以回滚」，用户点下去要等到 SFTP 下载阶段才失败，而那时部分目标可能已经被改过。
原则是：**宁可在按钮前判不能退，也不要让人点了才知道。**

两条取舍必须知道：

1. **DOCKER 不看 status**。它的产物是镜像仓库里的 tag，不在构建机磁盘上；
   `ReleaseRetentionService.artifactDir` 会因为 `buildServerId` 为空而返回 null，
   **只置废弃、不删任何东西**。对 DOCKER 加 status 判定，等于砍掉一个镜像明明还在、本来能回滚的版本。
2. **判定不做 SSH 探测**。`probeRollbackArtifact` 按版本号判定而非按机器，**它不知道目标机上有没有本机备份**。
   由此带来一个已知代价：构建机产物已被回收、但目标机 `static-bak` 里仍有该版本备份时，
   回滚技术上走得通（快路径只看备份目录里有没有匹配名字的目录），入口却会拦下。
   这是刻意选择的一致性——宁可保守拦下并给出「请重新构建」这种可行动指引，
   也不要放行后在快路径与慢路径之间碰运气。要保住这条能力就得把判定下沉到逐目标 SSH 探测，
   判定与执行之间还会产生时间差，现阶段不做。

### 8.8 本机备份的清理：scripts/cleanup-bak.sh

按 §8.6 的结论，本机备份采用**独立于 `retain_release_count` 的双上限**：份数上限 + 天数上限，任一超限即清最旧的；最近 N 份（默认 1）硬保护，永不删除。

```bash
# 预演（默认 dry-run，不删任何东西）
./scripts/cleanup-bak.sh -d /lx/jarapps/apps/auth-7888/exec/bak

# 真删：保留最近 10 份、30 天内
./scripts/cleanup-bak.sh -d /lx/jarapps/apps/auth-7888/exec/bak -n 10 -t 30 --apply

# STATIC 的备份条目是「目录」而非文件，同一份脚本通吃
./scripts/cleanup-bak.sh -d /usr/share/nginx/html/static-bak -n 20 -t 60 --apply
```

平台远程触发（脚本不在目标机留文件）：

```bash
ssh target 'bash -s -- -d /path/exec/bak -n 10 -t 30 --apply' < scripts/cleanup-bak.sh
```

脚本的几条硬约束：

- **默认 dry-run**，必须显式 `--apply` 才真删；
- 只处理 `-d` 目录下名字匹配 `*_bak_[0-9]*` 的**一级条目**，绝不递归进子目录，同目录的其他文件一律不碰；
- **按备份名里的 14 位时间戳字典序排时间序**（`LC_ALL=C sort`），不用 mtime 排序——备份是 `cp -p` 复制来的，mtime 保留的是源文件时间，跨次复制后不可靠；**天数维度仍用 `-mtime`**，因为备份落地后不再被修改；
- 拒绝在受保护的系统目录上运行，且必须是绝对路径；
- 末行输出机器可读摘要，便于平台解析：`REMOVED=<n> KEPT=<n> FREED_KB=<kb>`。

> ⚠️ **执行时机建议放在发布成功之后**，不要放在发布之前：发布前清理有可能删掉紧接着就要用的那一份备份。清理失败只应记日志，**绝不阻断发布**。

### 8.9 `retain_release_count` 的适用范围：文件类版本，不含 DOCKER

`ReleaseRetentionService.plan` 的查询条件只有 `projectId + status=RELEASABLE`，SQL 层不做运行时过滤，
拿到结果后由 `occupiesBuildDisk` 剔除镜像类版本——**配额只对占用构建机磁盘的文件类版本计数**。
因此 JAR 与 STATIC 共用完全相同的保留版本数策略（`project.retain_release_count`，默认 5）：
超出且不在保护窗口（最近 20 条部署引用过的版本）的版本，会被删掉构建机上的
`{build_artifact_dir}/{项目编码}/{版本}/` 目录并置「已废弃」。STATIC 的静态产物目录同样被删。

STATIC 与 JAR 的差别只有一处，而且意义重大：

| | 构建机产物被保留策略回收之后 |
| --- | --- |
| JAR | 目标机 `exec/bak` 虽有备份，但平台回滚不读它（§8.2）→ **彻底无法回滚** |
| STATIC | 目标机 `static-bak` 里若还有该版本备份，快路径**技术上仍能还原**（§8.3）→ 但按 §8.7 入口已拦下 |

也就是说：**本机备份对 STATIC 而言会从「加速件」升级为「唯一可能的恢复源」**，
只是这条后门当前被入口判定保守关闭了。这也是 §8.6 说「本机备份保留策略可独立于 `retain_release_count`」时，
STATIC 一侧唯一需要留意的地方——真要让这个后门可用，就得连带把入口判定改造成逐目标探测。

#### 8.9.1 DOCKER 版本不进配额（2026-09-28 修复）

> **2026-09-29 复核**：COMPOSE 形态引入后本结论**依然成立**——
> compose 内容存在 `release_record.compose_content`（几 KB 的库字段），
> 不落在构建机产物持久目录，因此 `artifactDir()` 仍为 null、仍不影响配额。


镜像类版本的产物是**镜像仓库里的 tag**：构建时不往产物持久目录落任何文件
（登记版本时只写 `image_tag` / `image_digest`，从不写 `artifact_path`），
所以 `artifactDir()` 对它恒返回 null，走到执行器也是「无目录可删，仅标记废弃」。

修复前这是一次**纯粹的净损失**——省不下一字节磁盘，却丢掉一个能用的版本：

| | 修复前 | 修复后 |
| --- | --- | --- |
| DOCKER 版本 | 占名额 → 超额时置「已废弃」→ 从新建部署的版本下拉消失 | 完全不参与回收 |
| 磁盘占用 | 一个字节没省（本来就没占） | 同左 |
| 连带影响 | 把文件类版本挤进超额区间**提前误删** | 无 |

**配额挤占**是最容易漏掉的一环：名额池是固定的，不占磁盘的版本每多占一个，
就有一个真正占磁盘的文件类版本被提前清掉。举例：retain=2，库里有 v4(DOCKER)、v3、v2、v1(JAR)，
修复前保留 {v4, v3}、回收 {v2, v1}——v2 是被挤掉的；修复后配额只对 {v3, v2, v1} 计数，只回收 v1。

**为什么过滤放在 Java 侧而不是写进 SQL**：SQL 里 `runtime_type <> 'DOCKER'` 对 `runtime_type` 为 NULL 的行
求值是 NULL（不成立），会把运行时为空的历史记录整批漏掉。这里要的是一条明确可调的判据，
而不是依赖三值逻辑的隐式行为。`runtime_type` 为空的记录按「占磁盘」处理：它们基本是早期文件类版本，
按「不占磁盘」放行会使其产物目录永远失去回收机会，等于留成永久垃圾。

**双保险**：回滚入口 `probeRollbackArtifact` 对 DOCKER 豁免 status 判定（§8.7），
与本次修复是两处独立防护——**历史上已被误废弃的 DOCKER 版本照样能回滚**。

**存量数据需要手工恢复**：本次修复只对后续回收生效，此前已被误置废弃的 DOCKER 版本仍选不到。
`DEPRECATED` 全项目只有 `ReleaseRetentionService.markDeprecated` 一个写入点，
因此 `runtime_type='DOCKER' AND status=2` 的记录可以放心恢复（MySQL 一律手工执行，平台不自动跑）：

```sql
-- 第一步：核查
SELECT r.id, p.code, r.version, r.image_tag
FROM release_record r JOIN project p ON p.id = r.project_id
WHERE r.runtime_type = 'DOCKER' AND r.status = 2 AND r.is_deleted = 0;

-- 第二步：确认无误后恢复为「可发布」
UPDATE release_record r JOIN project p ON p.id = r.project_id
SET r.status = 1
WHERE r.runtime_type = 'DOCKER' AND r.status = 2 AND r.is_deleted = 0;
```


## 9. 性能特征与已知边界

1. **每个目标各自下载一次产物**：N 台机器发同一版本，构建机 → 平台这一跳会跑 N 遍，带宽与构建机 SFTP 连接数都按 N 放大。同一版本在平台侧做一次临时文件复用是明确的优化方向（要处理并发与清理时机）。
2. **带宽翻倍**：两跳意味着每字节在平台上过两遍（进一次、出一次）。平台与构建机、目标机同内网时无所谓，跨公网时是真实成本。
3. **平台本地磁盘**：峰值占用 = 单个产物大小 × 并发目标数，落在系统临时目录。大静态包 + 多目标并发时要留意临时目录所在分区。
4. **STATIC 上传未走流式管道**：`StaticDeployService` 用的是 `sftpUpload`，没有享受 JAR 那条快路径。大静态包在窄带上会明显偏慢，是待补的一致化改造点。
5. **目标机 `docker login` 由运维预置**：发布链路不登录仓库，目标机必须已具备拉取权限（或仓库公开）。
6. **解包工具依赖目标机**：zip 需要 `unzip`，JAR 初始化需要 `python3`（且脚本兼容 3.5+），缺了都在对应步骤给出明确提示而不是让输出为空。
7. **本机备份的回收**：`exec/bak` 与 `static-bak` **不受 `project.retain_release_count` 管理**——该字段裁的是版本号维度，本机备份是「被换下去的那个包」，两者必须解耦（理由见 §8.6）。此前二者都只增不减，现已提供 `scripts/cleanup-bak.sh` 做「份数 + 天数」双上限清理，并强制保留最近 1 份，用法见 §8.8。

排障速查：

| 现象 | 先看什么 | 常见原因 |
| --- | --- | --- |
| 「未记录构建机（多为历史版本），请重新构建」 | `release_record.build_server_id` | 该列是后加能力，历史版本为空；只能重新构建 |

| 配置文件没更新 | 「已存在 X，本次不覆盖」 | 刻意设计，配置由运维在目标机维护 |
| 每台目标都重新下载一遍 | 日志中下载行的次数 | 现状如此（§9 第 1 条），不是故障 |
