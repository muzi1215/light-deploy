# 产物分发链路（构建机 → 平台 → 目标机）

> 范围：部署执行阶段「构建机上的产物如何到达目标机并生效」的完整内部逻辑，含回滚时的差异。
> 相关：`docs/发布模块.md` §6.3（三条运行时链路）、AGENTS.md §3.1 / §3.2（JAR / STATIC 形态）、§24.7（版本标识与完整性校验）、§24.10（回滚产物来源）。
> 本文按 2026-09-28 的代码实现撰写，与代码冲突时以代码为准。

---

## 1. 结论先行

- **文件类运行时（JAR / STATIC）走两跳中转**：构建机 → 平台本地临时文件 → 目标机。**不做服务器间直传**。
- **DOCKER 不走这条链路**：目标机自己 `docker pull`，平台只下发命令，全程没有文件传输。
- **两跳的传输方式不对称**：构建机 → 平台一律 SFTP 下载；平台 → 目标机在 JAR 上走 exec 流式管道（`cat > 文件`）并在异常时回落 SFTP，STATIC 仍是 SFTP。
- **每一步落盘都先写临时名再 `mv`，校验一律在「生效」之前**：JAR 在 `systemctl restart` 之前校验，STATIC 在替换目录内容之前校验。失败要么还原现场，要么中止在「还没碰过线上」的位置。

## 2. 全景

```text
             ┌──────────────── 平台（Spring Boot 进程）────────────────┐
             │ DeployTaskHandler：批次编排（策略、批次大小、中止/跳过）  │
             │   └─ deployTarget()：每台目标执行一次                    │
             │        └─ JarDeployService / StaticDeployService /      │
             │           DockerDeployService .deploy(DeployContext)     │
             └──────┬─────────────────────────────────────┬────────────┘
                    │ ① SFTP get                           │ ③ 投放 + 远程命令
                    │   sftpDownload()                     │   uploadLarge() / sftpUpload()
                    ▼                                     ▼
        ┌────────────────────────┐            ┌────────────────────────┐
        │ 构建机                  │            │ 目标机（N 台，串行）     │
        │ {build_artifact_dir}/   │            │ JAR:    {workDir}       │
        │   {项目编码}/{版本}/     │            │ STATIC: {static_root}   │
        │     xxx.jar | dist/     │            │ DOCKER: docker daemon   │
        │     config/  VERSION    │            └────────────────────────┘
        └────────────────────────┘                       ▲
                                                          │ ② 平台本地临时文件
                                                          │   /tmp/ld-deploy-{部署ID}-{文件名}
```

- ①②③ 是文件类运行时的完整路径；DOCKER 三条全不存在，只有一条命令通道。
- **N 台目标 = N 遍 ①②③**：每台的产物下载彼此独立，平台不会为同一次部署复用已下载的临时文件（见 §9）。

## 3. 分发前的三个前提

分发本身不查拓扑、不算版本，它只消费三份已经定稿的数据。

### 3.1 `release_record`：东西在哪

| 字段 | 分发时的作用 |
| --- | --- |
| `artifact_path` | 构建机上产物的绝对路径（JAR / STATIC），分发起点 |
| `build_server_id` | 定位构建机。**为空直接报错**「未记录构建机（多为历史版本），请重新构建」——不在代码里猜机器 |
| `sha256` | 投放完成后回读校验；同时用于「目标机已经是这个包」的跳过判断 |
| `image_tag` | DOCKER 用，`docker pull` 的目标 |

产物路径形如 `{build_artifact_dir}/{项目编码}/{版本}/{文件名}`，两个来源：

- 构建产出：`BuildTaskHandler.buildFileArtifact` 在工作区构建完成后 `cp -r` 转存到持久目录，并写入 `VERSION`（`version/commit/runtime/artifact/built_at`）。**必须先转存**：工作区在任务收尾时被整体删除。
- 手工上传：`ArtifactUploadService` 把运维上传的压缩包直接放到同一约定的持久目录，同样写 `VERSION`、算 SHA256。

### 3.2 `deployment_target`：发到哪、从哪退

目标列表、发布顺序、`old_version` / `new_version` 都在**创建部署时固化成快照**。执行器只读快照，不实时关联 `project_environment_target`（AGENTS §24.9），否则改一次拓扑就会改变历史部署的目标集合。

### 3.3 `DeployContext`：这次到底发哪个版本

发布与回滚共用同一批分发代码，方向由上下文换算：

| 方法 | 发布 | 回滚 | 用途 |
| --- | --- | --- | --- |
| `targetVersion()` | `new_version` | `old_version` | 本次要写到磁盘的版本，`VERSION` 文件与日志都用它 |
| `currentVersion()` | `old_version` | `new_version` | **仅用于备份命名**——标记「被换下去的是哪个版本」 |

构造时做一次对齐校验：若目标快照声明的版本与 `release_record.version` 不一致，直接抛异常，不让磁盘上的 `VERSION` 与平台记录错位（错位要到「回滚时找不到能退的版本」才暴露）。

## 4. 通用中转模型

### 4.1 为什么不让目标机直接去构建机取

- 目标机不需要持有构建机的免密通道；
- **网络与凭据收敛在平台侧**：平台只要能连构建机、能连目标机即可，构建机与目标机之间不需要互通（跨机房、跨 VPC 场景尤其重要）；
- 代价是明确的：多一跳带宽、多一份平台本地磁盘占用（§9）。

### 4.2 平台本地临时文件

`DeploySupport.downloadArtifact` 用 `Files.createTempFile("ld-deploy-" + deploymentId + "-", "-" + fileName)` 落在系统临时目录，返回值交给调用方，**由调用方在 `finally` 里 `deleteQuietly` 清理**。生命周期是「单个目标」而不是「单次部署」。

### 4.3 会话与凭据

每次 `SshSessionFactory.open(server)` 建立一条独立会话（`SshClient` 随会话一起关闭），认证方式按 `server.auth_type` 走密码或私钥，密文在连接前才解密、不缓存、不进日志。

发一台目标的典型会话数：

| 运行时 | 会话 |
| --- | --- |
| JAR | 构建机 1 条（下载 jar；有配置文件时再 1 条）+ 目标机 1 条（投放 + 命令） |
| STATIC | 构建机 1–2 条（必要时打包 + 下载）→ 目标机 1 条 |
| DOCKER | 目标机 1 条 |

## 5. 传输层：两种通道与一次抉择

| 通道 | 实现 | 用在哪 |
| --- | --- | --- |
| SFTP | `SshSession.sftpDownload` / `sftpUpload` | 构建机 → 平台（全部）、平台 → 目标机的 STATIC 包与配置文件 |
| exec 流式管道 | `cat > 远端文件`，本地文件流写进通道 stdin | 平台 → 目标机的大文件（JAR） |

`SshSession.uploadLarge` 的抉择逻辑：**先试流式管道，抛异常则回落 SFTP**，并把最终方式（"流式管道" / "SFTP 回落"）返回给调用方写进任务日志。

为什么大文件不走 SFTP：SFTP 是有窗口与逐包确认的应用层协议，高延迟链路上吞吐被 RTT 压住——实测同一条链路上 74 MB 走 SFTP 要 325 s（约 0.23 MB/s），而裸管道由 TCP 自己做流控，通常能贴近实际带宽。保留回落是因为个别加固机器会禁掉 exec 写 stdin，此时退回 SFTP 至少还能发布成功。

三点通用保障：

- **超时**：普通命令 120 s（`light-deploy.ssh.command-timeout-seconds`），长命令 1800 s（`light-deploy.ssh.long-command-timeout-seconds`）；流式上传按长命令超时。超时抛 `SshCommandTimeoutException` 并带上已收到的输出快照，不停在「一句超时、日志空白」。
- **脱敏**：所有远程输出在 `SshCommandResult` 里统一 `maskSecrets` 后才进任务日志与异常消息。
- **先临时名后 `mv`**：JAR 传成 `{jar名}.uploading` 再 `mv -f`；STATIC 传到 `/tmp/{时间戳}-{包名}` 再解压。中途失败不会在服务目录里留下半截产物。

## 6. 三条链路逐步展开

### 6.1 DOCKER：没有文件传输

```
docker pull {image_tag}      →  docker rm -f {容器名}  →  docker run -d --restart=always  →  docker inspect 确认 Running
```

- 产物在构建阶段已推送到仓库，发布只发三条命令，全部按长命令超时等待。
- `docker rm -f` 不是可选项：容器名是发布幂等的关键，不删会让 `run` 直接失败；`|| true` 兜住首次发布没有旧容器的情况。
- 启动后必须再 `docker inspect -f '{{.State.Running}}'`：一次确认把「启动即退出」从「发布成功」里剔除。
- **不做 `docker login`**：登录只发生在构建机（推送）与连通性测试。目标机的仓库凭据是运维在该机器上预先配置好的，平台不代劳（现状如此，见 §9 边界第 4 条）。

### 6.2 JAR：固定工作目录 + 原地替换

| # | 动作 | 实现要点 |
| --- | --- | --- |
| 1 | 下载 jar 到平台临时文件 | `DeploySupport.downloadArtifact`，SFTP，日志记「已从构建机下载产物 {path}（74.02 MB（77607226 字节））」 |
| 2 | 下载随版本转存的配置文件 | 构建机产物同级的 `config/` 目录，`sftpDownload` 逐个拉回来 |
| 3 | 打开目标机会话 | 一台目标全过程复用这一条 |
| 4 | 投放内置脚本 + 必要时初始化 | `exec/` 下三份脚本**每次发布都重写**（平台资产，版本随平台走）；仅当工作目录里还没有 jar 时才跑 `jar-init.py` 建目录与 systemd 单元 |
| 5 | 投放配置文件到 `{workDir}/config` | **已存在同名文件就跳过，不覆盖**——配置由运维自己维护，平台不该每次发版覆盖现场改动 |
| 6 | 判断目标机是否已是本次要发的包 | `artifactUpToDate`：比对 `release.sha256` 与目标机 `sha256sum`。命中则**跳过备份与上传** |
| 7 | 备份旧 jar | `cp -p` 到 `exec/bak/{jar名}_bak_{时间戳}_{版本号}.jar`，版本段读目标机 `VERSION`（磁盘事实，不取库快照） |
| 8 | 上传新 jar | `uploadLarge` 传到 `{jar名}.uploading` → `mv -f` 覆盖 |
| 9 | **复核 SHA256** | 不一致 → 先 `cp -p` 还原备份再抛异常 |
| 10 | 写 `VERSION` + 刷新 `exec/deploy.conf` 的 `version=` | 两者失败只记日志不影响结论，但必须留痕 |
| 11 | `systemctl restart` + `is-active` 确认 | 重启按长命令超时；`is-active` 非 active 判失败 |
| 12 | 清理平台临时文件 | `finally` 里 `deleteQuietly` |

三个容易忽略的设计点：

- **第 6 步的跳过发生在备份之前**。重复发布同一版本、或发布失败后重试时，目标机上往往已经放着完全相同的包，此时再传一遍大文件纯属浪费（74 MB 在窄带上几分钟，而比对摘要只是一次目标机本地 `sha256sum`）。既然被替换者与替换者是同一个包，备份也没有意义，因此两步一起跳。三种情况一律按「需要上传」处理：版本未登记摘要、目标机上还没有 jar、目标机算不出摘要——保守方向。
- **jar 文件名沿用工作目录里已有的名字**（`resolveJarName`），同一实例只保留一个 jar，产物文件名带版本号时也不会在工作目录里越堆越多。
- **systemd 单元只在首次生成**，之后绝不重写：运维手工调过的 `-Xmx`、`--spring.config.location` 必须被尊重。

时序不可调换，尤其 **校验与写标识必须早于重启**：此刻发现 jar 损坏还能无损还原，一旦重启就变成线上事故；标识若晚于重启，重启失败时会停在「磁盘新版本 + 标识旧版本」的错位状态。

### 6.3 STATIC：只换目录内容，绝不换目录

| # | 动作 | 实现要点 |
| --- | --- | --- |
| 1 | （必要时）构建机上打包 | 产物已是 `.zip` / `.tar.gz` / `.tgz` 时原样传输；目录型产物才 `tar -czf /tmp/ld-static-{部署ID}.tar.gz -C {目录} .` |
| 2 | 下载到平台临时文件 | 同 JAR |
| 3 | 上传到目标机 `/tmp/{时间戳}-{包名}` | **走 `sftpUpload`**（未走流式管道，见 §9 边界第 1 条） |
| 4 | 解压到旁路暂存目录 `static-new-{时间戳}` | zip 先探测 `unzip` 是否存在；解压前 `rm -rf` 清掉上次失败残骸 |
| 5 | 剥壳 / 告警 / 非空校验 | `stripTopLevelDir`（三条判据全中才剥）→ `warnIfNested`（只告警）→ `ensureStagingNotEmpty`（**为空直接中止，站点此时还没被碰过**） |
| 6 | 备份当前内容 | `_ld_move {static_root} {backupDir}/{目录名}_bak_{时间戳}_{版本}` —— **搬的是目录内的条目，目录本身不动** |
| 7 | 新内容就位 | `_ld_move {stagedDir} {static_root}`，失败则立刻把备份搬回 `static_root` |
| 8 | 清理暂存目录 + 记录 inode | 用 `rmdir` 而非 `rm -rf`：有残留就让它留在原地被看见；日志输出 inode 前后值 |
| 9 | 不执行 nginx reload | 平台不改 nginx 配置，reload 失败会把「文件已替换」误判成发布失败 |

为什么要搬内容而不是换目录（2026-09-28 事故定论）：`static_root` 常作为 Docker bind mount 的源，而 bind mount 在容器启动时**按路径解析一次并绑定 inode**。目录被 rename 走之后容器仍握着旧 inode，容器内目录变空，nginx 报 `directory index ... is forbidden`、全站 403，`nginx -s reload` 无效，只能重建容器。因此切换动作由 `MOVE_CONTENTS`（shell 函数 `_ld_move`）完成，两个目录自身的 inode 全程恒定，代价是切换期间存在极短的目录为空窗口——两种失败模式不对等：瞬时 404 会自愈，容器失效挂载必须重建容器。

`_ld_move` 四条 shell 细节都不能改：进子 shell 用相对路径；非隐藏条目用 `set -- *` **整批** `mv`（逐个 mv 等于逐个 fork，上千文件会把窗口拖到分钟级）；`.[!.]* ..?*` 显式覆盖隐藏文件（`*` 不匹配点开头，会漏掉 `.env`、`.well-known`）；`if [ -e "$f" ]` 判存在（glob 无匹配时保留字面量），**不能写成 `[ -e "$f" ] && mv ... || exit 1`**——`&&` 短路会去执行 `|| exit 1`，把「没有隐藏文件」判成失败。

### 6.4 配置文件分发（JAR 专用）

构建阶段按 `build_config_json.config_paths` 把配置转存到产物同级的 `config/` 目录；发布时：

1. `ls -1 {persistDir}/config` 列出文件名（无配置直接返回，不建立构建机会话）；
2. 逐个 `sftpDownload` 到平台临时文件；
3. 逐个 `sftpUpload` 到目标机 `{workDir}/{configDir}`，**已存在则跳过**。

「不覆盖」是刻意设计：jar 与配置分离的意义就在于配置由运维自己维护。缺配置也不阻断发版——是否真的起得来由服务启动与健康检查判定。

## 7. 失败与安全语义

| 环节 | 失败时的处理 | 理由 |
| --- | --- | --- |
| 产物下载（①） | 抛异常，目标判失败 | 磁盘尚未被触碰 |
| 上传中断（③） | 临时名残留，服务目录未变 | 先临时名后 `mv` |
| JAR 摘要不符 | **先 `cp -p` 还原备份再抛异常** | 否则停在「服务跑旧版、磁盘放坏包」，下次重启必然起不来 |
| JAR 还原失败 | 只记 ERROR，仍抛「完整性校验失败」 | 根因是校验失败，不能被还原异常覆盖 |
| STATIC 产物为空 | 中止发布 | 内容替换语义下，空包就位 = 站点被清空却报成功 |
| STATIC 新内容就位失败 | 把备份内容搬回 `static_root`，再抛异常 | 否则站点长时间空着 |
| 写 `VERSION` / 刷 `deploy.conf` 失败 | 只记日志，不影响结论 | 辅助信息，但必须留痕 |
| 平台临时文件清理失败 | 只 WARN | 不能让清理失败覆盖真正的发布结果 |

另外：

- **日志写入失败从不阻断发布**（`appendLog` 内部吞异常只告警）：发布动作可能已经改变了机器状态，一次日志库抖动不应把发布判成失败，否则会出现「记录说失败、磁盘已变更」的错位。
- **目标级失败不向外抛**：收敛成 `deployment_target.status + error_message`，由编排层决定策略（滚动中止剩余、全量跑完）。
- **脱敏在所有远程出口统一做**，异常消息里不含凭据。

## 8. 回滚时的分发差异

| 运行时 | 产物从哪来 | 说明 |
| --- | --- | --- |
| DOCKER | 镜像仓库 | 拉 `old_version` 对应的 `image_tag` 重跑同样流程，目标机不留任何历史副本 |
| JAR | **构建机，100%** | 按 `old_version` 反查 `release_record`，走完全相同的两跳；目标机 `exec/bak` 只供运维手工应急 |
| STATIC | **先查目标机 `static-bak`** | 命中 `{目录名}_bak_*_{版本}` 就 `cp -a` 还原——不下载、不解压、不过构建机，秒级；未命中回落构建机 |

- 回滚与发布共用 `deploy()`，唯一差别是 `ctx.release()` 指向的版本记录不同（编排层 `resolveVersionRelease` 换算）。
- STATIC 快路径只在 `ctx.rollingBack()` 时尝试：常规发布的目标是新版本，本机不可能有它的备份。
- 快路径用 `cp -a` 而不是 `mv`：备份必须保留，否则回滚一次后备份就没了。
- 入口判定先于一切：`DeploymentRollbackService.historyArtifactAvailable` 要求 `build_server_id` 与 `artifact_path` 都在，缺一个就在点按钮之前判「不可回滚」——本机备份根本轮不到。详见 AGENTS §24.10。

## 9. 性能特征与已知边界

1. **每个目标各自下载一次产物**：N 台机器发同一版本，构建机 → 平台这一跳会跑 N 遍，带宽与构建机 SFTP 连接数都按 N 放大。同一版本在平台侧做一次临时文件复用是明确的优化方向（要处理并发与清理时机）。
2. **带宽翻倍**：两跳意味着每字节在平台上过两遍（进一次、出一次）。平台与构建机、目标机同内网时无所谓，跨公网时是真实成本。
3. **平台本地磁盘**：峰值占用 = 单个产物大小 × 并发目标数，落在系统临时目录。大静态包 + 多目标并发时要留意临时目录所在分区。
4. **STATIC 上传未走流式管道**：`StaticDeployService` 用的是 `sftpUpload`，没有享受 JAR 那条快路径。大静态包在窄带上会明显偏慢，是待补的一致化改造点。
5. **目标机 `docker login` 由运维预置**：发布链路不登录仓库，目标机必须已具备拉取权限（或仓库公开）。
6. **解包工具依赖目标机**：zip 需要 `unzip`，JAR 初始化需要 `python3`（且脚本兼容 3.5+），缺了都在对应步骤给出明确提示而不是让输出为空。
7. **备份无回收策略**：JAR 的 `exec/bak` 与 STATIC 的 `static-bak` 都只增不减，长期发布需要外部清理。

排障速查：

| 现象 | 先看什么 | 常见原因 |
| --- | --- | --- |
| 「未记录构建机（多为历史版本），请重新构建」 | `release_record.build_server_id` | 该列是后加能力，历史版本为空；只能重新构建 |

| 静态发布后全站 403 | 日志里 inode 前后值 | 若 inode 变了说明目录被换过（不该发生）；若未变，检查容器 bind mount 与 nginx 配置 |

| 配置文件没更新 | 「已存在 X，本次不覆盖」 | 刻意设计，配置由运维在目标机维护 |
| 每台目标都重新下载一遍 | 日志中下载行的次数 | 现状如此（§9 第 1 条），不是故障 |
