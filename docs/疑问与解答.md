## Q-01 无历史版本也能回滚，且回滚后静默显示成功

**提问**：工作目录的 `exec/bak` 里没有历史版本包，为什么还能操作回滚？点了之后页面显示「已回滚」，机器上却什么都没变。

**结论**：这是两个缺陷叠在一起。

1. **判定缺失**：原实现只要部署状态是「成功」就放行回滚，没有校验目标是否真的可退。`exec/bak` 里有没有备份包**不是**回滚依据——平台回滚走的是「重新发布 `old_version`」，靠的是 `release_record` 与构建机上的产物。
2. **静默成功**：一个目标都回滚不了时，代码直接把部署状态置为「已回滚」并返回成功。

**落点**：抽出唯一判定入口 `DeploymentService.evaluateRollback`，按三种原因优先级拦截（状态非成功 → 变更过的目标全无 `old_version` → 有 `old_version` 但版本记录查不到或缺分发信息）；不可回滚时抛 `DeployException`；判定结论随列表返回（`rollbackable` / `rollbackBlockReason`），前端据此置灰按钮并用 tooltip 说明，**禁止前端自己拿状态码推断**。见 AGENTS §24.5。

**遗留**：无。

## Q-02 回滚日志缺要素，看不出退到了哪个版本

**提问**：可以回滚时，日志要有开始回滚、当前版本、回滚到什么版本、时间、成功失败、是否启动成功。

**结论**：回滚是代价高、不可逆的动作，日志必须能**独立交代这次回滚做了什么**，不能靠目标行零散的 INFO 加执行器结尾那句「任务执行成功」充当结论——那句话不区分发布与回滚。

**落点**：`DeployTaskHandler` 固定输出六个要素——开场（含策略、本次回滚 N/M 个目标）、每目标的「当前版本 X → 回滚到 Y」、目标级起止时间（写进日志正文，格式 `yyyy-MM-dd HH:mm:ss`）、收尾结论、`restartService` 后的「服务启动成功（`systemctl is-active = active`）」、失败时提示人工确认目标机当前版本。见 AGENTS §24.5 的六要素表。

**遗留**：无。

## Q-03 旧记录点「重新构建」发的是哪个包？为何没有「重新发布」？

**提问**：第一次构建成功后，隔天点旧记录的「重新构建」，是重建 9-25 那份产物，还是新建 9-26 的包？另外部署只有回滚、没有「重新发布」，为什么？

**结论**：两者都不是「把上次的动作再跑一遍」，实现上也不是，因此**禁止在 UI 文案、接口注释、文档里把它们描述成重放**。

- **「重新构建」= 新建构建，克隆分支最新 HEAD**。它只把 `projectId` 交给 `BuildService.createAndTrigger`，克隆命令只有 `--branch`、全程没有 `checkout`，所以**永远构建分支最新提交**；旧记录那次构建的产物不会被重建。`build.git_commit` 当前全项目**零读取点**，不能作为「按提交重建」的依据。因此「重新构建」不能承诺产物可复现。
- **部署记录是「一次执行的不可变快照」**，禁止在原记录上重跑：目标集在创建时快照到 `deployment_target`，原地重发会覆盖首次执行的统计与起止时间，更致命的是 `old_version` 与 `new_version` 会变成同一个值，目标行再也说不清「从哪来、到哪去」。回滚能在同一记录上执行，是因为它是**同一批目标的状态切换**，不是第二次独立执行。
- **「重新发布」的正确形态是复制出一条新部署记录**（新 `deployment` + 目标快照 + 新 DEPLOY 任务，旧记录一字不动）。而当前「重发同版本」直接用「新建部署」手选历史版本即可——`ReleaseStatus.DEPRECATED` 全项目零引用，历史版本**永远处于「可发布」**。

**落点**：AGENTS §24.6 全文；`docs/构建模块.md` §6.5；`docs/发布模块.md` §6.8；`docs/前端工程.md`。

**遗留**：「复制成新部署记录」这个形态尚未实现，属后续需求；**未经同步评估该链路，禁止引入版本自动废弃策略**。

## Q-04 后端抛异常与请求信息为何控制台都不打印

**提问**：项目里后端抛异常、接口请求信息，控制台都没有打印。

**结论**：三类日志各自缺失。异常被吃掉、访问不落痕，出问题时无法从服务端日志定位到具体请求。

**落点**：补三处——`GlobalExceptionHandler` 的 `handleBusiness` / `handleValidation` 加 `log.warn`（业务异常与参数校验**不打堆栈**）；`TaskExecutor` 的 `executeTask` 的 catch 分流，业务异常 WARN、未预期异常 ERROR 带堆栈；`RequestTraceFilter` 在 `finally` 输出访问日志（方法 + URI + 耗时 + 状态码 + `requestId`）。见 AGENTS §14.2 / §14.3。

**结论性约定**：**任何被吃掉的异常都必须至少留一条日志**；业务异常/参数校验 → WARN 不打堆栈，未预期异常 → ERROR 带堆栈。

## Q-05 版本号要不要加 `v` 序号？自动还是人工指定？轮询接口能否不打印日志

**提问**：构建产物提供给发布的版本号 `auth-7888-887b603c` 要加一个 `v` 版本号；这个是自动生成还是手动指定？另外 `GET /taskLog/pull` 这种轮询请求能不能不打印。

**结论**：三个问题三个答案。

1. **必须有序号**：改造前版本号只有「项目编码 + 提交短码」，同一 commit 重复构建会让镜像 tag、产物持久目录两处同名被覆盖，并在 `release_record` 上撞唯一键，而 `completeSuccess` 没有事务——结果是**构建记录显示成功、任务显示失败、版本列表里没有它**，该产物永远发不出去。
2. **默认自动取号，允许人工指定**：`MAX(version_seq) + 1`，取号时刻意**不过滤软删除**（防序号重用）；人工指定的序号**必须在创建构建时**就校验项目内未被占用，不许拖到构建跑完才在版本落库阶段失败。列与升级脚本见 `db/upgrade-release-version-seq.sql`。
3. **轮询日志降噪，但不能全静默**：`light-deploy.access-log.silent-paths`（默认 `/taskLog/pull`）命中的路径 `<400` 降 DEBUG、`>=400` 仍按 WARN 输出。**禁止把某路径配成完全静默**——那会让该接口的 4xx/5xx 一起消失。匹配前要剥掉 context-path `/deploy`。

**落点**：AGENTS §23.5（版本号）、§14.2（访问日志降噪）。

**遗留**：用户需手工执行 `upgrade-release-version-seq.sql` 回填老版本序号。

## Q-06 版本号里序号段的位置

**提问**：版本号还是在项目编码后面吧，`auth-7888-v3-887b603c`。

**结论**：采纳。格式定稿为 `{项目编码}-v{版本序号}-{提交短码}`。

**落点**：`BuildService.resolveReleaseVersion` 是**唯一生成点，一处改三处共用**（Docker 镜像 tag、构建机产物持久目录、`release_record.version`），禁止中途重算；历史版本号**不改写**，升级前后新旧格式并存属预期。因顺序变更，同步修正了 AGENTS §23.5、发布模块 §6.1、构建模块（§2.1/§2.3/§6.6）、前端工程、`schema.sql` 注释、两个 SQL 注释与前端提示文案。

**顺带修掉的缺陷**：`docs/构建模块.md` 的 §6.6 被两处引用（§6.3 / §6.5）但**章节实际不存在**，且 §2.3 的 `version` 列还是旧格式描述、两张表都缺 `version_seq` 字段行，本轮一并补齐。

**遗留**：无。

## Q-07 回滚逻辑怎么做的？能否把可回滚的版本查询展示出来

**提问**：回滚逻辑是怎么做的，仔细展示说说；能不能把可回滚的版本的查询展示出来？

**结论**：「可回滚 / 不可回滚」只是一句话，回答不了「点下去到底会动哪几台、各自退到哪个版本」。因此补一个只读预览接口，并顺手把三份重复判定收拢成一份。

**落点**：

- 新增 `GET /deployment/rollback-preview/{id}`（`DeploymentService.rollbackPreview`），返回总结论 + 逐目标明细（服务器名/地址、`当前版本 → 将回滚到的版本`、是否可回滚、跳过原因）；只读，不改状态、不建任务；不可回滚时返回结论而非抛异常，前端把 `blockReason` 展示在弹窗里。
- **判定收拢为一份**：抽出 `inspectTargets(projectId, targets) → List<RollbackDecision>`（record：target / rollbackable / skipReason / missingVersion），`RollbackEvaluation` 增加 `decisions` 字段。`evaluateRollback` 聚合、`rollback()` 决定重置或跳过、`rollbackPreview()` 渲染清单三处**消费同一份**。**禁止再各写一套判定条件**，否则会出现「预览说能退、提交说退不了」。
- 列表侧返回 `rollbackTargetCount` / `rollbackSkippedCount`（判定时已算出，**零额外查询**），tooltip 直接给台数，不必为每行调预览接口。
- `rollback()` 里 `rollbackCount == 0` 的兜底分支已删——判定为可回滚后该分支不可达。

**遗留**：网关若对 `/deployment/**` 有白名单，需放行 `/deployment/rollback-preview/{id}`。

## Q-08 首次发布不可回滚，那再发新版不又是首次发布吗？历史版本去哪里找

**提问**：v4 版本为首次发布，回滚提示「本次发布为首次发布，目标机上没有平台纳管的历史版本，无法回滚」。那么我再发新版提交到 git 仓库，项目拉取构建，那不是构建了新的 v5 产物？然后发布不是又是 v5 首次发布，压根没回滚版本可选？

**结论**：**不会。「首次发布」判定的是机器，不是版本号。** 它的条件是「该项目 + 该环境下，这台机器的历史部署里找不到任何一次真正成功过的部署」，而非「版本号是新的」。所以首次只会发生一次：

| 动作 | 机器上原有版本 | 这次部署的 `old_version` | 发布成功后 |
| --- | --- | --- | --- |
| 构建 + 发布 v4 | 无 | 空 → 首次发布 | 回滚按钮置灰 |
| 构建 + 发布 v5 | v4 | **v4** | 可回滚到 v4 |
| 构建 + 发布 v6 | v5 | **v5** | 可回滚到 v5 |

**回滚的参照物是部署记录自己的 `old_version` 快照，不是回滚时挑选**，因此可回滚的版本只有一个、也只有一层深度。`old_version` 在**创建部署那一刻**由 `resolveCurrentVersions` 推断并写进 `deployment_target`。

**会「又变回首次发布」的四种情况**（排查线索）：

1. 上一条部署记录被**删除**了——`Deployment` 继承 `BaseEntity`（`@TableLogic`），软删除后回溯链就断了；
2. 上一条部署**失败**了——状态不是 `SUCCESS`，不参与回溯；
3. 上一条该**目标被跳过**——目标状态不是 `SUCCESS`，同样不算；
4. **换了环境**——回溯按 `environmentId` 隔离，每个环境各自算第一次。

**另外两个容易误会的地方**：

- **回滚执行时产物不读目标机**：判定走 `historyArtifactAvailable` 反查 `release_record`（DOCKER 看 `image_tag`；JAR/STATIC 看 `build_server_id` + `artifact_path`），**明确不读目标机 `exec/bak`**。
- **回滚 ≠ 回到任意历史版本**：`canRollback` 只放行 `SUCCESS`，回滚后记录变 `ROLLED_BACK`，所以**同一条记录只能回滚一次**；要再退一层需找更早那条仍是「成功」的部署记录。想回到任意历史点则走**新建部署、手选旧版本重发**（历史版本永不置「已废弃」）。

**落点**：`DeploymentService.createAndTrigger` / `resolveCurrentVersions` / `inspectTargets` / `historyArtifactAvailable` / `evaluateRollback`；`DeploymentStatus.canRollback`；AGENTS §24.5。

**遗留**：无。

## Q-09 `exec/bak` 只有时间戳，平台宕机后手工回退怎么对上平台版本？平台自身怎么部署更新

### 第一问：手工回退如何准确识别版本

**提问**：如果平台宕机了，需要上服务器手工更新部署，失败了就按时间戳回退吗？`bak` 里怎么找到平台发布的准确的上个版本？

**结论**：先纠正一个前提——**`bak` 里的包不是「这次发的包」，而是「被换下去的那个包」**。`backupCurrentJar` 在 `mv` 覆盖**之前**先 `cp -p` 现有 jar 到 `exec/bak`，所以文件名里的时间戳是**执行替换的那一刻**，包的内容是**上个版本**。也就是说：**时间戳指向「替换它的那次发布」，不指向包里的版本。**

识别方式按可靠性排序：

1. **SHA256 比对（精确）**：`sha256sum {workdir}/{jar名} exec/bak/*.jar`，与平台 `release_record.sha256` 逐条对照。备份是 `cp -p` 的字节级复制，摘要必然一致；
2. **时间戳反查（便利）**：备份名时间戳 → 平台该时刻附近的部署记录 → 该记录的 `old_version`；
3. **`fallback.py --steps N`（应急）**：按 `mtime` 倒序退 N 步。因 `cp -p` 保留上传时的 mtime，mtime 序与发布序一致，`--steps 1` 恰好是上一个版本；但它**不知道版本号**，只能保证「退了一步」；
4. **DOCKER 最简单**：镜像 tag 就是版本号，本机残留旧镜像可直接 `docker run`，完全不依赖 `bak`。

**发现的三个缺口**（已在 Q-10 处理）：

- jar **未注入任何版本信息**，唯一带版本号的落点是构建机产物目录 `{artifact_base}/{项目编码}/{版本号}/`；
- `deploy.conf` 只记 `service_name` / `jar_name` / `work_dir`，**不记版本**；
- `ReleaseRecord.sha256` 的注释写了「部署前校验文件一致性」，但 `deployJar` **实际没有做校验**。

**另一个操作后果**：手工换包后**平台状态会与机器实际脱节**——`resolveCurrentVersions` 读的是数据库快照，下次发布算出的 `old_version` 会错。手工回退后应在平台**补一次「新建部署、重发对应版本」**对齐状态。

### 第二问：平台自身如何部署更新

**提问**：部署发布平台自身要怎么部署更新？用我之前的那个原始部署脚本服务器手动更新吗？

**结论**：**是的，目前平台自身没有任何自动化部署手段，只能服务器手工更新。** 仓库里**没有 Dockerfile、没有 docker-compose、没有任何 `.sh` 部署脚本**；`docs/轻量化部署发布平台设计方案.md` 里「平台自身可以使用 Docker Compose 部署，前端使用 Nginx 托管」**只是一句设计愿景，没有落地物**。

且 `src/main/resources/static/` 为空，**前端没有打进 jar**，所以平台是**两个交付物**：

| 组件 | 形态 | 运行时依赖 |
| --- | --- | --- |
| 后端 | Spring Boot jar，systemd 拉起，端口 `2027`，context-path `/deploy` | MySQL `deploy` 库（3306）、Redis（6379 库 0） |
| 前端 | `lighit-deploy-ui` 构建出 `dist`，Nginx 托管并把 `/deploy` 反代到 2027 | — |

三条可选路线：

- **A（推荐）复用平台内置的三件套**：`jar-init.py` / `jar-update.py` / `jar-fallback.py` 本来就是为应急手工发版设计的，直接拿它们管平台自己——先用 `jar-init.py` 把平台注册成 systemd 服务，之后更新用 `jar-update.py`、回退用 `jar-fallback.py`。**零新代码**，与平台内所有 JAR 项目统一运维口径。前端 `dist` 是纯静态，`rsync` 覆盖即可；要支持回退可用 `current` 软链接指向 `releases/{时间戳}/`。
- **B 补 Dockerfile + compose**：把设计愿景落地，环境一致性好，但要新增一套需要维护的工程物，建议作为后续升级；
- **C 自举（平台管自己）——不推荐**：平台重启自己会打断正在执行的任务；更根本的是**平台挂了的时候恰恰最需要它**，属循环依赖。

**铁律**：无论走哪条路线，**MySQL 结构升级必须手工执行**（如 `upgrade-release-version-seq.sql`）——平台的 JAR 部署链路只换包重启，没有执行 DDL 的能力。平台迭代的真实动作永远是「**手工执行升级 SQL → 更新后端 jar → 更新前端 dist**」。

**遗留**：路线 A/B 均未实施，属后续需求。

## Q-10 产物无版本标识、摘要算了不校验、`deploy.conf` 不记版本

**提问**：处理这三处缺口，然后把疑问与解释写进可追溯的文档。

**结论**：三处全部落地，且**版本标识一律用外部文件，不重写 jar 内部的 `MANIFEST.MF`**。

**为什么不注入 `MANIFEST`**：Spring Boot fat jar 的嵌套 jar 依赖 ZIP 的 STORED 布局，用 `jar --update` 重打包一旦改变压缩方式，会**静默产出「启动即失败」的产物**；而且重打包会改变 SHA256，与登记的产物摘要语义冲突。外部标识文件不改产物一个字节，且同时适用于 JAR 与 STATIC。

### 一、版本标识（`VERSION` + 备份名版本段）

同一份 `key=value` 文本落在**两处**，`version=` 行一律写**平台原始版本号**，与 `release_record.version` 同源；另有一个只有版本号、不带其它字段的落点——**备份文件名**：

| 位置 | 写入方 | 含义 |
| --- | --- | --- |
| `{build_artifact_dir}/{项目编码}/{版本号}/VERSION` | `BuildTaskHandler.writeArtifactVersionMarker` | 这份产物是哪个版本 |
| `{workdir}/VERSION` | `DeployTaskHandler.writeVersionMarker` | 这台机器上盘的 jar 是哪个版本 |
| `exec/bak/{jar名}_bak_{时间戳}_{版本号}.jar` | `DeployTaskHandler.backupCurrentJar` | 这个备份包里装的是哪个版本 |

> 第三处原先是 `exec/bak/{备份名}.version` 伴随文件，**Q-12 已改为把版本号内嵌进文件名**，伴随文件不再产生。

时序固定为「**jar 上盘 → 写标识 → 重启服务**」：标识必须与磁盘一致，写在重启之后会在重启失败时停在旧版本、与磁盘错位。写标识失败**只记 INFO 日志，不影响发布结论**。

### 二、产物完整性校验

`DeployTaskHandler.verifyJarDigest` 在**替换 jar 之后、重启服务之前**在目标机复核 `sha256sum`：

- 不一致时**先还原发布前的备份再抛异常**，不允许把损坏的包留在工作目录。只抛异常会让机器停在「服务跑着旧版本、磁盘放着坏包」的错位状态——下次重启必然起不来，而失败原因只写着校验失败，很难联想到磁盘；
- 还原动作本身失败**只记 ERROR 日志、不覆盖校验失败这个根因**；
- 摘要为空（历史版本）或目标机缺 `sha256sum` 时**跳过并写明原因**，不阻断发布；
- 校验**通过也写 INFO 日志**并带摘要值，让「检查确实执行过」可被追溯。

### 三、`deploy.conf` 记版本

`exec/deploy.conf` 增加 `version=` 行，表示**本机当前运行的版本**：首次初始化写空（此刻确实没有发布过任何版本），之后由**平台发布流程、`jar-update.py`、`jar-fallback.py` 三方刷新**，语义必须一致。`jar-init.py` 重复执行时**保留已登记的 version**，不重置。

脚本侧同步改造：`jar-update.py` 支持 `--version`、备份时把版本段写进备份名、更新后刷新 VERSION 与 conf；`jar-fallback.py` 从备份名读出版本打印版本对照。实测输出（命名格式见 Q-12 的后续调整）：

```text
将执行回滚: auth-7888-v5-1a2b3c4d -> auth-7888-v3-887b603c
已恢复: /lx/jarapps/auth-tool/exec/bak/auth-tool_bak_20260925211203v1.jar -> .../auth-tool.jar
服务已重启: auth-tool-7888
回滚完成: auth-tool.jar（版本 auth-7888-v3-887b603c）
```

**脚本禁止猜版本号**：来源固定为「`--version` 参数 > `exec/VERSION` > 空」，取不到就写空并提示——**记错版本比不记版本更危险**，而回退前的版本始终能从**备份文件名的版本段**找回（Q-12 起改为内嵌文件名，原先是从 `{备份名}.version` 伴随文件找回）。

**落点**：`BuildTaskHandler.writeArtifactVersionMarker`；`DeployTaskHandler.writeVersionMarker` / `verifyJarDigest` / `restorePreviousJar` / `refreshDeployConfVersion` / `backupCurrentJar`；三份脚本；AGENTS §23.5 / §24.5 / **§24.7** / §25。

### 适用范围与遗留

- 三项能力目前**只覆盖 JAR 运行时**。DOCKER 的版本就是镜像 tag，无需额外标识；**STATIC 直接覆盖 `static_root`，既无本地备份也无版本标识**，其回退完全依赖平台重发旧版本。若要支持静态站点的手工回退，需引入「按版本建目录 + `current` 软链接」方案，**属独立改造，本轮未做**；
- 早于本次改造产生的备份**名字里没有版本段**（改造过程中还短暂出现过 `{备份名}.version` 伴随文件这一中间态，见 Q-12），只能走 SHA256 比对或时间戳反查；
- 老旧目标机上已有的工作目录，`deploy.conf` 会在**下次发布时**由平台补上 `version=` 行；在此之前脚本读不到版本会显示「未登记」。

## Q-11 重新发布后 `exec/bak` 里仍无版本号、`ls` 时间还是旧的，为何仍需 SHA256

**提问**：重新发布后 `exec/bak` 里最新备份是 `auth-tool_bak_20260925213929v1.jar`，但 `ls -l` 显示的时间是 19:47 —— 不是说会加版本号吗？为什么这里还是需要 `sha256sum`？`sha256sum *.jar` 的用法文档里写了没有？

**结论**：这是**三条相互独立的原因**叠在一起，逐条对上。

### 一、平台后端没有重启，改动还没生效（本次现象的直接原因）

写 `{备份名}.version` 是**平台侧代码**（`DeployTaskHandler.backupCurrentJar`）的行为。改动只编译进了本地 `target/`，**运行中的平台仍是旧 jar**：它备份时只 `cp -p` jar，不写伴随文件，也不刷新 `deploy.conf` 的 `version=`。所以这几次发布产出的备份都不可能有 `.version`。**重启后端是这三项能力生效的前提**，重启前观察不到任何变化属预期。

### 二、已存在的历史备份永远不会补上版本信息

当时的方案是「备份时把 `{workdir}/VERSION` 复制成 `{备份名}.version` 伴随文件」，而伴随文件是**备份那一刻**从 `{workdir}/VERSION` 复制出来的，平台**不会事后回填**历史备份。所以已有的两个备份属于「改造前产生的备份」，识别它们**只能靠 SHA256 或时间戳反查**——这正是 SHA256 那条路径存在的意义。

> **后续变更（见 Q-12）**：伴随文件方案已被推翻，改为**把版本号内嵌进备份文件名**。本节第三节描述的现象在改名之后**依然成立**，只是表现形式从「少一个 `.version` 文件」变成「名字里少一段版本号」。

### 三、即使重启，下一次发布的备份仍不会有版本段（一次发布的预热期）

版本段取自「**被换下去那个包**」的标识，也就是 `{workdir}/VERSION`。而这台机器上 `{workdir}/VERSION` **此刻并不存在**（旧代码从未写过），因此重启后的**第一次**发布仍然取不到版本；这次发布结束时会写入 `VERSION`，**再下一次**发布的备份名字里才会带版本段。属预期行为，不是缺陷。

### 四、`ls -l` 看到的 19:47 不是备份时刻，是包当初被发布的时刻

`cp -p` 是**字节级复制且保留元数据**，备份文件的 `mtime` 沿用源 jar 的 `mtime`（源 jar 的 `mtime` 是上次发布上传时写的）。同一个备份里有两个时间，含义完全不同：

| 位置 | 含义 |
| --- | --- |
| 文件名里的 `20260925213929` | **备份时刻** = 替换动作发生的时刻 |
| `ls -l` 的 `Sep 25 19:47` | **包内版本的发布时刻** = 源 jar 被上传到工作目录的时刻 |

`auth-tool_bak_20260925213929v1.jar` 应读作「**21:39:29 做备份时，被换下去的那个包，是 19:47 那次发布投上去的**」。`ls -lt` 按 `mtime` 排序，得到的顺序与**版本序**一致（所以 `fallback.py --steps N` 是对的），但它**显示出来的日期不是备份时刻**；判断「哪个是最新备份」要看**文件名时间戳**。

### 五、为什么有了版本标识还要 SHA256

版本标识（当时是伴随文件，现在是备份名的版本段）是**辅助信息，载体是可写文件或文件名**——手工换包、改名、误删、脚本记错版本，都会让它与文件内容不符。脚本侧「禁止猜版本号」（AGENTS §25）说的就是这件事：**记错版本比不记版本更危险**。而 `sha256` 由构建机算出、登记在 `release_record.sha256`，是**唯一能证明「这段字节就是这个版本」的证据**。

因此口径固定：**日常识别看备份名版本段 / 时间戳；严肃确认（回退前、追责时）一律以 SHA256 为准。**

### 手工识别备份版本的完整操作

**方式零：直接看备份文件名（改造后最快，无需任何命令）**

```bash
ls -1 exec/bak
# auth-tool_bak_20260925222851_auth-7888-v6-c9bb25d3.jar
# auth-tool_bak_20260925213929v1.jar          ← 改造前的旧格式，名字里没有版本
```

**方式一：构建机产物目录（最直观，不用查库）**

```bash
# 在构建机上执行；目录名本身就是平台版本号
ls -1 {build_artifact_dir}/auth-tool-7888/

# 对每个版本的产物算摘要，与目标机的备份逐一配对
sha256sum {build_artifact_dir}/auth-tool-7888/*/auth-tool.jar
```

`{build_artifact_dir}` 是构建机档案里的「构建产物持久目录」（`build_server.build_artifact_dir`，`BuildTaskHandler` 启动前校验非空），产物落在 `{该目录}/{项目编码}/{版本号}/`，与 `release_record.artifact_path` 同源。

**方式二：查平台库，拿到「版本 ↔ 摘要」对照表**

```sql
SELECT version, version_seq, sha256, artifact_path, build_server_id, create_time
FROM release_record
WHERE project_id = '<项目ID>' AND runtime_type = 'JAR' AND is_deleted = 0
ORDER BY version_seq DESC
LIMIT 20;
```

**方式三：在目标机上直接比对**

```bash
cd /lx/jarapps/auth-tool-7888
ls -1 exec/bak                             # 改造后的备份名自带版本号
sha256sum auth-tool.jar exec/bak/*.jar     # 旧格式备份、或需要严肃确认时再算摘要
```

改造后的备份看名字即可；只有**旧格式备份**（名字里没有版本段）才必须拿摘要与方式一/方式二的结果对照。定位「上一个版本」：`ls -1 exec/bak | tail -1` 不成立——要按**文件名时间戳**取最大的那个，等价于 `fallback.py --steps 1` 挑中的那个（脚本已按文件名时间戳排序，不再依赖 `mtime`）。

**落点**：`DeployTaskHandler.backupCurrentJar`（把版本段写进备份名）；`AGENTS.md` §24.7（识别口径 + 时间戳语义 + 预热期）；`docs/发布模块.md` §6.3。

**遗留**：改造前的历史备份名里没有版本段；重启后第一次发布的名字里仍无版本段（预热期）。若要彻底消除预热期，可选做法是在备份前用本次部署的 `old_version` 快照「补种」`{workdir}/VERSION`——但这会让标识变成**平台推断值**而非**磁盘实测值**，与 §24.7「标识必须与磁盘一致」的口径冲突，**未做**，需另行评审。本条命名方案本身随后被 **Q-12** 推翻（伴随文件改为文件名版本段）。

## Q-12 备份名为什么不带版本号？为什么把 `.version` 挂在 `.jar` 后面

**提问**：不是就加个 `.version` 吗？**版本号呢？** 而且怎么可以在 `jar` 后面加东西——要隔开也应该是在时间戳后面加 `_版本号v` 这样的吧？`auth-7888-v7-1521739f → auth-7888-v6-c9bb25d3`，落到文件名上就是 `auth-tool_bak_2026092522285v6.jar` 这样，很难吗？

**结论**：诉求成立，改。**版本号内嵌进备份文件名，`{备份名}.version` 伴随文件删除。**

### 一、先纠正一个误读：`v1` 不是版本号

实测目录里三个备份都叫 `auth-tool_bak_...v1.jar`，很容易把结尾的 `v1` 读成「版本 1」。它其实是**防撞名序号**：备份命令先取 `date +%Y%m%d%H%M%S` 作时间戳，再用 `while [ -f ... ]` 探测同秒重名，从 1 开始往后加。三个文件全是 `v1`，恰恰说明**从没撞过名**。

这个命名是早期沿用 `jar_linux.py` 留下的，问题在于**同一个 `v` 前缀被用在两个完全不同的语义上**（版本号 / 防撞名序号），必然被误读。新命名把 `v` 的含义收敛到只剩平台版本号里的 `v{序号}`，防撞名序号改为纯数字后缀，且**只在真的撞名时才出现**。

### 二、新命名

| 形态 | 例子 | 何时出现 |
| --- | --- | --- |
| 标准 | `auth-tool_bak_20260925222851_auth-7888-v6-c9bb25d3.jar` | 正常发布 |
| 无版本段 | `auth-tool_bak_20260925222851.jar` | 工作目录还没有 `VERSION`（改造后首次发布，或手工投放未给版本） |
| 撞名后缀 | `..._auth-7888-v6-c9bb25d3_2.jar` | 同一秒内同版本重复备份，仅并发场景 |
| 旧格式 | `auth-tool_bak_20260925194718v1.jar` | 改造前产生，永久保留、脚本仍可识别 |

三条设计约束：**时间戳紧跟 `_bak_`**（字典序即时间序，`ls` 默认按名字排就是按时间排）；**版本段在时间戳之后**（先定位「什么时候备的」，再看「备的是哪个版本」）；**保留 `.jar` 结尾**（`*.jar` 通配与 `restore_name` 的还原规则都靠它）。

版本段取自目标机 `VERSION`（**磁盘事实**），不取平台库快照——库快照在手工换包后会失真。取不到就省略该段而不是猜：**记错版本比不记版本更危险**。写入文件名前清洗为 `[A-Za-z0-9._-]`，防止被改脏的 `VERSION` 带出 `/` 把备份写到别的目录。

### 三、为什么删掉 `{备份名}.version`

`auth-tool_bak_...v1.jar.version` 这种名字有三个毛病：**`ls` 看不见版本**（要 `cat` 才知道）；**要多养一个文件**（备份数翻倍，删除与同步都得成对处理）；**`.version` 挂在 `.jar` 后面看起来像包的后缀**。内嵌进文件名一次解决三条，且不损失信息——伴随文件里除 `version` 外的 `commit` / `runtime` / `deployed_at` 对 bak 目录没有判定价值（`deployed_at` 就是文件名时间戳，`runtime` 恒为 JAR）。

配套一并处理：`jar-update.py` 的手工投放旁车文件从 `exec/{jar名}.version` 改为 **`exec/VERSION`**——与构建机产物目录里的文件**同名同格式**，运维把产物连它的 `VERSION` 一起拷进 `exec/` 即可，**不用改名**；用完与 jar 一起删除，避免下次误用旧值。

### 四、脚本侧的兼容与行为变化

- `restore_name` 从 `_bak_\d{14}` 处截断到结尾 `.jar`，**新旧形态一并覆盖**，改造前产生的备份仍可被 `--steps` 退到；
- 新增 `version_from_name`：只认「`_bak_` + 14 位时间戳 + `_`」之后、末尾 `.jar` 之前那段，并剥掉撞名后缀——旧格式结尾的 `v1` 因此不会被误读成版本；
- `--steps` 排序改为按**文件名时间戳**（原先按 `mtime`）。`cp -p` 会把源 jar 的 `mtime` 带过来，`mtime` 的语义是「包当初被发布的时刻」而不是备份时刻；按文件名排序与「第几个备份」的语义严格一致；
- 回退到**没有版本段的旧格式备份**时，`VERSION` 与 `deploy.conf` 一并写空并提示用 `sha256sum` 比对——磁盘上确实是「未登记版本」，留着旧值反而与磁盘错位。

### 五、实测（`mvn compile` EXIT=0，脚本 `py_compile` 通过，端到端跑通）

```text
A1 有 VERSION        -> auth-tool_bak_20260925224110_auth-7888-v7-1521739f.jar
A2 无 VERSION        -> auth-tool_bak_20260925224111.jar
A3 VERSION 被改脏    -> auth-tool_bak_20260925224111_auth-7888-v9-....etcpasswdevil.jar（/ 被清洗，未逃出 bak）
A4 同秒同版本撞名    -> auth-tool_bak_20260925224111_auth-7888-v7-1521739f_2.jar
A5 首次投放（无 jar）-> none
B  jar-update.py     -> 备份 auth-tool_bak_..._auth-7888-v6-c9bb25d3.jar（旧版本），不再产生 .version；
                        VERSION 与 deploy.conf 更新为 v7，exec/ 下的 jar 与 VERSION 均被消费
C  --steps 1         -> 将执行回滚: auth-7888-v7-1521739f -> auth-7888-v5-abc12345
                        （事先把三份备份的 mtime 与文件名时间戳故意倒置，仍挑中最新那份，证明排序已切换）
   --steps 2         -> 将执行回滚: auth-7888-v5-abc12345 -> 未登记（旧格式，附 sha256sum 提示）
D  restore_name      -> 旧格式 `..._bak_20260925194718v1.jar` 与 `..._bak_20260104120000v1.jar` 均还原为 auth-tool.jar
```

**落点**：`DeployTaskHandler.backupCurrentJar`；`jar-update.py` 的 `safe_version` / `backup` / `main`；`jar-fallback.py` 的 `version_from_name` / `backup_order` / `restore_name`；AGENTS §3 / §24.7 / §25；`docs/发布模块.md` §6.3；`docs/项目模块.md`。

**遗留**：改造前的旧格式备份名里没有版本段，且**不改写历史文件名**，永久如此；版本段有一次发布的预热期（同 Q-11）。若要消除预热期，见 Q-11 遗留项——会让标识变成平台推断值，需另行评审。

## Q-13 备份名要不要统一下划线？日志弹窗为何锁关闭？回滚后列表版本为何还是新版本

**提问**：三个问题——① `auth-tool_bak_20260925235800_auth-7888-v7-1521739f.jar` 应该规范化、统一下划线；② 日志弹窗即使关掉，任务也一直在跑、日志也一直在加载，那就不要把运行中的弹窗锁住；③ 目标明细里的 `auth-7888-v7-1521739f → auth-7888-v8-13e04447` 看不出是什么意思，是当前版本还是下一个要更新到的版本？希望加悬浮说明；而且这条部署已经回滚了，列表里的版本却还是 `auth-7888-v8-13e04447`，是不是应该更新为当前版本？

**结论**：① 保持现状，**不转下划线**（版本段逐字保留平台版本号）；② 去掉运行中禁止关闭的限制，**任何时候都能关**；③ 目标明细统一改写成「当前 → 目标」并加 tooltip；列表的 `version` 是快照**不改写**，另加 `currentVersion` 让页面补一行「当前 xxx」。

### 一、备份名不转下划线

诉求是把文件名里混用的 `-` 与 `_` 统一成 `_`，即 `auth-tool_bak_20260925235800_auth_7888_v7_1521739f.jar`。**不做**，三条理由：

1. **版本段要能直接复制去查库**。`release_record.version`、Docker 镜像 tag、`VERSION` 文件里写的都是 `auth-7888-v7-1521739f`。文件名与它们字面一致时，运维的常规动作是 `SELECT ... WHERE version = '<粘贴>'` 或 `grep '<粘贴>' logs/info.log`，不用做任何字符转换；
2. **回译不是双射**。带 `-` 的版本号转成 `_` 之后，读回时只能按段把 `_` 换回 `-`。而**项目编码本身允许含 `_`**（`project.code` 是人工填写的字段），一旦编码里出现 `_`，`auth_my_db_1234_v7_abc12345` 就无法唯一还原。用一个隐式约定换一点视觉整齐，不划算；
3. **混用是有意为之，不是疏漏**。`_` 分隔备份名的**结构段**（`{jar名}_bak_{时间戳}_{版本号}.jar`），`-` 属于**版本号这个值本身**。把值里的字符也当分隔符处理，本质是让结构去改写数据。`auth-tool` 里的 `-` 更是 jar 自身文件名，`restore_name` 要靠它还原成 `auth-tool.jar`，更不能动。

已在 AGENTS §3 与 §24.7 各补一条：**版本段逐字保留平台版本号，不把其中的连字符换成下划线**。

### 二、日志弹窗不再锁关闭

原设计是「运行中锁死所有关闭入口」，四道一起做（`before-close` 兜底 + 隐藏 ✕ + 禁用 ESC + 页脚按钮同路）。实测确认这个前提**不成立**：

**日志轮询跑在浏览器里，任务跑在服务端执行器里**，两者互不依赖。关掉容器只停掉前端这段轮询，任务该跑多久还是跑多久、日志一条不少，重新打开会从服务端重新拉全量。锁住关闭换不来任何安全性，只会把用户困在弹窗里干等任务结束。

改动：

- `useTaskLogViewer` **删除 `beforeClose`** 并不再返回它；`running` 保留但**只用于页脚文案**，不再参与可关闭性判定；
- 5 处视图（任务列表 / 构建列表 / 发布列表 / 连通性测试 / 触发构建）删除 `:before-close`、`:show-close="!running"`、`:close-on-press-escape="!running"`，`closeLog()` 简化为直接置 `false`；
- 页脚文案由「任务执行中，完成后可关闭」改为「**任务执行中，关闭窗口不影响执行**」——把「能关且不影响」讲明白，而不是让人猜会不会打断发布；
- **`@closed`（drawer）/ `@close`（dialog）绑 `stop` 必须保留**：不拦关闭之后这条更容易被忽略，而漏掉它就是「窗口关了接口还在打」。

顺带清理了一处随之失效的逻辑：`pullLogs` 捕获异常时原本要「把状态退回未知并顺势解除关闭锁定」，现在只剩前半句——状态不可信时如实显示「未知」，已不存在需要解除的锁定。

### 三、目标明细的箭头方向 —— 根因是字段语义被复用

`deployment_target.old_version / new_version` 是**创建部署那一刻的快照**。回滚只在原记录上改状态（`rollback()` 里 `deployment.setStatus(ROLLING_BACK)`，`DeploymentService.java:429-432`），**两个版本字段原样不动**。于是同一个箭头在两处含义相反：

| 场景 | 字段实际内容 | 改动前显示 | 事实 |
| --- | --- | --- | --- |
| 发布 | old = v7（发布前），new = v8（发布后） | `v7 → v8` | v7 变成 v8 ✅ |
| 回滚 | old = v7（**回滚目标**），new = v8（**回滚前**） | `v7 → v8` | v8 退到 v7 ❌ **方向反了** |

日志里写的是「当前版本 v8 → 回滚到 v7」（执行器按场景正确输出），抽屉是拿两个字段按固定顺序拼的，于是两边对不上；而字段名 `oldVersion` / `newVersion` 不含角色信息，看的人只能猜「哪个是现在的」。

改法：**统一按「当前 → 目标」表述**——发布 = `old_version → new_version`，回滚 = `new_version → old_version`。这两种写法在任何场景下都自解释、方向永远与事实一致，比只加一句 tooltip 更彻底。悬浮说明再补两句：「当前＝发布前/回滚前机器上跑的版本，目标＝本次要发布的版本/要退回的历史版本」。回滚场景的判定只看主任务状态（5 回滚中 / 6 已回滚），与回滚预览接口里 `currentVersion` / `targetVersion` 的取法同源。

### 四、回滚后列表的版本列

诉求成立，但**不能改写 `version` 字段**。它来自 `release_id`，回答的是「这次动作针对哪个发布版本」；回滚动作本身不产生新的 `release_record`，所以这条记录的 `version` 只能是 v8。直接改成 v7 会与发布日志、产物路径、`release_record` 全部对不上，也让「版本」这一列在不同行之间语义不一致。

正确做法是**补充**而不是覆盖：

- `DeploymentVo` 新增 `currentVersion`，由 `DeploymentService.resolveCurrentVersion` 在 `toVo` 里用**已加载的目标列表**算出（**零额外查询**）：发布成功取各目标的 `new_version`，已回滚取 `old_version`（回滚就是把机器退回老版本）；
- **只有全部成功目标一致时才返回值**，多目标不一致（部分回滚、部分首次发布）时返回 null、页面不显示——一个版本号被当成「所有机器都是它」比不显示更糟，逐台真实版本到目标明细看；
- 列表版本列在**已回滚**时于版本号下方补一行「当前 xxx」（警示色），tooltip 写明「本次发布版本 X；机器当前实际运行 Y」。其他状态不补：要么 `version` 就是当前版本，要么还没有确定结论。

**落点**：`DeploymentVo.currentVersion`；`DeploymentService.resolveCurrentVersion` 与 `toVo`；前端 `api/deployTypes.ts`、`views/deploy/index.vue`（列表版本列 + 目标明细版本变化列）、`composables/useTaskLogViewer.ts` 及另 4 处日志视图；AGENTS §3 / §20.9 / §24.5 / §24.7；`docs/发布模块.md` §5 / §6.3 / §6.5。

**遗留**：容器不再拦截关闭后，关闭即停轮询，因此**任务在后台结束时列表不会自动刷新**（`onFinished` 只在轮询中触发）。这属于既有的主动行为——用户关掉容器就等于放弃实时跟踪，重新打开或切页都会重新拉取，未做额外补偿。

## Q-14 凭据里的「Git 令牌」到底是密码还是什么？三个平台在哪设置？私有仓库克隆为何报 `could not read Password`

**提问**：

1. `CredentialDto.credential` 写的是「明文凭据内容（Git 令牌 / 私钥 / 仓库密码）」，那这个**令牌是账号密码吗**？`SSH_PASSWORD` / `SSH_KEY` / `GIT_TOKEN` / `REGISTRY` 四类各填什么，能给示例吗？
2. 仓库改成私有后构建失败：

```text
[拉取代码] 执行克隆：git clone --branch master https://***@gitee.com/wangan2022/auth-system-Iteration.git ...
[拉取代码] fatal: could not read Password for 'https://***@gitee.com': No such device or address
```

**结论**：

### 一、令牌不是登录密码，而是「当密码用的一次性凭据」

`GIT_TOKEN` 装的是代码平台签发的**私人访问令牌（Personal Access Token）**，与账号登录密码是两个东西。Gitee 早已拒绝用账号密码做 HTTPS 克隆，两者在 URL 里的**位置也不同**：账号密码是「用户名 + 密码」两段，令牌是**填在密码那一段**、用户名那一段可以是 `oauth2` 也可以是真实用户名。所以枚举里「HTTPS 形式仓库地址的用户名 + 访问令牌」指的就是 `用户名:令牌`。

四类凭据的完整填写口径与示例已落到 `docs/凭据模块.md` §6.6，摘要：

| 类型 | 明文内容 | 示例 | 谁在读 |
| --- | --- | --- | --- |
| `GIT_TOKEN` | `用户名:令牌`，或只填令牌 | `wangan2022:a1b2c3...` | `buildCloneCommand` 拼进 HTTPS 地址 |
| `SSH_KEY` | **完整 PEM 私钥**（含首尾标识行、保留换行） | `-----BEGIN OPENSSH PRIVATE KEY-----…` | 写构建机临时文件，`GIT_SSH_COMMAND` 引用 |
| `REGISTRY` | `用户名:密码`（按**第一个**冒号切分） | `light-deploy:Abc123456` | `docker login -u … -p …` |
| `SSH_PASSWORD` | 不填 | —— | **没人读**，服务器 SSH 密码在「服务器管理」里维护 |

### 二、失败根因：拼出的 URL 缺了密码段

`buildCloneCommand` 的 GIT_TOKEN 分支生成的是：

```java
"https://" + plaintext + "@" + gitUrl.substring("https://".length())
// → https://<令牌>@gitee.com/wangan2022/auth-system-Iteration.git
```

令牌被放在了**用户名位**，URL 里**没有冒号、没有密码段**。git 看到「给了用户名却没给密码」，就转去交互式索要密码；构建机上的克隆跑在 SSH 通道里、没有终端，于是直接报 `No such device or address`。

**关键点：这个报错发生在 git 客户端层面，还没走到 Gitee 鉴权**——所以和令牌是否正确、权限是否勾选**毫无关系**，纯粹是 URL 形态问题。（对照：`https://<PAT>@github.com` 在 GitHub 上可用，Gitee 不认；Gitee 官方形式是 `https://oauth2:<令牌>@gitee.com/...` 或 `https://<用户名>:<令牌>@gitee.com/...`。）

**顺带一个教训**：日志里显示的是 `https://***@gitee.com`，脱敏正则 `https://[^@/]+@` 把整段 userinfo 替换成了 `***`，**连「有没有冒号」这个决定性特征一起抹掉了**。脱敏应当遮蔽**值**、保留**结构**，否则排查时看到的是一段看不出对错的地址。

### 三、修法（已实施）

**先说结论：三个平台统一补 `oauth2` 占位即可。** 依据是三家的官方口径一致——**URL 的用户名位不参与认证，但不允许为空**：GitLab 官方明确「任意非空字符串（GitLab 不会校验该值）」并直接示例 `oauth2:`；GitHub 官方明确「虽然要求输入用户名，但用户名不用于认证，实际用令牌认证；不输入用户名会报凭据无效」；Gitee 用 `oauth2`。所以「只填令牌」这种最自然的填法在三家都能成立。

改动落在 `BuildTaskHandler`，四处：

1. **`buildTokenUrl`（新增）**：明文含 `:` → 原样作 userinfo（兼容必须用真实用户名的平台或自建 Git 服务）；不含 `:` → 补 `oauth2:`，把令牌落到密码位。同时剥离用户误粘贴的 `https://` 前缀与结尾 `@`（否则会拼出 `https://https://`），并先剔除仓库地址里可能已有的 userinfo，避免两段用户名叠加。
2. **协议双向校验**：原来只校验了 `GIT_TOKEN` 必须是 HTTPS 地址；现补上 `SSH_KEY` 必须是 SSH 形式（`git@主机:组/仓库.git`），配成 HTTPS 地址直接报「仅适用于 SSH 协议仓库」。此前这类配错要到克隆时才炸，错误信息还是「仓库不存在」，排查成本高。
3. **`GIT_TERMINAL_PROMPT=0`（新增）**：三种鉴权形态（令牌 / 私钥 / 无凭据）的命令前统一加。非交互会话里 git 一旦转去索要凭据，就会给出 `could not read Password ... No such device or address` 这种把真实原因掩盖成「认证失败」的报错；禁掉提示后直接以 `terminal prompts disabled` 失败，指向真正的问题。这正是本次故障排查被带偏的直接原因。
4. **`resetRemoteUrl`（新增）**：`git clone https://oauth2:令牌@…` 会把**含明文令牌的完整地址**写进工作区的 `.git/config`（`remote.origin.url`），克隆成功后立即 `git remote set-url origin <不带凭据的地址>` 复位。为此把 `buildCloneCommand` 的返回值从 `String` 改为内部 record `CloneCommand(command, cleanUrl)`，`cleanUrl` 为 null 表示无需复位（SSH 协议与公开仓库，凭据本来就不进 URL）。复位失败只记 INFO，不影响构建结论。

**脱敏无需改动**：`maskSecret` 的 `https://[^@/]+@` → `https://***@` 里的 `[^@/]` 包含冒号，`oauth2:令牌@` 仍会被整体替换，令牌不会进日志。

### 四、三个平台的凭据分别是什么、在平台侧怎么设置

对照表已落到 `docs/凭据模块.md` §6.7（访问令牌与 Git 私钥各一张表：平台叫法 / 设置入口 / 需要的权限或只读读写 / 地址形态）。三条最容易踩的：

- **令牌只在生成时显示一次**，关掉页面就查不回来了，必须当场复制；Gitee 开启双因素认证后 HTTPS 推拉只能用私人令牌，账号密码直接失效——这通常就是「私有仓库忽然拉不动」的起因。
- **私钥与公钥不能搞反**：填进平台凭据的是 `ssh-keygen` 生成的**私钥**文件（`~/.ssh/ld_deploy`，无后缀那个）的完整内容，上传到代码平台的是**公钥**（`.pub`）；私钥必须含 `-----BEGIN` / `-----END` 两行、换行原样保留，且**不能带 passphrase**（克隆过程没有输入口令的环节）。
- **优先用「部署公钥 / Deploy key」而不是账号级公钥**：前者只对单个仓库生效、默认只读，泄露影响面最小；本项目只拉代码不推送，只读够用。三家都支持，语义一致。

**选型**：能配 SSH 就优先 `SSH_KEY` + 部署公钥（凭据不进 URL、不落 `.git/config`、单仓库只读）；HTTPS 是唯一出网通道时才用 `GIT_TOKEN`。

**落点**：`BuildTaskHandler.buildCloneCommand` / `buildTokenUrl` / `stripUserInfo` / `resetRemoteUrl` / `CloneCommand`；`lighit-deploy-ui/src/constants/credentialType.ts` 与 `views/credential/index.vue`（表单提示按类型给填写形态）；`docs/凭据模块.md` §3 / §6.6 / §6.7；`AGENTS.md` §7.1。

**验证**：后端 `./mvnw -q -o compile` EXIT=0；前端 typecheck / build 通过。

**遗留**：**尚未在真实构建机上用私有仓库跑通端到端**——本次改动只覆盖私有仓库路径，公开仓库路径不受影响因而无从验证。另：凭据管理页只有「填了什么类型」的静态提示，没有「测试连接」按钮，令牌填错仍要到构建时才发现，属后续演进项。

## Q-15 构建时才暴雷，能不能在构建前先测一遍？

### 一、提问

> 项目管理新增一个连通性测试，保证可以访问和拉取到 Git 仓库和镜像仓库，避免在构建的时候暴雷。

追问三个必须由使用方拍板的点：**测试跑在哪台机器上**、**构建机怎么确定**、**校验强度做到哪一档**。

### 二、结论

**跑在项目的构建机上，不在平台本机。** 这是三个问题里最关键的一个，理由不是「构建机更接近真实」这种感觉，
而是两条硬事实：平台所在机器常常**根本没装 git / docker**，而 `ls-remote` / `docker login` 恰好需要它们；
即便装了，平台机器的**网络策略通常与构建机不同**（构建机往往才配了出网代理或内网仓库白名单）。
在这两点都不成立的环境里测出的「通」，说明不了构建能否成功——那还不如不测。

**构建机由项目档案绑定**（`project.build_server_id`，选填），不是每次弹窗选。
理由是「在哪台机器上构建」本身就是项目属性，选一次就够；顺带两个好处：新建构建时默认带出该机器，
以及测试与构建天然是同一台机器，测出来的结论才对得上。

**校验强度取标准档**：`git ls-remote` + `docker login`，不做真克隆。
`ls-remote` 走的是完整网络 + 认证链路（令牌同样落在 URL 密码位、私钥同样走 `GIT_SSH_COMMAND`），
但不下载对象、不占磁盘、秒级返回；真克隆（`--depth 1`）在大仓库上要几十秒到几分钟、还占构建机磁盘，
换来的只是「再多验证一次对象传输」，收益远小于代价。

### 三、为什么必须抽公共工具类

原来 `buildTokenUrl` / `stripUserInfo` / `maskSecret` / `parseUserPassword` 都是 `BuildTaskHandler`
的**私有方法**。测试处理器要做完全相同的事，最省事的做法是复制一份——**这是本次明确要避免的**。

两份实现一定会在「谁该补 `oauth2`」「密码怎么传给 docker」这类细节上分叉，
而分叉的表现是最难查的一类问题：**测试通过、构建失败**（或反过来）。
排查时两边日志看起来都合理，只有逐字符比对命令才看得出差别。
因此把它们提到 `com.lx.deploy.common.util`：

| 工具类 | 收敛的内容 |
| --- | --- |
| `GitAuthSupport` | 令牌 URL 拼装（`oauth2` 占位）、userinfo 剥离、协议判定、`GIT_TERMINAL_PROMPT=0` 前缀、`GIT_SSH_COMMAND` 前缀 |
| `RegistryAuthSupport` | `用户名:密码` 按第一个冒号切分、`docker login --password-stdin`、`docker logout` |
| `SecretMasker` | 命令行密码参数与 URL userinfo 的脱敏 |

顺带把构建链路里的 `docker login -p <密码>` 一并改成 `--password-stdin`——原写法会把明文密码留在构建机
`ps -ef` 里，同机其他用户可见。这是抽公共类时发现的既有问题，不是新需求。

### 四、两个容易被忽略的判定细节

1. **分支不存在时 `git ls-remote --heads <url> <branch>` 会成功返回且输出为空。**
   只看退出码会漏掉「分支名写错」——这恰恰是构建失败最常见的起因之一。必须同时判空输出。
2. **`docker login` 会写同机 `~/.docker/config.json`。** 测试期登录、退出前若有构建正在推送，
   两者会互相登出。因此互斥键取 `build-server:{serverId}`（与 BUILD 同键）强制串行，
   而不是各用各的项目级键。

### 五、落点与验证

**落点**：新增 `TaskType.PROJECT_TEST` 与 `ProjectConnectTestTaskHandler`；
`ProjectService.submitConnectivityTest`（校验项目启用 / 构建机已绑定 / 防重复提交）；
`POST /project/test/{id}`；`Project` / `ProjectDto` / `ProjectVo` 加 `buildServerId`（VO 批量回填
`buildServerName`，避免 N+1）；`BuildService` 构建机解析改为「请求 > 项目档案 > 系统默认」；
前端项目列表加「连通性测试」按钮与日志抽屉（与构建对话框**各用一份** `useTaskLogViewer` 实例，
避免两个容器同时挂载时 `bodyRef` 与 `logs` 串台）、列表与详情展示构建机、编辑页加构建机下拉。

**DDL**：`src/main/resources/db/upgrade-project-build-server.sql`（`project.build_server_id` 一列 + 索引，
`schema.sql` 同步）。`lds_task.task_type` 是字符串列，**新增任务类型不需要改表**。

**验证**：后端 `./mvnw -o -q compile` EXIT=0；前端 `vue-tsc --noEmit` 0 错误、`vite build` 成功且新接口
`/project/test` 已进产物。

**遗留**：与 Q-14 同源——**尚未在真实构建机上跑通**（待手工执行升级 SQL 并重启后端后验证）。
另：镜像仓库只验证「能否登录」，不验证「能否向该命名空间推送」（推送权限不足要到 `docker push` 才暴露）；
要做需在测试里多推一个临时镜像，代价与收益待评估。

## Q-16 保留版本数设为 5，构建机上却堆了 10 个版本目录

**提问**：项目配置的「保留版本数」好像没起作用，设置为 5，但构建机 `/lx/light-deploy/artifacts/auth-7888/` 下已经留了 10 个目录（含 `v3-auth-7888-887b603c`、`auth-7888-6f046431` 这类旧格式命名）。这个看看怎么调整。

**结论**：**这个字段此前根本没有实现**——`project.retain_release_count` 在全项目只有实体字段定义与注释，**没有任何消费方**：既没有把历史版本置为「已废弃」，也没有删过构建机上的产物目录。目录只增不减属预期（对当时的实现而言）。本轮把它真正接进构建收尾。

### 一、为什么必须按「版本记录里的构建机」删，而不是按项目当前的构建机

`release.build_server_id` 是**构建完成时从 build 记录复制的快照**（`BuildService.completeSuccess`）。产物是磁盘上的文件，只在当初那台机器的 `artifact_path` 下存在。若按项目当前绑定的构建机去找，历史版本会**全部找不到包**——那才是错的。所以回收时必须逐条读它自己的 `build_server_id`，可能要额外开 SSH 连到另一台老构建机。

### 二、两条安全边界

1. **保护窗口**：最近 20 次部署引用过的版本**一律不回收**。回滚是按 `old_version` 重新发布，把某台机器正跑着的版本清掉会让回滚与新发同时断掉。宁可少删，不可错删。
2. **路径白名单**：待删目录只能由「构建机产物持久目录 / 项目编码 / 版本号」三段拼成，且版本号须匹配 `[A-Za-z0-9._-]`。版本号来自库记录而非用户输入，但 `rm -rf` 的目标仍做一次校验，杜绝路径穿越。

### 三、顺序与失败口径

固定为**「先删磁盘产物，再置记录废弃」**：反过来会让记录已不可见、磁盘却还占着，运维只能上机手工找目录。

回收**不是构建成功的必要条件**：算不出清单、连不上构建机、`rm` 失败，都只记日志（未预期异常 ERROR 带堆栈），**不影响本次构建结论**。否则会把「磁盘清理不顺」误报成「构建失败」。

置「已废弃」而不是物理删除：记录留着可追溯，且符合发布版本模块「不物理删除」的既有约定。废弃后不再出现在新建部署的版本下拉里（下拉只列「可发布」），避免出现「看得到却发不了」（见 Q-18）。

> **语义变更需知会**：此前约定「历史版本永不置已废弃，始终可在新建部署里选到，重发同版本走这条路」。接进保留策略后，**超出保留数且不在保护窗口内的版本会被废弃、从下拉中消失**。这是用户显式配置保留数的正常语义，但「手工换包后补一次新建部署重发对应版本」这类操作要趁那个版本还在窗口内做。

**落点**：新增 `ReleaseRetentionService`（`plan` / `markDeprecated`）；`BuildTaskHandler.applyRetentionPolicy`（构建成功后调用，含 `resolveSession` 复用会话）；AGENTS §23.6；构建模块 §6.7；项目模块 §2.3.4。

**遗留**：① **只在下次构建成功时触发**，存量目录不会立刻减少——想马上清理需手工删（只删 `release_record` 里查不到的孤儿目录，删前务必核对）；② 库里查不到记录的旧格式目录（版本号格式变更前的产物）**不会被自动回收**，只会作为孤儿目录长期存在；③ 保留数为 null 或 ≤0 时**不做任何回收**。

## Q-17 换构建机后没重新构建，版本下拉里全是旧构建机的产物，是不是不对？

**提问**：项目绑定了新的构建机，没有执行构建就直接新建部署，版本下拉里全是**之前那台构建机**产出的版本，这是不是不对？

**结论**：**这是对的**。两个「构建机」是两码事：

| | 存在哪 | 作用 |
| --- | --- | --- |
| 项目当前构建机 | `project.build_server_id` | 只决定**下一次构建在哪台跑**（以及连通性测试测哪台） |
| 版本记录的构建机 | `release.build_server_id` | 决定**发布这个版本时去哪台机器取产物** |

正确操作序列：换构建机 → **先「新建构建」**（在新构建机上 clone + 构建 + 产出新版本）→ 再发布新版本。旧版本仍从旧构建机取。没构建就发，发的是你选中的那个历史版本的代码，**不是最新 commit**——如果本意是上最新代码，这一步省不掉。

**落点**：`BuildService.completeSuccess`（写入快照）；`DeployTaskHandler.downloadArtifact`（按快照取）；构建模块 §6.7；发布模块 §6.9。

**遗留**：旧构建机下线 / 被删 / 产物被清后，那些版本变成「下拉看得到、点了发不了」。见 Q-18。

## Q-18 版本下拉看得到、点了却发不了

**提问**：版本记录还在，但产物可能已经被回收或构建机已更换，能不能别等到任务跑到一半才失败？

**结论**：补两处——**下拉带出构建机名** + **提交前预检**。

### 一、下拉带出构建机名称

`ReleaseRecordVo` 增加 `buildServerName`，由 `ReleaseService` **批量回填**（按构建机 ID 去重后一次 `selectByIds`，避免 N+1）。页面在版本下拉里显示 `auth-7888-v7-1521739f · 构建机 build-01`；构建机为空的历史版本直接标注「未记录构建机（多为历史版本）」，在点发布前就能看出它发不了。

### 二、提交前产物存在性预检

新增 `ArtifactProbe.requireExists`，在 `DeploymentService.createAndTrigger` 里、状态校验之后调用：连到版本记录的构建机执行 `test -e <artifact_path>`，不存在直接抛 `VALIDATION_ERROR`，原因写明「可能已被保留策略回收或构建机已更换，请重新构建后再发布」。

两个口径要固定：

- **只校验落盘产物**（JAR / STATIC）。Docker 版本的产物是镜像仓库里的 tag，目标机 `docker pull` 时才真正判定，平台侧探了也不代表目标机拉得到，因此不预检；
- **连不上构建机时不能放行**。放行等于把「未知」当成「存在」，任务照样会失败，只是更晚、且已经落了部署记录与目标快照。

**落点**：新增 `ArtifactProbe`；`DeploymentService.createAndTrigger` 注入并调用；`ReleaseRecordVo.buildServerName` + `ReleaseService.toVos`；前端 `views/deploy/index.vue` 的 `releaseServerLabel`；发布模块 §6.9。

## Q-19 两台机器 JDK 路径不同，一台成功一台 `status=203/EXEC`

**提问**：两台服务器 JDK 路径不同，生成 systemd 服务的脚本是写死的，导致分发两台服务器一台成功一台失败——`/usr/lib/jdk1.8.0_121/bin/java` 在 B 机上不存在，服务 `status=203/EXEC`。怎么解决？

**结论**：先纠正——**脚本没有写死 java 路径**。`jar-init.py` 的 `--java-bin` 是必填参数，值只有两个来源：① 项目/目标运行配置显式填的 `java_bin`；② 没填时在目标机上 `command -v java` 探测。B 机 unit 里的路径在 B 机上不存在，**不可能是 B 机探测出来的**——所以一定是配置里显式填了 A 机的路径，而它是**项目级配置，会套用到所有目标机**。

### 一、止血（B 机）

改 unit 的 ExecStart → `systemctl daemon-reload` → `systemctl restart`。平台约定**尊重运维手工改过的启动参数**，后续发布不会覆盖它。或在 B 机建软链让该路径存在（更快，但路径名与真实 JDK 版本会对不上）。

### 二、长效：JDK 差异配在「部署目标」上

`DeployTaskHandler.mergeTargetConfig` **已支持**部署目标级 `runtime_config_json` 按 key 覆盖项目配置。正确做法：项目级 `java_bin` **留空**由平台逐台探测，只在 java 不在 PATH 的那台**部署目标**上填 `{"java_bin": "/usr/lib/jdk-17/bin/java"}`。

### 三、改配置不会修好已有机器（关键）

`jar-init.py` 的 `write_unit` 遇到已存在的 unit **直接跳过**；`ensureInitialized` 又只在「工作目录里没有 jar」时才跑初始化。B 机现在 jar 已投放，所以改 `java_bin` **不会重写 unit**。

更要紧的是：**不能只删 unit**。删了之后下次发布因为「工作目录有 jar」会跳过初始化，unit 不会被重建，服务反而变成没有 unit。要重建必须手工跑一次 `jar-init.py`（`--jvm-opts` 需与原 unit 一致，否则丢参数）。

### 四、让平台早点发现

`ProjectConnectTestTaskHandler` 新增**目标机前置检查**阶段（仅 JAR 运行时）：逐台连目标机，配了 `java_bin` 就 `test -x`、没配就 `command -v java`，不可用即判任务失败，并把机器名与路径写进原因、指明「清空项目级 java_bin 由平台按机器自动探测，或在部署目标上单独覆盖」。

注意这一项**不在构建机上做**：java 是应用运行时依赖，跑在目标机上，在构建机上探 java 探不出问题。

**落点**：`ProjectConnectTestTaskHandler.checkJavaOnTargets` / `requireJava` / `resolveJavaBin`；前端 `constants/projectConfig.ts` 的 `java_bin` 字段补 tip 与三条 examples；AGENTS §3；项目模块 §2.3.3；任务模块 §6.8。

**遗留**：不做「`java_bin` 变更时自动重写 unit」——那与「尊重运维手工修改启动参数」的约定直接冲突。

## Q-20 两个环境各绑一台，怎么一次发到两台？新服务器没有产物会不会发失败？

**提问**：① 有两台服务器，环境管理里建了两条记录各绑一台，部署目标也是同一服务绑了两台，但新建部署只能选一个环境，那这个项目怎么发布到两台服务器上？② 新服务器绑定了测试环境，这台机器上没有任何构建产物，发布时是不是会找不到产物失败？

**结论**：

### 一、把「环境」当成「机器」用了

模型是三层：**项目 → 环境 → 部署目标**，部署目标表是 `项目 × 环境 × 服务器`（唯一键 `uk_project_env_server`）。**环境是全局逻辑环境（dev/test/prod），不是项目私有、也不代表机器**。两台机器要一起发同一个版本，必须绑在**同一个环境**下做两条部署目标，策略选全量或滚动。

分成两个环境的代价：① 版本链割裂（`resolveCurrentVersions` 按「项目 + 环境」推断 old_version，两套链路互不可见）；② 防重失效（`inProgress` 也按项目 + 环境判定，两个环境可同时发）；③ 历史记录碎片化。

判断标准：这两台是不是同一个集群、要一起上同一个版本。是 → 合并到同一环境；不是（一台测试一台生产）→ 保持两个环境，本来就该分开。

> **更正一处此前说错的话**：曾讲过「新建部署表单可以『目标只勾 S1』」——**错的**。表单只有 `projectId / environmentId / releaseId / strategy` 四个字段，**没有目标勾选**。只发一台只能靠：① 策略覆盖为 `SINGLE_TARGET`（发主目标那台）；② 在部署目标页停用另一台（影响后续所有部署）。

### 二、新服务器不需要预先有任何产物

产物链路是：平台 SFTP 从**构建机**下载到平台本地临时文件 → 再上传到**目标机**。目标机是空的没关系。而且**平台会替你建服务**——`ensureInitialized` 在首次部署时会 `mkdir -p {工作目录}/exec` → 投放三份 py 脚本 → 探测工作目录里有没有 jar → 没有就跑 `jar-init.py` 建目录并注册 systemd unit。

真实失败点按顺序是：① 服务器档案没填「部署根目录」（直接抛异常）；② 该目录在机器上不存在或不可写（**平台不自动创建**，连通性测试只给 WARN）；③ 目标机无 python3；④ 目标机无 java（`detectJavaBin` 兜底 `/usr/bin/java`，unit 建了但服务起不来，这种最坑）；⑤ **构建机上该版本产物不在**；⑥ `release.build_server_id` 为空（历史版本）。

**落点**：项目模块 §6.8；发布模块 §6.1。

**遗留**：新建部署的**环境下拉是全量加载**（`listEnvironments()` 不带过滤），不按所选项目收敛，能选到没绑目标的环境、提交后才报错。建议按项目过滤并在选项上标注目标数（如「prod（2 台）」），**本轮未做**。

## Q-22 都发布成功运行了，什么场景需要回退上个版本？不是发布有问题才回滚吗？

**提问**：滚动发布两台都发布运行成功了，在什么场景需要回退上个版本？印象里都是发布有问题才回滚。

**结论**：反了——**恰恰是「发布失败」的时候不能走回滚**。回滚的前置条件就是主任务状态为「成功」（`DeploymentStatus.canRollback` 只认 `SUCCESS`），失败/已取消/已回滚/进行中的部署都会在 `evaluateRollback` 第一档被拦下。原因：平台回滚的本质是「把 `old_version` **重新发布一次**」，需要旧版本产物还在、目标机处于干净可替换的状态；发布失败的机器可能停在半截（jar 换了一半、服务没起来），旧版本可能已经被动过，此时回滚反而不可靠。失败部署的恢复方式是**修复后重新发**，或手工用 `exec/bak` 备份包应急回退（SHA256 对齐）。

所以「发布成功 → 回滚」不是反常，它是回滚功能**唯一**的用法。平台的「成功」是机器层面的绿灯（进程活着、systemd active、健康检查端点通过），不等于「这个版本可以留在线上」。真实场景分五类：

| 类别 | 场景 | 为什么「成功了」还要退 |
| --- | --- | --- |
| 验收不过 | 服务起来了，但用户/测试点出功能 bug、数据错乱 | 健康检查是「假阳性」，业务链路是断的 |
| 延迟暴露 | 内存泄漏、连接池耗尽、慢 SQL——上线时正常，几小时后/高峰才崩 | 问题只在特定条件（大数据量、高并发、运行时长）下才触发 |
| 配置/依赖遗漏 | 新版本依赖新环境变量没配全、下游服务版本不兼容 | 服务能起，功能缺一块或间歇性报错 |
| 业务决策撤回 | 产品/法务拍板撤回、灰度期间投诉、选错版本发上生产 | 技术没问题，但要撤销 |
| 滚动发布观察 | batchSize=1 逐台上线，第一台发上去观察，指标异常 | 回滚是滚动发布的**计划内动作**，不是补救 |

**落点**：`DeploymentStatus.canRollback`、`DeploymentService.evaluateRollback`（第一档判定）；AGENTS §24.5（前置条件三档）。本文只解释，不新增约束。

**遗留**：无。

## Q-23 新建部署弹窗里「部署策略」「发布版本」下拉展开后面板被屏幕截断

**提问**：新建部署弹窗中，「部署策略」下拉展开后三个选项的描述文字被截断；「发布版本」下拉展开后一长串版本（每项两行：版本号 + 构建机）面板直接探出屏幕底部（附截图）。限高修复后用户复测：三个选项完整了，但「部署策略」面板**向下展开盖住了「环境默认」提示与页脚按钮，底部戳出弹窗边缘**——问题换个形态还在。翻转修好后再复测：面板位置正常了，但**每个选项的「标题 + 描述」两行被压进 34px 的选项盒子里**，描述行贴着下方裁切线、并与下一项标题几乎黏在一行。选项行高修好后再复测：**「干脆向下展开，只要求面板不探出弹窗」**——向上展开会盖住刚选完的项目 / 环境 / 发布版本，不如压住页脚。

**结论**：分四层，对应四次反馈。

**第一层（视口截断）**：下拉面板被 teleport 到 body，**随内容自由撑高、与弹窗和视口都没有约束关系**。「发布版本」每项两行，十来个版本就是 500px 以上的面板；「部署策略」位于表单最底部，展开即探出视口。修复是给面板高度加**全局兜底**：`styles/index.scss` 里 `.el-select-dropdown__wrap { max-height: min(274px, 45vh) !important }`——正常屏幕下与 Element Plus 默认 274px 一致，矮窗口下取 45vh，超出的选项在面板内部滚动。带 `!important` 是因为这条必须压过一切撑高面板的规则，是展示完整性的最后兜底；任何页面不得用局部样式放开或绕过。

**第二层（盖住页脚 / 戳出弹窗）**：popper 的翻转判定**只对视口边界负责**——视口内放得下面板就不翻转，它不知道弹窗的边界。视口高 660px 时输入框下方还有 ~295px 空间、面板 215px，popper 判定「放得下」便不翻转，于是面板盖住 `form-tip` 与页脚、底部戳出弹窗。修复：表单底部字段的下拉显式 `placement="top-start"` 向上展开，提示与页脚不再被遮挡；向上真放不下时 popper 自动翻回向下，不会溢出视口顶部。**判定口径**：字段下方还有 form-tip、或字段离弹窗页脚只有一个行距的，就算「表单底部字段」。（**该结论后来被第四层推翻**：向上展开虽然不盖页脚，却盖住了刚填好的字段，最终改为「固定向下 + 弹窗底部预留面板落位空间」。）

**第三层（选项文字被裁切 / 两项看起来黏在一起）**：前两层解决的是**面板**，这一层出在**选项本身**。`.el-select-dropdown__item` 是 Element Plus 按单行文本设计的：`height: 34px; line-height: 34px; overflow: hidden`。而这两个下拉的每个选项都是「标题 + 描述」两行，14px 标题 + 12px 描述共约 39px，装不进 34px——超出部分被下边界裁掉（最后一项的描述正好被面板下沿切平），中间各项的描述行也只能贴着下一项的标题（描述离自己标题 21px，离下一项标题只剩约 5px），看上去像两项黏在一起。修复：两个下拉都加 `popper-class="strategy-option-popper"`，在 `styles/index.scss` 里**只对这个面板**把选项放开成 `height: auto; min-height: 34px; line-height: 1.5; padding: 6px 32px 6px 20px`。**不直接改全局 `.el-select-dropdown__item`**：全站其它下拉都是单行文本，跟着改成 auto 会把行高和间距一起撑松，属于「为局部问题付全站代价」。

**第四层（改回向下展开 + 不探出弹窗）**：向上展开的代价是盖住刚填好的三个字段，不如压住页脚，所以结论是**固定向下**。但向下展开必须回答「面板落在哪」：popper 只对视口负责，不看弹窗边界。实测这段空间只有 **82px**（输入框底边 344 → 弹窗底边 426），而面板自然高度 **167px**（3 × 两行选项 51px + 列表内边距 12px + 边框）+ popper 偏移 12px，直接向下会戳出弹窗约 100px，面板底部挂在遮罩上，看着像弹窗破了。

三个动作配套，缺一不可：

1. **固定向下**：`deploy/index.vue` 的 `STRATEGY_POPPER_OPTIONS` 用 `popper-options` 关掉 flip 修正（`:popper-options` 里的 modifiers 追加在 element-plus 自己的之后，同名覆盖生效）；否则 popper 一旦判定视口放不下就会翻回上方，又要盖住字段；
2. **弹窗底部预留落位空间**：`styles/index.scss` 的 `.deploy-create-dialog .el-dialog__body` 预留 `padding-bottom: 112px`，可用空间从 82px 变成 194px，面板整块落在弹窗内（实测面板 356..523、弹窗底边 538，留 15px 余量）。代价是下拉关闭时这段是空档——这正是「向下展开且不戳出弹窗」要付的钱；
3. **按视口限高**：关掉 flip 后 popper 不再兜底，矮窗口里向下展开的面板会被屏幕底部截断，所以用 `strategyPanelMaxHeight` 修正器按「输入框底边 → 视口底部」算出上限，写进 popper 根元素的 `--strategy-panel-max-height`，由 `.strategy-option-popper .el-select-dropdown__wrap` 消费（500px 高的矮窗口实测：面板被压到 164px、底边 490 < 500，既不出弹窗也不出屏幕）。变量必须写在 popper 元素上而不是 `state.styles.popper`：main 阶段该对象还没由 computeStyles 建立，写它会抛 `TypeError`。

**落点**：`styles/index.scss`（`.el-select-dropdown__wrap` 限高、`.strategy-option-popper` 选项行高与面板限高、`.deploy-create-dialog` 面板落位空间）；`views/deploy/index.vue`（两个下拉的 `popper-class`、`STRATEGY_POPPER_OPTIONS`）；AGENTS §20.2（弹窗表单样式新增四条规则）。

**遗留**：面板高度 274px 的上限对小屏幕仍显长，且「发布版本」下拉长列表无论向上向下都会盖住弹窗内其它内容（上方空间 ~150px 放不下 500px 面板，popper 会自动翻回向下），这是长列表 + 弹窗的固有取舍，限高滚动已把代价压到「盖住、可滚动、完整可见」；若要彻底不遮挡需改用表格选择器或抽屉选版本，本轮不做。

## Q-24 部署目标配了发布顺序 1 / 2，滚动发布却先发顺序 2 的那台

**提问**：部署目标里「本地测试服务(127.0.0.1)」是主目标、发布顺序 1，阿里云轻量服务器(47.103.12.12) 是普通、顺序 2。发布时却显示「开始第 1/2 批」后**先在阿里云上发布**（策略 ROLLING，batch_size=1）。

**结论**：三个事实叠加，顺序在「创建完成」与「执行开始」之间丢失了。

1. **创建阶段的顺序是对的**：`createAndTrigger` 按 `ORDER BY deploy_order ASC, create_time ASC` 取绑定（`DeploymentService` 251-258），再 `for` 循环**逐条 insert** 快照（292-309），插入顺序就是发布顺序；
2. **但快照表里没有顺序列**：`deployment_target` 只有 `old_version / new_version / image_tag / health_status / …`，**没有 `deploy_order`**，顺序在创建完成后即丢失；
3. **执行阶段按 `create_time ASC` 重排**（`DeployTaskHandler` 302-306）：同一次创建的多条目标相隔微秒，而 `create_time` 是**秒级 `DATETIME`**，两条的值**完全并列**；MySQL 对并列行不保证稳定顺序，该查询走 `idx_deployment_target_deploy(deployment_id)`，二级索引内部按 `(deployment_id, 主键)` 排序，而主键是 `ASSIGN_UUID` 生成的**随机 UUID**——顺序因此变成随机。

**反直觉的一点**：`ORDER BY create_time` 本意是「保证顺序」，实际**反而把插入的物理顺序打乱了**。不加显式排序时 InnoDB 多数情况按插入顺序返回；一写显式排序就改走索引 / filesort 顺序，把随机的 UUID 顺序引了进来。

**为什么以前没暴露**：`SINGLE_TARGET` 只有一个目标；`ALL_AT_ONCE` 只有一批（`buildBatches` 首行直接 `List.of(targets)`）；**只有 `ROLLING` + 小 `batch_size`** 才把目标切成多批，顺序直接等于批次划分。

**修法**：把顺序随快照固化——`deployment_target` 新增 `deploy_order`，创建时写入 `binding.getDeployOrder()`；执行器与页面明细统一改按 `deploy_order ASC, create_time ASC`（`create_time` 降级为历史数据兜底键）。**不做**「执行时实时关联 `project_environment_target` 取顺序」：那张表可变（可改序、可解绑），回头读它会让后续的配置变更倒过来改写已经发生过的历史部署，与「`deployment` 是一次执行的不可变快照」冲突。

**落点**：DDL `db/upgrade-deployment-target-order.sql` + 只读校验 `db/verify-deployment-target-order.sql`；`DeploymentTarget.deployOrder`、`DeploymentService.createAndTrigger` / `listTargets` / `listTargetsEntity`、`DeployTaskHandler`（执行顺序与失败汇总两处）排序；前端 `deployTypes.ts` 的 `DeploymentTargetVo.deployOrder` 与部署目标明细的「发布顺序」列；AGENTS §24.9；发布模块 §2.4 / §6.2。

**遗留**：历史部署的 `deploy_order` 为空（**故意不回填**，回填只能依据并列的 `create_time`，等于把随机顺序固化成看似可信的数据），页面显示「—」，这批记录的展示顺序仍由 `create_time` 兜底，属随机但已执行完毕、不再影响任何行为。

## Q-25 发布时只选了一个环境，为什么另一个环境的目标也被发布了

**提问**：`auth-7888` 在「生产环境(lx-prod)」下绑定「本地测试服务(127.0.0.1)」，「虚拟机测试环境(vm-prod)」下绑定「阿里云轻量服务器(47.103.12.12)」。发布时选的是生产环境，结果**两台都发了**（阿里云成功、本地测试健康检查失败）。按「发布以环境为单位」的口径，不该发到另一个环境的机器上。

**结论**：**当前代码不存在「跨环境展开目标」的路径**。穷举后写入 `deployment_target` 的位置只有一处：

- `DeploymentService.createAndTrigger` 是全项目**唯一**的 `deploymentTargetMapper.insert` 调用点，其目标来源查询带 `.eq(ProjectEnvironmentTarget::getEnvironmentId, environment.getId())`；

- `resolveCurrentVersions(projectId, environmentId)`、防重 `inProgress` 同样按环境过滤。

因此「一次部署里同时出现两个环境的机器」，在当前代码下**不可能**由代码产生。

**最可能的解释**：发布当时这两条绑定**属于同一个环境**，之后其中一条被改到了另一个环境。`project_environment_target` 的 `environment_id` 是可改的，且改环境不会刷新 `create_time`，所以事后看截图就像是「跨环境发布了」。

**一条佐证**：该次部署里阿里云的 `old_version = auth-7888-v7-1521739f`。`resolveCurrentVersions` 是按「项目 + 环境」回溯历史部署取版本的——若本次 `environmentId` 是 `lx-prod`，而阿里云此前只在 `vm-prod` 下发过，它取不到 `v7`。目标行上出现了 `v7`，说明本次 `environmentId` 指向的是**阿里云留有发布记录的那个环境**。

**待确认（查库核对）**：

-- 2. 该项目两条绑定当前的环境与最后修改时间

## Q-26 绑定记录被改了环境却追溯不到，能不能加操作记录表？

**提问**：Q-25 的结论只能是「绑定记录事后被改过环境」，但平台没有任何留痕，`update_time` 又回答不了
「改的是哪个字段、从什么改成什么」，追溯只能靠猜。能不能加一张操作记录表做审计？
参考的 `sys_login_log` 是 `utf8mb3`，字符集要改成 `utf8mb4_unicode_ci`；写入方式想用 AOP 切面 + 注解。

**结论**：加，但**不新建表，扩展既有的 `audit_log`**。

`schema.sql` 里早就有 `audit_log`（操作人 / 动作 / 资源 / 请求地址 / 结果），只是一直没有 Java 代码写入，
等于一张空表。再建一张 `sys_oper_log` 会让「审计」这个概念在平台里有两套模型：查询要 union、
前端要选表、归档要对齐两份。做法是补上切面需要的列（trace_id / title / method / request_method /
oper_ip / os / browser / json_result / cost_time），`action` 复用为操作类型编码、
`request_body` 复用为脱敏后的请求参数。

字符集按 `utf8mb4_unicode_ci`（AGENTS §4.2），参考脚本里的 `utf8mb3` 不采用。

写入链路固定为「`@OperLog` 注解 + `OperLogAspect` 切面」：

- 只标**会改变状态**的接口，查询类不标——全量记录只会让操作日志变成第二份访问日志；
- **失败也落库**（`result=0` + 脱敏后的原因），异常原样上抛，切面不吞异常；
- **落库失败只记 ERROR**，绝不因为审计写不进去就让业务操作失败；
- 参数先过 `SecretMasker.maskJsonFields`，服务器 / 凭据这类「参数整体就是凭据」的接口直接
  `recordParam = false`；
- 页面只提供分页与详情，没有写接口——审计记录被改写就不再是审计。

**落点**：`src/main/resources/db/upgrade-audit-log-operation.sql` + `verify-audit-log-operation.sql`；
`com.lx.deploy.audit` 模块；`common/annotation/OperLog`、`common/aop/OperLogAspect`、
`common/enums/audit/BusinessType`、`common/constants/AuditResult`、`common/web/ClientInfoResolver`；
`SecretMasker` 新增 `maskJsonFields`；前端 `views/auditLog/index.vue` 挂「系统设置 → 操作日志」；
AGENTS §26；`docs/操作日志模块.md`。

**遗留**：① 操作人取请求头，可被伪造，接入权限中心后必须改成服务端从认证信息解析；
② 不记字段级 diff（看不出「环境从 A 改成 B」），后续可在 Service 层加字段变更明细；
③ 同步写入，量大后改异步；④ 无归档策略。

### Q-28　2026-09-27　加了操作日志切面之后，应用启动失败：No qualifying bean of type 'ObjectMapper'

**提问**：`UnsatisfiedDependencyException: Error creating bean with name 'operLogAspect' …
No qualifying bean of type 'com.fasterxml.jackson.databind.ObjectMapper' available`。
切面昨天还能编译通过，为什么一启动就炸？是不是少了什么依赖？

**结论**：**Spring Boot 4 起容器只自动配置 Jackson 3（`tools.jackson.databind.ObjectMapper`）**，
项目代码引用的却是 Jackson 2（`com.fasterxml.jackson.databind.ObjectMapper`），注入自然找不到 bean。

- **不是缺依赖，是版本错位**。`spring-boot-jackson:4.1.0` 里的 `JacksonAutoConfiguration`
  注册的是 `tools.jackson` 的 Mapper；classpath 上的 Jackson 2 是 springdoc 的传递依赖，
  没有任何组件把它注册成 bean；
- **为什么只有切面报错**：项目其余 10 处 Jackson 用法全是 `new ObjectMapper()`
  （各 Service 的 JSON 校验、三个 TaskHandler 的配置解析），只有切面走了注入，
  所以报错只落在这一个 bean 上。`No qualifying bean` 报的是「第一个创建失败的」而非「全部」，
  别据此以为其它地方没事；
- **修复**：切面不再注入，序列化改走 `SecretMasker.toJson / toTree / parseTree`
  （`SecretMasker` 内部持有静态 Jackson 2 实例）。顺带解决一个更本质的问题——
  审计文本不该跟随业务序列化器的全局配置变动，命名策略一改历史日志的可读性就跟着变；
- **不采用「手工注册一个 Jackson 2 的 bean」**：那样只是绕过报错，
  HTTP 层到底用哪套 Jackson 仍然悬而未决（见遗留）。

**落点**：`OperLogAspect` 构造器与 `serialize`；`SecretMasker` 新增
`toJson` / `toTree` / `parseTree` / `isSensitiveKey`（后者从 private 放开供变更比对复用）；
AGENTS §26；操作日志模块 §6.8。

**遗留**：项目内 Jackson 2 / Jackson 3 并存。自己写的代码统一用 `SecretMasker`（Jackson 2），
但实体上的 `com.fasterxml.jackson.annotation.JsonProperty`（如 `Server.ciphertext` 的
`WRITE_ONLY`）只有在 HTTP 层走 **Jackson 2 转换器**时才生效；若哪天 Jackson 3 的转换器接管，
密文可能被序列化进响应体。**上线前务必抽查** `GET /server/list` 的响应是否含 `ciphertext`
——这是本项目唯一一处靠 `@JsonProperty` 做字段屏蔽的地方，值得单独盯一眼。

### Q-29　2026-09-27　操作日志只有请求参数，看不出「改了哪个字段」

**提问**：操作日志详情里能看到改完之后的参数，但看不出改之前是什么。
部署目标的环境归属被改（`environmentId` 从 A 变成 B）这类事故，还是问不出答案。能不能做字段级 diff？

**结论**：做，但不新建表、不动 Service 的写法，而是在 `@OperLog` 上加 `resourceType`
让切面自己采集：`proceed()` 之前取变更前快照，成功之后取变更后快照，比对得到
`changed_fields`（`[{field, oldValue, newValue}]`）。

- **必须前置取快照**：业务方法一执行旧值就被覆盖，之后再查只会比出空。
  这是放在切面层而不是各 Service 上报的根本理由——扩容一个模块不用改任何已有代码，
  也不会出现「某个 Service 忘了上报所以永久无明细」；
- **资源定位按 Mapper 名字索引**：`getBeansOfType(BaseMapper.class)` 扫描后，
  bean 名去掉 `Mapper` 后缀即为资源类型（`serverMapper` → `server`）。
  刻意不用构造器注入 `Map<String, BaseMapper<?>>`：那依赖容器对泛型通配符的可赋值判定，
  判定失败就是启动崩溃——踩 Q-28 的坑还不到 24 小时，同一类风险不重复赌；
- **只给 update / delete 声明**：新增没有旧值，比出来是满屏「- → 新值」的噪音；
- **排除 `update_time` 这类必变字段**：它每次都变却毫无业务含义，
  留着只会把真正的变更淹没在一堆无关差异里；敏感字段（凭据、私钥、令牌）
  按与参数脱敏同一套判定跳过，避免「参数脱敏了、明细里留原文」；
- **删除**时查不到变更后记录（MyBatis-Plus 逻辑删除让 `selectById` 落空），
  此时旧值全部以 `(已删除)` 作为新值呈现，回答「删掉的是什么」；
- **明细存展示值不存原始类型**：数字、枚举、嵌套 JSON 统一转文本，否则页面上没法同表展示；
- **字段名的中文映射放前端**（`constants/auditLog.ts` 的 `fieldLabel`，三级回落到原字段名）：
  翻译是展示层职责，放后端会让每次加字段都要改后端。

**落点**：`@OperLog.resourceType` / `resourceIdParam`；`ResourceDiffRecorder`；
`AuditLog.changedFields` / `AuditFieldChangeVo`；`audit_log.changed_fields`
（JSON 列，升级脚本与 verify 脚本同步）；8 个 Controller 的 update / delete 共 16 处；
前端 `views/auditLog/index.vue` 的「变更明细」卡片与列表「变更」列。AGENTS §26.2、操作日志模块 §6.7。

**遗留**：明细里 `environmentId` 这类外键是主键原值不是可读名称。反查名称要么在详情页
再查一次（多 N 次查询），要么在落库时把名称一并写进去（快照一旦放开就不是快照了）。
当前保留原值，靠时间邻近的其它日志回溯；若要「一眼看懂」，更合适的做法是给明细补一列
`label` 由切面在取快照时带上——等有明确需求再说。

## Q-30（2026-09-27）接口明明有返回，操作日志详情的「响应 JSON」却是空的

**提问**：操作日志详情页里「参数信息 → 返回结果」一直是空的，但接口确实返回了数据。
是不是切面没取到返回值？还是前端字段对不上？

**结论**：不是没取到，也不是前端问题，是**序列化失败被静默吞掉了**。

- 切面在 `proceed()` 之后拿到的就是 Controller 的返回值（统一响应 `ApiResponse`），
  `recordResult` 默认 true，链路本身没问题；
- 真正的原因在 `SecretMasker` 里的静态 Jackson 2 `ObjectMapper`：**没有注册 `JavaTimeModule`**。
  Jackson 2.21 起 `java.time` 类型默认要求显式处理器，未注册时序列化 `LocalDateTime`
  直接抛 `InvalidDefinitionException`（报文里明写着 add Module jackson-datatype-jsr310），
  而 `toJson` / `toTree` 用 `catch (Exception) return null` 把它吞了。
  统一响应里有 `timestamp` 字段，所以每一条成功日志的 `json_result` 都是 null；
- **同一个原因还会打掉变更明细**：`ResourceDiffRecorder.snapshot` 走 `SecretMasker.toTree(实体)`，
  而 `BaseEntity` 自带 `create_time` / `update_time`，序列化同样失败 → 快照为 null →
  `changed_fields` 永远采不到。也就是说 Q-29 做的功能在这之前一直是「静默不生效」；
- 修复：静态 mapper 注册 `JavaTimeModule` 并 `disable(WRITE_DATES_AS_TIMESTAMPS)`（写时间戳数组
  不利于人读），同时在 pom 里显式声明 `jackson-datatype-jsr310`（版本由 spring-boot-dependencies
  管理，此前是 springdoc 的传递依赖，直接引用属于隐式依赖）。
  另外给 `ResourceDiffRecorder.snapshot` 补一条 WARN——实体非 null 却拿到空快照属于静默丢数据，
  按 AGENTS §14.3 必须留痕；
- 顺带把返回结果也过一遍 `SecretMasker.maskJsonFields`：统一响应可能带回凭据类字段，
  只脱敏请求参数等于防线只修了一半。

**落点**：`SecretMasker` 的静态 mapper 与 JavaTimeModule；`pom.xml` 显式依赖；
`OperLogAspect` 对 `jsonResult` 脱敏；`ResourceDiffRecorder.snapshot` 的 WARN；
`verify-audit-log-operation.sql` 结果集 4 增加「返回结果」列、新增结果集 6 统计空值占比。
AGENTS §26.3、操作日志模块 §6.8 / §6.10。

**遗留**：`toJson` / `toTree` 吞异常返回 null 的设计本身就是这次排查困难的根源。
彻底做法是失败时抛出由调用方决定降级（切面已在 try 里，不会外泄），但会牵动
`SecretMasker` 的全部调用点，本轮只在两处补 WARN，等下次再动这块时一并收敛。

## Q-31（2026-09-27）操作日志要加「应用系统」字段，每个接口都写一遍太蠢，能不能配置化

**提问**：操作日志要新增 `application`（应用系统）字段，标注「操作的是哪个系统」。
但这个值是系统范围的——每个 `@OperLog` 上都写 `application = "轻量部署发布系统"` 不合适，
能不能在 `application.yml` 配一个系统名参数，代码读配置？

**结论**：能，而且正解就是配置化。

- 系统名是**实例级事实**：同一个平台实例里所有接口的取值必然相同，
  跟着注解逐个声明意味着改名要改 28 处且必然漏，漏了的表现是同一张表里出现两种系统名，
  比字段缺失更难解释；
- 做法：`application.yaml` 增加 `light-deploy.application-name`（默认「轻量部署发布系统」），
  `OperLogAspect` 构造注入 `@Value("${light-deploy.application-name:轻量部署发布系统}")`，
  写日志时统一 `audit.setApplication(...)`。改名只改配置一行，历史记录不受影响；
- 用 `@Value` 而不是 `@ConfigurationProperties`：只有一个标量值，项目里
  `light-deploy.build.server-id`、`light-deploy.task.log-echo-enabled` 也都是这个写法；
  保留默认值，配置缺失时不会启动失败；
- 数据库侧：`audit_log.application VARCHAR(64)`，历史 NULL 行由
  `upgrade-audit-log-application.sql` 回填一次（脚本里是字面量，需要别的名字就改脚本再执行）。
  **不加索引**——取值高度重复（通常只有一种），索引只会增加写入成本；
- 前端只在详情页「基本信息」展示，列表不加列：所有行同值，列出来只是噪音。

**落点**：`application.yaml` 的 `light-deploy.application-name`；`OperLogAspect` 构造参数与
`buildBaseLog`；`AuditLog.application` / `AuditLogVo.application` / `AuditLogService.toVo`；
`db/upgrade-audit-log-application.sql`；`schema.sql` 与 `verify-audit-log-operation.sql` 同步；
前端 `deployTypes.ts` 与 `views/auditLog/index.vue`。AGENTS §26.3、操作日志模块 §6.9。

**遗留**：回填用的是脚本里的字面量，如果部署时系统名配置成了别的名字，历史行的回填值
与实际配置会不一致（历史日志本身也不会改）。多实例共用一张 `audit_log` 且系统名不同时，
这个字段才有真正的区分价值——届时应当按实例各自配置，回填语句也要拆开执行。

## Q-32（2026-09-27）除了操作日志，其它页面都没有时间查询条件，要加上

**提问**：页面好像除了操作日志，基本没有时间查询条件，这个我觉得要加上。

**结论**：加，口径统一为**筛 `create_time`**，覆盖全部 9 个带搜索区的列表页。

- **为什么不按业务时间筛**：构建有 `started_at` / `finished_at`、任务有开始与结束时间，
  但这些列在排队或执行中时是空的，按它们筛会让「明明有数据却查不到」变成常态。
  创建时间对任何一行都存在，语义也最直白——「这段时间里新增了哪些」。
  业务时间照常作为列展示，只是不参与筛选；
- **后端三处成套**：DTO 继承 `TimeRangeQuery`（字段带 `@DateTimeFormat`，
  否则 `@ModelAttribute` 绑不上「yyyy-MM-dd HH:mm:ss」这种带空格的格式，会直接 400）、
  Service 调 `TimeRangeSupport.apply(wrapper, Xxx::getCreateTime, condition)`。
  工具内部是闭区间 `ge/le`，开始晚于截止抛参数错误——与其返回 0 条让人以为「这段时间没数据」，
  不如当场说清条件填反了。操作日志原来的那份内联实现一并换成公共工具，避免两套口径；
- **前端也只有一份实现**：`components/CreateTimeRange.vue`（`default-time` 固定
  开始 00:00:00 / 截止 23:59:59；不设置的话选同一天查的是 [09-01 00:00:00, 09-01 00:00:00]，
  当天数据一条都查不到）+ `utils/index.ts` 的 `splitTimeRange`。
  操作日志页原先内联的 `el-date-picker` 改为共用组件；
- **顺带补列**：发布 / 构建 / 任务三个流水型页面原先只有「开始时间 / 结束时间」列，没有创建时间列。
  筛选项与展示列对不上时用户无法核对筛选是否生效，因此补上「创建时间」列。

**落点**：`common/model/TimeRangeQuery.java`、`common/util/TimeRangeSupport.java`；
9 个 DTO（Server / Project / Environment / ProjectEnvironmentTarget / Credential / Registry /
Build / Deployment / Task）+ `AuditLogDto`；9 个 Service 的 `buildQueryWrapper` + `AuditLogService`；
前端 `components/CreateTimeRange.vue`、`utils/index.ts`、9 个列表页 + 操作日志页。
AGENTS §10.4、前端工程 §3.4。

**遗留**：时间区间只落在分页 / 列表查询上，`list` 类下拉接口（如版本下拉、环境下拉）不带该条件——
它们是「全量候选」语义，加时间筛选会让下拉内容随筛选变化，反而更难用。
另外 `create_time` 上没有单独索引的表，大表按时间筛选仍会走全表扫描；
当前各表数据量在千级以内，出现性能问题时再按 `(业务键, create_time)` 补复合索引。

## Q-33（2026-09-27）`AuditLogService` 里没看到 `AuditLogMapper` 注入，它是怎么查库的

**提问**：翻遍 `AuditLogService`，只有一个类声明 `extends ServiceImpl<AuditLogMapper, AuditLog>`，
没有 `@Autowired`、没有构造器，那 `page()` / `getById()` 到底是谁在查库？

**结论**：Mapper 由 **MyBatis-Plus 的父类字段**注入，注入点在框架里而不是本项目代码里。

- **继承链**（MP 3.5.17，Boot 4 starter）：
  `AuditLogService` → `com.baomidou.mybatisplus.spring.service.impl.ServiceImpl<M extends BaseMapper<T>, T>`
  → `com.baomidou.mybatisplus.spring.repository.CrudRepository<M, T>`
  → `com.baomidou.mybatisplus.extension.repository.AbstractRepository<M, T>`；
- **注入点**：`CrudRepository` 里声明了 `@Autowired protected M baseMapper;`。
  用 `javap -v` 反编译 jar 可实证（实测输出）：

  ```
  protected M baseMapper;
    RuntimeVisibleAnnotations:
      org.springframework.beans.factory.annotation.Autowired
  ```

  Spring 实例化子类时做字段注入，靠 `ResolvableType` 解析继承来的泛型实参 `M = AuditLogMapper`，
  从容器里取到对应 bean 塞进 `baseMapper`。所以子类里一行注入代码都不需要；
- **Mapper bean 从哪来**：启动类 `@MapperScan("com.lx.deploy.**.mapper")` 把每个接口注册成
  `MapperFactoryBean` 代理（bean 名首字母小写，如 `auditLogMapper`）。
  `ResourceDiffRecorder` 用 `getBeansOfType(BaseMapper.class)` 按 bean 名索引（`serverMapper` → `server`）
  也依赖同一次扫描；
- **调用路径**：Service 里写的 `page(...)` / `getById(...)` / `save(...)` 全是继承来的默认方法，
  内部落到 `baseMapper.selectPage(...)` / `selectById(...)` / `insert(...)`。
  分页能生效靠 `config/MybatisPlusConfig` 的 `PaginationInnerInterceptor(DbType.MYSQL)`；
  审计表无 XML——本表是追加写 + 只读页，通用方法够用；
- **写入侧同理**：`OperLogAspect` 第 220 行 `auditLogService.save(audit)` 也是继承来的 `save`，
  最终 `baseMapper.insert`。

**落点**：`audit/service/AuditLogService.java`、`audit/mapper/AuditLogMapper.java`、
`LightDeployApplication`（`@MapperScan`）、`config/MybatisPlusConfig.java`。

**遗留**：
① **MP 3.5.17 的 `ServiceImpl` 包名是 `...mybatisplus.spring.service.impl`**，
旧资料里的 `...mybatisplus.extension.service.impl` 在该版本 jar 中已不存在，新增 Service 时别照抄旧包名；
② 注入失败的表现是**首次调用**时抛 `baseMapper can not be null`（`getBaseMapper()` 里的断言），
不是启动失败——看到这句先查 `@MapperScan` 路径是否覆盖该 Mapper 包、继承时的泛型是否写死成具体 Mapper。

## Q-34（2026-09-27）为什么 Service 跨表 Mapper 用构造器注入，Controller 引用 Service 却用 `@Autowired`

**提问**：同样是依赖注入，Service 里引用其它表的 Mapper 是 `private final` + 构造器，
Controller 里引用 Service 却是 `@Autowired` 字段注入，是有意为之还是随手写的？

**结论**：**没有成文约定，是模块演进顺序造成的历史差异**，两种写法都能正常工作。

- **现状盘点**（2026-09-27 改造前）：12 个 Controller **全部** `@Autowired` 字段注入
  （每个只依赖 1 个 Service）；Service 层反而不统一——`DeploymentService`（8 个依赖）、
  `ProjectService`、`EnvironmentService`、`ProjectEnvironmentTargetService`、`ReleaseService`、
  `ReleaseRetentionService` 用构造器注入，而 `ServerService`、`CredentialService`、
  `RegistryService` 是 `@Autowired` 字段注入。所以「Service 一律构造器」这个印象并不成立；
- **为什么会这样**：`AGENTS.md` 全文没有关于注入方式的约束（无从遵守，也无从违反）。
  实际演进是：早期模块（server / credential / registry）依赖只有 1~2 个，字段注入最省事；
  后来写的模块（deployment / project）依赖成倍增长，字段注入会把「这个类到底依赖了什么」
  散落在类中部，于是改用构造器——依赖清单集中在顶部，`final` 保证不可变，
  且 AGENTS 要求每个字段带 javadoc，构造器天然对应一份 `@param` 清单
  （`DeploymentService` 构造器就是 8 个 `@param`）。Controller 依赖恒定为 1 个 Service，
  字段注入的缺点几乎不体现，就一直沿用了最初写法；
- **两者的真实差别**（不是风格问题）：
  ① **完整性**：构造器注入的对象一出生就依赖齐全；字段注入允许对象处于「未注入」状态，
  单测里 `new ServerService()` 再用会直接 NPE；
  ② **可测性**：构造器可以 `new XxxService(mockMapper)` 直给，字段注入要靠反射或 `@InjectMocks`；
  ③ **循环依赖**：Spring Boot 自 2.6 起默认禁止循环引用（本项目未放开），
  两种方式都不会靠三级缓存蒙混过关，但构造器注入在构造期就暴露，字段注入要等容器刷新时才炸；
- **同一个类里两种方式并存并不矛盾**：改造前的 `ServerService` 既有父类 `baseMapper`
  （框架固定的 `@Autowired` 字段，改不了），又有自己 `@Autowired` 的 `taskService`。
  本表 CRUD 走父类字段，跨表依赖走自己的声明，两者互不冲突。

**后续动作**（同日完成）：用户确认「Service 层统一构造器注入」，于是把剩余 3 处字段注入
（`server` / `credential` / `registry`）全部改为 `private final` + 显式构造器，写法与
`DeploymentService` 对齐（字段带 javadoc、构造器带 `@param` 清单）。
改造后 **Service 层跨模块依赖已无 `@Autowired`**。

**落点**：改造项 `server/service/ServerService.java`、`credential/service/CredentialService.java`、
`registry/service/RegistryService.java`；既有构造器注入 `deployment/service/DeploymentService.java`、
`project/service/ProjectService.java` 等；仍为字段注入的只剩 12 个 `*Controller.java` 与
MP 父类 `baseMapper`。口径摘要见 项目总览 §7；Mapper 注入机制见 Q-33、操作日志模块 §6.11。

**遗留**：
- **Controller 的 12 处字段注入本轮不动**——每个 Controller 只依赖 1 个 Service，
  字段注入的缺点（不完整初始化、可测性）几乎不体现，统一只会产生大量无意义 diff；
  新增 Controller 建议用构造器注入 + `private final`，存量遇到时顺手改；
- **MP 父类 `baseMapper` 只能是字段注入**（框架固定），改不了，也不必改——它是 `protected`，
  子类无需声明就可用；
- 若后续系统性统一，需连同单测一起做（`private final` 改造后字段注入时代的 `@InjectMocks` 会失效）。
