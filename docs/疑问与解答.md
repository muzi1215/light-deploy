## Q-01 无历史版本也能回滚，且回滚后静默显示成功

**提问**：工作目录的 `exec/bak` 里没有历史版本包，为什么还能操作回滚？点了之后页面显示「已回滚」，机器上却什么都没变。

**结论**：这是两个缺陷叠在一起。

1. **判定缺失**：原实现只要部署状态是「成功」就放行回滚，没有校验目标是否真的可退。`exec/bak` 里有没有备份包**不是**回滚依据——平台回滚走的是「重新发布 `old_version`」，靠的是 `release_record` 与构建机上的产物。
2. **静默成功**：一个目标都回滚不了时，代码直接把部署状态置为「已回滚」并返回成功。

**落点**：抽出唯一判定入口 `DeploymentService.evaluateRollback`，按三种原因优先级拦截（状态非成功 → 变更过的目标全无 `old_version` → 有 `old_version` 但版本记录查不到或缺分发信息）；不可回滚时抛 `DeployException`；判定结论随列表返回（`rollbackable` / `rollbackBlockReason`），前端据此置灰按钮并用 tooltip 说明，**禁止前端自己拿状态码推断**。见 AGENTS §24.5。

**遗留**：无。

## Q-02 回滚日志缺要素，看不出退到了哪个版本

**提问**：可以回滚时，日志要有开始回滚、当前版本、回滚到什么版本、时间、成功失败、是否启动成功。

**结论**：回滚是代价高、不可逆的动作，日志必须能**独立交代这次回滚做了什么**，不能靠目标行零散的 INFO 加执行器结尾那句「任务执行成功」充当结论——那句话不区分发布与回滚。

**落点**：`DeployTaskHandler` 固定输出六个要素——开场（含策略、本次回滚 N/M 个目标）、每目标的「当前版本 X → 回滚到 Y」、目标级起止时间（写进日志正文，格式 `yyyy-MM-dd HH:mm:ss`）、收尾结论、`restartService` 后的「服务启动成功（`systemctl is-active = active`）」、失败时提示人工确认目标机当前版本。见 AGENTS §24.5 的六要素表。

**遗留**：无。

## Q-03 旧记录点「重新构建」发的是哪个包？为何没有「重新发布」？

**提问**：第一次构建成功后，隔天点旧记录的「重新构建」，是重建 9-25 那份产物，还是新建 9-26 的包？另外部署只有回滚、没有「重新发布」，为什么？

**结论**：两者都不是「把上次的动作再跑一遍」，实现上也不是，因此**禁止在 UI 文案、接口注释、文档里把它们描述成重放**。

- **「重新构建」= 新建构建，克隆分支最新 HEAD**。它只把 `projectId` 交给 `BuildService.createAndTrigger`，克隆命令只有 `--branch`、全程没有 `checkout`，所以**永远构建分支最新提交**；旧记录那次构建的产物不会被重建。`build.git_commit` 当前全项目**零读取点**，不能作为「按提交重建」的依据。因此「重新构建」不能承诺产物可复现。
- **部署记录是「一次执行的不可变快照」**，禁止在原记录上重跑：目标集在创建时快照到 `deployment_target`，原地重发会覆盖首次执行的统计与起止时间，更致命的是 `old_version` 与 `new_version` 会变成同一个值，目标行再也说不清「从哪来、到哪去」。回滚能在同一记录上执行，是因为它是**同一批目标的状态切换**，不是第二次独立执行。
- **「重新发布」的正确形态是复制出一条新部署记录**（新 `deployment` + 目标快照 + 新 DEPLOY 任务，旧记录一字不动）。而当前「重发同版本」直接用「新建部署」手选历史版本即可——`ReleaseStatus.DEPRECATED` 全项目零引用，历史版本**永远处于「可发布」**。

**落点**：AGENTS §24.6 全文；`docs/构建模块.md` §6.5；`docs/发布模块.md` §6.8；`docs/前端工程.md`。

**遗留**：「复制成新部署记录」这个形态尚未实现，属后续需求；**未经同步评估该链路，禁止引入版本自动废弃策略**。

## Q-04 后端抛异常与请求信息为何控制台都不打印

**提问**：项目里后端抛异常、接口请求信息，控制台都没有打印。

**结论**：三类日志各自缺失。异常被吃掉、访问不落痕，出问题时无法从服务端日志定位到具体请求。

**落点**：补三处——`GlobalExceptionHandler` 的 `handleBusiness` / `handleValidation` 加 `log.warn`（业务异常与参数校验**不打堆栈**）；`TaskExecutor` 的 `executeTask` 的 catch 分流，业务异常 WARN、未预期异常 ERROR 带堆栈；`RequestTraceFilter` 在 `finally` 输出访问日志（方法 + URI + 耗时 + 状态码 + `requestId`）。见 AGENTS §14.2 / §14.3。

**结论性约定**：**任何被吃掉的异常都必须至少留一条日志**；业务异常/参数校验 → WARN 不打堆栈，未预期异常 → ERROR 带堆栈。

## Q-05 版本号要不要加 `v` 序号？自动还是人工指定？轮询接口能否不打印日志

**提问**：构建产物提供给发布的版本号 `auth-7888-887b603c` 要加一个 `v` 版本号；这个是自动生成还是手动指定？另外 `GET /taskLog/pull` 这种轮询请求能不能不打印。

**结论**：三个问题三个答案。

1. **必须有序号**：改造前版本号只有「项目编码 + 提交短码」，同一 commit 重复构建会让镜像 tag、产物持久目录两处同名被覆盖，并在 `release_record` 上撞唯一键，而 `completeSuccess` 没有事务——结果是**构建记录显示成功、任务显示失败、版本列表里没有它**，该产物永远发不出去。
2. **默认自动取号，允许人工指定**：`MAX(version_seq) + 1`，取号时刻意**不过滤软删除**（防序号重用）；人工指定的序号**必须在创建构建时**就校验项目内未被占用，不许拖到构建跑完才在版本落库阶段失败。列与升级脚本见 `db/upgrade-release-version-seq.sql`。
3. **轮询日志降噪，但不能全静默**：`light-deploy.access-log.silent-paths`（默认 `/taskLog/pull`）命中的路径 `<400` 降 DEBUG、`>=400` 仍按 WARN 输出。**禁止把某路径配成完全静默**——那会让该接口的 4xx/5xx 一起消失。匹配前要剥掉 context-path `/deploy`。

**落点**：AGENTS §23.5（版本号）、§14.2（访问日志降噪）。

**遗留**：用户需手工执行 `upgrade-release-version-seq.sql` 回填老版本序号。

## Q-07 回滚逻辑怎么做的？能否把可回滚的版本查询展示出来

**提问**：回滚逻辑是怎么做的，仔细展示说说；能不能把可回滚的版本的查询展示出来？

**结论**：「可回滚 / 不可回滚」只是一句话，回答不了「点下去到底会动哪几台、各自退到哪个版本」。因此补一个只读预览接口，并顺手把三份重复判定收拢成一份。

**落点**：

- 新增 `GET /deployment/rollback-preview/{id}`（`DeploymentService.rollbackPreview`），返回总结论 + 逐目标明细（服务器名/地址、`当前版本 → 将回滚到的版本`、是否可回滚、跳过原因）；只读，不改状态、不建任务；不可回滚时返回结论而非抛异常，前端把 `blockReason` 展示在弹窗里。
- **判定收拢为一份**：抽出 `inspectTargets(projectId, targets) → List<RollbackDecision>`（record：target / rollbackable / skipReason / missingVersion），`RollbackEvaluation` 增加 `decisions` 字段。`evaluateRollback` 聚合、`rollback()` 决定重置或跳过、`rollbackPreview()` 渲染清单三处**消费同一份**。**禁止再各写一套判定条件**，否则会出现「预览说能退、提交说退不了」。
- 列表侧返回 `rollbackTargetCount` / `rollbackSkippedCount`（判定时已算出，**零额外查询**），tooltip 直接给台数，不必为每行调预览接口。
- `rollback()` 里 `rollbackCount == 0` 的兜底分支已删——判定为可回滚后该分支不可达。

**遗留**：网关若对 `/deployment/**` 有白名单，需放行 `/deployment/rollback-preview/{id}`。

## Q-08 首次发布不可回滚，那再发新版不又是首次发布吗？历史版本去哪里找

**提问**：v4 版本为首次发布，回滚提示「本次发布为首次发布，目标机上没有平台纳管的历史版本，无法回滚」。那么我再发新版提交到 git 仓库，项目拉取构建，那不是构建了新的 v5 产物？然后发布不是又是 v5 首次发布，压根没回滚版本可选？

**结论**：**不会。「首次发布」判定的是机器，不是版本号。** 它的条件是「该项目 + 该环境下，这台机器的历史部署里找不到任何一次真正成功过的部署」，而非「版本号是新的」。所以首次只会发生一次：

| 动作 | 机器上原有版本 | 这次部署的 `old_version` | 发布成功后 |
| --- | --- | --- | --- |
| 构建 + 发布 v4 | 无 | 空 → 首次发布 | 回滚按钮置灰 |
| 构建 + 发布 v5 | v4 | **v4** | 可回滚到 v4 |
| 构建 + 发布 v6 | v5 | **v5** | 可回滚到 v5 |

**回滚的参照物是部署记录自己的 `old_version` 快照，不是回滚时挑选**，因此可回滚的版本只有一个、也只有一层深度。`old_version` 在**创建部署那一刻**由 `resolveCurrentVersions` 推断并写进 `deployment_target`。

**会「又变回首次发布」的四种情况**（排查线索）：

1. 上一条部署记录被**删除**了——`Deployment` 继承 `BaseEntity`（`@TableLogic`），软删除后回溯链就断了；
2. 上一条部署**失败**了——状态不是 `SUCCESS`，不参与回溯；
3. 上一条该**目标被跳过**——目标状态不是 `SUCCESS`，同样不算；
4. **换了环境**——回溯按 `environmentId` 隔离，每个环境各自算第一次。

**另外两个容易误会的地方**：

- **回滚执行时产物不读目标机**：判定走 `historyArtifactAvailable` 反查 `release_record`（DOCKER 看 `image_tag`；JAR/STATIC 看 `build_server_id` + `artifact_path`），**明确不读目标机 `exec/bak`**。
- **回滚 ≠ 回到任意历史版本**：`canRollback` 只放行 `SUCCESS`，回滚后记录变 `ROLLED_BACK`，所以**同一条记录只能回滚一次**；要再退一层需找更早那条仍是「成功」的部署记录。想回到任意历史点则走**新建部署、手选旧版本重发**（历史版本永不置「已废弃」）。

**落点**：`DeploymentService.createAndTrigger` / `resolveCurrentVersions` / `inspectTargets` / `historyArtifactAvailable` / `evaluateRollback`；`DeploymentStatus.canRollback`；AGENTS §24.5。

**遗留**：无。

## Q-09 `exec/bak` 只有时间戳，平台宕机后手工回退怎么对上平台版本？平台自身怎么部署更新

### 第一问：手工回退如何准确识别版本

**提问**：如果平台宕机了，需要上服务器手工更新部署，失败了就按时间戳回退吗？`bak` 里怎么找到平台发布的准确的上个版本？

**结论**：先纠正一个前提——**`bak` 里的包不是「这次发的包」，而是「被换下去的那个包」**。`backupCurrentJar` 在 `mv` 覆盖**之前**先 `cp -p` 现有 jar 到 `exec/bak`，所以文件名里的时间戳是**执行替换的那一刻**，包的内容是**上个版本**。也就是说：**时间戳指向「替换它的那次发布」，不指向包里的版本。**

识别方式按可靠性排序：

1. **SHA256 比对（精确）**：`sha256sum {workdir}/{jar名} exec/bak/*.jar`，与平台 `release_record.sha256` 逐条对照。备份是 `cp -p` 的字节级复制，摘要必然一致；
2. **时间戳反查（便利）**：备份名时间戳 → 平台该时刻附近的部署记录 → 该记录的 `old_version`；
3. **`fallback.py --steps N`（应急）**：按 `mtime` 倒序退 N 步。因 `cp -p` 保留上传时的 mtime，mtime 序与发布序一致，`--steps 1` 恰好是上一个版本；但它**不知道版本号**，只能保证「退了一步」；
4. **DOCKER 最简单**：镜像 tag 就是版本号，本机残留旧镜像可直接 `docker run`，完全不依赖 `bak`。

**发现的三个缺口**（已在 Q-10 处理）：

- jar **未注入任何版本信息**，唯一带版本号的落点是构建机产物目录 `{artifact_base}/{项目编码}/{版本号}/`；
- `deploy.conf` 只记 `service_name` / `jar_name` / `work_dir`，**不记版本**；
- `ReleaseRecord.sha256` 的注释写了「部署前校验文件一致性」，但 `deployJar` **实际没有做校验**。

**另一个操作后果**：手工换包后**平台状态会与机器实际脱节**——`resolveCurrentVersions` 读的是数据库快照，下次发布算出的 `old_version` 会错。手工回退后应在平台**补一次「新建部署、重发对应版本」**对齐状态。

### 第二问：平台自身如何部署更新

**提问**：部署发布平台自身要怎么部署更新？用我之前的那个原始部署脚本服务器手动更新吗？

**结论**：**是的，目前平台自身没有任何自动化部署手段，只能服务器手工更新。** 仓库里**没有 Dockerfile、没有 docker-compose、没有任何 `.sh` 部署脚本**；`docs/轻量化部署发布平台设计方案.md` 里「平台自身可以使用 Docker Compose 部署，前端使用 Nginx 托管」**只是一句设计愿景，没有落地物**。

且 `src/main/resources/static/` 为空，**前端没有打进 jar**，所以平台是**两个交付物**：

| 组件 | 形态 | 运行时依赖 |
| --- | --- | --- |
| 后端 | Spring Boot jar，systemd 拉起，端口 `2027`，context-path `/deploy` | MySQL `deploy` 库（3306）、Redis（6379 库 0） |
| 前端 | `lighit-deploy-ui` 构建出 `dist`，Nginx 托管并把 `/deploy` 反代到 2027 | — |

三条可选路线：

- **A（推荐）复用平台内置的三件套**：`jar-init.py` / `jar-update.py` / `jar-fallback.py` 本来就是为应急手工发版设计的，直接拿它们管平台自己——先用 `jar-init.py` 把平台注册成 systemd 服务，之后更新用 `jar-update.py`、回退用 `jar-fallback.py`。**零新代码**，与平台内所有 JAR 项目统一运维口径。前端 `dist` 是纯静态，`rsync` 覆盖即可；要支持回退可用 `current` 软链接指向 `releases/{时间戳}/`。
- **B 补 Dockerfile + compose**：把设计愿景落地，环境一致性好，但要新增一套需要维护的工程物，建议作为后续升级；
- **C 自举（平台管自己）——不推荐**：平台重启自己会打断正在执行的任务；更根本的是**平台挂了的时候恰恰最需要它**，属循环依赖。

**铁律**：无论走哪条路线，**MySQL 结构升级必须手工执行**（如 `upgrade-release-version-seq.sql`）——平台的 JAR 部署链路只换包重启，没有执行 DDL 的能力。平台迭代的真实动作永远是「**手工执行升级 SQL → 更新后端 jar → 更新前端 dist**」。

**遗留**：路线 A/B 均未实施，属后续需求。

## Q-10 产物无版本标识、摘要算了不校验、`deploy.conf` 不记版本

**提问**：处理这三处缺口，然后把疑问与解释写进可追溯的文档。

**结论**：三处全部落地，且**版本标识一律用外部文件，不重写 jar 内部的 `MANIFEST.MF`**。

**为什么不注入 `MANIFEST`**：Spring Boot fat jar 的嵌套 jar 依赖 ZIP 的 STORED 布局，用 `jar --update` 重打包一旦改变压缩方式，会**静默产出「启动即失败」的产物**；而且重打包会改变 SHA256，与登记的产物摘要语义冲突。外部标识文件不改产物一个字节，且同时适用于 JAR 与 STATIC。

### 一、版本标识（`VERSION` + 备份名版本段）

同一份 `key=value` 文本落在**两处**，`version=` 行一律写**平台原始版本号**，与 `release_record.version` 同源；另有一个只有版本号、不带其它字段的落点——**备份文件名**：

| 位置 | 写入方 | 含义 |
| --- | --- | --- |
| `{build_artifact_dir}/{项目编码}/{版本号}/VERSION` | `BuildTaskHandler.writeArtifactVersionMarker` | 这份产物是哪个版本 |
| `{workdir}/VERSION` | `DeployTaskHandler.writeVersionMarker` | 这台机器上盘的 jar 是哪个版本 |
| `exec/bak/{jar名}_bak_{时间戳}_{版本号}.jar` | `DeployTaskHandler.backupCurrentJar` | 这个备份包里装的是哪个版本 |

> 第三处原先是 `exec/bak/{备份名}.version` 伴随文件，**Q-12 已改为把版本号内嵌进文件名**，伴随文件不再产生。

时序固定为「**jar 上盘 → 写标识 → 重启服务**」：标识必须与磁盘一致，写在重启之后会在重启失败时停在旧版本、与磁盘错位。写标识失败**只记 INFO 日志，不影响发布结论**。

### 二、产物完整性校验

`DeployTaskHandler.verifyJarDigest` 在**替换 jar 之后、重启服务之前**在目标机复核 `sha256sum`：

- 不一致时**先还原发布前的备份再抛异常**，不允许把损坏的包留在工作目录。只抛异常会让机器停在「服务跑着旧版本、磁盘放着坏包」的错位状态——下次重启必然起不来，而失败原因只写着校验失败，很难联想到磁盘；
- 还原动作本身失败**只记 ERROR 日志、不覆盖校验失败这个根因**；
- 摘要为空（历史版本）或目标机缺 `sha256sum` 时**跳过并写明原因**，不阻断发布；
- 校验**通过也写 INFO 日志**并带摘要值，让「检查确实执行过」可被追溯。

### 三、`deploy.conf` 记版本

`exec/deploy.conf` 增加 `version=` 行，表示**本机当前运行的版本**：首次初始化写空（此刻确实没有发布过任何版本），之后由**平台发布流程、`jar-update.py`、`jar-fallback.py` 三方刷新**，语义必须一致。`jar-init.py` 重复执行时**保留已登记的 version**，不重置。

脚本侧同步改造：`jar-update.py` 支持 `--version`、备份时把版本段写进备份名、更新后刷新 VERSION 与 conf；`jar-fallback.py` 从备份名读出版本打印版本对照。实测输出（命名格式见 Q-12 的后续调整）：

```text
将执行回滚: auth-7888-v5-1a2b3c4d -> auth-7888-v3-887b603c
已恢复: /lx/jarapps/auth-tool/exec/bak/auth-tool_bak_20260925211203v1.jar -> .../auth-tool.jar
服务已重启: auth-tool-7888
回滚完成: auth-tool.jar（版本 auth-7888-v3-887b603c）
```

**脚本禁止猜版本号**：来源固定为「`--version` 参数 > `exec/VERSION` > 空」，取不到就写空并提示——**记错版本比不记版本更危险**，而回退前的版本始终能从**备份文件名的版本段**找回（Q-12 起改为内嵌文件名，原先是从 `{备份名}.version` 伴随文件找回）。

**落点**：`BuildTaskHandler.writeArtifactVersionMarker`；`DeployTaskHandler.writeVersionMarker` / `verifyJarDigest` / `restorePreviousJar` / `refreshDeployConfVersion` / `backupCurrentJar`；三份脚本；AGENTS §23.5 / §24.5 / **§24.7** / §25。

### 适用范围与遗留

- 三项能力目前**只覆盖 JAR 运行时**。DOCKER 的版本就是镜像 tag，无需额外标识；**STATIC 直接覆盖 `static_root`，既无本地备份也无版本标识**，其回退完全依赖平台重发旧版本。若要支持静态站点的手工回退，需引入「按版本建目录 + `current` 软链接」方案，**属独立改造，本轮未做**；
- 早于本次改造产生的备份**名字里没有版本段**（改造过程中还短暂出现过 `{备份名}.version` 伴随文件这一中间态，见 Q-12），只能走 SHA256 比对或时间戳反查；
- 老旧目标机上已有的工作目录，`deploy.conf` 会在**下次发布时**由平台补上 `version=` 行；在此之前脚本读不到版本会显示「未登记」。

## Q-11 重新发布后 `exec/bak` 里仍无版本号、`ls` 时间还是旧的，为何仍需 SHA256

**提问**：重新发布后 `exec/bak` 里最新备份是 `auth-tool_bak_20260925213929v1.jar`，但 `ls -l` 显示的时间是 19:47 —— 不是说会加版本号吗？为什么这里还是需要 `sha256sum`？`sha256sum *.jar` 的用法文档里写了没有？

**结论**：这是**三条相互独立的原因**叠在一起，逐条对上。

### 一、平台后端没有重启，改动还没生效（本次现象的直接原因）

写 `{备份名}.version` 是**平台侧代码**（`DeployTaskHandler.backupCurrentJar`）的行为。改动只编译进了本地 `target/`，**运行中的平台仍是旧 jar**：它备份时只 `cp -p` jar，不写伴随文件，也不刷新 `deploy.conf` 的 `version=`。所以这几次发布产出的备份都不可能有 `.version`。**重启后端是这三项能力生效的前提**，重启前观察不到任何变化属预期。

### 二、已存在的历史备份永远不会补上版本信息

当时的方案是「备份时把 `{workdir}/VERSION` 复制成 `{备份名}.version` 伴随文件」，而伴随文件是**备份那一刻**从 `{workdir}/VERSION` 复制出来的，平台**不会事后回填**历史备份。所以已有的两个备份属于「改造前产生的备份」，识别它们**只能靠 SHA256 或时间戳反查**——这正是 SHA256 那条路径存在的意义。

> **后续变更（见 Q-12）**：伴随文件方案已被推翻，改为**把版本号内嵌进备份文件名**。本节第三节描述的现象在改名之后**依然成立**，只是表现形式从「少一个 `.version` 文件」变成「名字里少一段版本号」。

### 三、即使重启，下一次发布的备份仍不会有版本段（一次发布的预热期）

版本段取自「**被换下去那个包**」的标识，也就是 `{workdir}/VERSION`。而这台机器上 `{workdir}/VERSION` **此刻并不存在**（旧代码从未写过），因此重启后的**第一次**发布仍然取不到版本；这次发布结束时会写入 `VERSION`，**再下一次**发布的备份名字里才会带版本段。属预期行为，不是缺陷。

### 四、`ls -l` 看到的 19:47 不是备份时刻，是包当初被发布的时刻

`cp -p` 是**字节级复制且保留元数据**，备份文件的 `mtime` 沿用源 jar 的 `mtime`（源 jar 的 `mtime` 是上次发布上传时写的）。同一个备份里有两个时间，含义完全不同：

| 位置 | 含义 |
| --- | --- |
| 文件名里的 `20260925213929` | **备份时刻** = 替换动作发生的时刻 |
| `ls -l` 的 `Sep 25 19:47` | **包内版本的发布时刻** = 源 jar 被上传到工作目录的时刻 |

`auth-tool_bak_20260925213929v1.jar` 应读作「**21:39:29 做备份时，被换下去的那个包，是 19:47 那次发布投上去的**」。`ls -lt` 按 `mtime` 排序，得到的顺序与**版本序**一致（所以 `fallback.py --steps N` 是对的），但它**显示出来的日期不是备份时刻**；判断「哪个是最新备份」要看**文件名时间戳**。

### 五、为什么有了版本标识还要 SHA256

版本标识（当时是伴随文件，现在是备份名的版本段）是**辅助信息，载体是可写文件或文件名**——手工换包、改名、误删、脚本记错版本，都会让它与文件内容不符。脚本侧「禁止猜版本号」（AGENTS §25）说的就是这件事：**记错版本比不记版本更危险**。而 `sha256` 由构建机算出、登记在 `release_record.sha256`，是**唯一能证明「这段字节就是这个版本」的证据**。

因此口径固定：**日常识别看备份名版本段 / 时间戳；严肃确认（回退前、追责时）一律以 SHA256 为准。**

### 手工识别备份版本的完整操作

**方式零：直接看备份文件名（改造后最快，无需任何命令）**

```bash
ls -1 exec/bak
# auth-tool_bak_20260925222851_auth-7888-v6-c9bb25d3.jar
# auth-tool_bak_20260925213929v1.jar          ← 改造前的旧格式，名字里没有版本
```

**方式一：构建机产物目录（最直观，不用查库）**

```bash
# 在构建机上执行；目录名本身就是平台版本号
ls -1 {build_artifact_dir}/auth-tool-7888/

# 对每个版本的产物算摘要，与目标机的备份逐一配对
sha256sum {build_artifact_dir}/auth-tool-7888/*/auth-tool.jar
```

`{build_artifact_dir}` 是构建机档案里的「构建产物持久目录」（`build_server.build_artifact_dir`，`BuildTaskHandler` 启动前校验非空），产物落在 `{该目录}/{项目编码}/{版本号}/`，与 `release_record.artifact_path` 同源。

**方式二：查平台库，拿到「版本 ↔ 摘要」对照表**

```sql
SELECT version, version_seq, sha256, artifact_path, build_server_id, create_time
FROM release_record
WHERE project_id = '<项目ID>' AND runtime_type = 'JAR' AND is_deleted = 0
ORDER BY version_seq DESC
LIMIT 20;
```

**方式三：在目标机上直接比对**

```bash
cd /lx/jarapps/auth-tool-7888
ls -1 exec/bak                             # 改造后的备份名自带版本号
sha256sum auth-tool.jar exec/bak/*.jar     # 旧格式备份、或需要严肃确认时再算摘要
```

改造后的备份看名字即可；只有**旧格式备份**（名字里没有版本段）才必须拿摘要与方式一/方式二的结果对照。定位「上一个版本」：`ls -1 exec/bak | tail -1` 不成立——要按**文件名时间戳**取最大的那个，等价于 `fallback.py --steps 1` 挑中的那个（脚本已按文件名时间戳排序，不再依赖 `mtime`）。

**落点**：`DeployTaskHandler.backupCurrentJar`（把版本段写进备份名）；`AGENTS.md` §24.7（识别口径 + 时间戳语义 + 预热期）；`docs/发布模块.md` §6.3。

**遗留**：改造前的历史备份名里没有版本段；重启后第一次发布的名字里仍无版本段（预热期）。若要彻底消除预热期，可选做法是在备份前用本次部署的 `old_version` 快照「补种」`{workdir}/VERSION`——但这会让标识变成**平台推断值**而非**磁盘实测值**，与 §24.7「标识必须与磁盘一致」的口径冲突，**未做**，需另行评审。本条命名方案本身随后被 **Q-12** 推翻（伴随文件改为文件名版本段）。

## Q-12 备份名为什么不带版本号？为什么把 `.version` 挂在 `.jar` 后面

**提问**：不是就加个 `.version` 吗？**版本号呢？** 而且怎么可以在 `jar` 后面加东西——要隔开也应该是在时间戳后面加 `_版本号v` 这样的吧？`auth-7888-v7-1521739f → auth-7888-v6-c9bb25d3`，落到文件名上就是 `auth-tool_bak_2026092522285v6.jar` 这样，很难吗？

**结论**：诉求成立，改。**版本号内嵌进备份文件名，`{备份名}.version` 伴随文件删除。**

### 一、先纠正一个误读：`v1` 不是版本号

实测目录里三个备份都叫 `auth-tool_bak_...v1.jar`，很容易把结尾的 `v1` 读成「版本 1」。它其实是**防撞名序号**：备份命令先取 `date +%Y%m%d%H%M%S` 作时间戳，再用 `while [ -f ... ]` 探测同秒重名，从 1 开始往后加。三个文件全是 `v1`，恰恰说明**从没撞过名**。

这个命名是早期沿用 `jar_linux.py` 留下的，问题在于**同一个 `v` 前缀被用在两个完全不同的语义上**（版本号 / 防撞名序号），必然被误读。新命名把 `v` 的含义收敛到只剩平台版本号里的 `v{序号}`，防撞名序号改为纯数字后缀，且**只在真的撞名时才出现**。

### 二、新命名

| 形态 | 例子 | 何时出现 |
| --- | --- | --- |
| 标准 | `auth-tool_bak_20260925222851_auth-7888-v6-c9bb25d3.jar` | 正常发布 |
| 无版本段 | `auth-tool_bak_20260925222851.jar` | 工作目录还没有 `VERSION`（改造后首次发布，或手工投放未给版本） |
| 撞名后缀 | `..._auth-7888-v6-c9bb25d3_2.jar` | 同一秒内同版本重复备份，仅并发场景 |
| 旧格式 | `auth-tool_bak_20260925194718v1.jar` | 改造前产生，永久保留、脚本仍可识别 |

三条设计约束：**时间戳紧跟 `_bak_`**（字典序即时间序，`ls` 默认按名字排就是按时间排）；**版本段在时间戳之后**（先定位「什么时候备的」，再看「备的是哪个版本」）；**保留 `.jar` 结尾**（`*.jar` 通配与 `restore_name` 的还原规则都靠它）。

版本段取自目标机 `VERSION`（**磁盘事实**），不取平台库快照——库快照在手工换包后会失真。取不到就省略该段而不是猜：**记错版本比不记版本更危险**。写入文件名前清洗为 `[A-Za-z0-9._-]`，防止被改脏的 `VERSION` 带出 `/` 把备份写到别的目录。

### 三、为什么删掉 `{备份名}.version`

`auth-tool_bak_...v1.jar.version` 这种名字有三个毛病：**`ls` 看不见版本**（要 `cat` 才知道）；**要多养一个文件**（备份数翻倍，删除与同步都得成对处理）；**`.version` 挂在 `.jar` 后面看起来像包的后缀**。内嵌进文件名一次解决三条，且不损失信息——伴随文件里除 `version` 外的 `commit` / `runtime` / `deployed_at` 对 bak 目录没有判定价值（`deployed_at` 就是文件名时间戳，`runtime` 恒为 JAR）。

配套一并处理：`jar-update.py` 的手工投放旁车文件从 `exec/{jar名}.version` 改为 **`exec/VERSION`**——与构建机产物目录里的文件**同名同格式**，运维把产物连它的 `VERSION` 一起拷进 `exec/` 即可，**不用改名**；用完与 jar 一起删除，避免下次误用旧值。

### 四、脚本侧的兼容与行为变化

- `restore_name` 从 `_bak_\d{14}` 处截断到结尾 `.jar`，**新旧形态一并覆盖**，改造前产生的备份仍可被 `--steps` 退到；
- 新增 `version_from_name`：只认「`_bak_` + 14 位时间戳 + `_`」之后、末尾 `.jar` 之前那段，并剥掉撞名后缀——旧格式结尾的 `v1` 因此不会被误读成版本；
- `--steps` 排序改为按**文件名时间戳**（原先按 `mtime`）。`cp -p` 会把源 jar 的 `mtime` 带过来，`mtime` 的语义是「包当初被发布的时刻」而不是备份时刻；按文件名排序与「第几个备份」的语义严格一致；
- 回退到**没有版本段的旧格式备份**时，`VERSION` 与 `deploy.conf` 一并写空并提示用 `sha256sum` 比对——磁盘上确实是「未登记版本」，留着旧值反而与磁盘错位。

### 五、实测（`mvn compile` EXIT=0，脚本 `py_compile` 通过，端到端跑通）

```text

A2 无 VERSION        -> auth-tool_bak_20260925224111.jar
A3 VERSION 被改脏    -> auth-tool_bak_20260925224111_auth-7888-v9-....etcpasswdevil.jar（/ 被清洗，未逃出 bak）
A4 同秒同版本撞名    -> auth-tool_bak_20260925224111_auth-7888-v7-1521739f_2.jar
A5 首次投放（无 jar）-> none
B  jar-update.py     -> 备份 auth-tool_bak_..._auth-7888-v6-c9bb25d3.jar（旧版本），不再产生 .version；
                        VERSION 与 deploy.conf 更新为 v7，exec/ 下的 jar 与 VERSION 均被消费
C  --steps 1         -> 将执行回滚: auth-7888-v7-1521739f -> auth-7888-v5-abc12345
                        （事先把三份备份的 mtime 与文件名时间戳故意倒置，仍挑中最新那份，证明排序已切换）
   --steps 2         -> 将执行回滚: auth-7888-v5-abc12345 -> 未登记（旧格式，附 sha256sum 提示）
D  restore_name      -> 旧格式 `..._bak_20260925194718v1.jar` 与 `..._bak_20260104120000v1.jar` 均还原为 auth-tool.jar
```

**落点**：`DeployTaskHandler.backupCurrentJar`；`jar-update.py` 的 `safe_version` / `backup` / `main`；`jar-fallback.py` 的 `version_from_name` / `backup_order` / `restore_name`；AGENTS §3 / §24.7 / §25；`docs/发布模块.md` §6.3；`docs/项目模块.md`。

**遗留**：改造前的旧格式备份名里没有版本段，且**不改写历史文件名**，永久如此；版本段有一次发布的预热期（同 Q-11）。若要消除预热期，见 Q-11 遗留项——会让标识变成平台推断值，需另行评审。

## Q-13 备份名要不要统一下划线？日志弹窗为何锁关闭？回滚后列表版本为何还是新版本

**提问**：三个问题——① `auth-tool_bak_20260925235800_auth-7888-v7-1521739f.jar` 应该规范化、统一下划线；② 日志弹窗即使关掉，任务也一直在跑、日志也一直在加载，那就不要把运行中的弹窗锁住；③ 目标明细里的 `auth-7888-v7-1521739f → auth-7888-v8-13e04447` 看不出是什么意思，是当前版本还是下一个要更新到的版本？希望加悬浮说明；而且这条部署已经回滚了，列表里的版本却还是 `auth-7888-v8-13e04447`，是不是应该更新为当前版本？

**结论**：① 保持现状，**不转下划线**（版本段逐字保留平台版本号）；② 去掉运行中禁止关闭的限制，**任何时候都能关**；③ 目标明细统一改写成「当前 → 目标」并加 tooltip；列表的 `version` 是快照**不改写**，另加 `currentVersion` 让页面补一行「当前 xxx」。

### 一、备份名不转下划线

诉求是把文件名里混用的 `-` 与 `_` 统一成 `_`，即 `auth-tool_bak_20260925235800_auth_7888_v7_1521739f.jar`。**不做**，三条理由：

1. **版本段要能直接复制去查库**。`release_record.version`、Docker 镜像 tag、`VERSION` 文件里写的都是 `auth-7888-v7-1521739f`。文件名与它们字面一致时，运维的常规动作是 `SELECT ... WHERE version = '<粘贴>'` 或 `grep '<粘贴>' logs/info.log`，不用做任何字符转换；
2. **回译不是双射**。带 `-` 的版本号转成 `_` 之后，读回时只能按段把 `_` 换回 `-`。而**项目编码本身允许含 `_`**（`project.code` 是人工填写的字段），一旦编码里出现 `_`，`auth_my_db_1234_v7_abc12345` 就无法唯一还原。用一个隐式约定换一点视觉整齐，不划算；
3. **混用是有意为之，不是疏漏**。`_` 分隔备份名的**结构段**（`{jar名}_bak_{时间戳}_{版本号}.jar`），`-` 属于**版本号这个值本身**。把值里的字符也当分隔符处理，本质是让结构去改写数据。`auth-tool` 里的 `-` 更是 jar 自身文件名，`restore_name` 要靠它还原成 `auth-tool.jar`，更不能动。

已在 AGENTS §3 与 §24.7 各补一条：**版本段逐字保留平台版本号，不把其中的连字符换成下划线**。

### 二、日志弹窗不再锁关闭

原设计是「运行中锁死所有关闭入口」，四道一起做（`before-close` 兜底 + 隐藏 ✕ + 禁用 ESC + 页脚按钮同路）。实测确认这个前提**不成立**：

**日志轮询跑在浏览器里，任务跑在服务端执行器里**，两者互不依赖。关掉容器只停掉前端这段轮询，任务该跑多久还是跑多久、日志一条不少，重新打开会从服务端重新拉全量。锁住关闭换不来任何安全性，只会把用户困在弹窗里干等任务结束。

改动：

- `useTaskLogViewer` **删除 `beforeClose`** 并不再返回它；`running` 保留但**只用于页脚文案**，不再参与可关闭性判定；
- 5 处视图（任务列表 / 构建列表 / 发布列表 / 连通性测试 / 触发构建）删除 `:before-close`、`:show-close="!running"`、`:close-on-press-escape="!running"`，`closeLog()` 简化为直接置 `false`；
- 页脚文案由「任务执行中，完成后可关闭」改为「**任务执行中，关闭窗口不影响执行**」——把「能关且不影响」讲明白，而不是让人猜会不会打断发布；
- **`@closed`（drawer）/ `@close`（dialog）绑 `stop` 必须保留**：不拦关闭之后这条更容易被忽略，而漏掉它就是「窗口关了接口还在打」。

顺带清理了一处随之失效的逻辑：`pullLogs` 捕获异常时原本要「把状态退回未知并顺势解除关闭锁定」，现在只剩前半句——状态不可信时如实显示「未知」，已不存在需要解除的锁定。

### 三、目标明细的箭头方向 —— 根因是字段语义被复用

`deployment_target.old_version / new_version` 是**创建部署那一刻的快照**。回滚只在原记录上改状态（`rollback()` 里 `deployment.setStatus(ROLLING_BACK)`，`DeploymentService.java:429-432`），**两个版本字段原样不动**。于是同一个箭头在两处含义相反：

| 场景 | 字段实际内容 | 改动前显示 | 事实 |
| --- | --- | --- | --- |
| 发布 | old = v7（发布前），new = v8（发布后） | `v7 → v8` | v7 变成 v8 ✅ |
| 回滚 | old = v7（**回滚目标**），new = v8（**回滚前**） | `v7 → v8` | v8 退到 v7 ❌ **方向反了** |

日志里写的是「当前版本 v8 → 回滚到 v7」（执行器按场景正确输出），抽屉是拿两个字段按固定顺序拼的，于是两边对不上；而字段名 `oldVersion` / `newVersion` 不含角色信息，看的人只能猜「哪个是现在的」。

改法：**统一按「当前 → 目标」表述**——发布 = `old_version → new_version`，回滚 = `new_version → old_version`。这两种写法在任何场景下都自解释、方向永远与事实一致，比只加一句 tooltip 更彻底。悬浮说明再补两句：「当前＝发布前/回滚前机器上跑的版本，目标＝本次要发布的版本/要退回的历史版本」。回滚场景的判定只看主任务状态（5 回滚中 / 6 已回滚），与回滚预览接口里 `currentVersion` / `targetVersion` 的取法同源。

### 四、回滚后列表的版本列

诉求成立，但**不能改写 `version` 字段**。它来自 `release_id`，回答的是「这次动作针对哪个发布版本」；回滚动作本身不产生新的 `release_record`，所以这条记录的 `version` 只能是 v8。直接改成 v7 会与发布日志、产物路径、`release_record` 全部对不上，也让「版本」这一列在不同行之间语义不一致。

正确做法是**补充**而不是覆盖：

- `DeploymentVo` 新增 `currentVersion`，由 `DeploymentService.resolveCurrentVersion` 在 `toVo` 里用**已加载的目标列表**算出（**零额外查询**）：发布成功取各目标的 `new_version`，已回滚取 `old_version`（回滚就是把机器退回老版本）；
- **只有全部成功目标一致时才返回值**，多目标不一致（部分回滚、部分首次发布）时返回 null、页面不显示——一个版本号被当成「所有机器都是它」比不显示更糟，逐台真实版本到目标明细看；
- 列表版本列在**已回滚**时于版本号下方补一行「当前 xxx」（警示色），tooltip 写明「本次发布版本 X；机器当前实际运行 Y」。其他状态不补：要么 `version` 就是当前版本，要么还没有确定结论。

**落点**：`DeploymentVo.currentVersion`；`DeploymentService.resolveCurrentVersion` 与 `toVo`；前端 `api/deployTypes.ts`、`views/deploy/index.vue`（列表版本列 + 目标明细版本变化列）、`composables/useTaskLogViewer.ts` 及另 4 处日志视图；AGENTS §3 / §20.9 / §24.5 / §24.7；`docs/发布模块.md` §5 / §6.3 / §6.5。

**遗留**：容器不再拦截关闭后，关闭即停轮询，因此**任务在后台结束时列表不会自动刷新**（`onFinished` 只在轮询中触发）。这属于既有的主动行为——用户关掉容器就等于放弃实时跟踪，重新打开或切页都会重新拉取，未做额外补偿。

## Q-14 凭据里的「Git 令牌」到底是密码还是什么？三个平台在哪设置？私有仓库克隆为何报 `could not read Password`

**提问**：

1. `CredentialDto.credential` 写的是「明文凭据内容（Git 令牌 / 私钥 / 仓库密码）」，那这个**令牌是账号密码吗**？`SSH_PASSWORD` / `SSH_KEY` / `GIT_TOKEN` / `REGISTRY` 四类各填什么，能给示例吗？
2. 仓库改成私有后构建失败：

```text
[拉取代码] 执行克隆：git clone --branch master https://***@gitee.com/wangan2022/auth-system-Iteration.git ...
[拉取代码] fatal: could not read Password for 'https://***@gitee.com': No such device or address
```

**结论**：

### 一、令牌不是登录密码，而是「当密码用的一次性凭据」

`GIT_TOKEN` 装的是代码平台签发的**私人访问令牌（Personal Access Token）**，与账号登录密码是两个东西。Gitee 早已拒绝用账号密码做 HTTPS 克隆，两者在 URL 里的**位置也不同**：账号密码是「用户名 + 密码」两段，令牌是**填在密码那一段**、用户名那一段可以是 `oauth2` 也可以是真实用户名。所以枚举里「HTTPS 形式仓库地址的用户名 + 访问令牌」指的就是 `用户名:令牌`。

四类凭据的完整填写口径与示例已落到 `docs/凭据模块.md` §6.6，摘要：

| 类型 | 明文内容 | 示例 | 谁在读 |
| --- | --- | --- | --- |
| `GIT_TOKEN` | `用户名:令牌`，或只填令牌 | `wangan2022:a1b2c3...` | `buildCloneCommand` 拼进 HTTPS 地址 |
| `SSH_KEY` | **完整 PEM 私钥**（含首尾标识行、保留换行） | `-----BEGIN OPENSSH PRIVATE KEY-----…` | 写构建机临时文件，`GIT_SSH_COMMAND` 引用 |
| `REGISTRY` | `用户名:密码`（按**第一个**冒号切分） | `light-deploy:Abc123456` | `docker login -u … -p …` |
| `SSH_PASSWORD` | 不填 | —— | **没人读**，服务器 SSH 密码在「服务器管理」里维护 |

### 二、失败根因：拼出的 URL 缺了密码段

`buildCloneCommand` 的 GIT_TOKEN 分支生成的是：

```java
"https://" + plaintext + "@" + gitUrl.substring("https://".length())
// → https://<令牌>@gitee.com/wangan2022/auth-system-Iteration.git
```

令牌被放在了**用户名位**，URL 里**没有冒号、没有密码段**。git 看到「给了用户名却没给密码」，就转去交互式索要密码；构建机上的克隆跑在 SSH 通道里、没有终端，于是直接报 `No such device or address`。

**关键点：这个报错发生在 git 客户端层面，还没走到 Gitee 鉴权**——所以和令牌是否正确、权限是否勾选**毫无关系**，纯粹是 URL 形态问题。（对照：`https://<PAT>@github.com` 在 GitHub 上可用，Gitee 不认；Gitee 官方形式是 `https://oauth2:<令牌>@gitee.com/...` 或 `https://<用户名>:<令牌>@gitee.com/...`。）

**顺带一个教训**：日志里显示的是 `https://***@gitee.com`，脱敏正则 `https://[^@/]+@` 把整段 userinfo 替换成了 `***`，**连「有没有冒号」这个决定性特征一起抹掉了**。脱敏应当遮蔽**值**、保留**结构**，否则排查时看到的是一段看不出对错的地址。

### 三、修法（已实施）

**先说结论：三个平台统一补 `oauth2` 占位即可。** 依据是三家的官方口径一致——**URL 的用户名位不参与认证，但不允许为空**：GitLab 官方明确「任意非空字符串（GitLab 不会校验该值）」并直接示例 `oauth2:`；GitHub 官方明确「虽然要求输入用户名，但用户名不用于认证，实际用令牌认证；不输入用户名会报凭据无效」；Gitee 用 `oauth2`。所以「只填令牌」这种最自然的填法在三家都能成立。

改动落在 `BuildTaskHandler`，四处：

1. **`buildTokenUrl`（新增）**：明文含 `:` → 原样作 userinfo（兼容必须用真实用户名的平台或自建 Git 服务）；不含 `:` → 补 `oauth2:`，把令牌落到密码位。同时剥离用户误粘贴的 `https://` 前缀与结尾 `@`（否则会拼出 `https://https://`），并先剔除仓库地址里可能已有的 userinfo，避免两段用户名叠加。
2. **协议双向校验**：原来只校验了 `GIT_TOKEN` 必须是 HTTPS 地址；现补上 `SSH_KEY` 必须是 SSH 形式（`git@主机:组/仓库.git`），配成 HTTPS 地址直接报「仅适用于 SSH 协议仓库」。此前这类配错要到克隆时才炸，错误信息还是「仓库不存在」，排查成本高。
3. **`GIT_TERMINAL_PROMPT=0`（新增）**：三种鉴权形态（令牌 / 私钥 / 无凭据）的命令前统一加。非交互会话里 git 一旦转去索要凭据，就会给出 `could not read Password ... No such device or address` 这种把真实原因掩盖成「认证失败」的报错；禁掉提示后直接以 `terminal prompts disabled` 失败，指向真正的问题。这正是本次故障排查被带偏的直接原因。
4. **`resetRemoteUrl`（新增）**：`git clone https://oauth2:令牌@…` 会把**含明文令牌的完整地址**写进工作区的 `.git/config`（`remote.origin.url`），克隆成功后立即 `git remote set-url origin <不带凭据的地址>` 复位。为此把 `buildCloneCommand` 的返回值从 `String` 改为内部 record `CloneCommand(command, cleanUrl)`，`cleanUrl` 为 null 表示无需复位（SSH 协议与公开仓库，凭据本来就不进 URL）。复位失败只记 INFO，不影响构建结论。

**脱敏无需改动**：`maskSecret` 的 `https://[^@/]+@` → `https://***@` 里的 `[^@/]` 包含冒号，`oauth2:令牌@` 仍会被整体替换，令牌不会进日志。

### 四、三个平台的凭据分别是什么、在平台侧怎么设置

对照表已落到 `docs/凭据模块.md` §6.7（访问令牌与 Git 私钥各一张表：平台叫法 / 设置入口 / 需要的权限或只读读写 / 地址形态）。三条最容易踩的：

- **令牌只在生成时显示一次**，关掉页面就查不回来了，必须当场复制；Gitee 开启双因素认证后 HTTPS 推拉只能用私人令牌，账号密码直接失效——这通常就是「私有仓库忽然拉不动」的起因。
- **私钥与公钥不能搞反**：填进平台凭据的是 `ssh-keygen` 生成的**私钥**文件（`~/.ssh/ld_deploy`，无后缀那个）的完整内容，上传到代码平台的是**公钥**（`.pub`）；私钥必须含 `-----BEGIN` / `-----END` 两行、换行原样保留，且**不能带 passphrase**（克隆过程没有输入口令的环节）。
- **优先用「部署公钥 / Deploy key」而不是账号级公钥**：前者只对单个仓库生效、默认只读，泄露影响面最小；本项目只拉代码不推送，只读够用。三家都支持，语义一致。

**选型**：能配 SSH 就优先 `SSH_KEY` + 部署公钥（凭据不进 URL、不落 `.git/config`、单仓库只读）；HTTPS 是唯一出网通道时才用 `GIT_TOKEN`。

**落点**：`BuildTaskHandler.buildCloneCommand` / `buildTokenUrl` / `stripUserInfo` / `resetRemoteUrl` / `CloneCommand`；`lighit-deploy-ui/src/constants/credentialType.ts` 与 `views/credential/index.vue`（表单提示按类型给填写形态）；`docs/凭据模块.md` §3 / §6.6 / §6.7；`AGENTS.md` §7.1。

**验证**：后端 `./mvnw -q -o compile` EXIT=0；前端 typecheck / build 通过。

**遗留**：**尚未在真实构建机上用私有仓库跑通端到端**——本次改动只覆盖私有仓库路径，公开仓库路径不受影响因而无从验证。另：凭据管理页只有「填了什么类型」的静态提示，没有「测试连接」按钮，令牌填错仍要到构建时才发现，属后续演进项。

## Q-15 构建时才暴雷，能不能在构建前先测一遍？

### 一、提问

> 项目管理新增一个连通性测试，保证可以访问和拉取到 Git 仓库和镜像仓库，避免在构建的时候暴雷。

追问三个必须由使用方拍板的点：**测试跑在哪台机器上**、**构建机怎么确定**、**校验强度做到哪一档**。

### 二、结论

**跑在项目的构建机上，不在平台本机。** 这是三个问题里最关键的一个，理由不是「构建机更接近真实」这种感觉，
而是两条硬事实：平台所在机器常常**根本没装 git / docker**，而 `ls-remote` / `docker login` 恰好需要它们；
即便装了，平台机器的**网络策略通常与构建机不同**（构建机往往才配了出网代理或内网仓库白名单）。
在这两点都不成立的环境里测出的「通」，说明不了构建能否成功——那还不如不测。

**构建机由项目档案绑定**（`project.build_server_id`，选填），不是每次弹窗选。
理由是「在哪台机器上构建」本身就是项目属性，选一次就够；顺带两个好处：新建构建时默认带出该机器，
以及测试与构建天然是同一台机器，测出来的结论才对得上。

**校验强度取标准档**：`git ls-remote` + `docker login`，不做真克隆。
`ls-remote` 走的是完整网络 + 认证链路（令牌同样落在 URL 密码位、私钥同样走 `GIT_SSH_COMMAND`），
但不下载对象、不占磁盘、秒级返回；真克隆（`--depth 1`）在大仓库上要几十秒到几分钟、还占构建机磁盘，
换来的只是「再多验证一次对象传输」，收益远小于代价。

### 三、为什么必须抽公共工具类

原来 `buildTokenUrl` / `stripUserInfo` / `maskSecret` / `parseUserPassword` 都是 `BuildTaskHandler`
的**私有方法**。测试处理器要做完全相同的事，最省事的做法是复制一份——**这是本次明确要避免的**。

两份实现一定会在「谁该补 `oauth2`」「密码怎么传给 docker」这类细节上分叉，
而分叉的表现是最难查的一类问题：**测试通过、构建失败**（或反过来）。
排查时两边日志看起来都合理，只有逐字符比对命令才看得出差别。
因此把它们提到 `com.lx.deploy.common.util`：

| 工具类 | 收敛的内容 |
| --- | --- |
| `GitAuthSupport` | 令牌 URL 拼装（`oauth2` 占位）、userinfo 剥离、协议判定、`GIT_TERMINAL_PROMPT=0` 前缀、`GIT_SSH_COMMAND` 前缀 |
| `RegistryAuthSupport` | `用户名:密码` 按第一个冒号切分、`docker login --password-stdin`、`docker logout` |
| `SecretMasker` | 命令行密码参数与 URL userinfo 的脱敏 |

顺带把构建链路里的 `docker login -p <密码>` 一并改成 `--password-stdin`——原写法会把明文密码留在构建机
`ps -ef` 里，同机其他用户可见。这是抽公共类时发现的既有问题，不是新需求。

### 四、两个容易被忽略的判定细节

1. **分支不存在时 `git ls-remote --heads <url> <branch>` 会成功返回且输出为空。**
   只看退出码会漏掉「分支名写错」——这恰恰是构建失败最常见的起因之一。必须同时判空输出。
2. **`docker login` 会写同机 `~/.docker/config.json`。** 测试期登录、退出前若有构建正在推送，
   两者会互相登出。因此互斥键取 `build-server:{serverId}`（与 BUILD 同键）强制串行，
   而不是各用各的项目级键。

### 五、落点与验证

**落点**：新增 `TaskType.PROJECT_TEST` 与 `ProjectConnectTestTaskHandler`；
`ProjectService.submitConnectivityTest`（校验项目启用 / 构建机已绑定 / 防重复提交）；
`POST /project/test/{id}`；`Project` / `ProjectDto` / `ProjectVo` 加 `buildServerId`（VO 批量回填
`buildServerName`，避免 N+1）；`BuildService` 构建机解析改为「请求 > 项目档案 > 系统默认」；
前端项目列表加「连通性测试」按钮与日志抽屉（与构建对话框**各用一份** `useTaskLogViewer` 实例，
避免两个容器同时挂载时 `bodyRef` 与 `logs` 串台）、列表与详情展示构建机、编辑页加构建机下拉。

**DDL**：`src/main/resources/db/upgrade-project-build-server.sql`（`project.build_server_id` 一列 + 索引，
`schema.sql` 同步）。`lds_task.task_type` 是字符串列，**新增任务类型不需要改表**。

**验证**：后端 `./mvnw -o -q compile` EXIT=0；前端 `vue-tsc --noEmit` 0 错误、`vite build` 成功且新接口
`/project/test` 已进产物。

**遗留**：与 Q-14 同源——**尚未在真实构建机上跑通**（待手工执行升级 SQL 并重启后端后验证）。
另：镜像仓库只验证「能否登录」，不验证「能否向该命名空间推送」（推送权限不足要到 `docker push` 才暴露）；
要做需在测试里多推一个临时镜像，代价与收益待评估。
