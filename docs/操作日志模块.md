# 操作日志模块

> 模块包名：`com.lx.deploy.audit`（切面与注解另含 `com.lx.deploy.common.aop`、`com.lx.deploy.common.annotation`）
> 对应数据表：`audit_log`
> 当前状态：已完成并编译通过（后端 + 前端 typecheck 通过），需手工执行升级 SQL 后生效

## 1. 模块定位

操作日志回答一个具体的追溯问题：**谁在什么时候、通过哪个接口、做了什么，成功还是失败。**

它不参与任何业务流程，是一条纯粹的旁路：

```text
Controller 方法（标注 @OperLog）
        │
        ▼
OperLogAspect 切面（@Around：取上下文 → 执行 → 记账 → 落库）
        │
        ▼
audit_log（只追加，页面只读）
```

直接动因是一次真实排查：部署目标（`project_environment_target`）的 `environment_id` 是可改的，
改完不会刷新 `create_time`，于是「发布当时属于同一环境、事后被改到另一个环境」这种变更
在页面上完全看不出来，只能靠猜。没有留痕，任何「配置被谁改过」的问题都只能靠 `update_time`
反推，而 `update_time` 回答不了「改的是哪个字段、从什么改成什么」。

与相邻能力的分工：

| 能力 | 回答什么 | 载体 |
| --- | --- | --- |
| 访问日志 `RequestTraceFilter` | 有没有请求进来、耗时多少、状态码 | 日志文件 |
| 任务日志 `lds_task_log` | 一次构建 / 发布内部执行了哪些命令 | 数据库 + 前端日志抽屉 |
| **操作日志 `audit_log`** | **谁触发了写操作、参数是什么、成没成** | 数据库 + 操作日志页面 |

## 2. 数据表结构

### 2.1 audit_log

| 列 | 说明 |
| --- | --- |
| trace_id | 请求追踪 ID，与响应头 `X-Request-Id`、日志 `%X{requestId}` 同一个值 |
| application | 应用系统名称，来自配置 `light-deploy.application-name`，由切面统一写入（§6.9） |
| operator_id / operator_name | 操作者，来自请求头 `X-Operator-Id` / `X-Operator-Name`，缺省 `system` |
| title | 操作模块，来自 `@OperLog` 注解，如「部署目标」 |
| action | 操作类型编码，取值见 `BusinessType`（复用早期「操作动作」列，不新增重叠列） |
| resource_type / resource_id | 资源类型与主键，有值表示本次采集了字段级变更明细 |
| changed_fields | 字段级变更明细 `[{field, oldValue, newValue}]`，无变更或未声明资源类型时为 NULL |
| method | 被切的方法，格式「类全名#方法名」 |
| request_method / request_uri | HTTP 方法与请求地址（**不含查询串**） |
| oper_ip / os / browser | 客户端信息，IP 优先取 `X-Forwarded-For` 首段 |
| request_body | 请求参数 JSON，敏感键已替换为 `***` |
| json_result | 返回结果 JSON，超长截断 |
| result | 0 失败 / 1 成功 |
| error_message | 失败原因，成功时为空 |
| cost_time | 耗时（毫秒） |

- 升级脚本（幂等）：`src/main/resources/db/upgrade-audit-log-operation.sql`（操作字段）、
  `upgrade-audit-log-application.sql`（`application` 列 + 历史回填）
- 只读校验脚本：`src/main/resources/db/verify-audit-log-operation.sql`
- 字符集统一 `utf8mb4_unicode_ci`（AGENTS.md §4.2），早期参考脚本里的 `utf8mb3` 不采用。

### 2.2 为什么不新建 `sys_oper_log`

`schema.sql` 里早已有 `audit_log`（操作人 / 动作 / 资源 / 请求地址 / 结果），只是没有任何
Java 代码写入。另起一张 `sys_oper_log` 会让「审计」这个概念在平台里有两套模型：
查询要 union、前端要选表、后续归档要对齐两份。做法是**扩展既有表**：补列为切面所用，
`action` 承载操作类型编码，`request_body` 承载脱敏参数。

## 5. 接口清单

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/auditLog/page` | 条件分页查询，默认按操作时间倒序 |
| GET | `/auditLog/detail/{id}` | 单条详情，含请求参数与返回结果 |

**没有新增 / 修改 / 删除接口**：审计记录被改写就不再是审计，与其靠约定禁止，
不如让接口层根本没有入口。

查询条件里操作人、操作模块走**模糊匹配**（检索时用户通常只记得片段），
类型、请求方式、结果走**等值匹配**（固定取值 + 下拉筛选）。

## 6. 核心业务规则与代码逻辑

### 6.1 用 `@Around` 而不是两个通知

```java
@Around("@annotation(com.lx.deploy.common.annotation.OperLog)")
public Object recordOperation(ProceedingJoinPoint joinPoint) throws Throwable {
    Method targetMethod = AopUtils.getMostSpecificMethod(signature.getMethod(), joinPoint.getTarget().getClass());
    OperLog operLog = AnnotatedElementUtils.findMergedAnnotation(targetMethod, OperLog.class);
    ...
    try {
        Object result = joinPoint.proceed();
        audit.setResult(AuditResult.SUCCESS);
        ...
        return result;
    } catch (Throwable ex) {
        audit.setResult(AuditResult.FAILURE);
        audit.setErrorMessage(truncate(SecretMasker.maskSecret(ex.getMessage()), MAX_ERROR_LENGTH));
        throw ex;
    } finally {
        audit.setCostTime(...);
        saveQuietly(audit);
    }
}
```

耗时与成败需要同一份状态，拆成 `@AfterReturning` + `@AfterThrowing` 就得靠 ThreadLocal 传递，
异常路径更容易漏写。取注解用 `AopUtils.getMostSpecificMethod`：CGLIB 代理下
`signature.getMethod()` 可能拿到代理类上的方法，直接读注解会读不到。

### 6.2 落库失败只记日志，绝不抛异常

```java
private void saveQuietly(AuditLog audit) {
    try {
        auditLogService.save(audit);
    } catch (Exception ex) {
        log.error("写入操作日志失败，title={}，method={}", audit.getTitle(), audit.getMethod(), ex);
    }
}
```

审计是旁路能力：写不进去最多是「这次操作没留痕」，绝不能反过来让操作本身失败。
但静默吞掉同样不行（AGENTS.md §14.3），因此记 ERROR 并保留堆栈，让「日志没写进去」这件事自己可见。

### 6.3 脱敏只有一份实现

请求参数走 `SecretMasker.maskJsonFields`：先把 JSON 解析成树再递归替换敏感键的值，
而不是正则替换文本——键名可能出现在任意层级（数组元素、嵌套的 `runtime_config_json`）。
解析失败时退回正则兜底，**绝不返回原文**（那等于脱敏被静默跳过）。

敏感键清单与代码生成器排除敏感查询字段的清单一致：
`password` / `credential` / `secret` / `token` / `privateKey` / `encrypted`，
用「包含」而非「等于」判定：实际字段形如 `sshPassword`、`registryToken`，逐个枚举会漏。

参数整体就是凭据的接口（新建/修改服务器、保存凭据）显式声明 `recordParam = false`：
脱敏是兜底，不是把明文收进数据库的理由。

### 6.4 只记 URI，不记查询串

```java
audit.setRequestUri(request == null ? null : request.getRequestURI());
```

与访问日志 `RequestTraceFilter` 的口径一致：查询串可能携带凭据与业务敏感参数。

### 6.5 操作人与 IP 的来源

- 操作人：请求头 `X-Operator-Id` / `X-Operator-Name`，前端 axios 拦截器统一带出（取自登录信息），
  取不到记 `system`。过渡期没有登录态（AGENTS.md §16），接入统一权限中心后改为认证信息填充，
  切面读取逻辑不变；
- IP：优先 `X-Forwarded-For` 首段。平台前端经 Nginx 反代，直接取 `getRemoteAddr()`
  拿到的永远是网关地址，日志里会变成「所有人同一个 IP」。

### 6.6 已标注的操作范围

| 模块 | 标注的方法 |
| --- | --- |
| 服务器管理 | create / update（`recordParam = false`）/ test（EXECUTE）/ delete |
| 凭据管理 | create / update（`recordParam = false`）/ delete |
| 项目管理 | create / update / test（EXECUTE）/ delete |
| 环境管理 | create / update / delete |
| 部署目标 | create / update / delete |
| 镜像仓库 | create / update / delete |
| 构建管理 | create（EXECUTE）/ update / delete |
| 发布管理 | create（EXECUTE）/ update / rollback（ROLLBACK）/ cancel（CANCEL）/ delete |

任务模块（`task` / `taskLog`）未标注：任务由服务内部创建，其 Controller 的 CRUD 是生成产物、
页面不调用，标注只会给「内部动作」伪造一个人工操作者。

其中 **update / delete 额外声明 `resourceType`**（server / projectEnvironmentTarget / credential /
project / environment / registry / deployment / build），用于采集字段级变更明细；
insert 不声明——新增没有旧值可比，比出来只会是满屏「- → 新值」的噪音。

### 6.7 字段级变更明细

「把这行数据给我看一下」不足以回答事故复盘，运维真正要问的是「**环境是不是被从 vm-prod 改成了 lx-prod**」。
`changed_fields` 就是回答这个问题的部分，由 `ResourceDiffRecorder` 采集：

```java
// 前置快照必须在 proceed 之前取：方法一旦执行，旧值就被覆盖了
JsonNode before = resourceDiffRecorder.snapshot(resourceType, resourceId);
try {
    Object result = joinPoint.proceed();
    if (before != null) {
        audit.setChangedFields(resourceDiffRecorder.captureDiff(before,
                resourceDiffRecorder.snapshot(resourceType, resourceId)));
    }
    ...
}
```

**四条设计取舍**：

1. **放在切面层而不是 Service 上报**。前置快照天然要在业务方法之前取，环绕通知正好有这个时机；
   改成 Service 内部上报，每个 update 方法都要多两行，漏一处就永久少一个模块的明细。
2. **Mapper 索引按名字建立而不是按类型注入一堆 Mapper**。用
   `applicationContext.getBeansOfType(BaseMapper.class)` 扫描，bean 名去掉 `Mapper` 后缀即为资源类型
   （`serverMapper` → `server`），新增模块无需改动 `ResourceDiffRecorder`。
   这里刻意不走构造器注入 `Map<String, BaseMapper<?>>`：那要依赖容器对泛型通配符的可赋值判定，
   判定失败就是启动崩溃——同类风险已踩过一次（见 §6.8）。索引首次使用时才构建，
   避免启动期强制实例化全部 Mapper。
3. **三种情形分别处理**：两侧都有值则逐字段比对，只留真正变化的；变更后查不到（删除，含逻辑删除导致
   `selectById` 落空）则把旧值全部列为「→ (已删除)」；变更前查不到则按「- → 新值」输出。
4. **排除两类字段**：基础字段（`id` / `createTime` / `updateTime` / `isDeleted`）——`update_time`
   每次必变却毫无业务含义，列进去只会淹没真变更；敏感字段（凭据、私钥、令牌等）按
   `SecretMasker.isSensitiveKey` 跳过，与请求参数脱敏共用同一套判定，避免「参数脱敏了、明细里却留原文」。
   `ciphertext` 单独排除：它是 AES-GCM 密文不构成明文泄漏，但每次重加密整段变化，
   展示出来既不可读也会挤掉真正的变更。

明细是**展示值而非原始类型**：数字、枚举、嵌套 JSON 统一转文本后才能在页面上同表展示。
前端 `src/constants/auditLog.ts` 的 `fieldLabel()` 负责字段名中文映射（三级回落：
资源级翻译 → 通用翻译 → 原字段名），翻译命中时附上原字段名，便于对照文档与检索日志。

### 6.8 不注入 Spring 管理的 ObjectMapper

切面与 `SecretMasker` 都用自己的静态 Jackson 实例，不注入容器里的那个：

- **技术上**：Spring Boot 4 起容器只自动配置 Jackson 3（`tools.jackson.databind.ObjectMapper`），
  按惯例注入 Jackson 2 的 `com.fasterxml.jackson.databind.ObjectMapper` 会直接让上下文启动失败
  （`UnsatisfiedDependencyException: No qualifying bean`）；
- **更重要的是**：审计文本不该跟随业务序列化器的全局配置变动——命名策略、日期格式一旦被业务调整，
  历史日志的可读性就跟着变。

`SecretMasker` 对外提供 `toJson` / `toTree` / `parseTree` / `isSensitiveKey`，
「序列化 + 脱敏 + 变更比对」因此共用同一个 mapper，不会出现两边结构判定不一致。

**该静态实例必须注册 `JavaTimeModule`**（`com.fasterxml.jackson.datatype:jackson-datatype-jsr310`）：
Jackson 2.21 起 `java.time` 类型默认要求显式处理器，未注册时序列化 `LocalDateTime` 直接抛
`InvalidDefinitionException`，而这个异常被 `toJson` / `toTree` 吞成 null，表现是**双重静默丢数据**——
`json_result` 全空（统一响应 `ApiResponse.timestamp` 是 `LocalDateTime`）、
`changed_fields` 永远采不到（实体基类 `BaseEntity` 自带 `create_time` / `update_time`）。
两者都不报错，只会「少了东西」，排查入口见 §6.10。

### 6.9 应用系统字段走配置，不走注解

`audit_log.application` 由配置 `light-deploy.application-name` 提供（默认「轻量部署发布系统」），
`OperLogAspect` 构造注入后在写日志时统一填充，`AuditLogVo` 原样透传给页面：

- **不在 `@OperLog` 上写系统名**：它是实例级事实，同一平台里所有接口取值必然相同。
  28 个接口各写一遍意味着改名要改 28 处，且必然漏——漏改的表现是同一张表里出现两种系统名，
  比字段缺失更难解释；
- **改名只改配置一行**：历史记录不受影响（历史 NULL 行由 `upgrade-audit-log-application.sql`
  回填一次，回填的是脚本里的字面量）；
- **该列不加索引**：取值高度重复（通常只有一种），索引只会增加写入成本；
- 页面只在详情页「基本信息」展示，列表不加列——所有行同值，列出来只是噪音。

### 6.10 排查「响应 JSON 为空」

现象：接口明明有返回，操作日志详情的「返回结果」却是空的；严重时变更明细也一并为空。
按以下顺序确认：

1. 看 `verify-audit-log-operation.sql` 结果集 4 的「返回结果」列与结果集 6 的空值占比，
   确认是全部为空还是个别为空（个别为空通常是 `recordResult = false` 的正常表现）；
2. 全部为空且变更明细也为空 → 基本就是 `java.time` 序列化失败（§6.8），
   确认 `SecretMasker` 的静态 mapper 注册了 `JavaTimeModule`；
3. 服务日志里搜 `操作日志序列化对象失败` 与 `资源快照序列化失败`，这两条 WARN 是唯一的直接线索
   ——异常被吞成 null 后不会冒泡，只有这两处会留下痕迹（AGENTS.md §14.3）。

### 6.11 数据访问：`AuditLogMapper` 从哪里注入

`AuditLogService` 里看不到 `AuditLogMapper` 的注入痕迹——它不在本类，而在 MyBatis-Plus 的父类字段上：

```
AuditLogService
  └─ com.baomidou.mybatisplus.spring.service.impl.ServiceImpl<M extends BaseMapper<T>, T>
       └─ com.baomidou.mybatisplus.spring.repository.CrudRepository<M, T>   ← @Autowired protected M baseMapper
            └─ com.baomidou.mybatisplus.extension.repository.AbstractRepository<M, T>
```

- **注入方式**：`CrudRepository` 声明了 `@Autowired protected M baseMapper;`（可用 `javap -v` 反编译
  `mybatis-plus-spring` jar 实证）。Spring 靠 `ResolvableType` 解析继承来的泛型实参
  `M = AuditLogMapper`，把对应 bean 注入该字段，因此子类无需任何注入代码；
- **bean 来源**：启动类 `@MapperScan("com.lx.deploy.**.mapper")` 把接口注册为 `MapperFactoryBean` 代理，
  bean 名为首字母小写（`auditLogMapper`）；
- **调用路径**：Service 里的 `page(...)` / `getById(...)` / `save(...)` 都是继承来的默认方法，
  落到 `baseMapper.selectPage` / `selectById` / `insert`；分页靠 `config/MybatisPlusConfig`
  的 `PaginationInnerInterceptor(DbType.MYSQL)`。本表无自定义 SQL，因此 `AuditLogMapper` 是空接口；
- **写入侧**：切面 `OperLogAspect` 调 `auditLogService.save(audit)`，同样是继承来的 `save`；
- **两个坑**：① MP 3.5.17 的 `ServiceImpl` 在 `...mybatisplus.spring.service.impl` 包，
  旧资料里的 `extension.service.impl` 已不存在；② 注入失败不会启动报错，而是首次调用时抛
  `baseMapper can not be null`。

## 7. 与其他模块的关系

- **所有写操作 Controller**：声明 `@OperLog`，不感知切面实现；
- **发布模块**：新建部署 / 回滚 / 取消是追溯价值最高的三类操作，全部标注；
- **部署目标**（`project_environment_target`）：环境归属被改是引入本模块的直接动因，
  create / update / delete 全部标注；
- **任务模块**：不标注（见 §6.6）；
- **前端**：`src/views/auditLog/index.vue` 挂「系统设置 → 操作日志」，
  `src/utils/request.ts` 的拦截器统一带出操作人请求头。

## 8. 已知边界与后续演进

1. **操作者依赖请求头**：过渡期前端传的是登录信息，可被伪造。接入统一权限中心后必须改为
   服务端从认证信息解析，否则审计的操作人只能作为「参考」而非证据；
2. **不做 IP 归属地解析**：需要第三方 IP 库或外部接口，本轮不引入；详情页只展示 IP、
   操作系统与浏览器；
3. **变更明细不含关联实体的可读名称**：`changed_fields` 记录的是原始值，例如部署目标的
   `environmentId` 是环境主键而不是「生产环境」。反查名称要么在展示层再查一次（给详情页增加 N 次查询），
   要么落库时把名称一并记下（快照一旦放开就不是快照了）。当前选择保留主键，
   配合审计的主从记录回溯：本轮不做；
4. **同步写入**：落库在请求线程内完成，日志量极大时会给写接口增加一次 DB 往返。
   数据量上来后改为异步（独立线程池 + 有界队列，队列满时丢弃并计数），
   但必须保证不会因异步丢失而静默；
5. **无归档策略**：`audit_log` 只增不减，长期运行需要归档或保留期策略（如按时间分表、
   定期导出后清理）。本轮不做，但索引已按查询模式建好（`idx_audit_create_time`）；
6. **项目内 Jackson 2 / Jackson 3 并存**：自己写的代码统一走 `SecretMasker` 用 Jackson 2，
   容器提供的是 Jackson 3，两边各自独立、互不影响。但实体上的
   `com.fasterxml.jackson.annotation.JsonProperty` 只有在 HTTP 层走 Jackson 2 转换器时才生效；
   一旦哪天 Jackson 3 的转换器接管，`Server.ciphertext` 等 WRITE_ONLY 字段可能被序列化出去。
   上线前建议抽查一次 `GET /server/list` 的响应体确认不含 `ciphertext`（详见 Q-28）。
