# 操作日志模块文档

> 模块包：`com.lx.deploy.audit` ｜ 对应数据表：`audit_log` ｜ 状态：已完成并编译通过

## 1. 模块定位

操作日志模块记录「谁、在什么时候、通过哪个接口、改了什么、成功还是失败」。它与业务解耦：**不靠业务代码手动写库，而是由 `@OperLog` 注解 + `OperLogAspect` 切面在方法返回后自动落 `audit_log`**。

- 本模块提供：操作日志的自动采集与只读查询；
- 本模块不提供：任何写接口（日志只由切面产生）、业务动作本身（切面只旁观）。
- 与发布/构建链路的差异：操作日志**不触发 `lds_task`、不连 SSH、不走 `TaskExecutor`**——它是同步的 AOP 副作用，请求线程内完成。

## 1.1 调用链路（注解 → 切面 → 落库）

```text
任意 Controller 方法（标注 @OperLog）
  └─ 例如 ProjectController.create / ServerController.create / CredentialController.create …
        │  方法正常返回（或抛业务异常被全局处理器接管）
        ▼
OperLogAspect（环绕/后置通知）          // common/aop/OperLogAspect.java:57
        │  读取 @OperLog 的 title / businessType / resourceType
        │  从 RequestContext / Security 取操作人、IP、请求路径
        │  组装 AuditLog 并 insert
        ▼
AuditLogMapper.insert → audit_log 表
```

查询侧（纯读，不触发切面）：

```text
auditLog.ts → GET /auditLog/page | /auditLog/detail/{id}
        ▼
AuditLogController                       // audit/controller/AuditLogController.java
  （detail@59）
        ▼
AuditLogService → AuditLogMapper 直查 audit_log
```

> 关键点：**`@OperLog` 是唯一的写入入口**。业务代码不要直接 `auditLogMapper.insert`——那样会绕过切面统一采集的操作人/请求上下文，造成日志缺字段。若需要自定义字段，应在注解或切面里扩展。

## 2. 数据表结构（`audit_log`）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | VARCHAR(32) | 主键 |
| user_id | VARCHAR(32) | 操作人 ID（外部用户 ID，后续接统一权限中心） |
| username | VARCHAR(100) | 操作人姓名/账号（落库快照，避免用户改名后日志失联） |
| module | VARCHAR(50) | 操作模块，来自 `@OperLog` 的 title（如「服务器管理」） |
| business_type | TINYINT | 操作类型编码，来自 `@OperLog` 的 businessType（枚举 `BusinessType`：1 新增 / 2 修改 / 3 删除 / 4 查询 / 5 其他） |
| resource_type | VARCHAR(50) | 资源类型，来自 `@OperLog` 的 resourceType，页面按它映射字段中文名 |
| request_method | VARCHAR(10) | HTTP 方法 |
| request_url | VARCHAR(255) | 请求路径 |
| request_ip | VARCHAR(64) | 客户端 IP |
| request_param | TEXT | 请求参数（脱敏后） |
| result | TINYINT | 0 失败 / 1 成功 |
| error_msg | VARCHAR(500) | 失败原因 |
| cost_time | BIGINT | 耗时（ms） |
| create_time | DATETIME | 操作时间 |

## 3. 枚举设计

| 枚举 | 取值 |
| --- | --- |
| `BusinessType` | 1 新增 / 2 修改 / 3 删除 / 4 查询 / 5 其他（数字编码，见 `common.enums.audit`） |
| 状态码 | `result` 用 `0 失败 / 1 成功`（`TINYINT` + 常量，AGENTS.md §4.5） |

## 5. 接口清单

| 方法 | 路径 | 说明 | 关键方法@行 |
| --- | --- | --- | --- |

## 6. 核心业务规则

- **切面统一采集**：操作人、IP、请求路径、耗时、成败由 `OperLogAspect` 从请求上下文与返回值自动取，业务方法零侵入；
- **参数脱敏**：`request_param` 写入前按敏感字段规则脱敏（密码/私钥/Token 不落库）；
- **只写不回显写入**：切面调用 `AuditLogService` 的内部插入方法，业务 Controller 不感知；
- **失败也记录**：方法抛业务异常时切面仍落一条 `result=0` 的日志，便于审计「谁尝试了什么、为什么失败」。

## 7. 与其他模块的关系

| 方向 | 关系 |
| --- | --- |
| ← 所有写操作的 Controller | 标注 `@OperLog` 即自动产生日志，无需各模块各自写库 |
| → 统一权限中心（规划中） | `user_id` 当前为过渡期账号，后续统一权限中心接入后语义不变 |

## 8. 已知边界与后续演进

- **仅 HTTP 层切面**：纯内部 Service 调用（非 Controller 入口）默认不产生日志，需审计的内部动作要显式走带 `@OperLog` 的接口；
- **异步任务不自动记操作日志**：`DeployTaskHandler` / `BuildTaskHandler` 的执行过程走 `lds_task_log`，不属于 `audit_log`；两者的受众不同（操作审计 vs 执行留痕）；
- **日志量无上限**：高频写操作会持续累积，后续可加保留策略或归档。
