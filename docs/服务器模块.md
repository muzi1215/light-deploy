# 服务器模块文档

> 模块包：`com.lx.deploy.server` ｜ 对应数据表：`server` ｜ 状态：已完成并编译通过（已提供连通性测试入口，探活由任务模块异步执行，真机验证通过）

## 1. 模块定位

服务器模块是 Light Deploy 平台的基础资源模块，负责纳管所有部署目标 Linux 服务器的 SSH 连接信息。

- 平台规模基线：至少纳管 6 台服务器，支持不同服务器上的项目并发发布；
- 同一台服务器同一时刻默认只执行一个发布任务（该约束由后续任务模块的调度逻辑实现，本模块不负责）；
- 本模块只管「服务器档案 + SSH 凭据」，**不直接建立连接**：连通性测试只负责创建 SERVER_TEST 任务并立即返回，真正的 SSH 连接由任务模块的执行器调用 `com.lx.deploy.ssh.SshSessionFactory` 异步建立；
- 环境标签（`env_tag`）是服务器默认归属，只用于列表展示与筛选，不决定发布目标。

## 2. 数据表结构（`server`）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | VARCHAR(32) | 主键，MyBatis-Plus `ASSIGN_UUID` 生成 |
| server_name | VARCHAR(100) | 服务器名称，必填 |
| host | VARCHAR(255) | IP 或域名，与端口组成唯一键 |
| ssh_port | INT | SSH 端口，默认 22 |
| username | VARCHAR(100) | SSH 登录用户 |
| auth_type | TINYINT | 认证类型：1 密码，2 私钥 |
| ciphertext | TEXT | **AES-GCM 加密后的密码或私钥内容，禁止明文** |
| env_tag | TINYINT | 环境标签：1 开发，2 测试，3 生产（仅用于列表展示与筛选） |
| status | TINYINT | 服务器状态：0 停用，1 启用 |
| description | VARCHAR(500) | 描述 |
| build_workspace_dir | VARCHAR(255) | 构建工作区根目录，仅构建机使用；默认 `/opt/light-deploy/build-workspace`，**建议显式填写**（见 §2.1） |
| build_artifact_dir | VARCHAR(255) | 构建产物持久目录，仅构建机使用；默认 `/opt/light-deploy/artifacts`，**建议显式填写** |
| agent_base_dir | VARCHAR(255) | 平台在该机器上的部署根目录；默认 `/opt/light-deploy`，应用部署在其 `apps` 子目录下，**建议显式填写** |
| build_env_script | VARCHAR(255) | 构建环境初始化脚本，仅构建机使用；**可空无默认值**，留空只用平台 `. /etc/profile` 兜底（见 §6.6） |
| created_by / updated_by | VARCHAR(100) | 操作者 |
| create_time / update_time / is_deleted | - | BaseEntity 统一审计字段，软删除 |

唯一键：`uk_server_host_port (host, ssh_port, is_deleted)` —— 同一 host+端口 只能登记一台服务器。

### 2.1 三个目录的填写口径与边界

三个目录都带 DB 默认值（`/opt/light-deploy/...`），但**默认值只在页面留空时兜底**，落地前建议按机器实际规划显式填写。
它们在流水线里的角色是：

| 目录 | 谁在用 | 平台在里面做什么 | 生命周期 |
| --- | --- | --- | --- |
| 构建工作区 `build_workspace_dir` | 构建机 | `{工作区}/{项目编码}_{构建ID}` 下 git clone、跑构建命令 | **临时**：构建开始先 `rm -rf` 重建、结束清理 |
| 产物持久目录 `build_artifact_dir` | 构建机 | `{持久目录}/{项目编码}/{版本}` 存 jar 与 config | **持久**：构建结束保留，供发布阶段下载 |
| 部署根目录 `agent_base_dir` | 目标机 | 应用落在其 `apps` 子目录下（JAR 未配 `work_dir` 时即 `apps/{项目编码}`） | **持久** |

填写规则（照这四条填就不会和项目里的构建 / 运行配置冲突）：

1. **三者互不包含**，尤其产物持久目录**不能**放在构建工作区下面——工作区每次构建都会被整体清理，
   持久目录落在里面等于把已发布的产物一起删掉。
2. **部署根目录不是 `work_dir`**：运行配置显式给了 `work_dir`（如接管既有的 `/lx/jarapps/auth-tool-7888`）
   时平台完全按 `work_dir` 走，部署根目录只作为「未配 `work_dir` 时的默认落点」；
   但该字段仍必填——代码不含兜底路径，为空会在发布阶段直接报错。
3. **目录不用提前创建**：工作区每次 `rm -rf` + `mkdir -p`、持久目录 `mkdir -p`、`apps` 子目录由初始化脚本创建；
   前提是 SSH 登录用户对**父目录**有写权限。
4. **目标机 SSH 用户需要 root**（或能免密执行 systemctl）：初始化脚本直接执行 `systemctl daemon-reload/enable`，
   脚本内不带 `sudo`。

单机自测（构建机与目标机同一台）时，只要四个路径互不包含即可，例如：
工作区 `/lx/light-deploy/workspace`、持久目录 `/lx/light-deploy/artifacts`、部署根目录 `/lx/light-deploy/agent`、
运行配置 `work_dir` `/lx/jarapps/auth-tool-7888`。

## 3. 代码结构

```text
com.lx.deploy.server
├── controller/ServerController.java      # REST 接口，只做参数接收与响应包装
├── mapper/ServerMapper.java              # BaseMapper，无自定义 SQL
├── model/
│   ├── Server.java                       # 持久化实体（含 ciphertext）
│   ├── dto/ServerDto.java                # 请求对象（含 credential 只写字段）
│   └── vo/ServerVo.java                  # 响应对象（不含 ciphertext）
└── service/ServerService.java            # 业务规则与加解密边界 + submitConnectivityTest()（跨模块注入 TaskService）

枚举统一放在公共枚举包（AGENTS.md §22）：
com.lx.deploy.common.enums.server
├── ServerAuthType.java                   # 1 密码 / 2 私钥
├── EnvironmentTag.java                   # 1 开发 / 2 测试 / 3 生产
└── ServerStatus.java                     # 0 停用 / 1 启用
```

跨模块依赖方向：`ServerService` → `TaskService`（提交连通性测试时创建任务），`TaskService` 不反向依赖 `ServerService`；执行器需要读 `server` 实体时，由 task 模块的处理器注入 `ServerMapper`，避免两个 Service 互相注入。

## 4. 枚举设计

数据库保存数字编码，Java 层统一走枚举 `fromCode()` 转换，禁止在业务代码中直接比较魔法数字。

| 枚举 | 取值 | 用途 |
| --- | --- | --- |
| ServerAuthType | PASSWORD(1) / PRIVATE_KEY(2) | 决定 ciphertext 中加密的是密码还是私钥 |
| EnvironmentTag | DEV(1) / TEST(2) / PROD(3) | 服务器归属标签；正式发布目标以项目环境绑定为准，不以标签为准 |
| ServerStatus | DISABLED(0) / ENABLED(1) | 只表示「是否允许被平台连接和参与部署」，不表达环境 |

## 5. 接口清单

统一前缀 `/server`，统一返回 `ApiResponse<T>` 并携带 `requestId`。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/server/page` | 条件分页查询（PageQuery + 动态条件） |
| GET | `/server/list` | 条件列表查询（下拉选择场景） |
| GET | `/server/detail/{id}` | 主键查询，不存在抛 DATA_NOT_FOUND(4004) |
| POST | `/server/create` | 新增，credential 必填 |
| PUT | `/server/update/{id}` | 修改，credential 选填（不传保留旧密文） |
| DELETE | `/server/delete/{id}` | 逻辑删除 |
| POST | `/server/test/{id}` | 提交连通性测试：校验服务器存在且启用、无未完成测试任务后创建 SERVER_TEST 任务，**立即返回任务 ID，不等待连接结果** |

`POST /server/test/{id}` 的响应体是新建任务的 VO（`taskId` / `taskNo` / `status`），页面拿到 `taskId` 后用 `GET /taskLog/pull?taskId=&lastSeq=` 增量拉取执行日志（约定见 AGENTS.md §20.9）。校验规则：

- 服务器不存在 → `DATA_NOT_FOUND(4004)`；
- 服务器已停用（`status = 0`）→ `DATA_CONFLICT(4005)`「服务器已停用，无法执行连通性测试」；
- 该服务器已有未完成任务（排队中或执行中）→ `DATA_CONFLICT(4005)` 提示等待其结束，避免同一服务器并发测试，与 AGENTS.md §1 的「同一服务器同一时刻只跑一个任务」一致。

## 6. 核心业务规则与代码逻辑

### 6.1 凭据加密链路（最核心）

```text
前端提交明文 credential（ServerDto.credential）
        │
        ▼  ServerService.create/update
CredentialCrypto.encrypt()   ← AES/GCM/NoPadding，key 来自环境变量 LIGHT_DEPLOY_AES_KEY
        │
        ▼
写入 server.ciphertext（数据库只存密文）
        │
        ▼  发布执行时（后续模块）
CredentialCrypto.decrypt()   ← 仅在建立 SSH 连接前短暂解密，用后不缓存
```

关键实现细节：

1. **只写不读**：`ServerDto.credential` 标注 `@Schema(accessMode = WRITE_ONLY)`，`ServerVo` 根本不声明密文字段，从类型结构上保证任何查询接口都不可能返回凭据；
2. **新增必填**：`create()` 强制校验 credential 非空，否则抛 VALIDATION_ERROR(4001)「SSH 密码或私钥不能为空」；
3. **修改选填**：`update()` 仅在传入新凭据时重新加密覆盖旧密文，未传则保留数据库旧值 —— 支持只改服务器名称/端口而不必每次都重填密码；
4. **禁止明文落库**：全链路（数据库、日志、异常消息、VO）不允许出现明文凭据，AES key 只能外部注入，绝不进 Git。

### 6.2 动态查询条件

`buildQueryWrapper()` 遵循统一规则：

- 字符串非空才参与查询，默认等值匹配；
- `ciphertext` 属于敏感字段，**永远不会**进入查询条件；
- 固定 `ORDER BY create_time DESC`；
- MyBatis-Plus 自动追加 `is_deleted = 0`。

### 6.3 主键与审计

- 新增时 `entity.setId(null)`，主键由 `ASSIGN_UUID` 策略（底层 `IdGenerator.generateUUID()`）生成；
- 修改时始终以**路径参数 id** 为准 `entity.setId(id)`，防止请求体篡改主键越权改其他记录。

### 6.4 删除

`removeById()` 由 BaseEntity 的逻辑删除配置转为 `UPDATE is_deleted = 1`，不物理删除。唯一键包含 `is_deleted` 字段，软删除后同 host+端口可重新登记。

### 6.5 机器目录配置

三列都是**某台机器上的目录**，按机器维护，在服务器页面填写：

| 列 | 消费方 | 说明 |
| --- | --- | --- |
| `build_workspace_dir` | BuildTaskHandler | 每次构建在其下建 `{项目编码}_{构建ID}` 子目录，结束后整体清理，属临时目录 |
| `build_artifact_dir` | BuildTaskHandler | 文件型/目录型产物转存到 `{该目录}/{项目编码}/{版本号}`，供发布阶段 SFTP 下载 |
| `agent_base_dir` | ServerTestTaskHandler、DeployTaskHandler | 连通性测试检查其存在且可写；应用部署根目录默认为其 `apps` 子目录 |

规则与背景：

- 三列 `NOT NULL` 且带 `DEFAULT`，默认值只在数据库定义一处；**代码与 `application.yaml` 中不得出现机器上的绝对路径**，执行器全部从服务器档案读取（见 AGENTS.md §6.4）；
- Service 保存时把空白视为未配置并置 `null`，由数据库默认值填充；读取时去首尾空白，为空则抛出指向「去服务器页面配置」的校验错误，不静默兜底；
- 修改这三个值**不影响历史数据**：产物路径在创建时已快照进 `build_artifact.metadata_json`，历史版本仍从原路径发布与回滚；
- `apps` 是平台约定的子目录名（常量 `APPS_SUBDIR`），不单独提供配置项。

> 最初这三个目录是配置项，靠 `@Value("${...:/opt/...}")` 兜底。改一个目录要动配置文件并重启平台，
> 且所有构建机只能共用同一个根目录——不同机器挂的数据盘不同时无法分别设置，因此下沉为按机器维护。

### 6.6 构建环境初始化脚本 `build_env_script`

构建机上「已安装、但只有登录环境才知道路径」的工具，在平台执行构建时找不到——平台通过 SSH 执行命令走的是**非交互式 shell**，不加载 `/etc/profile`、`/etc/profile.d/*.sh`、`~/.bashrc`，`PATH` 通常只剩 `/usr/bin:/bin` 之类。最典型的受害者是 Maven：装在 `/opt/apache-maven-3.8.8/bin`，靠 profile 导出 PATH，构建时的报错只有一行 `bash: mvn: command not found`，看不出是「没装」还是「没配 PATH」。

应对分两层：

| 层 | 位置 | 行为 |
| --- | --- | --- |
| 平台兜底 | `BuildTaskHandler.PROFILE_SOURCE_COMMAND` | 每条构建命令前固定执行一次 `. /etc/profile >/dev/null 2>&1`（输出丢弃，不污染构建日志；profile 不存在或返回非零都不影响后续命令） |
| 机器级补充 | `server.build_env_script` | 在兜底之后、用户构建命令之前执行，用于补 profile 里也没有的路径；单行，多个用 `;` 分隔，留空即不执行 |

两种写法的作用范围不同，按场景选：

```bash
# 场景一：机器上装了 Maven，只是 PATH 里没有（推荐配在服务器档案，一劳永逸）
export PATH=/opt/apache-maven-3.8.8/bin:$PATH

# 场景二：机器上装了多个 JDK，构建用哪个由项目决定（配在项目的 build_config_json.build_command 里）
JAVA_HOME=/usr/lib/jdk1.8.0_121 mvn -B clean package -DskipTests
```

约束与边界：

- 该列**可空、无默认值**：脚本内容与具体机器强相关，任何默认值都是错的，空值表示「只用平台兜底」；
- Service 保存时空白归一为 `null`，非空只去首尾空白，内容原样保存（运维可写任意 shell 片段，平台不解析、不做白名单）；
- 只对构建流程生效，部署侧（`DeployTaskHandler`）不使用该字段——目标机上跑的是 systemd，环境由 unit 文件决定；
- 修改后只影响**之后发起**的构建，不影响历史版本。

> 相关能力：连通性测试的「构建依赖」阶段会探活 `git` 与 `mvn`（可选项，失败只提示不判失败），
> 并在失败时给出「安装 / 补 PATH / 写绝对路径」三种处理办法；
> 构建执行前还有一次命令可执行性预检，命令首词找不到时直接失败并报出具体原因，
> 不再依赖 `bash: command not found` 这种难以定位的报错（见 [构建模块.md §6.2.2](构建模块.md)）。

## 7. 与其他模块的关系

| 方向 | 关系 |
| --- | --- |
| → project 模块 | `project_environment_target.server_id` 引用本表；ProjectEnvironmentTargetService 通过 ServerMapper 校验服务器存在且启用 |
| → task 模块 | 连通性测试通过 `TaskService` 创建 SERVER_TEST 任务（`biz_id = server.id`），任务状态机与执行器都在对方模块；本模块只提供「提交」入口和配置数据 |
| → ssh 执行层 | `SshSessionFactory.open(server)` 读取本表 ciphertext 并在建立连接前解密；本模块负责写入密文，解密只在 SSH 层发生 |
| → common.crypto | 凭据加解密统一委托 `CredentialCrypto`，本模块不实现算法 |
| ← 前端 | 服务器列表页的「连通性测试」按钮调用 `POST /server/test/{id}`，随后打开日志抽屉增量拉取日志 |

## 8. 已知边界与后续演进

- 删除服务器前未校验是否被 `project_environment_target` 引用（project 模块反向校验了服务器，本模块正向未拦截）。若出现「目标指向已删服务器」的脏数据风险，可在 ServerService.delete 中补充引用检查；
- 连通性测试已可用（真机验证：系统信息 / 运行时检查 / 构建依赖 / 磁盘容量 / 部署目录逐项出日志，结束时进度 100），但**只验证 SSH 通道、基础运行时与构建依赖（git / mvn）**，不校验 Docker 镜像仓库、Git 凭据等后续链路依赖；
- 连通性测试结果**不落库**（`server` 表没有「最后测试时间 / 最后测试结果」字段），页面刷新后看不到历史测试结论。若要「列表直接显示最近连通状态」，需新增字段并配合定时探测，属于后续演进；
- `uk_server_host_port` 数据库层唯一，Service 层未提前预检，依赖数据库异常转换为统一响应（当前由 GlobalExceptionHandler 兜底）。
